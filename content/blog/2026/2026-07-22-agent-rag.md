这段代码定义了一套用于 **RAG（检索增强生成）流水线** 的不可变数据模型，并通过“工厂方法”强制每个对象的构造方式，从而杜绝字段来源混乱、隐式契约和 `dict` 透传的问题。

## 1. 代码设计解释

### 核心思路
- 四个 `@dataclass(frozen=True)` 的类：**Document → Chunk → RetrievalResult → RAGAnswer**。
- 每个类都有且只有**一个合法的构造入口**（通过 `@staticmethod` 工厂方法，如 `Document.build()`、`Chunk.build()`），外部不能直接调用构造函数（虽然 Python 无法完全禁止，但约定如此）。
- 工厂方法内部自动计算某些字段（如 `checksum`、`chunk_id`），调用方不需要知道生成逻辑，避免了“谁来算、怎么算”的推诿。
- 下游对象必须接收完整的上游对象（例如 `Chunk.build` 要求传入整个 `Document` 对象，而不是单独的 `document_id`），从而保证 `chunk_id` 可以依赖 `document.checksum` 来感知内容变化。

### 各类型职责与约束

| 类 | 代表什么 | 唯一入口 | 关键约束 |
|---|---------|---------|---------|
| `Document` | 原始文档 | `Document.build()` | `checksum` 自动用 SHA256(text) 计算；若未传 `document_id`，用 `source + checksum` 确定性地生成。 |
| `Chunk` | 文档切片 | `Chunk.build(document, ...)` | 必须传入完整 `Document`，`chunk_id` 由 `document_id:checksum:position:规范化内容` 的哈希生成；内容自动做空白规范化。 |
| `RetrievalResult` | 检索结果 | `RetrievalResult.from_chunk()` | 保存对应 `Chunk`、分数、检索器名称、各分数分量（用于后续调参分析）。 |
| `RAGAnswer` | 最终回答 | `RAGAnswer.build(answer, contexts)` | 从 `contexts` 自动提取引用的 `chunk_id` 列表，无需调用方手动维护。 |

这样做的好处：
- **类型即契约**：每个环节的输入输出都有明确的类型声明，不能再传字典蒙混过关。
- **字段来源可追溯**：比如 `chunk_id` 的生成逻辑锁死在 `Chunk.build` 里，将来改 hash 策略只要改一处。
- **不可变**：`frozen=True` 保证对象创建后不会被下游偷偷修改，适合在多步处理与缓存场景中使用。
- **可验证**：`Chunk.rebuild_id()` 允许外部复现 `chunk_id`，用于校验或去重。

## 2. 缺失的依赖

代码中用到了几个未定义 / 未导入的符号，实际运行时会出现 `NameError`，需要补充：

### 2.1 缺失的函数定义
- **`_sha256(text: str) -> str`**  
  用于计算 SHA‑256 哈希，通常实现为：
  ```python
  import hashlib

  def _sha256(text: str) -> str:
      return hashlib.sha256(text.encode("utf-8")).hexdigest()
  ```

- **`_normalize_whitespace(text: str) -> str`**  
  用于规范化内容中的空白字符，比如：
  ```python
  def _normalize_whitespace(text: str) -> str:
      return " ".join(text.split())
  ```

### 2.2 缺失的导入语句
- `from dataclasses import dataclass, field`
- `from typing import Any`（如果使用 Python < 3.9 还需要 `Dict`, `List` 等，但 3.9+ 可直接用小写 `dict`，不过 `Any` 仍需从 `typing` 导入）

### 2.3 隐含依赖
- 标准库 `hashlib`（如上所述）。
- 类型注解中的 `dict[str, Any]` 在 Python 3.9+ 可直接使用，但若环境是 3.7/3.8 则需要 `from typing import Dict, Any` 并改为 `Dict[str, Any]`。

## 核心问题：为什么传 dict 会失控

当前每个环节的产出都是"调用方负责填字段"。loader 产出 `Document`，但 `checksum` 是 loader 自己算还是调用方传？splitter 产出 `Chunk`，但 `chunk_id`
谁生成？如果每个环节的输入/输出类型不强制，很快就会出现 `dict` 透传——某个环节往 `metadata` 里塞了一个字段，下游依赖它，但没有任何地方声明这个契约。

## 解法：每个类型自带工厂 + 唯一入口

四个对象各自只有**一个合法构造路径**。外部不能直接 `Document(...)` 或 `Chunk(...)`，必须通过工厂方法。这样每个字段的来源和约束被锁死在类型内部。

### Document

```python
@dataclass(frozen=True)  # 不可变——防止下游偷偷改
class Document:
    document_id: str
    user_id: str
    namespace: str
    source: str          # 原始路径或 URL
    text: str            # 全文
    checksum: str        # sha256(text)，构造时自动算
    metadata: dict[str, Any] = field(default_factory=dict)

    @staticmethod
    def build(
        *,
        user_id: str,
        namespace: str,
        source: str,
        text: str,
        document_id: str | None = None,
        metadata: dict[str, Any] | None = None,
    ) -> "Document":
        """
        loader 的唯一入口。
        document_id 不传则用 source + checksum 确定性生成。
        checksum 自动计算，调用方不用管。
        """
        checksum = _sha256(text)
        doc_id = document_id or _sha256(f"{source}:{checksum}")
        return Document(
            document_id=doc_id,
            user_id=user_id,
            namespace=namespace,
            source=source,
            text=text,
            checksum=checksum,
            metadata=metadata or {},
        )
```

**边界**：loader 的返回值类型声明为 `Document`。调用方不需要知道 `checksum` 怎么算的、`document_id` 怎么生成的。loader 内部拿到原始文本后，调
`Document.build()`，完事。

### Chunk
```python
@dataclass(frozen=True)
class RetrievalResult:
    chunk: Chunk
    score: float
    retriever: str                    # "bm25" / "dense" / "hybrid"
    score_components: dict[str, float] = field(default_factory=dict)
    # 例: {"bm25": 0.72, "dense": 0.65, "rrf": 0.018}

    @staticmethod
    def from_chunk(
        chunk: Chunk,
        score: float,
        retriever: str,
        score_components: dict[str, float] | None = None,
    ) -> "RetrievalResult":
        return RetrievalResult(
            chunk=chunk,
            score=score,
            retriever=retriever,
            score_components=score_components or {},
        )
```

**边界**：retriever 的输入是 `str`（查询文本），输出是 `list[RetrievalResult]`。`score_components` 在 hybrid 模式下把 BM25 和 dense
各自的分数都保留——将来调参时能看到是哪一路贡献的。

### RAGAnswer

```python
@dataclass(frozen=True)
class RAGAnswer:
    answer: str
    contexts: list[RetrievalResult]
    citations: list[str]              # 引用的 chunk_id 列表
    metadata: dict[str, Any] = field(default_factory=dict)

    @staticmethod
    def build(
        *,
        answer: str,
        contexts: list[RetrievalResult],
    ) -> "RAGAnswer":
        citations = [r.chunk.chunk_id for r in contexts]
        return RAGAnswer(
            answer=answer,
            contexts=contexts,
            citations=citations,
        )
```

**边界**：pipeline 的输入是 `str`（用户问题），输出是 `RAGAnswer`。`citations` 自动从 `contexts` 里提取，调用方不需要手动维护。

## 各环节的类型契约

改完之后，五个环节的输入/输出类型是确定的：

```
loader   : 输入=文件路径 → 输出=Document
splitter : 输入=Document   → 输出=list[Chunk]
index    : 输入=list[Chunk] → 输出=None（副作用：写入存储）
retriever: 输入=str(query)  → 输出=list[RetrievalResult]
pipeline : 输入=str(query)  → 输出=RAGAnswer
```

**没有一环的输入或输出是 `dict`**。如果某个环节需要额外信息，只能在对应的类型上加字段，不能靠 `metadata["xxx"]` 口头约定。

## chunk_id 的确定性意味着什么
```python
# 第一次导入
doc = Document.build(source="note.md", text="# Title\n\nHello world.")
chunks = splitter.split(doc)
# chunk_id = sha256("doc_abc:def123:0:title")

# 一周后，同一个文件重新导入（内容没变）
doc2 = Document.build(source="note.md", text="# Title\n\nHello world.")
chunks2 = splitter.split(doc2)
# chunk_id = sha256("doc_abc:def123:0:title")  ← 相同！

# 但如果内容变了
doc3 = Document.build(source="note.md", text="# Title\n\nHello world!!!")
chunks3 = splitter.split(doc3)
# checksum 不同 → chunk_id 全变 → 旧 chunk 是孤儿，index 可以清理
```

index 层的去重逻辑变得极简单：`INSERT OR IGNORE` 即可，不需要额外的 diff 逻辑。

## metadata 的最后防线

`metadata: dict[str, Any]` 不删——过度约束会让 loader/splitter 写起来很痛苦。但加了两个约束：

1. **所有对象 `frozen=True`**，下游不能偷偷改字段。要加信息用 `metadata`，但改不了已有字段。
2. **metadata 里不放影响正确性的字段**。`user_id`、`namespace`、`checksum` 都是显式字段，不在 metadata 里——检索时不需要 `item.metadata.get("user_id")`
这种脆弱写法。

先不写代码，把三个文件的接口设计和边界条件说清楚。

## retrieval/loaders/base.py — 基类

```python
from abc import ABC, abstractmethod
from pathlib import Path
from retrieval.models import Document


class BaseLoader(ABC):
    """所有 loader 的抽象基类。一个文件 → 一个 Document。"""

    @abstractmethod
    def load(self, path: str | Path) -> Document:
        """
        加载单个文件为 Document。

        必须抛出的异常：
          FileNotFoundError  — 路径不存在
          ValueError         — 文件为空
          UnicodeDecodeError — 所有编码尝试均失败
        """
        ...

    # ---------- 共享工具 ----------

    @staticmethod
    def _resolve(path: str | Path) -> Path:
        """校验路径存在且非空，返回 resolved Path。所有子类在 load() 第一行调用。"""
        p = Path(path).resolve()
        if not p.exists():
            raise FileNotFoundError(f"文件不存在: {p}")
        if p.stat().st_size == 0:
            raise ValueError(f"文件为空: {p}")
        return p

    @staticmethod
    def _try_read_text(file_path: Path) -> str:
        """先 UTF-8，失败再 gbk。都不行就抛 UnicodeDecodeError。"""
        for encoding in ("utf-8", "gbk"):
            try:
                return file_path.read_text(encoding=encoding)
            except UnicodeDecodeError:
                continue
        raise UnicodeDecodeError(
            "utf-8/gbk",
            b"",
            0, 1,
            f"无法以 UTF-8 或 GBK 解码: {file_path}"
        )
```

**设计决策**：

- `_resolve` 和 `_try_read_text` 放在基类而非工具模块——它们只被 loader 用，放基类避免引入额外的 import 层次。
- 不强制子类用 `_try_read_text`——Markdown 文件可能只需要 UTF-8，二进制文件（PDF/Office）根本不用文本读取。基类提供工具但不强制调用路径。
- 异常类型全部用标准库——不自定义 `LoaderError` 层级。调用方 `except FileNotFoundError` 比 `except LoaderFileNotFoundError` 更直观。等真的有 3+ 种
loader 特有错误需要统一处理时再引入。

## retrieval/loaders/text.py — 纯文本
```python
class TextLoader(BaseLoader):
    """纯文本加载器。UTF-8 → GBK 降级。"""

    def load(self, path: str | Path) -> Document:
        file_path = self._resolve(path)
        text = self._try_read_text(file_path)

        return Document.build(
            user_id="default",        # 调用方后续覆盖
            namespace="default",
            source=str(file_path),
            text=text,
            metadata={
                "loader": "text",
                "file_name": file_path.name,
                "file_size": file_path.stat().st_size,
                "encoding": "utf-8",   # TODO: 从 _try_read_text 返回实际编码
            },
        )
```

**边界**：输入是文件路径，输出是一个 `Document`。`user_id`/`namespace` 填默认值——由上层（pipeline 或 RAGTool）在拿到 Document 后覆盖，loader 不管租户隔离。

**当前缺口**：`_try_read_text` 没返回实际用的编码。可以让它返回 `tuple[str, str]`。

## retrieval/loaders/markdown.py — Markdown + Frontmatter
```python
import yaml


class MarkdownLoader(BaseLoader):
    """
    Markdown 加载器。解析 YAML frontmatter，保留正文 Markdown。

    输入：.md 文件
    处理：
      1. UTF-8 读取全文
      2. 检测 --- ... --- frontmatter 块
      3. YAML 解析 → 提取 title / date / tags 等已知字段
      4. 正文保持原始 Markdown 不转换
    输出：Document
      - text = 正文 Markdown（不含 frontmatter）
      - metadata = {title, date, tags, ...} + 所有 frontmatter 字段
    失败：同 BaseLoader._resolve
    """

    def load(self, path: str | Path) -> Document:
        file_path = self._resolve(path)
        raw = file_path.read_text(encoding="utf-8")

        frontmatter: dict[str, Any] = {}
        body = raw

        if raw.startswith("---"):
            parts = raw.split("---", 2)
            if len(parts) >= 3:
                try:
                    frontmatter = yaml.safe_load(parts[1]) or {}
                except yaml.YAMLError:
                    pass  # frontmatter 解析失败 → 全文当正文
                body = parts[2].strip()

        return Document.build(
            user_id="default",
            namespace="default",
            source=str(file_path),
            text=body,
            metadata={
                "loader": "markdown",
                "file_name": file_path.name,
                "title": frontmatter.get("title", file_path.stem),
                "date": frontmatter.get("date"),
                "tags": frontmatter.get("tags", []),
                "topics": frontmatter.get("topics", []),
                "projects": frontmatter.get("projects", []),
                "summary": frontmatter.get("summary"),
                # 原始 frontmatter 全量保留，不丢字段
                "raw_frontmatter": frontmatter,
            },
        )
```

**设计决策**：
```python
class MarkitdownLoader(BaseLoader):
    """
    多格式统一加载器。内部委托给 markitdown 库转换，再走 MarkdownLoader 逻辑。

    支持格式（按扩展名分发）：
      - 文档: .pdf .docx .pptx .xlsx .html .xml
      - 图片: .png .jpg .jpeg .gif .bmp（OCR 提取文字）
      - 音频: .mp3 .wav .m4a（需要 whisper 提取转录文本）
      - 代码: .py .js .ts .go .rs .java 等（保留语法高亮的代码块）
      - 兜底: 所有未知格式尝试 markitdown 的通用转换

    输入：任意文件路径
    处理：
      1. 检测扩展名 → 选择转换策略
      2. markitdown 转换 → Markdown 字符串
      3. 把 Markdown 字符串当作"伪文件"交给 MarkdownLoader 的内联逻辑
      4. 附加原始格式信息到 metadata
    输出：Document
      - text = 转换后的 Markdown
      - metadata["source_format"] = 原始扩展名
      - metadata["converter"] = "markitdown"
    失败：
      - 不支持的格式 → ValueError
      - markitdown 转换失败 → RuntimeError（带原始错误信息）
    """

    # 格式 → 转换策略
    _MARKITDOWN_EXTENSIONS = {
        ".pdf", ".docx", ".pptx", ".xlsx",
        ".html", ".htm", ".xml", ".csv",
        ".json", ".epub",
    }

    _IMAGE_EXTENSIONS = {".png", ".jpg", ".jpeg", ".gif", ".bmp", ".webp"}

    _AUDIO_EXTENSIONS = {".mp3", ".wav", ".m4a", ".ogg", ".flac"}

    _CODE_EXTENSIONS = {
        ".py", ".js", ".ts", ".jsx", ".tsx",
        ".go", ".rs", ".java", ".c", ".cpp", ".h",
        ".sh", ".bash", ".yaml", ".yml", ".toml",
        ".sql", ".r", ".swift", ".kt",
    }

    def load(self, path: str | Path) -> Document:
        file_path = self._resolve(path)
        suffix = file_path.suffix.lower()

        # 1. 纯文本/代码 → 直接读，包装成 Markdown 代码块
        if suffix in self._CODE_EXTENSIONS:
            raw = self._try_read_text(file_path)
            lang = suffix.lstrip(".")
            text =f"```{lang}\n{raw}\n```"
            return self._build_document(
                source=file_path, text=text,
                source_format=suffix, converter="code-block",
            )

        # 2. Markdown → 委托给 MarkdownLoader
        if suffix == ".md":
            from retrieval.loaders.markdown import MarkdownLoader
            doc = MarkdownLoader().load(file_path)
            doc.metadata["source_format"] = ".md"
            doc.metadata["converter"] = "markdown"
            return doc

        # 3. 图片 → markitdown 内置 OCR（或后续接 paddleocr）
        if suffix in self._IMAGE_EXTENSIONS:
            return self._via_markitdown(file_path, source_format=suffix)

        # 4. 文档格式 → markitdown
        if suffix in self._MARKITDOWN_EXTENSIONS:
            return self._via_markitdown(file_path, source_format=suffix)

        # 5. 音频 → 暂不支持（需要 whisper，不是 markitdown 的职责）
        if suffix in self._AUDIO_EXTENSIONS:
            raise ValueError(
                f"音频文件暂不支持: {suffix}。"
                f"计划使用 whisper 提取转录文本，尚未实现。"
            )

        # 6. 兜底：未知格式也试一次 markitdown
        return self._via_markitdown(file_path, source_format=suffix)

    def _via_markitdown(self, file_path: Path, source_format: str) -> Document:
        """通过 markitdown 库转换为 Markdown，再包装为 Document。"""
        try:
            from markitdown import MarkItDown
        except ImportError:
            raise ImportError("markitdown 未安装。pip install markitdown")

        md = MarkItDown()
        result = md.convert(str(file_path))
        return self._build_document(
            source=file_path,
            text=result.text_content,
            source_format=source_format,
            converter="markitdown",
        )

    def _build_document(
        self,
        *,
        source: Path,
        text: str,
        source_format: str,
        converter: str,
    ) -> Document:
        """统一的 Document 构造——所有转换路径最终都走这里。"""
        return Document.build(
user_id="default",
            namespace="default",
            source=str(source),
            text=text,
            metadata={
                "loader": "markitdown",
                "file_name": source.name,
                "file_size": source.stat().st_size,
                "source_format": source_format,
                "converter": converter,
            },
        )
```

## 三个 loader 的分工

```
TextLoader       → 纯 .txt / .csv / .log
MarkdownLoader   → .md（解析 frontmatter，保留原始 Markdown）
MarkitdownLoader → 以上两种 + PDF/Office/图片/代码/HTML
                   （内部委托给 TextLoader / MarkdownLoader，不重复实现）
```

`MarkitdownLoader` 遇到 `.md` 时不自己处理——委托给 `MarkdownLoader`，拿到带 frontmatter 的 Document 后只补两个 metadata 字段。这样 frontmatter
解析逻辑只在一处。

`MarkitdownLoader` 遇到 `.py`/`.go` 等代码文件时，用 `_try_read_text` 读原始内容，包装成 ` ```lang\ncode\n``` ` 的 Markdown 代码块。之后的 splitter
和 index 看到的就是统一的 Markdown。

**当前明确不支持的是音频**（`.mp3` 等）。直接抛 `ValueError` 说明原因，不静默跳过。

## 和 models.py 的对接

所有 loader 的返回值类型签名都是 `-> Document`。splitter 拿到 `Document` 后调 `Chunk.build(document=doc, ...)`，`chunk_id` 的
`document.checksum` 来自 `Document.build()` 自动计算的 `sha256(text)`。

关键链路：

```
loader.load(path) → Document (checksum 自动算)
    ↓
splitter.split(doc) → list[Chunk] (chunk_id = sha256(doc_id + checksum + position + content))
    ↓
index.add(chunks) → INSERT OR IGNORE (确定性 chunk_id 天然去重)
```
Hello-Agents 的分块逻辑是 Markdown 结构感知：先按标题层级和段落切分，再按 token 数合并 chunk，并加 overlap。教程还特别提到中英文混合 token 估算，CJK 字符按 1 token 计算，英文按空白分词。

做标题感知分块。

意义：对bubblevan.github.io的个人博客和技术文档更重要。博客本身有 #、##、frontmatter，非常适合这个 splitter。

需要保留：

heading_path
start_char
end_char
position
source file

边界行为：

标题太短：不单独成 chunk。
代码块：尽量不要从代码块中间切开。
列表：尽量和上一段保留在一起。
类似```
标准Markdown文本 → 标题层次解析 → 段落语义分割 → Token计算分块 → 重叠策略优化 → 向量化准备
       ↓                ↓              ↓            ↓           ↓            ↓
   统一格式          #/##/###        语义边界      大小控制     信息连续性    嵌入向量
   结构清晰          层次识别        完整性保证    检索优化     上下文保持    相似度匹配
```

由于所有文档都已转换为Markdown格式，系统可以利用Markdown的标题结构（#、##、###等）进行精确的语义分割：

```python
def _split_paragraphs_with_headings(text: str) -> List[Dict]:
    """根据标题层次分割段落，保持语义完整性"""
    lines = text.splitlines()
    heading_stack: List[str] = []
    paragraphs: List[Dict] = []
    buf: List[str] = []
    char_pos = 0
    
    def flush_buf(end_pos: int):
        if not buf:
            return
        content = "\n".join(buf).strip()
        if not content:
            return
        paragraphs.append({
            "content": content,
            "heading_path": " > ".join(heading_stack) if heading_stack else None,
            "start": max(0, end_pos - len(content)),
            "end": end_pos,
        })
    
    for ln in lines:
        raw = ln
        if raw.strip().startswith("#"):
            # 处理标题行
            flush_buf(char_pos)
            level = len(raw) - len(raw.lstrip('#'))
            title = raw.lstrip('#').strip()
            
            if level <= 0:
                level = 1
            if level <= len(heading_stack):
                heading_stack = heading_stack[:level-1]
            heading_stack.append(title)
            
            char_pos += len(raw) + 1
            continue
        
        # 段落内容累积
        if raw.strip() == "":
            flush_buf(char_pos)
            buf = []
        else:
            buf.append(raw)
        char_pos += len(raw) + 1
    
    flush_buf(char_pos)
    
    if not paragraphs:
        paragraphs = [{"content": text, "heading_path": None, "start": 0, "end": len(text)}]
    
    return paragraphs
```

在Markdown段落分割的基础上，系统进一步根据Token数量进行智能分块。由于输入已经是结构化的Markdown文本，系统可以更精确地控制分块边界，确保每个分块既适合向量化处理，又保持Markdown结构的完整性：

```python
def _chunk_paragraphs(paragraphs: List[Dict], chunk_tokens: int, overlap_tokens: int) -> List[Dict]:
    """基于Token数量的智能分块"""
    chunks: List[Dict] = []
    cur: List[Dict] = []
    cur_tokens = 0
    i = 0
    
    while i < len(paragraphs):
        p = paragraphs[i]
        p_tokens = _approx_token_len(p["content"]) or 1
        
        if cur_tokens + p_tokens <= chunk_tokens or not cur:
            cur.append(p)
            cur_tokens += p_tokens
            i += 1
        else:
            # 生成当前分块
            content = "\n\n".join(x["content"] for x in cur)
            start = cur[0]["start"]
            end = cur[-1]["end"]
            heading_path = next((x["heading_path"] for x in reversed(cur) if x.get("heading_path")), None)
            
            chunks.append({
                "content": content,
                "start": start,
                "end": end,
                "heading_path": heading_path,
            })
            
            # 构建重叠部分
            if overlap_tokens > 0 and cur:
                kept: List[Dict] = []
                kept_tokens = 0
                for x in reversed(cur):
                    t = _approx_token_len(x["content"]) or 1
                    if kept_tokens + t > overlap_tokens:
                        break
                    kept.append(x)
                    kept_tokens += t
                cur = list(reversed(kept))
                cur_tokens = kept_tokens
            else:
                cur = []
                cur_tokens = 0
    
    # 处理最后一个分块
    if cur:
        content = "\n\n".join(x["content"] for x in cur)
        start = cur[0]["start"]
        end = cur[-1]["end"]
        heading_path = next((x["heading_path"] for x in reversed(cur) if x.get("heading_path")), None)
        
        chunks.append({
            "content": content,
            "start": start,
            "end": end,
            "heading_path": heading_path,
        })
    
    return chunks
```

同时为了兼容不同语言，系统实现了针对中英文混合文本的Token估算算法，这对于准确控制分块大小至关重要：

```python
def _approx_token_len(text: str) -> int:
    """近似估计Token长度，支持中英文混合"""
    # CJK字符按1 token计算
    cjk = sum(1 for ch in text if _is_cjk(ch))
    # 其他字符按空白分词计算
    non_cjk_tokens = len([t for t in text.split() if t])
    return cjk + non_cjk_tokens

def _is_cjk(ch: str) -> bool:
    """判断是否为CJK字符"""
    code = ord(ch)
    return (
        0x4E00 <= code <= 0x9FFF or  # CJK统一汉字
        0x3400 <= code <= 0x4DBF or  # CJK扩展A
        0x20000 <= code <= 0x2A6DF or # CJK扩展B
        0x2A700 <= code <= 0x2B73F or # CJK扩展C
        0x2B740 <= code <= 0x2B81F or # CJK扩展D
        0x2B820 <= code <= 0x2CEAF or # CJK扩展E
        0xF900 <= code <= 0xFAFF      # CJK兼容汉字
    )
```
三个 splitter 的设计已经很完整了。我只提几个对接点和对齐问题。

---

## 1. base.py：Protocol vs ABC

用 `Protocol` 而不是 `ABC` 是对的。splitter 的核心契约就是 `split(document) -> list[Chunk]`，不需要共享任何实现。如果将来有人想写一个调外部 API 的
splitter，只要函数签名对上就能插进去，不用继承任何类。

但有一个问题：Protocol 无法约束构造参数。`RecursiveSplitter(chunk_size=800)` 和 `MarkdownSplitter(chunk_size=800)` 的参数签名完全一致，但 Protocol
不强制这一点。将来 pipeline 里想 `splitter = cls(chunk_size=cfg.chunk_size)` 统一实例化时，如果某个 splitter 的参数名不一样就会炸。

**建议**：base.py 里同时放一个 `SplitterParams` dataclass：

```python
@dataclass
class SplitterParams:
    chunk_size: int = 800
    chunk_overlap: int = 120
```

不做强制约束，但约定所有 splitter 的 `__init__` 第一个参数都接受 `SplitterParams`。recursive 和 markdown 都用它，将来 semantic splitter 如果不需要
`chunk_size` 可以不接。

---

## 2. Chunk.build() 对接点

splitter 最终要产出 `Chunk` 对象。`Chunk.build(document=doc, content=..., position=..., ...)` 需要 5 个必传字段。现在的 markdown splitter
返回的 dict 里有 `content`/`start`/`end`/`heading_path`，缺 `position`。

position 的语义是 chunk 在文档中的序号，不是字符位置。最简单的做法是在 `_chunk_paragraphs` 产出 dict 列表后，外面再包一层 enumerate：

```python
def split(self, document: Document) -> list[Chunk]:
    paragraphs = self._split_paragraphs_with_headings(document.text)
    raw_chunks = self._chunk_paragraphs(paragraphs, ...)

    return [
        Chunk.build(
            document=document,
            content=rc["content"],
            position=i,
            start_char=rc["start"],
            end_char=rc["end"],
            heading_path=rc.get("heading_path"),
        )
        for i, rc in enumerate(raw_chunks)
    ]
```

`chunk_id` 由 `Chunk.build()` 内部的 `sha256(doc_id + checksum + position + normalized_content)` 自动生成。splitter 完全不需要知道 hash
逻辑。

---

## 3. heading_path 的归属

heading_path 存的是 chunk 所属的最深层标题路径（`"## Memory 系统 > ### 拒答阈值"`）。当前逻辑是用 `reversed(cur)` 取最后一个有 heading_path
的段落。这个做法有一个隐含假设：chunk 内部可能跨了多个标题段落，只保留最内层的是合理的——因为那是当前 chunk 内容最精确的位置。

但有一类边界：一个 chunk 恰好跨了两个同级标题。比如 `### A` 的最后两段 + `### B` 的第一段被合并了。取最内层会返回 `### B`，但实际上这个 chunk 大部分内容属于 `### A`。
**我的判断**：这个问题不值得现在修。博客和文档的 chunk_size=800 时，两个 `###` 标题之间通常有足够内容填满一个 chunk，不太会跨标题合并。等 eval 数据里出现 heading_path
错误导致的检索失败再改。现在在代码注释里标一笔就行。

---

## 4. 代码块保护

你提到的"代码块不要从中间切开"——当前的 `_split_paragraphs_with_headings` 是按行 split 的，代码块里 `\n` 会被当成行分隔，但在 `flush_buf`
时会把一个代码块内的所有行合并成一个段落（因为中间没有空行触发 flush）。所以只要代码块前后有空行（Markdown 标准格式），就不会从中间切开。

不是标准格式的情况（代码块前没空行），会被当成普通段落处理。这个不值得额外加状态机检测——代价高、收益低。要求输入是标准 Markdown 就行。

---

## 5. recursive.py 的设计

recursive 是 baseline，不需要 heading_path。最简单的实现就是按分隔符优先级切，再按 token 数合并。

```
"\n\n" → "\n" → "。" → "." → 硬切
```

和 markdown splitter 共享 `_approx_token_len`。建议把这个函数抽到 base.py 或一个 `_token_utils` 里——两个 splitter 都要用，不放 base 里也得有个公共位置。

---

## 6. 三个 splitter 的适用范围

| splitter | 输入 | 产出 |
|----------|------|------|
| `RecursiveSplitter` | 无结构文本（纯 .txt、代码块的文本内容） | 纯内容 chunk，无 heading_path |
| `MarkdownSplitter` | 有标题的 Markdown | 带 heading_path 的 chunk |
| 未来的 `SemanticSplitter` | 任何文本 | 按语义边界切，可能是 LLM-based |

pipeline 里选择 splitter 的逻辑不是"只有一个"——不同的 Document 应该用不同的 splitter。纯文本用 recursive，博客文章用 markdown。这应该是 splitter 自己的职责还是
pipeline 的职责？

**建议放在 splitter 的入口层**——加一个 `get_splitter(document: Document) -> TextSplitter` 工厂函数，根据 `document.metadata["loader"]` 或
`document.metadata["source_format"]` 选择。markdown loader 产出的 Document 走 MarkdownSplitter，text loader 产出的走
RecursiveSplitter。这样 pipeline 只需要调 `splitter.split(doc)`，不需要知道内部用了哪个。

**Loaders：ABC，不换 Protocol。**
原因很简单——loader 的子类共享了 `_resolve()` 和 `_try_read_text()` 两个具体实现。`MarkitdownLoader` 内部还委托给 `MarkdownLoader` 和 `TextLoader`，这三个都继承 `BaseLoader`，ABC 的继承关系正好表达"它们是一类东西"。
换成 Protocol 会丢两样东西：`_resolve` 和 `_try_read_text` 没地方放了（要么每个 loader 复制粘贴，要么再抽一个工具模块——多一层间接，不值得）。
splitter 用 Protocol 是因为 `RecursiveSplitter` 和 `MarkdownSplitter` 之间**零共享实现**——连构造函数参数都刚好一样才没出事。如果将来 `SemanticSplitter` 不需要 `chunk_size`，Protocol 照样容得下，ABC 反而束缚。
