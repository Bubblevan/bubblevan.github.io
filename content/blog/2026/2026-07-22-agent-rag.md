## 1. 为什么 Hi-Agent 需要 RAG

在完成 Memory 模块后，我发现它解决的是 Agent “记不记得住”的问题，而 Agent 面临的另一个更棘手的挑战是“知不知道”。

Memory 擅长存储用户偏好、历史对话和长期目标等**内部衍生信息**。但当用户的需求指向外部静态知识，例如“解释这篇论文中的 RAG Evaluation 方法”或“分析这个项目的目录结构”时，Memory 就失灵了。强行将这些文档一股脑塞进 Memory，不仅会让长期记忆库迅速膨胀、难以管理，更关键的是，PDF、代码这类非结构化知识与用户动态上下文在更新频率和管理方式上格格不入。

因此，在设计 Hi-Agent 的初始阶段，我就为 Memory 和 RAG 划定了明确边界：
- **Memory**：负责记录 Agent 与用户交互过程中产生的历史、偏好与状态。
- **RAG**：作为 Agent 访问外部静态知识库的接口，专门处理项目文档、论文、博客等外部资料。

## 2. 超越“向量搜索”的宏观数据流

初次接触 RAG 时，很容易将其简化为“文档丢进向量库，搜出来完事”的线性过程。但一旦着手实现，就会发现真正的链路要复杂得多。每个环节都承担着不容推卸的独立职责，数据依次流经文档加载、智能切分、向量化与索引，最终才能被检索并拼接上下文，用于生成增强回答。

我由此意识到，相比于看似核心的 Embedding 和向量搜索，真正决定系统可用性的往往是那些琐碎的前置环节：
- 一个 Markdown 文件被切成了若干片段，未来从向量库里只召回一个 `{“content”: “...”, “score”: 0.82}` 是远远不够的。它还来自哪个文件？属于哪个章节？
- 如果源文件更新了，旧的片段如何失效？
- 在多租户/多知识库场景下，如何确保严格的命名空间隔离？

这些挑战无法通过向量数据库解决。因此，在 Hi-Agent 中，我选择先设计清晰的数据流与领域模型，再填充具体实现。

## 3. 领域模型

为了根治数据传递中 `dict` 透传、字段来源不明等“口头契约”的弊病，我设计了一套不可变（`frozen=True`）的数据模型，作为整条流水线严格遵循的类型契约：`Document` → `Chunk` → `RetrievalResult` → `RAGAnswer`。每个对象都有且仅有一个通过 `@staticmethod` 工厂方法定义的合法构造入口，关键字段在内部自动计算，将生成逻辑牢牢锁死在类型内部。

### Document：描述完整知识来源

`Document` 代表一份经过加载的完整文档。其关键设计在于：
- **唯一标识**：`document_id` 基于 `source` 和内容校验和(checksum)**确定性**生成，即使不传也能保证唯一。
- **变更感知**：`checksum` 由工厂方法通过 SHA256(text) 自动计算，无需调用方操心。这是后续判断文档是否变更，并触发增量索引更新的核心依据。
- **严格不可变**：`frozen=True` 配合 `MappingProxyType` 的 metadata，防止对象在流水线中被下游意外篡改。

### Chunk：检索的基本单位

`Chunk` 是文档的一个切片，其核心设计在于：
- **确定性 ID**：`chunk_id` 由 `document_id + checksum + 片段位置 + 规范化内容` 的哈希构成。这意味着，只要文档内容和切分位置不变，重新导入将产生完全一致的 ID，为索引层的幂等去重提供了基石。
- **强关联**：构建 `Chunk` 必须传入完整的 `Document` 对象，保证 `chunk_id` 能感知文档内容的任何细微变化。

### 追踪检索与生成

- **RetrievalResult**：它不仅是最终得分，还通过 `score_components` 字段保留了来自不同检索器（如 BM25、Dense）的原始分数。这为后续分析各路检索的实际贡献、校准融合参数提供了宝贵数据。
- **RAGAnswer**：除了最终回答文本，它自动从输入的上下文结果中提取 `citations`（引用的 chunk_id 列表），为生成后的证据验证提供了抓手。

## 4. 输入层：用 Loader 策略屏蔽多样性

RAG 面对的第一道坎是知识来源格式的多样性：`txt`、`markdown`、`pdf`……如果针对每种格式在业务逻辑里堆砌 `if-else`，代码将迅速腐化。因此，我引入了 Loader 层，将所有格式统一转化为标准的 `Document` 对象。

我设计了三个核心 Loader：
- `TextLoader`：负责纯文本文件，支持 UTF-8 到 GBK 的编码降级。
- `MarkdownLoader`：专门解析 Markdown 和 YAML frontmatter，从中提取标题、日期、标签等元数据，同时保留正文的原始 Markdown 格式。
- `MarkitdownLoader`：充当多格式的统一入口。它内部采用委托模式，遇到 `.md` 文件交给 `MarkdownLoader` 以复用其 frontmatter 解析能力；对于 PDF、Office 等，则交给 `markitdown` 库转换为 Markdown；甚至对于代码文件，也会将其包装成带语言标记的 Markdown 代码块。这让后续的 Splitter 只需面对统一的 Markdown 内容。

## 5. 切分层：结构感知的 Markdown 分块

分块策略直接决定了检索的颗粒度与准确度。对于以技术博客和文档为主要对象的 Hi-Agent，利用 Markdown 的标题结构进行语义分割是自然而然的选择。

`MarkdownSplitter` 实现了一个三段式流水线：
1.  **段落与标题解析**：遍历每一行，识别 `#` 标题并维护标题栈，将正文按空行聚合为段落。这个过程同时为每个段落记录了它归属的完整标题路径（`heading_path`），如 `“RAG > 检索策略 > RRF”`。
2.  **Token 感知合并**：依据预设的 `chunk_size` 和 `overlap`，对段落进行智能合并。这里使用了支持中英文混合的 token 估算算法（CJK 字符按 1 token 计，其余按空白分词），确保分块大小与模型的上下文窗口对齐。
3.  **构建 Chunk 对象**：为合并后的每个块填充 `start_char`、`end_char`、`position` 等元数据，并通过 `Chunk.build()` 将其固化为领域模型。

此外，还着重处理了几个关键的边界情况：
- **代码块保护**：利用 Markdown 代码块前后空行的特性，确保代码不会被意外切断，保障其语法完整性。
- **chunk_id 的确定性**：通过继承文档的 checksum 和明确的分块位置，确保了 chunk_id 的稳定复现，让索引层可以简单地实现 `INSERT OR IGNORE` 逻辑。

## 6. 生成层：基于证据的回答

到了这一层，RAG 与普通 LLM 问答的区别才真正显现。`ContextBuilder` 的职责是将检索到的碎片化 `Chunk` 列表，组装成 LLM 能理解的、结构化的上下文。

- **组装上下文**：它不止是简单的拼接，而是负责对结果去重、将同一文档的相邻片段合并，并在硬性 token 预算限制下，优先保留信息量最丰富的部分，形成包含 `[Source 1]` 标记和 `heading_path` 等信息的格式化文本。
- **提示词约束**：此处的提示词明确要求 LLM “只能基于给定的上下文回答”、“缺少证据时请明确说明”，并对其施加“每个事实必须提供引用编号”的硬性约束。
- **生成后验证**：系统会解析 LLM 的回答，提取所有 `[n]` 引用标记，并与提供的上下文来源 ID 进行比对。任何引用不存在来源的“幻觉”都会被当场捕获并报告，从而在最后一环保障了答案的忠实性。

## 7. Loader：让 RAG 支持不同类型知识来源

在确定 `Document` 这一核心数据结构之后，下一步要解决的就是那个最现实的问题——不同来源的知识，如何进入同一条 RAG 流程？

Hi-Agent 未来需要检索的远不止纯文本。实际场景中，知识的形态千差万别：个人博客的 Markdown 源文件、项目里的 `README`、沉淀的技术文档、要快速理解的论文 PDF、课程资料，甚至是散布在代码注释里的设计思路。如果针对每一种格式都在主流程里写一堆 `if path.endswith(".pdf"): ... elif path.endswith(".md"): ...`，那么每增加一种格式，核心逻辑就会膨胀一次，最终变成难以维护的“意大利面条”。

为此，我们在文档和后续流程之间抽象出独立的 **Loader 层**。

整个关系非常清晰：`TXT`、`Markdown`、`PDF`、`DOCX`、`HTML` 等不同格式的文件，统一经过 Loader 这一道关口，最终都转化为标准的 `Document` 对象。

Loader 的职责单一而明确：读取文件、提取纯文本、保留必要的元数据（如文件名、类型等），然后创建 `Document`。它绝不越界去操心切分、embedding 或向量存储的事，那些都是下游模块该负责的。这样的边界划分，让我们可以随时为新的知识来源增加新的 Loader，而后续的 Splitter 和 Index 完全不需要感知上游文件的原始格式。

### 7.1 BaseLoader：统一 Loader 接口

不同 Loader 最终产出的形状必须一致——都是一个 `Document`。因此我们先定义了一个抽象基类，所有具体 Loader 只需实现 `load` 方法即可无缝接入 RAG Pipeline：

```python
from abc import ABC, abstractmethod

class BaseLoader(ABC):
    @abstractmethod
    def load(self, path: str) -> Document:
        pass
```

在这套体系下，`TextLoader`、`MarkdownLoader` 乃至负责多格式转换的 `MarkItDownLoader`，都只是这个接口的不同实现。未来即便要接入 `GitHubLoader`、`NotionLoader` 这类新型来源，也只需要新增一个类，完全不用去触碰 Splitter 和 Index 的代码。

### 7.2 TextLoader：最基础的文本输入

`TextLoader` 是 Loader 家族中最简单的一类。它的流程几乎就是“读字符串，包成 Document”。但即便是这么简单的环节，也会在实际环境中碰到编码问题。Windows 环境下常遇到 GBK 编码的文件，如果固定使用 UTF-8 打开，就可能直接抛出 `UnicodeDecodeError` 让整条流水线中断。

因此在 `TextLoader` 内部，我们加入了编码 fallback 机制：依次尝试 `utf-8`、`gb18030` 等常见编码，直到成功读取为止。这里的目标并不是做一个完美的全自动编码检测器，而是保证绝大多数常见文本文件都能稳定进入后续流程。

### 7.3 MarkdownLoader：为什么 Hi-Agent 特别重视 Markdown

Hi-Agent 有很大一部分知识天然沉淀为 Markdown：Hugo 博客、GitHub README、项目设计文档、学习笔记。Markdown 和普通纯文本最大的区别在于，它本身内嵌了结构信息。例如一份 Markdown 文档里，`BM25` 这段内容不仅是一段字，它在结构上属于 `RAG > Retriever` 这个层级之下。

对 RAG 来说，这个结构信息很珍贵。当用户问“BM25 在 RAG 中负责什么？”，模型除了需要知道 `BM25` 这个片段，还应该能意识到它处在整个知识体系的哪个位置上。因此，`MarkdownLoader` 需要做两件事：一是解析 YAML frontmatter，提取出标题、标签、日期等元数据；二是保留文档的完整层级结构。这些信息会作为 metadata 挂载到 Document 上，并进一步传递给后续的 Chunk，使整个检索链路都能感知文档的“骨架”。

### 7.4 MarkItDownLoader：统一处理复杂文档格式

除去 Markdown 之外，RAG 还必须面对 PDF、DOCX、PPTX、HTML 等二进制或半结构化格式。它们显然不适合直接丢给 Splitter。这里我们引入了 `MarkItDownLoader`，借助 `markitdown` 这类统一转换工具，将形形色色的格式先转换成 Markdown，然后再包装成 Document。

这样做的好处是巨大的：一旦所有文档都被统一成了 Markdown，后续专门为 Markdown 设计的 `MarkdownSplitter` 就可以直接复用，无需为每种原始格式都写一套切分逻辑。不过必须清醒地认识到，格式转换并不等于完美解析，双栏论文、复杂表格、扫描版图片这类 PDF 的解析质量依然严重依赖原始文件的质量。

因此，当前设计的首要目标是“让不同文件进入同一条 RAG Pipeline”，而非“在现阶段解决所有 PDF 理解问题”。未来如果需要处理论文级、扫描级 PDF，完全可以在这个 Loader 之下继续扩展 `PDFLoader`、OCR 和布局分析器等更专用的方案，而整体架构不会受到冲击。

## 8. Splitter：如何设计适合技术文档的 Chunk 切分策略

Loader 产出的 Document 往往很长：一本两百页的 PDF，或者一个上万字的项目 README。直接将整个文档的文本生成一个 Embedding 向量，不仅容易超出模型的输入长度限制，更严重的问题是，一个长文本只用一个向量表示，会把它涵盖的多个不同主题混杂在一起。一篇 Agent 文档可能同时涉及 Memory、Planning、Tool Calling 和 Evaluation，当用户询问“Memory 如何实现？”时，整篇文档的向量可能被大量无关信息稀释，导致检索效果不佳。

因此，必须将 Document 切分成更小的 **Chunk**，作为检索的基本单位。而这一职责，就落在 Splitter 身上。

### 8.1 为什么不能简单按照字符数量切割

最直观的切分方式是按固定字符数滑动窗口截取，简单粗暴，能跑通。但放到技术文档里，问题立刻暴露出来。假设一段 Markdown 文本，在“Vector Database”段落后紧接着就是“# Retriever”标题，固定长度的切分很可能把上一个主题的尾巴和下一个主题的标题混在同一个 chunk 里，而下一个 chunk 又因为丢失了标题而变得语义模糊。

因此，切分策略远不止是长度控制问题，它还关乎语义完整性、文档结构保持以及后续检索时的精确定位。一个无法精确归位到特定章节的 chunk，在最终回答的引用中也是残缺的。

### 8.2 RecursiveSplitter：通用文本切分方案

对于没有任何显式结构的纯文本，Hi-Agent 提供了 `RecursiveSplitter` 作为基础策略。它的核心思想是按照优先级逐步尝试不同的分隔符：先尝试用双换行（段落）切，如果片段仍太大，就降级到单换行，再不行就降级到中英文句号，最终在字符级别硬切。

这种分层降级的方式实现简单、泛化能力强，非常适合作为处理日志、纯文本资料的 baseline。

### 8.3 MarkdownSplitter：针对技术博客的结构化切分

`RecursiveSplitter` 虽然也能处理 Markdown，但它完全“看不见”标题，更不懂标题之间的父子关系。因此，Hi-Agent 专门实现了 `MarkdownSplitter`，其目标是保留标题层级与正文的归属关系，并保证代码块不被腰斩。

它的流程是：先解析 Markdown 的标题，构建出章节树，同时把正文内容按段落聚合，并给每个段落标注它当前所属的“标题路径”（如 `Memory > Retrieval`）。然后，基于 token 预算将这些段落智能合并为 chunk，每个 chunk 都携带着最内层标题的路径信息。这样一来，当检索召回到某个 chunk 时，我们不仅能得到正文，还能清楚地知道它出自文档的哪个角落，这对生成高质量回答和精确引用至关重要。

### 8.4 Chunk Metadata：为什么需要保存位置信息

一个 Chunk 除了 `content`，还必须携带充分的 metadata：`document_id`、`heading_path`、`start_char`、`end_char` 等。这些元数据是调试检索结果、生成引用标注以及未来重新索引时追溯源头的关键。没有它们，召回的一堆文本片段就只是一堆无根的文字，难以验证也难以为后续的评估提供依据。

### 8.5 Token 长度估算：为什么不能简单使用字符数量

切分时所谓的 `chunk_size`，在工程上很容易被误解为字符数。然而，不同模型 tokenizer 的粒度差异极大，中文单字往往就是一个 token，而英文可能需要好几个字符才构成一个 token。直接按 `len(text)` 去切，实际喂给模型的 token 数很可能大幅偏离预期。

当前 Hi-Agent 采用了一种无依赖的近似算法：CJK 字符近似计为 1 个 token，英文及其他字符按空白分词后的单词数估算。这种方式实现简单、不绑定特定模型，适合在早期快速落地。同时，我们在设计中预留了 `TokenCounter` 接口，未来可以轻松替换为 `tiktoken` 或 HuggingFace tokenizer 的实现，而 Splitter 本身无需感知具体计数策略的变更。
