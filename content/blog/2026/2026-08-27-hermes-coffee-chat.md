```
金鱼锅：我不确定UP实际的流程是怎么样的，但是听起来好像UP在这次搞砸了的做法上，Hermes并没有用对。

Hermes处理复杂任务的情况，没法靠单一Agent的，本身Hermes的特点就偏向个人助理，自进化。

势必各种任务的复杂记忆、关于你个人的记忆、各种各样的不同领域的skill和工具，等等全作为prompt在会话开始载入的话，prompt能有多重，用过llm的都很容易想象。

我用下来觉得，真正的能用的舒心的做法是分层：

第一层，1-2个大总管agent（比如一个日常事务，一个肉偏技术类事务），这是主要交流的入口，也是对复杂任务拆分分配的第一层。  
↓  
第二层，各路用的上的专家，比如你的数据库处理就值得建一个，这个专家的soul、工具、skill、以及基于llm wiki的知识库都围绕着他的专精范围设定，这个专家的初始prompt一定是比大总管轻量化的。

可以和他们直接交互的聊需求，也可以接受大总管通过kanban传递过来的整块任务，视任务简单还是复杂，是否有重复性，agent可以选择是否再次拆分，订计划分任务。  
↓  
第三层（如果需要）：  
纯worker，基本不会和它聊天，单纯做一些专门且重复性强的任务用的，视情况如果是可以用soul去约束的重复类别，则做个专门的worker，用kanban去做。如果重复性不强，自由度偏高则用delegaion 建立子agent并由第二层写prompt塞技能分派任务。

这样分配的话，我个人感觉在处理事务方面，其实Hermes并不比那些，比如编程或其他的计算机专精技术agent方案差。 只不过初期配置可能要多花费不少精力，但只要是经常涉及的领域，之后用起来就爽了。

视频里把Hermes比做老头乐，其实并不是，Hermes更像一个专家自由选的公司。

但如果处理某些业务不招人，不建立公司组织架构，作为总裁只揪着光杆总经理一个人嚯嚯，这总经理是又当秘书又得当底层员工，还得照顾总裁的情绪和日常起居。

你的具体情况要分为三部分：

1.建立一个Chrome的开发工具MCP，具体搜“Chrome dev tools mcp” 了解是什么，以及Hermes官方文档中有一篇【Use MCP with Hermes】，下方最推荐的例子就有。

你可以自己动手建，也可以让你的Agent读官方文档后指导你建立，（不过最好碰到不了解的概念问问Agent，自己知道是什么。）。

2.建立一个新文件夹，用于存放独立的给agent用Chrome Profile。这样不会和你用的Chrome搞混。

然后让agent自己写个技能，能自己打开这个开了开发工具的浏览器并记住线程号，reload mcp，操控浏览器，操控结束后自己单独关掉这个浏览器，而不关掉你用的。

3.再让agent 写个skill，用于填表，基于网页的不同（主要是交互js怎么写的），你可以一步一步演示给他看；也可以让他填一次不提交，出错你就发对话告诉他错哪了，让它修正，直到全填对；又或者用对话让他一步一步学填表网页上关键功能的操作。

最后总结操作经验，汇入这个填表skill，同时这个填表skill的工作流程定义中必须有一项是打开2.那个技能。

当然如果你有其他工作要求，也可以约束，比如每填一个，agent不许点提交，必须你审核后人工点等。随你工作的要求定。

最后就是这技能的触发条件是你给他一组资料，让它填，则技能启动。

然后，基本上你的这个工作流就做好了。

而技能串是：你给数据→触发填表.skill → 启动Chrome devtools.skill → 根据数据、约束和填表.skill规定流程，一个一个依次完成所有人的填表工作 → 直到最后一个完成后 Agent 自己关Chrome。
```

## 评论区地图

我把这 521 行评论完整看了一遍。它其实比视频本身更有价值，因为评论区已经自然分化成了几套非常不同的 **Hermes 使用哲学**。表面上大家在讨论「Hermes vs Claude Code」，实际上至少有 **8 类不同的人在用 Hermes**，而且他们嘴里的“好用/不好用”往往根本不是在评价同一种东西。

| 流派     | Hermes 在他们眼里是什么              | 典型改造                                                           |
| ------ | ---------------------------- | -------------------------------------------------------------- |
| 原生养成派  | 长期个人助理                       | SOUL + Memory + Skill                                          |
| 角色扮演派  | 24h 在线的赛博老婆/管家               | SOUL、人设、长期记忆、语音、飞书                                             |
| 记忆工程派  | 带长期状态的 Personal Agent        | Hindsight / Honcho / OpenViking / Mem0 / Smriti / Scope Recall |
| 总管编排派  | Agent Router / Manager       | Hermes → Claude Code / Codex / OpenCode / Worker               |
| 多层组织派  | “AI 公司”                      | 总管 → 专家 → Worker                                               |
| 自动化生活派 | HomeLab / IoT / 浏览器 / VPS 管家 | MCP、Chrome DevTools、Skill 链、NAS                                |
| 源码魔改派  | Python Agent Framework       | 改权限、Tool routing、安全、恢复逻辑、Memory                                |
| 反长期记忆派 | 一个被过度设计的 Harness             | 项目隔离 + 简单 Markdown + Claude Code/Codex                         |

这也解释了为什么评论区会出现极端相反的结论：有人说“**Hermes 核心就是记忆**”，有人说“**Hermes 的记忆就是它变蠢的根源**”；有人说“编程一坨”，有人说“我改源码之后吊打 CC”；有人觉得“每一步确认才正常”，还有人反问“你都要每一步确认了，那为什么还用 Hermes？”  

---

## 一、最基础的一派：Hermes 是“养成系 Personal Agent”

评论区里有一派人，他们不把 Hermes 当开箱即用的工具，而是当成一个需要慢慢养成的长期 Agent。一开始它可能笨笨的，但只要你肯教，它会逐渐记住你的习惯、背景、工作流、Skill、记忆甚至人格。所以那句“hermes就是养起来才好用”后面才会跟着“贾维斯”“养成系女友”之类的说法。

这一派的人不在乎 Hermes 单次 benchmark 跑分多高，他们在意的是今天教过的东西，下周不用再重复。比如以前你想让它帮你登服务器，得把地址、路径、步骤全列一遍；养熟之后，你只要说“看看 VPS 怎么了”，它自己就知道你指的是哪台机器、用什么 SSH、哪些目录不能碰、检查哪些服务、先报告还是直接修、修完给什么格式的反馈。

有人就说，他主要用 Hermes 来复制自己的行为习惯，跟养娃一样，让她当经理去操作 Claude 干活。

顺着这个思路往下走，就会碰到一个关键问题：Hermes 不一定非得是最强的执行者 Worker，它完全可以做一个“认识你”的管理者 Manager。

## 二、非常大的一派：角色扮演 / 赛博老婆 / 情绪价值

这一派在评论区后半段非常显眼。有人直接晒出 Hermes 的 soul.md 还原了爱蜜莉雅，然后整栋楼就开始讨论 AstrBot、SillyTavern、人设长度、OOC、长期记忆、语音克隆、飞书接入这些话题。这类玩法其实把四层能力叠在了一起。

**第一层是 SOUL.md，相当于人设内核。** 不是简单写一句“你是爱蜜莉雅”就完事，而是要把角色的经历、性格、世界观、和用户的关系、语言习惯、行为边界、情绪反应、价值判断全部写进去。评论区里有人强调，角色应该知道原著剧情，然后根据经历推演回答，而不是只模仿口癖。这一步就从“风格模仿”变成了“角色模拟”。

**第二层是 Memory，记录“你们之间发生过什么”。** 真正让角色扮演从聊天机器人变成陪伴感的，不是人设本身，而是记忆。SOUL 回答“她是谁”，Memory 回答“你们之间发生过什么”。所以有人才会说“记忆和人格系统感觉天生就适合这种模式”。三个月后你问“还记得上次深圳那件事吗”，如果她真的记得，那种连续的人格体验和单次加载角色卡完全不是一回事。

**第三层是 Gateway，让角色住进你的日常。** 有人问“Hermes 好像没有手机客户端？”，对方直接回“这是飞书啊……Hermes 可以接入即时消息”。所以 Hermes 的 RP 玩法跟 SillyTavern 不完全是一回事：SillyTavern 更像是你打开一个软件去和角色聊天，而这一派想要的是她就在飞书/微信/Telegram 上全天候在线，还能主动给你发消息，甚至顺手帮你管 VPS（Virtual Private Server，虚拟专用服务器）。

**第四层是 Voice + Tool，让她不只是会陪聊。** 评论区那位老哥说自己已经用上了语音克隆的爱蜜莉雅，全语音对话，而且这个 Emilia 还要帮他做 VPS 运维。这样一来，它就不再是单纯的 Character AI，而变成了“角色 + 个人记忆 + 消息网关 + 语音 + 工具 + 自动化”的组合，已经有点 Embodied Personal Agent 的雏形了。另一个人总结得也很到位：“总管除了总管当然还要抚慰我的情绪，回头研究研究准备接硬件。”再接下去就是 Home Assistant、IoT、音箱、摄像头、NAS，确实越来越像贾维斯。

## 三、评论区技术含量最高的一块：把 Hermes 原生 Memory 拆掉重做

Hermes 原生记忆系统的问题在评论区被反复提及：旧记忆覆盖新状态、记忆膨胀、注意力被稀释、项目之间互相污染。围绕“怎么修”，讨论大致分成两条路线：
一条是不换底层，在原生机制上做生命周期管理；
另一条是干脆外接独立的记忆引擎，把 Memory 从 prompt 里拿出来。
这里其实至少有 **六种路线**。

### 原生 Memory 的改良：从“人肉整理”到“记忆卡片”

有人针对“三天前的任务流程覆盖了两天后的变更”这个具体痛点，给出一套定时整理方案：让 Hermes 每晚总结当天内容，把高价值事实更新进 Memory，过期内容删除，复杂操作流程写成外部文档、Memory 里只留引用。
```text
Memory
├─ 高价值长期事实
└─ 外部操作文档引用

Cron 每晚：
今天发生什么
→ 总结
→ 更新 Memory
→ 删除过期 Memory
→ 输出整理报告
```
这很像数据库的 compaction 加 garbage collection，核心思想是 **Memory 只存索引和 durable fact，过程性知识应该变成 Skill 或 Document**，而不是把一百行工作流直接塞进 prompt。

---

第二派是 Memory Card 派：给记忆加入“层级、时间、新鲜度”。

他们更进一步的玩法是“记忆卡片插件”：会话中注入短标题摘要，让 Agent 自主判断重要性，非常重要的写进 Memory，次一级的写成带 **时间戳** 和 **分类** 的卡片，Agent 根据时间判断新鲜度。这已经是一套完整的 memory lifecycle management，同时处理了重要性、时效性、冲突、检索范围和 token 预算五个问题。它本质上是“让该记住的留下来，该过期的消失”。

一个真正的 **memory architecture** 类似：

```text
Raw Conversation
      ↓
Importance Scoring
      ↓
┌────────────────┐
│ Critical Facts │ → MEMORY
├────────────────┤
│ Memory Cards   │ → timestamp/category
├────────────────┤
│ Session Logs   │
└────────────────┘
```

与其说这是“提示词”，不如说是在做 **memory lifecycle management**。这里同时解决五个问题：
* importance
* freshness
* temporal conflict
* retrieval scope
* token budget

### 外部 Memory Provider：从 Hindsight 到 OpenViking

前面的做法仍然没有脱离 Hermes 原生的文件式记忆：无论是人工清理 `MEMORY.md`，还是把复杂流程外置成 Markdown，本质上都是在想办法控制一个不断膨胀的文本上下文。

另一派人的思路更加彻底：

> **既然长期记忆本来就涉及抽取、去重、时序、冲突、检索和遗忘，为什么还要让一个 Markdown 文件承担数据库的职责？**

于是他们开始给 Hermes 外接真正的 Memory Engine。

评论区里有人用 Hindsight，有人试过 Mem0、Honcho，后来又有人转向 OpenViking；还有人干脆自己基于 SQLite 写 Smriti、Scope Recall 一类的方案。这里真正值得关注的并不是“哪个记忆库最好用”，而是它们分别代表了几种完全不同的 **Agent Memory Architecture**。

严格来说，这些 external provider 并不会“替代” Hermes 原生的 `MEMORY.md / USER.md`。截至 2026 年 8 月，Hermes 官方已经把 External Memory 做成了一套独立的 `MemoryProvider` 插件系统，内置：

* Honcho
* OpenViking
* Mem0
* Hindsight
* Holographic
* RetainDB
* ByteRover
* Supermemory

八个 Provider；同时只能启用一个 External Memory Provider，但原生的 `MEMORY.md / USER.md` 仍然继续工作，因此它实际上是一种 **additive memory layer**。

这件事情很能体现 Hermes 后来逐渐形成的一种设计思路：Memory、Context Engine、Model Provider 都不再被硬编码成唯一实现，而是被抽象成可替换的 provider boundary。用户甚至可以在 `~/.hermes/plugins/memory/<name>/` 下放入自己的实现，并覆盖同名 bundled provider，而不需要直接修改 Agent 主循环。

真正的 `MemoryProvider` 生命周期也比“检索一下然后塞进 Prompt”稍微完整一些：

```text
Agent startup
    ↓
initialize()
    │
    ├── 建立连接
    ├── 创建资源
    └── warm up
    ↓
system_prompt_block()
    │
    └── 注入少量静态 Memory Provider 信息
    ↓
用户提出问题
    ↓
prefetch(query)
    │
    └── 在当前 turn 前检索相关长期记忆
    ↓
Context Assembly
    │
    └── 把召回内容加入当前工作上下文
    ↓
LLM Agent Loop
    │
    ├── 普通推理
    └── 必要时主动调用 Provider Tools
          ↓
      get_tool_schemas()
      handle_tool_call()
    ↓
Assistant Response
    ↓
sync_turn(...)
    │
    └── 将本轮信息异步/同步写回长期记忆
    ↓
Session End
    │
    └── 部分 Provider 再做 consolidation / extraction
    ↓
shutdown()
```

也就是说 External Memory 实际上有两条访问路径：

```text
Passive Memory
prefetch → 自动召回 → 自动进入 Context

Active Memory
LLM → memory tool → 主动搜索 / 写入 / 推理
```

这一区分很重要。

如果所有记忆都自动 `prefetch` 到 Prompt 中，长期使用之后很容易重新遇到前面讨论过的 Attention Pollution；但如果完全依赖 Agent 主动调用工具，又可能出现“模型明明有记忆库却忘了查”的问题。

所以很多 Provider 后来都会同时支持类似：

```text
context / auto-inject
tools / active recall
hybrid
```

这样的模式。

这也意味着所谓“Agent Memory”已经不只是一个数据库问题，而变成了：

> **什么时候写、写什么、存在哪里、什么时候取、取多少、由谁决定取，以及取出来后如何进入 Context。**

这其实已经跨进 Context Engineering 的范畴了。

#### Mem0：把长期记忆真正做成“Memory Layer”

Mem0 反而应该放在 Hindsight 前面讲，因为它算是这一波 Agent Memory 里最典型、也最容易理解的工业化基线之一。

它不只是一个 GitHub 上很火的 Memory SDK。2025 年 Chhikara 等人把系统整理成论文 **《Mem0: Building Production-Ready AI Agents with Scalable Long-Term Memory》**，后来正式发表于 **ECAI 2025**。论文想回答的不是“怎么把聊天记录存进 Vector DB”，而是一个更完整的问题：

> **面对持续数周甚至数月的多 Session 对话，Agent 应该从每轮交互中记住什么、什么时候修改旧记忆，以及下一次到底应该取回哪些信息？**

这也是为什么 Mem0 比最简单的：

```text
conversation
    ↓
embedding
    ↓
vector database
```

多了一层真正的 **Memory Management**。

---

##### 论文版 Mem0：Extract → Compare → Update

Mem0 2025 论文里的核心 Pipeline 可以粗略画成：

```text
New Conversation Turn
        ↓
Recent Context
        ↓
Memory Extraction
        ↓
Candidate Facts
        ↓
Vector Search Existing Memories
        ↓
Top-s Similar Memories
        ↓
LLM compares:
new fact + existing facts
        ↓
┌────────┬────────┬────────┬────────┐
│  ADD   │ UPDATE │ DELETE │  NOOP  │
└────────┴────────┴────────┴────────┘
        ↓
Persistent Memory Store
```

论文实验中保留最近 `m=10` 条消息作为提取上下文；对于每一个提取出的 candidate fact，又从已有 Memory 中找 `s=10` 条最相似的记忆，让 GPT-4o-mini 通过 function calling 决定下一步操作。

四种操作分别是：

```text
ADD
新信息，以前没有
→ 新增 Memory

UPDATE
已有事实存在，但新信息更完整
→ 更新原 Memory

DELETE
新信息与旧事实冲突
→ 删除旧 Memory

NOOP
已经知道 / 没有新增价值
→ 不操作
```

例如：

```text
旧记忆：
User lives in Hangzhou.

新对话：
I moved to Hong Kong last month.
```

一个理想的 Memory System 不应该简单变成：

```text
Memory 1:
User lives in Hangzhou.

Memory 2:
User lives in Hong Kong.
```

然后把矛盾甩给未来的 LLM。

论文版 Mem0 会在 **write path** 上主动判断：

```text
Hong Kong
    ↓
和已有 location memories 比较
    ↓
旧信息已经过时
    ↓
DELETE / UPDATE
```

所以 Mem0 的一个重要思想是：

> **Memory 不应该是 append-only 的聊天摘要仓库，它必须拥有自己的 lifecycle。**

这已经明显区别于最原始的 RAG。

RAG 更多是在解决：

```text
我应该 retrieve 哪段文本？
```

Mem0 同时试图解决：

```text
什么值得成为 Memory？
Memory 之间冲突怎么办？
什么时候修改？
什么时候删除？
最后又该 retrieve 哪些？
```

---

##### Mem0g：为什么还要再加 Graph？

论文还实现了增强版本 **Mem0g**。

普通 Mem0 的核心单位依旧是自然语言 Fact，例如：

```text
Alice works at Acme.
Alice is working on Project Hermes.
Bob leads Project Hermes.
```

如果只是做 Vector Search，这些事实彼此之间主要依靠 embedding similarity 找回来。

Mem0g 进一步把 Entity 和 Relationship 显式组织成图结构，希望把：

```text
Alice
  ↓ works_at
Acme

Alice
  ↓ works_on
Hermes

Bob
  ↓ leads
Hermes
```

这样的关系保存下来。

理论上这特别适合：

```text
Who...
Which project...
How are A and B related...
What happened before...
```

这类需要跨事实连接的问题。

所以可以把两者理解为：

```text
Mem0
=
Natural-language Memory
+
Vector Retrieval

Mem0g
=
Natural-language Memory
+
Graph-structured Relational Memory
```

论文真正有意思的地方恰恰在于：

> **Graph 并没有无条件战胜普通 Memory。**

---

##### 论文到底跑出了什么结果？

Mem0 的论文主要在 **LoCoMo** 上评测。

LoCoMo 是专门研究 Long-Term Conversational Memory 的 benchmark，它不是只问：

```text
“用户喜欢什么颜色？”
```

而是把问题分成：

```text
Single-hop
    ↓
一个历史事实即可回答

Multi-hop
    ↓
需要组合多个 Session 中的信息

Open-domain
    ↓
历史对话 + 外部常识

Temporal
    ↓
事件顺序、时间、持续时间、过去和现在
```

论文同时记录：

* F1；
* BLEU-1；
* GPT-4o-mini LLM-as-a-Judge；
* retrieval token 数量；
* search latency；
* total response latency。

其中 LLM-as-a-Judge 还进行了 10 次独立运行并报告均值与标准差。

比较有代表性的结果是：

| 方法             | Overall Judge Score | Context / Memory Tokens | Total p95 Latency |
| -------------- | ------------------: | ----------------------: | ----------------: |
| Full Context   |               72.90 |                  26,031 |          17.117 s |
| **Mem0g**      |           **68.44** |                   3,616 |           2.590 s |
| **Mem0**       |           **66.88** |                   1,764 |       **1.440 s** |
| Zep            |               65.99 |                   3,911 |           2.926 s |
| Best RAG（论文配置） |              ≈60.97 |                     512 |          ≈1.907 s |
| LangMem        |               58.10 |                     127 |           60.40 s |
| OpenAI Memory  |               52.90 |                   4,437 |           0.889 s |
| A-Mem          |               48.38 |                   2,520 |           4.374 s |

这里第一眼其实会发现一件很有意思的事情：

> **原始准确率最高的不是 Mem0，而是 Full Context。**

Full Context：

```text
把平均约 26k token 的整段 conversation
全部给模型
```

最后 Judge Score 是：

```text
72.90
```

而 Mem0：

```text
66.88
```

Mem0g：

```text
68.44
```

所以论文真正证明的并不是：

> “Memory 一定比 Long Context 更聪明。”

而是一个更工程化的 trade-off：

```text
Full Context
Accuracy         ██████████
Token Cost       ██████████
Latency          ██████████

Mem0
Accuracy         █████████
Token Cost       █
Latency          █
```

Mem0 相对于 Full Context 把 p95 总延迟从：

```text
17.117 s
↓
1.440 s
```

降了大约 **91%**，同时节省 **90% 以上的 Context Token**。

这才是论文标题里：

> **Production-Ready**

真正想强调的地方。

一个线上 Companion Agent 不可能用户每问一句：

```text
请稍等 17 秒，
我重新阅读一下你过去半年所有聊天记录。
```

所以 Memory System 的目标不是单纯追求理论 Accuracy，而是在：

```text
Recall Quality
     ×
Token Cost
     ×
Latency
     ×
Storage
     ×
Long-term Scalability
```

之间找到平衡。

---

##### Graph 真的更好吗？结果比想象中复杂

更值得记的其实是分类型结果：

| Question Type | Mem0 Judge | Mem0g Judge |
| ------------- | ---------: | ----------: |
| Single-hop    |  **67.13** |       65.71 |
| Multi-hop     |  **51.15** |       47.19 |
| Open-domain   |      72.93 |   **75.71** |
| Temporal      |      55.51 |   **58.13** |

按直觉来说：

> Graph 应该最擅长 Multi-hop。

但论文里居然不是。

普通 Mem0：

```text
Multi-hop J = 51.15
```

反而高于：

```text
Mem0g = 47.19
```

作者自己也承认，Graph 在复杂 multi-step integration 中可能产生额外 overhead 或 redundancy；自然语言 Memory 已经包含了足够丰富的信息，显式 Graph 不一定总有收益。

Graph 真正明显占优的是：

```text
Temporal
55.51 → 58.13

Open-domain
72.93 → 75.71
```

所以一个非常值得记住的 Memory Engineering 经验是：

> **Structured Memory 并不意味着越结构化越好。**

Natural Language 本身就是一种信息密度极高、表达能力极强的 representation。

从：

```text
Text
```

强行转换成：

```text
Entity
Relation
Triplet
Graph
```

本身也是一次 lossy transformation。

Graph 只有在：

```text
Relationship
Entity
Temporal Connection
Cross-memory Linking
```

确实是主要问题时才可能值得额外成本。

---

##### 26% improvement 到底是什么意思？

Mem0 摘要里最常被宣传的一句话是：

> Mem0 achieves 26% relative improvement over OpenAI Memory.

这个数字不是：

```text
+26 percentage points
```

而是 **relative improvement**。

论文中的 Overall Judge Score 大致为：

```text
OpenAI Memory ≈ 52.90
Mem0          ≈ 66.88
```

所以：

```text
(66.88 - 52.90) / 52.90
≈ 26.4%
```

因此应该表述成：

> Mem0 在 LoCoMo 的 LLM-as-a-Judge Overall 指标上，相比论文测试的 OpenAI Memory 基线取得约 **26% 的相对提升**。

而不是：

> “准确率提高了 26 个百分点。”

---

##### 特别注意：2026 年的 Mem0 已经不是论文那套算法

这一点特别容易看 README 看乱。

**ECAI 2025 论文版：**

```text
LLM Call 1
Fact Extraction
     ↓
LLM Call 2
Compare existing memory
     ↓
ADD / UPDATE / DELETE / NOOP
```

但是 2026 年 Mem0 推出的新一代算法已经改成：

```text
Conversation
     ↓
Retrieve related memories
     ↓
ONE LLM CALL
     ↓
ADD-only fact extraction
     ↓
Exact dedup
     ↓
Entity Linking
     ↓
Storage
```

不再在自动写入阶段做：

```text
UPDATE
DELETE
NOOP
```

同时 Retrieval 也从过去更偏 Semantic Search 的方案，升级成：

```text
Semantic
   +
BM25
   +
Entity Matching
   +
Temporal Signals
   ↓
Hybrid Ranking
```

为什么反而取消 UPDATE/DELETE？

因为后来的 Mem0 开始认为：

```text
2025:
User lives in Hangzhou.

2026:
User lives in Hong Kong.
```

这两条并不一定是真的“矛盾”。

它们可能共同组成一个：

```text
timeline
```

如果 2026 年简单 DELETE：

```text
Hangzhou
```

那么：

> “我以前住在哪里？”

反而无法回答。

所以新的哲学变成：

> **不要太早破坏历史事实，把 Temporal Resolution 更多留给 Retrieval。**

这和后面 Smriti 的：

```text
Supersession
```

其实出现了非常有意思的呼应。

两者都认为：

```text
旧事实 ≠ 错误事实
```

真正需要表示的是：

```text
什么时间成立？
什么时候失效？
现在什么是真的？
```

截至 2026 年，Mem0 自己的新 benchmark 已经报告远高于 2025 论文的成绩，例如其当前公开 evaluation suite 报告 LoCoMo 约 **92.5%**；但这是 **2026 新算法 + 新 evaluation pipeline 的结果**，不能倒灌到 ECAI 2025 论文里说“论文做到了 92.5%”。Mem0 官方自己也明确提醒：2026 algorithm update post-dates 原论文。

因此如果学习 Mem0，我会把它分成两代：

```text
Mem0 v1/v2 / ECAI 2025
    ↓
Memory Lifecycle Management
Extract → ADD / UPDATE / DELETE / NOOP

Mem0 v3 / 2026
    ↓
History Preservation + Better Retrieval
ADD-only
+
Hybrid Retrieval
+
Entity Linking
+
Temporal Reasoning
```

这本身就是 Agent Memory 在一年之内设计思想变化的一个很好案例。

#### Hindsight：不仅 Recall，还想做“经验学习”

评论区有人说：

> “hermes+hindsight，很好用……感觉 hindsight 很好地解决了 Hermes 的记忆本质是提示词的问题。”

这当然是一种使用体验，不能理解成“接上 Hindsight 以后 LLM 就真的获得了神经网络意义上的长期记忆”。

LLM API 本身依旧是无状态的。

Hindsight 真正做的事情是：

> **把“应该进入 Context 的历史信息”从一堆聊天记录，变成一个独立、可检索、可整理、可推理的 Memory Layer。**

它最核心的三个接口非常直观：

```text
retain
recall
reflect
```

但是这三个词背后其实对应三个不同阶段。

##### `retain`：不是保存聊天记录，而是把经历转成结构化记忆

最简单的 Memory 实现可以这样做：

```text
Conversation
    ↓
Embedding
    ↓
Vector DB
```

下次查询时找相似 chunk。

Hindsight 并不满足于这一层。

它在 `retain()` 时会从原始对话或文档中抽取：

```text
Raw conversation / document
        ↓
     Fact Extraction
        ↓
   Entity Resolution
        ↓
Temporal Information
        ↓
Relationships / Connections
        ↓
     Memory Bank
```

例如：

```text
“我去年还一直用 React，
后来项目迁移以后现在主要写 Vue。”
```

如果只是传统 chunk retrieval，它可能始终是一段文本。

而 Memory System 更希望得到类似：

```text
Experience:
2025:
    user primarily used React

2026:
    user migrated project to Vue
    user now primarily uses Vue
```

这也是长期记忆与普通 RAG 最大的差别之一：

> **RAG 更关心“哪段文本和 Query 相似”，Memory 更关心“这个主体在什么时候发生了什么变化”。**

Hindsight 官方进一步把记忆中的知识区分为几种层次：

```text
World Fact
    ↓
客观世界事实

Experience Fact
    ↓
用户或 Agent 自己经历过的事件

Observation
    ↓
由多条事实逐渐归纳出的稳定认识

Mental Model
    ↓
针对高频问题预先维护的高层认识
```

例如：

```text
Fact 1:
用户三次要求异步沟通

Fact 2:
用户不喜欢临时会议

Fact 3:
用户倾向先看书面方案

        ↓ consolidation

Observation:
用户长期偏好 asynchronous communication
```

Observation 并不是简单覆盖旧 Fact，而是可以持续根据新的 supporting evidence、contradiction 和 extension 修正。Hindsight 官方因此把它看成一种 evidence-grounded consolidation，而不只是“把聊天摘要写进去”。

##### `recall`：也不是单纯 Vector Search

传统的 Memory Demo 经常只有：

```text
query
  ↓
embedding
  ↓
top-k cosine similarity
```

Hindsight 的 recall 会组合多种 retrieval signal，包括：

```text
Semantic Search
        +
BM25 / Keyword Search
        +
Graph Traversal
        +
Temporal Retrieval
        ↓
     Fusion / Ranking
        ↓
Relevant Memories
```

因此像：

```text
“我之前为什么最后没继续那个方案？”
```

这种 Query 并不只是需要寻找语义相似文本。

它可能涉及：

```text
旧方案
→ 当时的问题
→ 后续发生的修改
→ 最终决策
```

需要把不同时间、不同实体之间的信息重新联系起来。

官方把这种 retrieval 架构称为多策略 recall，而不是单纯 vector retrieval。

##### `reflect`：真正有意思的是“在记忆上再推理一次”

`recall()` 返回的是资料：

```text
这些是和当前问题有关的记忆。
```

`reflect()` 则更接近：

```text
请你阅读所有相关记忆，
主动继续搜索需要的信息，
然后给我形成一个判断。
```

例如：

```text
recall:
“过去 CI 出过哪些问题？”
```

返回：

```text
timezone bug
dependency mismatch
flaky network test
cache invalidation
...
```

而：

```text
reflect:
“我们 CI 反复不稳定的根因是什么？
以后应该形成什么工程规范？”
```

要求 Memory System 自己在相关记忆之上做一次 synthesis：

```text
Memories
    ↓
search
    ↓
reason
    ↓
发现信息不够
    ↓
再次 search
    ↓
synthesis
    ↓
Higher-level answer
```

因此 Hindsight 官方明确区分：

```text
Recall
= retrieve memories for the Agent to reason over

Reflect
= let the memory system reason over memories
```

前者更像 RAG，后者已经是一层 **Memory-side Agentic Reasoning**。

这也是评论区那句话真正值得注意的地方：

> “让 Hermes 不是只记聊天，而是能从过去经历学习。”

这里的“学习”不是更新模型参数，而是：

```text
Experience
    ↓
Structured Facts
    ↓
Observations
    ↓
Reflection
    ↓
Reusable conclusion
```

本质上是一种 **non-parametric learning**。

另外 Hindsight 还有一个很容易被忽略但非常重要的概念：

```text
Memory Bank
```

Bank 是它的 isolation boundary。

```text
bank:user-A
bank:user-B
bank:project-X
bank:agent-Y
```

不同 Bank 之间默认不共享记忆。

这其实直接回应了长期 Agent 最麻烦的问题之一：

> **Memory 不只是要“记得住”，还必须知道这段记忆属于谁、属于哪个项目、属于哪个上下文。**

否则 recall 做得越强，污染可能反而越严重。

Hermes 接入 Hindsight 后，目前还可以配置：

```text
memory_mode = hybrid
              context
              tools

auto_retain = true / false
auto_recall = true / false

recall_budget = low / mid / high
```

默认情况下可以在 turn 前自动 recall，turn 后自动 retain，也可以关掉自动注入，只保留 `hindsight_recall`、`hindsight_retain`、`hindsight_reflect` 三个工具，让模型需要时主动访问。

因此 Hindsight 代表的一条路线可以概括为：

> **Memory as structured experience + retrieval + reasoning。**

它想解决的不仅是：

```text
“我过去说过什么？”
```

而是：

```text
“过去发生了什么？”
“这些事情之间有什么联系？”
“从这些经历里能得出什么？”
```

---

#### Honcho：重点不是“存信息”，而是持续建模 User / Peer

评论区还有一个很有意思的评价：

> Hindsight、Mem0、Honcho 都实际使用过，Honcho 是目前最接近人类记忆的一个。

这显然属于个人体验，不能拿来当 benchmark 结论。

但 Honcho 的确和传统的“Memory = 一堆 Fact”思路有明显区别。

如果 Mem0 一类系统最自然的表示方式是：

```text
user likes coffee
user uses Python
user prefers dark mode
```

那么 Honcho 更关心的是：

> **这个持续存在的 Peer 到底是一个怎样的主体？**

官方因此把自己称为：

> **Memory that reasons.**

Honcho 的数据模型从四个 primitive 开始：

```text
Workspace
├── Peers
└── Sessions
     └── Messages
```

其中：

##### Workspace：记忆世界的硬隔离边界

Workspace 并不是普通的文件夹。

官方设计指南直接把它定义为 hard isolation boundary：

```text
Workspace A
    ↓
Project A / User A / Environment A

Workspace B
    ↓
Project B / User B / Environment B
```

如果两个 Agent 应该共同理解同一个项目、用户或团队，可以让它们处于同一个 Workspace；如果两边的 Memory 不应该互相影响，就应该拆开 Workspace。

因此它首先回答的是：

> **谁有资格看到哪些长期经验？**

##### Peer：真正长期存在的主体

Peer 可以是：

```text
User
Agent
Assistant
NPC
Customer
Student
甚至某个持续变化的对象
```

Peer 的关键在于：

> 它跨 Session 持续存在。

例如：

```text
Session 1 ─┐
Session 2 ─┼── Alice (Peer)
Session 3 ─┤
Session 4 ─┘
```

每个 Session 都会结束，但 Alice 并不会因为聊天窗口关闭就“消失”。

因此 Honcho 能逐渐维护一个关于 Alice 的 representation。

这和：

```text
"user likes coffee"
```

有很大的抽象层级区别。

后者是：

```text
isolated facts
```

前者更像：

```text
Who is Alice?
What patterns characterize Alice?
How has Alice changed?
How should this Agent understand Alice?
```

这就是所谓 **user modeling / peer modeling**。

##### Session：当前 interaction scope

Session 则负责限定：

```text
这一次具体聊的是什么？
```

官方推荐把 Session 对应到一个 bounded interaction，例如：

```text
conversation
channel
task run
project
import
```

因此 Honcho 实际上形成了两层时间尺度：

```text
Session
    ↓
当前局部上下文

Peer
    ↓
跨 Session 长期表示
```

可以粗略理解成：

```text
Working / Episodic Context
           +
Persistent Entity Model
```

这就比单纯“每次聊天结束生成 Summary”更有结构。

##### Honcho 真正特别的地方：Representation + Dialectic

Hermes 对 Honcho 的集成甚至又往前走了一步。

它不是每轮只搜索一些历史 Message，而是采用两层 Context Injection：

```text
Base Context
├── session summary
├── peer representation
└── peer card

        +

Dialectic Supplement
└── 针对当前 query 的额外 reasoning
```

Base Context 负责回答：

```text
这个人是谁？
这个 Session 到目前发生了什么？
```

Dialectic 则负责回答：

```text
针对“当前这个问题”，
过去的信息意味着什么？
```

Hermes 甚至把二者的刷新频率拆开：

```text
contextCadence
    ↓
多久更新一次基础 Context

dialecticCadence
    ↓
多久进行一次 dialectic reasoning

dialecticDepth
    ↓
一次 reasoning 做几轮
```

所以可以出现：

```text
每轮都更新基本用户状态
但不是每轮都调用昂贵的 reasoning
```

从工程角度看，这其实是在显式控制：

```text
Memory Quality
vs
Latency
vs
Token Cost
vs
LLM Call Cost
```

而不是一句粗暴的：

```text
每轮把所有 Memory 塞进去。
```

Honcho 的另一个重要优势是 **scope**。

官方的 Codex-Honcho 集成已经支持：

```text
per-directory
git-branch
chat-instance
```

例如：

```text
repo/
├── main
│    └── memory A
│
├── feature-login
│    └── memory B
│
└── feature-agent
     └── memory C
```

这样某个 feature branch 中临时做出的决定，就不会天然污染整个项目长期上下文。

这正好回应评论区反复出现的一个痛点：

> **项目记忆必须隔离。**

所以 Honcho 代表的并不是“更高级的 Vector DB”。

它代表的是：

> **Memory as persistent entity modeling。**

如果说 Hindsight 更像：

```text
过去发生了哪些事情？
从这些经验中能推出什么？
```

Honcho 更像：

```text
这个长期存在的人 / Agent / Entity 到底是谁？
它在不同 Session 中如何持续变化？
```

这对于 Personal Agent、Companion Agent、Multi-Agent System 特别有吸引力。

因为长期 Agent 最终需要记住的并不只是：

```text
事实
```

还包括：

```text
人。
```

---

#### OpenViking：与其造一个 Memory DB，不如直接造 Context Database

这是评论区里明显有人非常推崇的一条路线。

有人总结自己的体验：

> Hindsight 太重，Mem0 不喜欢，Honcho 又比较小众，最后更喜欢 OpenViking，因为透明度高、容易维护，而且可以单独部署成 Server 给多个 Agent 共用。

这些依然只是评论者个人评价。

但 OpenViking 为什么很容易吸引喜欢折腾 Agent Infra 的人，倒是非常好理解。

因为它的出发点已经和前两个不太一样：

> **为什么要把 Memory、Knowledge RAG、Skill 分散在三套基础设施里？它们对于 Agent 来说，不都是 Context 吗？**

于是 OpenViking 直接把自己定义成：

> **Context Database for AI Agents**

而不是单纯的 Memory Database。

它首先把 Agent 所需的长期 Context 分为三个基本类型：

```text
Resource
Memory
Skill
```

三者职责不同：

```text
Resource
    ↓
外部世界中相对稳定的知识
文档 / 论文 / API Docs / Code Repository

Memory
    ↓
Agent 从交互和任务执行中逐渐获得的认知
用户偏好 / 事件 / 经验 / Pattern

Skill
    ↓
Agent 可以调用的能力定义
工作流 / Tool 配置 / Script / 操作方法
```

这里实际上是在回答一个非常容易混乱的问题：

```text
“用户喜欢 Python”
应该放哪？

“FastAPI 官方文档”
应该放哪？

“如何部署这个项目”
又应该放哪？
```

如果全部塞进：

```text
MEMORY.md
```

它们只是三个 Markdown 段落。

但从生命周期来看，它们根本不是一种东西：

| Context  | 谁产生          | 变化频率 | 本质    |
| -------- | ------------ | ---: | ----- |
| Resource | 用户/系统加入      |   较低 | 外部知识  |
| Memory   | Agent 从经历中提取 |   较高 | 长期认知  |
| Skill    | 用户/系统定义      |   较低 | 可执行能力 |

于是 OpenViking 用一个统一的虚拟文件系统组织它们。

现在的结构更准确地写应该类似：

```text
viking://
├── resources/
│   └── shared knowledge
│
├── user/
│   └── {user_id}/
│       ├── memories/
│       ├── resources/
│       ├── sessions/
│       ├── skills/
│       └── peers/
│           └── {peer_id}/
│               ├── memories/
│               └── resources/
│
└── agent/
    └── skills/
```

也就是说你面对的不再是：

```text
VectorDB.query(...)
```

而更像：

```text
ls
tree
find
read
```

Agent 可以先“看看这里有什么”，再决定是否深入。

这也是 OpenViking 所谓 filesystem paradigm 的核心。

##### 从 Flat RAG 变成 Hierarchical Retrieval

传统 RAG 最典型的数据结构是：

```text
Document
   ↓
Chunk
   ↓
Embedding
   ↓
Vector DB

query
   ↓
top-k chunks
```

它有一个天然的问题：

> 一个复杂知识库最终被压扁成了很多地位相同的 Chunk。

Agent 很难知道：

```text
这段来自哪个项目？
它上一级目录在讲什么？
旁边还有什么相关内容？
这只是摘要还是完整定义？
```

OpenViking 的思路更接近：

```text
Query
 ↓
Intent Analysis
 ↓
找到相关目录
 ↓
阅读目录摘要
 ↓
判断是否相关
 ↓
进入子目录
 ↓
继续浏览
 ↓
必要时加载原文
```

也就是：

```text
Flat Retrieval
        ↓
Hierarchical Navigation
```

这其实非常符合人类自己查资料的方式。

我查一个大型代码库也不会第一步：

```text
把所有文件切成 500-token chunk
然后 cosine similarity。
```

我往往先：

```text
看 repo tree
→ 找对应模块
→ 看 README / interface
→ 找具体文件
→ 最后读 implementation
```

OpenViking 本质上想让 Agent 也这么做。

##### L0 / L1 / L2：Progressive Context Disclosure

为了避免 Agent 一进入目录就把完整内容全部读取，它又给 Context 做了三层表示：

```text
L0 — Abstract
    ↓
最短的语义摘要，用于快速搜索和筛选

L1 — Overview
    ↓
较完整的目录概览，用于 rerank 和导航

L2 — Detail
    ↓
原始文件和子目录，需要时才真正加载
```

官方当前默认大致是：

```text
L0
~256 characters
用于 vector retrieval / quick filtering

L1
~4000 characters
用于 rerank / navigation

L2
full content
按需读取
```

需要注意的是，L0/L1 更准确地说是**目录级 semantic sidecar**，并不是简单给每个普通文件都机械生成三份副本。

于是一个 Agent 的 Context Acquisition 可以变成：

```text
Query
 ↓
大量 L0
 ↓
“哪些方向值得看？”
 ↓
少量 L1
 ↓
“具体应该进入哪里？”
 ↓
极少量 L2
 ↓
Full Detail
```

这和现在越来越重要的一个 Context Engineering 思路高度一致：

> **Progressive Disclosure：先给模型地图，不要一开始就给它整个世界。**

它解决的是 Context Window 的一个非常根本的问题：

```text
Context Capacity
≠
Attention Capacity
```

模型允许 1M context，并不意味着：

```text
塞 1M token
=
模型能同等精确地关注所有 1M token
```

因此更好的架构往往不是：

```text
How can I fit more context?
```

而是：

```text
How can I expose less context,
while making the right context easier to find?
```

这也是为什么我觉得 OpenViking 与单纯的“长期记忆插件”相比，更值得从 Context Engineering 角度理解。

##### Session 也进入了 Context Database

OpenViking 甚至把 Session 本身也做成分层内容：

```text
Session
├── L0: abstract
├── L1: key decisions / overview
└── L2: complete messages
```

而 Session 在 commit 时还能进一步向长期 Memory 提取内容。

于是：

```text
Raw Conversation
     ↓
Session Context
     ↓
Session Commit
     ↓
Memory Extraction
     ↓
Durable Memory
```

短期上下文和长期记忆之间终于不是：

```text
聊天结束
→ LLM 总结一下
→ append MEMORY.md
```

而是拥有比较明确的数据生命周期。

Hermes 对 OpenViking 的 Provider 也利用了这一点，目前提供：

```text
viking_search
viking_read
viking_browse
viking_remember
viking_add_resource
```

也就是说 Agent 既可以：

```text
search
```

也可以：

```text
browse → read
```

后者尤其重要。

因为 Search 的默认假设是：

> **Agent 已经知道自己要找什么。**

Browse 的默认假设则是：

> **Agent 可能还不知道这里到底有什么。**

这两种任务其实完全不同。

所以 OpenViking 代表的路线可以概括成：

> **Memory as Context Infrastructure。**

它没有把重点放在“如何让一个 Memory Retrieval 算法越来越聪明”，而是试图首先把 Agent 的所有长期 Context 变成：

```text
可组织
可定位
可浏览
可检索
可分层
可追踪
可按需读取
```

的资产。

这也是评论区那句：

> “长期 memory 最合适的还是快速的 fact check，越轻量、越透明反而越省事。”

背后真正有意思的工程思想。

不是：

```text
把所有历史都变成 Memory
```

而是：

```text
把所有历史整理成 Agent 知道如何寻找的 Context。
```

---

把 Hindsight、Honcho、OpenViking 放在一起，其实能看到三条非常不同的 Agent Memory 路线：

```text
Hindsight
│
└── Experience → Fact → Observation → Reflection
    “Agent 能从过去经历中得到什么？”

Honcho
│
└── Workspace → Peer → Session → Representation
    “Agent 应该如何持续理解一个人？”

OpenViking
│
└── Resource + Memory + Skill
    → Hierarchy
    → L0 / L1 / L2
    → Browse / Search / Read
    “Agent 应该如何组织和取得自己的 Context？”
```

所以我现在越来越觉得：

> **“Agent Memory”这个词其实太宽了。**

很多所谓 Memory 项目解决的根本不是同一个问题。

有人解决：

```text
Storage
```

有人解决：

```text
Retrieval
```

有人解决：

```text
User Modeling
```

有人解决：

```text
Experience Consolidation
```

还有人像 OpenViking 一样，最后干脆把问题重新定义成：

```text
Context Management
```

这也是为什么单纯问：

> “Mem0、Hindsight、Honcho、OpenViking 哪个最好？”

其实没有太大意义。

真正应该先问的是：

```text
我希望 Agent 记住什么？
      ↓
Fact / Experience / Person / Knowledge / Workflow？

这些东西应该存在哪里？
      ↓
Global / User / Project / Peer / Session？

什么时候需要它？
      ↓
Always-on / Auto Recall / Agent Pull？

召回后应该给多少？
      ↓
Fact / Summary / Overview / Full Detail？

旧信息和新信息冲突怎么办？
      ↓
Overwrite / Temporal Versioning / Consolidation / Evidence？

最后，
谁来决定这一切？
      ↓
Prompt？
Memory Engine？
Context Compiler？
还是 Agent 自己？
```

到了这里，Memory Engineering 和 Context Engineering 已经很难再被真正分开了。

### 还有人自己造 Memory：Smriti 和 Scope Recall

前面几个项目至少都已经形成了比较完整的产品、论文或者 Memory Platform。

评论区还有另一种更符合 Hermes 精神的玩法：

> **我为什么一定得选你们的 Memory Engine？Hermes 都已经暴露 `MemoryProvider` 了，我自己写一个不行吗？**

这也是评论区里我觉得最有意思的一条支线。

有人直接问：

> “mem0吗？”

回答是：

> “我用的 smriti，不过核心记忆逻辑都被我和我的 agent 一起改过，算是半手写的插件。”

另外也有人建议：

> “可以给 Hermes 配其他的记忆提供商，scope recall。”

这两者虽然都大量使用 SQLite，但解决的问题其实完全不同：

```text
Smriti
    ↓
Temporal Truth
“旧事实和新事实冲突怎么办？”

Scope Recall
    ↓
Scope Isolation
“不同 Chat / Project 的记忆怎么不串？”
```

---

#### Smriti：一个 SQLite 也能做 Temporal Memory

Smriti 的全称是：

> **Structured Memory with Reflective Indexing and Temporal Inference**

项目名 `smriti`（स्मृति）本身就是梵语里的“记忆”。

它最鲜明的设计哲学不是“我们有一个更牛的 Vector DB”，而是：

> **Agent Memory 应该足够小、Local-first、Auditable，以至于一个开发者真的能够看懂自己 Agent 到底记了什么。**

因此整个核心 Memory Store 就是：

```text
memory.db
```

一个 SQLite 文件。

官方强调：

```text
No Neo4j
No PostgreSQL
No Qdrant
No Redis
No Docker
No Cloud Account
```

基础依赖甚至主要只有：

```text
Python stdlib
+
numpy
```

所以它代表的不是“大型 Memory Platform”路线，而是：

```text
Hermes / Claude / Cursor
          ↓
       MCP/API
          ↓
       Smriti
          ↓
       SQLite
```

也就是：

> **Embedded Memory Engine。**

---

##### Smriti 真正解决的核心问题：Memory Update 是一个时间问题

它 README 最上面的例子非常能说明设计目标：

```text
2026-01-15
User lives in Hyderabad.

2026-06-01
User moved to Bengaluru.
```

普通 Flat Memory 很容易得到：

```text
User lives in Hyderabad.
User lives in Bengaluru.
```

接下来全部依赖 Retrieval 或 LLM 自己判断哪条更新。

另一种做法是直接 UPDATE：

```text
DELETE Hyderabad
KEEP Bengaluru
```

但这样又失去了历史。

Smriti 的答案叫：

> **Supersession，而不是 Mutation。**

最后保存成类似：

```text
Fact A:
User lives in Hyderabad.

valid_from = 2026-01-15
invalid_at = 2026-06-01
superseded_by = Fact B


Fact B:
User lives in Bengaluru.

valid_from = 2026-06-01
invalid_at = null
CURRENT
```

因此：

```text
“Where do I live?”
```

读取：

```text
CURRENT → Bengaluru
```

但：

```text
“Where did I live before June?”
```

仍然能读取：

```text
SUPERSEDED → Hyderabad
```

这就是所谓：

> **Bi-temporal / validity-aware memory**

在 Smriti 中最核心的工程体现。

它强调：

```text
Correction
≠
erase history

Correction
=
new event that changes validity
```

这个思想其实非常漂亮。

对于 Personal Agent 来说，大量 Memory 天生就是 temporal 的：

```text
住在哪里
在哪家公司
现在用什么模型
正在做哪个项目
当前目标是什么
喜欢什么工具
课程进度
项目状态
```

这些都不是 eternal facts。

如果 Memory Schema 只有：

```text
content: string
```

其实从一开始就表达能力不足。

---

##### Raw Episode 和 Extracted Fact 都要留下

Smriti 的第二个重要设计是：

> **Episode 和 Fact 都是一等公民。**

它的 Write Path 大概是：

```text
Session
   │
   ├─────────────→ Episodic Log
   │               append-only
   │               FTS-indexed
   │               embedded
   │
   └→ Fact Extraction
          ↓
      Atomic Facts
          ↓
      Conflict Check
          ↓
  ┌──────────────────┐
  │ exact collision  │
  │ semantic conflict│
  └──────────────────┘
          ↓
 ADD / SUPERSEDE / SKIP
          ↓
 Consolidated Fact Store
```

官方把两个层次分别叫：

```text
anubhava
=
raw experience / episode

samskara
=
experience 留下来的 consolidated impression
```

为什么不能只存 Fact？

因为：

```text
Conversation
     ↓
LLM Extraction
     ↓
Fact
```

本身就是有损压缩。

如果 Extractor 当时漏掉了一条细节：

```text
原始聊天已经删了
↓
永远找不回来
```

所以 Smriti 保留 Raw Episode，当事实提取失败时它仍然可以充当 Recall Safety Net。

反过来，如果只保存 Episode：

```text
10000 turns raw conversation
```

对于：

> “我现在住在哪里？”

这种 current-state query 又很不友好。

于是它采用：

```text
Facts
    ↓
Precision

Episodes
    ↓
Recall Safety Net
```

两者融合。

这是一个非常值得抄的设计。

---

##### Read Path：不是只有 Vector Search，而是“四条河”

Smriti 当前实现四种 retrieval channel：

```text
Query
 │
 ├→ Lexical
 │   BM25 / SQLite FTS5
 │
 ├→ Semantic
 │   Embedding similarity
 │
 ├→ Entity
 │   Entity-hop relation
 │
 └→ Temporal
     Time proximity / validity
          ↓
        RRF
          ↓
Validity Annotation
          ↓
Budget-capped Context
```

官方给它们分别用了：

```text
shabda      → lexical
artha       → semantic
sambandha   → relation
kala        → temporal
```

然后通过 Reciprocal Rank Fusion：

```text
sangama
```

合并。

这其实体现出一个越来越明显的 Memory Retrieval 趋势：

> **Embedding Similarity 已经不够了。**

因为：

```text
“项目编号 PRD-1437 是什么？”
```

Lexical 往往比 Semantic 好。

而：

```text
“Rachel 和哪个团队关系最密切？”
```

需要 Entity。

再比如：

```text
“六月之前我住在哪里？”
```

需要 Temporal。

所以一个成熟 Memory Retriever 越来越像：

```text
Hybrid Search Engine
```

而不是：

```text
Vector DB wrapper
```

---

##### Retrieval Profile：不同问题根本不应该用同一种 Recall

Smriti 进一步提供：

```text
facts
relations
timeline
deep
auto
```

几种 profile。

例如：

```text
facts
=
lexical
+ semantic
+ 1-hop entity
+ CURRENT-first

适合：
“我现在住哪里？”
```

而：

```text
timeline
=
temporal boost
+ chronological evidence
+ as-of semantics

适合：
“三月份发生了什么？”
```

再比如：

```text
deep
=
all channels
+ observation digest
+ expanded keys

适合：
“总结我过去半年参加过的所有会议。”
```

这其实又触及了 Context Engineering：

> **Retrieve Strategy 本身应该根据 Query 类型动态变化。**

也就是说不应该永远：

```python
vector.search(query, top_k=10)
```

而应该：

```text
Query Understanding
      ↓
Retrieval Policy
      ↓
Candidate Generation
      ↓
Fusion
      ↓
Packing
```

Smriti 把这种“如何看同一个 Memory Store”的方式叫作：

> `drishti` —— way of seeing。

---

##### Lite / Full：写 Memory 不一定每次都要调用 LLM

Smriti 还特别提供两种模式：

```text
lite / laghu
```

完全不在 write path 调 LLM：

```text
Episode Ingest
+
Lexical
+
Semantic
+
Entity
+
Temporal Retrieval
```

因此可以做到 offline。

而：

```text
full / purna
```

才增加：

```text
Fact Extraction
+
Consolidation
+
Supersession
```

正常情况下每个 Session 做一次 Extraction，只有语义冲突时才增加小规模 arbitration。

这实际上是在明确区分：

```text
Memory Storage
≠
Memory Understanding
```

便宜场景可以：

```text
先全部可靠存下来
```

真正需要时再：

```text
花 LLM Cost 做 semantic consolidation。
```

---

##### 它不是“Smriti 论文 SOTA”，至少现在不能这么写

这里反而要特别克制一下。

Smriti README 已经提供：

* LongMemEval harness；
* LoCoMo harness；
* fixed-judge A/B；
* per-question error analysis；

但项目作者明确写了：

> **目前还没有正式完成整个 full benchmark。**

它提供的是可重复评测框架，而不是一个应该直接相信的“我们 SOTA 95%”数字。

目前 README 比较明确公开的是内部 A/B：

> per-type retrieval router 在其测试中让 multi-session aggregation 提升约 10 points，且没有造成 knowledge-update regression。

但这是 **within-system A/B**，不是与 Mem0/Hindsight 的统一独立 benchmark，所以不能写：

> “Smriti 比 Mem0 强 10%。”

反而我挺喜欢它 README 的态度：

> benchmark harness 给你，你自己在自己的 Model、Judge、Conversation 上跑。

因为 Memory Benchmark 特别容易受到：

```text
Extractor Model
Answer Model
Judge Model
Embedding Model
Top-K
Dataset Split
Prompt
```

影响。

所以不同项目官网上：

```text
91%
94%
92%
```

往往并不能直接横向比较。

---

##### 它和 Hermes 的关系也要写准确

评论区那个人确实说自己把 Smriti 接到了 Hermes，而且核心逻辑还自己改过。

但是 **Smriti upstream 目前主要正式提供的是 MCP Server**：

```text
remember
recall
search
facts_about
add_fact
stats
```

任何 MCP-compatible Agent 都可以接。

官方 README 当前仍把：

```text
smriti-hermes
```

专用 adapter 列在 roadmap 中，而不是说已经属于 Hermes bundled MemoryProvider。

所以评论区那套更准确地说应该是：

> **Smriti Core + 用户自己写的 Hermes glue/plugin。**

这反而更符合这一节主题：

> “别人家的 Memory Engine 不适合，我自己接。”

---

#### Scope Recall：Memory 最重要的也许不是 Recall，而是 Scope

Scope Recall 和 Smriti 又完全是另一种味道。

它不是一篇学术论文，而是一个明确面向 **Hermes Agent** 的社区第三方 Memory Provider：

> `scope-recall-hermes`

项目作者还专门向 Hermes 官方仓库提交过 Show & Tell / RFC。

它解决的问题一开始就非常具体：

> **同一个 Hermes 在多个聊天窗口、Telegram 群、项目和 Session 中工作，哪些 Memory 应该共享，哪些必须严格隔离？**

这其实就是评论区一直抱怨的：

> **Memory Pollution。**

---

##### 一个最简单的污染例子

假设项目 A 中用户说：

```text
今天测试环境不稳定，
先不要重启数据库。
```

这句话很重要。

但是重要范围只是：

```text
Project A
+
Current Session
```

如果直接写入 Global Memory：

```text
MEMORY:
Do not restart database.
```

过两周项目 B：

```text
User:
数据库挂了，帮我恢复。

Agent recalls:
“不要重启数据库。”
```

问题就来了。

Memory System 不是“忘了”。

恰恰是：

> **记得太好了，但不知道这段记忆到底属于哪里。**

所以 Scope Recall 的核心命题不是：

```text
Recall more.
```

而是：

```text
Recall from the correct scope.
```

---

##### Durable Memory 和 Local Scratch 必须分开

Scope Recall 当前把信息粗略分成两大类。

一类是 durable：

```text
user
memory
project
ops
```

这些可以跨窗口共享。

例如：

```text
user:
用户习惯先看 plan 再执行

project:
Hermes blog 使用 Hugo

ops:
生产数据库禁止自动 DROP

memory:
某项长期决定
```

另一类是：

```text
general / raw turn captures
```

默认只属于当前：

```text
chat
thread
session
```

也就是说：

```text
          Same User + Agent
                  │
       ┌──────────┴──────────┐
       │                     │
Durable Memory          Local Scratch
       │                     │
user                  chat A only
project               thread B only
ops                   session C only
memory
       │
cross-chat recall      never leak
```

所以它代表一个非常重要的 Memory Principle：

> **Memory lifetime 和 Memory visibility 必须是两个独立维度。**

不是只有：

```text
Remember / Forget
```

两个状态。

更合理的是：

```text
What?
Who?
Where?
How long?
Under which project?
Under which session?
Can another agent see it?
```

---

##### 三层存储：Journal ≠ Memory ≠ Index

Scope Recall 我觉得最值得学的反而是它把三类东西分开了：

```text
1. Journal / Provenance

2. SQLite Truth

3. Vector Companion
```

架构大概是：

```text
Raw Turn
   ↓
Journal / Provenance
   │
   │ background digest
   ↓
Durable Memory Candidate
   ↓
SQLite Truth
   │
   ├→ FTS / BM25
   │
   ├→ Entity indexes
   │
   └→ Vector Companion
          LanceDB
          or sqlite-bruteforce
```

这里三个层次的职责完全不同。

---

##### Journal：原始经历只是证据，不应该天然进入 Recall

`journal_entries` 保存：

```text
eligible raw conversation turns
evidence links
digest provenance
```

但项目特意强调：

> **普通 recall 不会直接把 raw journal rows 注入 Prompt。**

这其实是在做：

```text
Experience
≠
Memory
```

和 Smriti 的思想很像。

Raw Turn 只是：

```text
candidate evidence
```

经过 digest / extraction / governance 后，部分内容才能升格成：

```text
durable memory
```

这比：

```text
每晚把今天所有聊天总结一下
→ append MEMORY.md
```

严格很多。

---

##### SQLite 是 Truth，Vector DB 只是“可以随时烧掉重建的索引”

Scope Recall 有一句我觉得特别值得写进 Agent Infra 笔记：

> **SQLite truth, vector companion.**

SQLite 保存：

```text
durable memory rows
scope metadata
timestamps
FTS
provenance
governance metadata
```

它是：

> **Authoritative Source of Truth。**

而 LanceDB 只保存可以从 SQLite 重新构建出来的：

```text
id
scope_id
content
summary
updated_at
vector
...
```

因此：

```text
SQLite
=
Data

LanceDB
=
Index
```

这和很多：

```text
Vector DB = Memory DB
```

的 Demo 差别很大。

如果 LanceDB 损坏：

```text
delete index
↓
rebuild from SQLite
```

不会丢 Memory。

这其实就是传统数据库很成熟的一个思想：

> **不要把 Secondary Index 当 Source of Truth。**

放到 Agent Memory 一样成立。

---

##### 为什么还需要 LanceDB？

因为 SQLite FTS 很适合：

```text
exact word
identifier
keyword
BM25
```

例如：

```text
"PRD-134"
"Claude Code"
"scope-recall"
```

但：

```text
“之前我们对长期上下文隔离有什么决定？”
```

可能与原 Memory 一个词都对不上。

这时候 Semantic Embedding 有优势。

所以：

```text
SQLite / FTS / BM25
        ↓
Lexical Candidates

LanceDB
        ↓
Semantic Candidates

Entity Index
        ↓
Entity Candidates

        ↓
RRF / Scoring
        ↓
Final Memory
```

Scope Recall 默认就是 hybrid retrieval，并提供 Reciprocal Rank Fusion。

其 current-turn path 大概是：

```text
Hermes User Query
        ↓
prefetch(query)
        ↓
┌────────────────────────┐
│ USER.md / MEMORY.md     │
│ SQLite FTS/BM25         │
│ Entity Index            │
│ Vector Companion        │
└────────────────────────┘
        ↓
Hybrid Ranking
        ↓
Scope Filter
        ↓
Freshness / Governance
        ↓
Bounded Prompt Block
        ↓
LLM
```

这里还有一个非常重要的点：

> **它做的是 current-turn recall。**

也就是说下一轮 Query 是什么，就根据**这一轮 Query**重新 retrieve。

不是：

```text
上一轮查出了十条 Memory
↓
下一轮继续惯性注入
```

避免 stale recall 越滚越大。

---

##### 双 Memory Authority：它并没有粗暴替掉 Hermes 的 MEMORY.md

Scope Recall 甚至没有选择：

```text
SQLite wins
MEMORY.md delete
```

而是明确做成 Dual-memory architecture：

```text
Hermes curated memory
│
├── USER.md
└── MEMORY.md

        +

Scope Recall provider memory
│
├── journal
├── SQLite truth
└── vector companion
```

职责分别是：

```text
USER.md / MEMORY.md
=
少量、人工可读、
高度 curated 的核心事实

Scope Recall
=
大量、可检索、
带 scope 和 provenance 的长期 Memory
```

这正好回应评论区另一个很好的思想：

> 不应该把几千几万条数据点全部塞进 Hermes 原生 Memory；原生文本更适合保存高价值核心信息和索引。

---

##### Gateway 场景为什么 Scope 特别重要？

假设 Hermes 接入飞书：

```text
Hermes
├── 私聊：我
├── Group A：项目 A
├── Group B：项目 B
└── Group C：朋友聊天
```

如果所有聊天都共用：

```text
Global MEMORY.md
```

问题会非常严重。

甚至不只是 hallucination。

还有：

> **Cross-user / Cross-channel information leakage。**

Scope Recall 因此甚至规定：

当 gateway context 有明确：

```text
user_id
```

时，全局 `USER.md / MEMORY.md` 的 recall 默认需要 opt-in / allowlist，避免全局 Profile 文件里的内容被错误泄漏给另一个 Gateway 用户。

这已经不只是 Memory Quality 问题。

而是：

```text
Memory Isolation
=
Security Boundary
```

所以项目自己的 Security Policy 也把：

> unintended cross-scope memory recall or deletion

直接列为安全问题。

这点对于：

```text
Personal Agent
→ Multi-user Agent
```

是非常关键的一步。

---

##### Memory Governance：不是所有东西都应该自动晋升成“真相”

Scope Recall 现在还加入了一套相对保守的治理逻辑：

```text
exact dedupe
near-duplicate merge
filtering
metadata
decay review
candidate promotion
```

它尤其强调：

```text
raw evidence
↓
candidate
↓
review / promotion
↓
durable knowledge
```

而不是：

```text
LLM 说了一句
↓
从此成为永久事实
```

包括 workflow / experience 也不是发现一次：

```text
“这样部署成功了”
```

就直接升级成：

```text
以后永远这样部署。
```

高风险 Playbook 默认仍需要 review。

这里其实又回到了一个很根本的问题：

> **Long-term Memory 的危险不只是 Forgetting，也包括错误信息被永久固化。**

一次 hallucination 如果只活一个 Session：

```text
影响一小时。
```

一次 hallucination 被 Memory Engine 写成 durable fact：

```text
可能影响半年。
```

所以 Memory Agent 越“会记”，Write Governance 越重要。

---

##### Scope Recall 其实是典型的“Engineering-first Memory”

与 Hindsight 相比：

```text
Hindsight
更关注：
experience → observation → reflection
```

与 Honcho 相比：

```text
Honcho
更关注：
persistent Peer Representation
```

与 Smriti 相比：

```text
Smriti
更关注：
Temporal Fact Evolution
```

Scope Recall 最关注的是：

```text
Isolation
Source of Truth
Provenance
Determinism
Repairability
Governance
```

所以它非常像传统 Infra 工程师会写出来的 Memory：

```text
不要 magic
不要黑盒
坏了能 repair
数据能 inspect
index 能 rebuild
scope 必须明确
delete 必须 fail closed
```

这也是为什么它会坚持：

```text
SQLite Truth
+
Rebuildable Vector Index
```

而不是把所有东西直接压进某个 opaque hosted Memory Service。

---

##### 但它也不是成熟论文 SOTA

这里同样需要把定位说准确。

Scope Recall 是：

* 社区第三方 Hermes Provider；
* 有公开 RFC；
* 有 tests、golden benchmark、retrieval regression benchmark；
* 有 operator tooling；
* 当前 PyPI package metadata 标为 Beta；
* MIT License。

但它并不是：

> 一篇已经在统一 LongMemEval / LoCoMo protocol 下证明 SOTA 的论文。

因此更适合把它当作：

> **Hermes-specific Memory Engineering Reference Implementation**

来学习，而不是和 Hindsight、Mem0 的论文 benchmark 硬排一个 leaderboard。

它最值得抄的不是一个 Accuracy 数字，而是：

```text
Scope model
Truth/index separation
Journal provenance
Current-turn recall
Hybrid retrieval
Fail-closed safety
Memory governance
```

这些设计。

---

最后把三个放在一起，就能很清楚地看出为什么“Agent Memory”根本不是一个单一问题：

| 系统               | 最核心的问题                           | 主要抽象                                      |
| ---------------- | -------------------------------- | ----------------------------------------- |
| **Mem0**         | 什么值得记、怎么管理、怎么便宜地取回来              | Extracted Fact + Memory Lifecycle         |
| **Smriti**       | 新旧事实如何同时保持时间上的正确性                | Episode + Bi-temporal Fact + Supersession |
| **Scope Recall** | 哪条记忆应该在哪个 Agent/Project/Chat 中可见 | Scope + SQLite Truth + Provenance         |

可以进一步写成：

```text
Mem0
    ↓
Memory Lifecycle
“这件事值得记吗？”

Smriti
    ↓
Memory Evolution
“这件事在什么时候是真的？”

Scope Recall
    ↓
Memory Isolation
“这件事应该被谁记住？”
```

这三个问题其实缺一不可。

一个真正长期运行的 Personal Agent 最后可能需要同时回答：

```text
1. Should I remember this?
            ↓
Importance / extraction

2. What exactly should I remember?
            ↓
Fact / episode / workflow

3. Is it still true?
            ↓
Temporal evolution

4. Who does it belong to?
            ↓
User / agent / project / peer

5. Where is it valid?
            ↓
Global / workspace / chat / session

6. How do I find it?
            ↓
Lexical / semantic / entity / temporal

7. How much should enter Context?
            ↓
Ranking + budget

8. What if it was wrong?
            ↓
Provenance + supersession + governance

9. What if the index breaks?
            ↓
Truth store + rebuild

10. When should I forget it?
            ↓
TTL / decay / archive / delete
```

于是走到这里以后，所谓：

> **Memory Provider**

实际上已经不太像“给 LLM 装一个记忆插件”了。

它越来越像一个完整的：

> **Agent State & Context Infrastructure。**

### 最激烈的争论：长期 Memory 到底是不是伪命题？

这是整个评论区技术思想冲突最强的一段。

一派说：

> 外置 memory provider 非常好用，我开新窗口提到关键词就能自动 recall，老记忆随时召回。

另一派直接反驳：

> 你根本没有给 LLM 增加 memory，你只是在往 context window 里面塞更多东西，破坏 attention。

双方吵了非常久。

反 Memory 派的核心架构是每个项目一个独立目录，CLAUDE.md、notes.md、docs 各司其职：

```text
Project A/
  CLAUDE.md
  notes.md
  docs/

Project B/
  CLAUDE.md
  notes.md
  docs/
```
需要的时候 Agent 自己读文件，不要搞全局向量记忆自动检索自动注入，因为过时记忆、当前状态、用户习惯、历史工作流和当前代码混在一起，Attention 必然混乱。

```text
global vector memory
→ 自动检索
→ 自动注入
```

因为容易发生：

```text
过时记忆
+ 当前状态
+ 用户习惯
+ 历史工作流
+ 当前代码
──────────────
Attention 混乱
```

这个观点在另一条评论也出现了：

> Context 长 ≠ Attention 长；Hermes 把环境状态、个人喜好、过去工作流都放在开头，就会挤占编码任务注意力。


这个争议其实非常前沿，本质不是“RAG 好不好”，而是 Agent Memory 应该采用 Push（主动注入）还是 Pull（Agent-controlled retrieval）。也可以写成 `Push Memory vs Pull Memory`

评论区很多高手明显越来越倾向少量 always-on memory，加上结构化索引，按需 retrieval，严格 scope。与其无限扩大 prompt，不如让 Agent 知道该去哪里取，而不是把所有东西都放在眼前。：

```text
少量 always-on memory
+
结构化索引
+
按需 retrieval
+
严格 scope
```


## 四、另一个大流派：Hermes 不干活，只当“总管”
> “Hermes适合做编排，不适合做执行。”

这个观点出现了很多次。有人甚至直接：

```text
Hermes
  ↓
管理 Claude
  ↓
Claude 干活
```

评论区还有人问：

> 为什么没人用 Hermes 管理其他 CLI？

下面回复：

* Hermes 管 OpenCode
* 写 ACP 协议
* MCP / bridge
* Hermes 当“大内总管”

甚至有人让不同 Agent 共用一个私有 Git 仓库：

```text
Codex 干一半
↓
commit:
进度
结果
剩余问题
↓
Claude Code 接力
```

这已经不是“哪个 Agent 更强”的问题，而是：

> **heterogeneous agent orchestration**

也就是不同 Agent 有不同 specialty。

## 五、评论区最完整的一套方案：“AI 公司三层架构”

有人提出 Hermes 不该是“一个 Agent 包办所有事情”，而应该分三层。

![Hermes 三层 AI 公司架构：总管、专家 Agent 与 Worker](/blog/2026/hermes-three-layer-ai-company-architecture.png)

> 图：Hermes 作为“AI 公司”时的三层分工，以及专家 Agent 向 Worker 派发任务的流程。

### 第一层：1～2 个总管

例如：

```text
Daily Manager
Technical Manager
```

负责：

* 和用户交流
* 理解需求
* 拆任务
* 找专家
* 汇总结果

### 第二层：专家 Agent

例如：

```text
Database Expert
Research Expert
Browser Expert
Finance Expert
Coding Expert
```

每一个都有自己的：

```text
SOUL
Tools
Skills
Knowledge
Memory
```

而且初始 context 比“大总管”轻很多。

### 第三层：Worker

重复任务直接专用 Worker。

高自由度任务则动态 spawn 子 Agent：

```text
Expert
↓
生成 prompt
↓
附带必要 Skill
↓
spawn Worker
```

提出者认为 Hermes 不是老头乐，而更像一个专家自由选的公司：
- 第一层是 1～2 个总管，负责和用户交流、拆任务、找专家、汇总结果；
- 第二层是各类专家 Agent，比如 Database Expert、Browser Expert、Coding Expert，每个专家有自己的 SOUL、Tools、Skills、Knowledge 和 Memory，而且初始 context 比大总管轻很多；
- 第三层是 Worker，重复任务用专用 Worker，高自由度任务由专家动态 spawn 子 Agent，生成 prompt、附带必要 Skill 后派发出去。
原评论甚至用了很形象的话（**multi-agent context isolation**）：
> Hermes 不是“老头乐”，更像一个专家自由选的公司；如果不招人，老板抓着光杆总经理，让他又当秘书又当底层员工还照顾老板生活，真人也受不了。

这个架构的本质是用**多 Agent 的上下文隔离**来解决单 Agent 记忆污染的问题。每个专家只在自己的领域内积累记忆，不会把项目 A 的临时状态带到项目 B。他的核心逻辑是：Hermes 本身是通用 personal agent，如果只用一个 Agent 包揽所有事，上下文会被各种琐碎记忆和技能撑爆，所以需要分层隔离。

但另一派人马上反驳：对 coding 任务而言，多 Agent 的协调成本太高，尤其是子 Agent 之间的信息同步和错误传递，远不如一个强约束的单 Agent 用几个文件管理记忆来得可靠。这其实就是之前“长期 Memory 是不是伪命题”争论的延伸。

反 Memory 派坚持认为，任何外挂记忆库或者多 Agent 架构都是在人为干预 LLM 的注意力机制，做得越多错得越多。他们主张用最笨的方法：每个 topic 开一个独立项目目录，CLAUDE.md、notes.md 各管各的，需要时让 Agent 自己读文件。而支持外部记忆和多 Agent 的人则反驳：你不可能把公司所有项目的上下文都塞进一个 prompt，分层和隔离是必然方向，只是当前工具还不够成熟。

迁移到纯粹 coding 场景，比如 Claude Code 或 Codex，它们本身就有很强的单 Agent 工作流（渐进式计划、子代理等），未必需要自己再搭一套多 Agent 架构。所以这个争议的本质还是：**任务类型决定架构**，而不是 multi-agent 一定好或一定坏。

这场争论最终没有分出胜负，但评论区大多数人的实践倾向是：**少量 always-on memory + 结构化索引 + 按需 retrieval + 严格 scope**，而不是无限扩大 prompt 或盲目堆叠 Agent。对于个人日常助手，Hermes 的多 Agent 分层可能有效；对于高强度 coding，Claude Code 式的单 Agent 深度工作流仍然更稳。这或许就是“养 Agent”和“用工具”之间最实际的分界线。

## 六、Browser Agent 派：把 Hermes 变成真正办公 RPA

评论区里有人描述了自己的日常工作：

> 收贷款材料 → 浏览器填表 → 上传 → 点按钮 → 提交审核。

这种重复性的网页操作，正是机器人流程自动化（RPA，Robotic Process Automation）的典型场景——用软件模拟人工在电脑上的点击、输入、复制粘贴等操作，把繁琐的流程自动化。

于是有人给出了一套完整的 Hermes 实现方案，目标就是让 Hermes 扮演这个“数字员工”。

这套方案的架构可以概括为：

```text
Hermes
   ↓
Fill Form Skill
   ↓
Browser Control Skill
   ↓
Chrome DevTools MCP
   ↓
独立 Chrome Profile
```

Hermes 首先触发一个“填表技能”（Fill Form Skill），该 Skill 再调用“浏览器控制技能”（Browser Control Skill），最后通过 Chrome DevTools MCP 连接到一个专门供 Agent 使用的 Chrome。

这里的关键并不只是用 Playwright、Puppeteer 或 CDP 去驱动浏览器，而是：

> **Agent 的 Browser Runtime 不能和人的日常浏览环境混成一团。**

评论区的方案因此专门建立一个：

```text
Agent Chrome Profile
≠
User Chrome Profile
```

让 Agent 和用户拥有相互隔离的：

```text
Cookies
Session
Cache
Tabs
Browser State
```

否则一个最朴素的 Browser Agent 很容易出现：

```text
Agent:
“我要打开客户管理系统。”

↓

抢走当前 Tab

↓

用户：
“我刚刚看的网页呢？”
```

更严重的情况是 Agent 完成任务之后执行：

```text
taskkill chrome.exe
```

于是连用户自己正在用的 Chrome 也一起消失了。

所以评论区那套方案还会在启动 Agent Browser 时先保存进程号 PID：

```text
启动浏览器
→ 记录 PID
→ MCP attach
→ snapshot
→ 操作
→ verify
→ 完成
→ 精确 kill PID
```

这样结束任务时只销毁 Agent 对应的 Browser Process。

这看起来是个小细节，其实已经体现出 Browser Agent 一个非常重要的工程问题：

> **Browser automation 不只有“怎么点按钮”，还必须管理 Browser Lifecycle。**

包括：

```text
谁启动？
启动哪个 Profile？
登录状态从哪里来？
谁拥有这个 Tab？
操作失败如何恢复？
什么时候需要用户接管？
任务结束以后谁清理资源？
```

这也是为什么 Browser Agent 比一个简单的：

```python
page.click(...)
page.fill(...)
```

复杂得多。

---

### Human-in-the-loop：自动填写不等于自动提交

评论区那套方案还有一个很好的设计：

```text
Agent 自动填写
      ↓
Agent 验证
      ↓
STOP
      ↓
用户审核
      ↓
人工提交
```

而不是：

```text
资料
↓
Agent
↓
一路点击
↓
Submit
```

例如对于：

* 银行资料；
* 客户申请；
* 合同；
* 财务系统；
* 删除操作；
* 发布内容；

最后一步往往意味着：

```text
Reversible
    ↓
Irreversible
```

因此最合理的 Agent Workflow 往往不是：

```text
Fully Autonomous
```

而是：

```text
Observe
   ↓
Plan
   ↓
Operate
   ↓
Verify
   ↓
Human Approval
   ↓
Commit
```

这里的 `Commit` 和数据库事务其实很像。

前面：

```text
填写表格
选择选项
上传附件
```

都还能修改。

但点击：

```text
Submit
Pay
Delete
Publish
Confirm
```

以后，操作的风险等级就发生了变化。

因此可以把这种模式称作：

> **Human-in-the-loop Browser Automation**

而不是简单的“让 AI 自动点网页”。

到这里，评论区实际上已经自行摸索出一套相当完整的：

> **Agentic Browser Automation SOP**

从启动、观察、操作、验证、人工审批到退出，都有明确的状态和边界。

---

#### Ego Lite：如果“独立 Profile + MCP + PID”本来就是个工程问题，能不能直接把它做到浏览器里？

我后来才发现，2026 年已经有项目直接瞄准了这个问题：

> **CitroLabs / ego-lite**

它的定位不是普通 Browser Automation Library，而是：

> **Agent Browser——一个从浏览器这一层开始，就假设“人类和 Agent 要同时使用它”的浏览器。**

这区别很重要。

传统方案通常是：

```text
Chrome
   ↑
Playwright / Puppeteer / CDP
   ↑
MCP / CLI
   ↑
Agent
```

浏览器本身完全不知道什么叫 Agent。

于是我们只能不断在外围打补丁：

```text
创建临时 Profile
复制 Cookie
启动独立 Chromium
保存 PID
连接 CDP
管理 Tab
任务结束杀进程
```

Ego Lite 的思路则是：

```text
Agent-aware Browser
        ↑
   ego-browser
        ↑
       Skill
        ↑
Hermes / Codex / Claude Code / Cursor
```

`ego-browser` 是 Agent 和浏览器之间的连接层。

官方明确列出了：

```text
Claude Code
Codex
Cursor
Gemini CLI
Hermes Agent
OpenClaw
OpenCode
Custom Agent
```

只要 Agent 能执行 shell command，就可以通过 `ego-browser` 控制浏览器。

这意味着对于 Hermes 来说，理论上的结构可以直接变成：

```text
Hermes
   ↓
Fill Form Skill
   ↓
ego-browser Skill
   ↓
ego lite
   ↓
Agent Space
```

而不一定需要再自己维护：

```text
Chrome DevTools MCP
+
独立 Chrome Profile
+
PID Lifecycle
```

---

#### Space：它把“Agent 独立浏览器”变成浏览器原生抽象

Ego Lite 最值得注意的概念叫：

> **Space**

但 Space 并不是：

```text
开一个新的 Chrome
```

也不是：

```text
复制一份 Chrome Profile
```

更不是：

```text
启动一个远程 Headless Browser
```

官方定义里，一个 Space 是：

> 同一个 Ego Lite 浏览器进程内部，为某个 Agent Task 分配的独立 BrowserContext。

也就是说：

```text
ego lite Browser Process
│
├── Human Workspace
│
├── Space: fill-loan-form
│   ├── Tab A
│   └── Tab B
│
├── Space: research-company
│   ├── Tab C
│   └── Tab D
│
└── Space: update-crm
    └── Tab E
```

每个 Space 有自己隔离的：

```text
Tabs
Cookies
Storage
Browser Context
```

但是共享同一个浏览器基础设施。

这和评论区方案最大的区别就出现了。

### 评论区的做法

```text
User Chrome Process
│
└── User Profile

Agent Chrome Process
│
└── Agent Profile
```

需要额外处理：

```text
Process lifecycle
Profile path
PID
Login
CDP attach
```

### Ego Lite

```text
One Browser Process
│
├── Human
├── Agent Space A
├── Agent Space B
└── Agent Space C
```

Browser 本身负责：

```text
Isolation
Ownership
Lifecycle
Parallelism
```

也就是说：

> **它把原来 Harness 需要自己解决的问题，下沉成了 Browser Runtime Primitive。**

---

#### 最微妙的问题：隔离和“复用登录态”不是矛盾的吗？

这恰恰是 Ego Lite 最想解决的痛点。

传统 Browser Agent 最烦人的事情之一就是：

```text
Agent 打开 Gmail
↓
“请登录”
↓
用户登录
↓
下一次新 Browser
↓
“请重新登录”
```

尤其碰到：

```text
SSO
2FA
CAPTCHA
QR Code
企业内部系统
```

Browser Automation 很容易直接卡死。

Ego Lite 第一次启动时可以迁移 Chrome 数据，包括：

* Cookie；
* 登录 Session；
* Bookmark；
* Password；
* Extension；
* Profile。

Agent 创建的 Space 默认能够继承可用的登录环境，因此它可以直接进入已经认证的网站，同时任务自己的 Space 又保持独立。

所以它真正想实现的是：

```text
Shared Authentication Context
          +
Isolated Task Context
```

而不是两个极端：

```text
完全共享浏览器
→ Agent 和人互相抢 Tab

完全隔离浏览器
→ Agent 每次重新登录
```

这其实是 Browser Agent 一个非常核心、却很少被单独拿出来讨论的设计问题：

> **Identity Sharing 和 Execution Isolation 应该是两个不同维度。**

可以共享：

```text
“我是谁、我登录过哪些系统”
```

但不应该共享：

```text
“我现在正在操作哪个页面”
```

---

#### 从 Process Isolation 变成 Context Isolation

因此可以把两种设计抽象成：

```text
传统方案：

Isolation Boundary
=
Process / Profile


Ego Lite：

Isolation Boundary
=
BrowserContext / Space
```

这是一个很有意思的变化。

评论区那套：

```text
独立 Profile + PID
```

不是错。

实际上它是一种非常清晰、很好理解的隔离方案。

但缺点是：

```text
一个 Agent Task
≈
一套 Browser Process / Profile 管理问题
```

并行十个 Browser Agent 时，资源和生命周期管理就越来越麻烦。

Ego Lite 官方给出的六路空白页并发测试里，独立 browser instance + profile copy 比 Space 增加了明显更多的内存、进程和启动时间；不过官方也明确注明这只是为了展示两种 resource model，并不是一个可以泛化到真实网站的精确 benchmark。

所以更值得记的不是某个性能数字，而是：

> **如果 Browser Agent 最终会大规模并发，那么 BrowserContext 可能比 Browser Process 更合适成为 Task Isolation Primitive。**

---

#### 更像 Coding Agent 的 Browser API：不是每点一下就来回一次

Ego Lite 还有一个我觉得特别符合现在 Coding Agent 思路的地方：

> **Code-based，而不是 one-tool-call-at-a-time。**

传统 MCP / CLI 模式很容易变成：

```text
LLM
↓
snapshot

LLM
↓
click

LLM
↓
snapshot

LLM
↓
fill

LLM
↓
snapshot

LLM
↓
click
```

整个任务实际上变成：

```text
Think
→ Tool
→ Observe
→ Think
→ Tool
→ Observe
→ Think
→ Tool
...
```

一次普通填表可能产生大量：

```text
LLM round-trip
Tool Call
Tool Result
Tokens
```

Ego Lite 则给 Agent 暴露一组 JavaScript helper：

```text
snapshotText()
click()
fillInput()
openOrReuseTab()
waitForLoad()
uploadFile()
captureScreenshot()
js()
cdp()
...
```

Agent 可以一次生成：

```javascript
const task = await useOrCreateTaskSpace("fill customer form");

await openOrReuseTab(url, { wait: true });

const page = await snapshotText();

await fillInput("@name", customer.name);
await fillInput("@phone", customer.phone);
await fillInput("@company", customer.company);

await click("@next");

cliLog(await snapshotText());
```

然后一次交给内嵌的 Node.js Runtime 执行。

所以执行模型变成：

```text
LLM
  ↓
Write Browser Program
  ↓
Browser Runtime
  ├── action
  ├── action
  ├── action
  └── observation
  ↓
LLM
```

而不是：

```text
LLM
↕
Browser
↕
LLM
↕
Browser
↕
LLM
```

这件事情看起来只是：

> “少调几次 Tool。”

但它其实涉及 Agent Harness 一个非常大的问题：

> **Tool Granularity 应该多细？**

---

#### Tool Granularity：Agent 应该调用动作，还是编写动作？

假设有一个任务：

```text
登录 CRM
→ 搜索客户
→ 打开详情
→ 修改电话号码
→ 保存
```

一种 Harness 提供：

```text
click()
type()
click()
click()
```

Agent 是：

> action planner。

另一种 Harness 提供一个可以执行代码的 Browser Runtime：

```text
Agent
↓
写一个小程序
↓
Runtime 执行
```

Agent 就变成：

> program synthesizer。

对于 Claude Code、Codex、Hermes 这种本来就擅长写代码的 Agent，后者其实非常自然。

Ego Lite 官方将这一点称为：

> **Code base, not CLI base**

并声称自己的内部测试能因此减少复杂 Browser Workflow 的 Tool Call 和 Token，并提高执行速度；这些数字目前是项目方自己的 benchmark，而不是独立第三方 benchmark，因此更适合作为设计动机而不是绝对性能结论。

这个思想和 Coding Agent 中：

```text
让 Agent 自己写 Python
```

有点类似。

比如分析数据时，我们不会给 Agent：

```text
add_number
divide_number
calculate_mean
calculate_variance
```

四十个 Tool。

我们直接给：

```text
Python
```

然后让它组合 Primitive。

Ego Lite 实际上是在问：

> **Browser Automation 为什么不能也这样？**

---

#### Snapshot：Agent 看到的不是完整 HTML

Browser Agent 的另一个大问题是：

> **网页到底应该以什么形式进入 LLM Context？**

最暴力的方法：

```text
document.documentElement.outerHTML
```

问题显而易见：

```text
HTML 100k tokens
↓
其中 90% 对任务没意义
```

另一种方法是：

```text
Screenshot
↓
Vision Model
```

虽然直观，但成本、定位和重复观察也存在问题。

Ego Lite 默认提供：

```text
snapshotText()
```

生成压缩后的 Semantic Snapshot，并给可操作元素标记：

```text
[ref=N]
```

以及 locator。

Agent 可以：

```text
snapshot
↓
看到：
Button "Submit" [ref=12]
↓
click("@12")
```

在常规页面上走 Semantic Workflow。

遇到：

```text
Canvas
地图
复杂富文本编辑器
高度视觉化 UI
```

则可以退回：

```text
Screenshot
+
Coordinates
```

如果需要更底层的信息：

```text
DOM
Network
Browser internals
```

又可以使用：

```text
js()
cdp()
```

所以它实际上提供了三层 Browser Perception：

```text
Semantic
snapshotText()
      ↓
普通 DOM / 表单 / Link / Table

Visual
screenshot()
      ↓
Canvas / Virtualized UI / Visual Target

Low-level
js() / cdp()
      ↓
DOM / Network / Raw Browser Protocol
```

这其实就是 Browser Agent 版本的：

> **Progressive Tool Escalation。**

不要一开始就把最底层的 CDP 和所有 HTML 扔给模型。

先用最便宜、最结构化的 representation。

失败了再往下钻。

---

#### Space 还有一个比 PID 更漂亮的东西：Ownership 和 Handoff

评论区的 Skill 已经意识到了：

```text
自动填完
↓
用户审核
↓
用户提交
```

而 Ego Lite 进一步把“谁现在控制这个 Browser Context”本身做成了 API。

它有：

```text
handOffTaskSpace()
takeOverTaskSpace()
waitForAgentControl()
claimTaskSpace()
```

这样的控制原语。

于是 CAPTCHA 的 Workflow 可以直接是：

```text
Agent
   ↓
填写前半部分
   ↓
遇到 CAPTCHA
   ↓
handOffTaskSpace()
   ↓
User
   ↓
完成 CAPTCHA
   ↓
“continue”
   ↓
takeOverTaskSpace()
   ↓
Agent 继续
```

付款也是：

```text
Agent
↓
搜索商品
↓
填写地址
↓
进入付款页
↓
HANDOFF
↓
User 确认付款
↓
Agent 继续整理订单信息
```

Ego Lite 官方文档甚至明确建议，对于：

* SMS / Email Code；
* QR 登录；
* Hardware Security Key；
* Payment；
* Ordering；
* Transfer；
* Refund；
* Publish；
* Delete；
* Bulk modification；
* Third-party authorization；

让 Agent 暂停，把控制权交回人。

这就比简单写一句：

```text
“危险操作之前记得问主人。”
```

工程化很多。

因为：

> **Human Handoff 不再只是 Prompt Policy，而是 Browser Runtime State。**

---

#### 所以评论区方案和 Ego Lite 到底是什么关系？

我觉得不能简单写成：

> “Ego Lite 比 Chrome DevTools MCP 好，所以前面的方案过时了。”

两者其实代表两个层级。

### Chrome DevTools MCP 路线

```text
General Browser
+
External Agent Tooling
```

优点是：

```text
开放
通用
底层能力强
Chrome 原生生态
容易自行魔改
```

尤其：

```text
调试网页
看 Network
看 Console
研究前端问题
```

CDP 本来就是非常强的 Protocol。

### Ego Lite 路线

```text
Agent-native Browser
+
Browser Runtime Primitive
```

重点在：

```text
登录态复用
Space Isolation
Parallelism
Agent/User Handoff
Semantic Snapshot
Tool-call efficiency
```

所以两者关注的问题其实不同：

```text
Chrome DevTools MCP
↓
“How can an Agent control Chrome?”


Ego Lite
↓
“What should a browser look like
if Agents are first-class users?”
```

我觉得后一个问题更有意思。

因为它不再把 Agent 当成：

```text
一个需要外挂在 Browser 上面的 Robot
```

而是假设：

```text
Browser 有两个原生使用者：

Human
+
Agent
```

---

#### 重新画一下 Browser Agent 的演进路线

这样回头看评论区的方案，可以看到一个非常清楚的演进：

```text
Level 0
人工浏览器
↓
Human manually clicks


Level 1
Playwright / Puppeteer
↓
Script controls browser


Level 2
Browser MCP
↓
LLM calls browser tools


Level 3
Hermes + Browser Skill
↓
Agent plans complete workflows


Level 4
Independent Agent Profile
↓
Execution isolation
+ logged-in workflow
+ lifecycle management


Level 5
Agent-native Browser
↓
Space
+ shared identity
+ isolated execution
+ handoff
+ parallelism


Level 6
Persistent Browser Agent
↓
Memory
+ Skill
+ Experience
+ scheduled workflows
```

而 Ego Lite 大概已经在尝试 Level 5，并且官方还预告了“Experience accumulation”：把成功执行过的网站操作沉淀成可复用 Skill / Workflow，让类似任务之后减少探索和试错；截至目前这项能力仍属于 coming soon / limited beta，不能当作已经成熟可用的功能。

这就和前面我们讨论的 Memory / Skill Evolution 又重新接上了。

例如第一次操作 CUHK 某个系统：

```text
Agent
↓
探索页面
↓
找按钮
↓
失败
↓
修正 locator
↓
成功
```

如果每次都重新来：

```text
Browser Agent
=
永远失忆的实习生
```

但如果能把成功路径压缩成：

```text
Skill:
CUHK-form-submit

```

下一次就是：

```text
Experience

```

这已经从：

> Browser Automation

进一步变成：

> **Browser Skill Learning。**

#### 一个很现实的限制：目前还不是 Windows 工具

最后要留一个非常重要的注释。

截至 **2026 年 8 月 27 日**，Ego Lite 官方 README 仍明确写着：

```text
macOS: supported

Windows: roadmap
Linux: roadmap
```

GitHub 上 8 月还有专门要求 Windows 支持的 Feature Request，目前也没有公开 Windows stable release。

所以现在更准确的评价应该是：

> **Ego Lite 已经给出了一个很漂亮的 Agent Browser 架构答案，但它目前还不能完全替代所有平台上的 Chrome DevTools MCP / Playwright 方案。**

尤其对于 Windows/Linux 用户，前面评论区的：

```text
独立 Chrome Profile
+
Chrome DevTools MCP
+
Skill
+
Human Confirmation
```

仍然是一套很现实的实现。

所以我不会删掉前面的方案。

恰恰相反，我会把 Ego Lite 放在它后面。

因为这样刚好形成一种很漂亮的学习顺序：

```text
先自己搭一遍
↓
发现 Browser Agent 有哪些麻烦
↓
再看 Ego Lite
↓
突然理解为什么它要造 Space、
为什么要复用 Login State、
为什么要做 Handoff、
为什么不愿意一个 Tool Call 点一下
```

只有经历过前面的工程问题以后，才能真正理解：

> **Ego Lite 做的不是“更方便地 click 一个 button”，而是在尝试重新定义 Agent 与 Browser 之间的边界。**

## 七、HomeLab / IoT 派：Hermes 作为 24h 基础设施

评论区还有一类用户，他们的兴趣不在单次任务表现，而在于把 Hermes 变成家里或服务器上长期运行的“数字管家”。有人提到：

> “从龙虾走到 Hermes 到 homelab……有自己的内网，搭配记忆库和 IoT 才有意思。”

自己的折腾路径是“从龙虾走到 Hermes 到 homelab”，强调要有自己的内网、记忆库和 IoT 设备一起配合才有意思。这里的 HomeLab 指的是在自家搭建的服务器、网络和存储环境，NAS（网络附加存储）和 VPS（虚拟专用服务器）都是常见组件，IoT 则是各种联网的智能设备。典型任务包括用 Blender MCP 控制 3D 软件、自动记账、追踪体检单、管理 NAS 和 VPS 等。



这一派真正看中的不是 Hermes 在某个 benchmark 上的分数，而是它作为一个常驻进程（Daemon）的能力：有消息网关（Gateway）可以接入各种聊天软件，有记忆系统可以跨会话保留状态，还有技能和工具可以操作外部世界。这几点合起来构成一个“持久化的智能体运行时”（Persistent Agent Runtime），能够 7×24 小时待命，主动推送消息或执行定时任务。相比之下，Claude Code 或 Codex 更像是一次性的工程工具：进入项目目录、干活、退出。所以评论区里才反复有人说，Hermes 是自下而上地协助你，而 Codex 是一个工程做完就收工。


这派真正看中 Hermes 的其实不是 benchmark。

而是：

```text
Daemon
+ Gateway
+ Memory
+ Skills
+ Tools
```

也就是：

> **Persistent Agent Runtime**

而 Claude Code 更像：

```text
cd project
claude
干活
exit
```

这就是评论里反复出现的：

> Hermes 自下而上协助你；Codex 是一个工程做完就收工。

## 八、源码魔改派：真正把 Hermes 当 Framework，而不是产品

这派也非常有意思。

有人说：

> 原版 Hermes 不好用，但是 Python 写的，源码就在你电脑，改一下非常好用。

然后列了一堆他实际改的东西。

大概包括：

### 1. Windows terminal support

修 Windows 下 terminal 行为。

### 2. 自动重连 / 恢复

处理：

* 断线
* 空回复
* 输出截断
* 无限重复

### 3. Tool 强制路由

解决：

```text
明明有 Skill
↓
模型就是不用
```

于是直接在 Harness 层：

```text
task_type=X
→ FORCE skill Y
```

而不是靠 system prompt 希望模型自觉。

### 4. 文件删除安全层

例如：

```text
禁止删除 D:\
禁止 rm -rf ~
禁止删除指定目录
```

### 5. Git Safety

例如直接禁：

```bash
git reset
```

或者 interception：

```text
危险命令
↓
reject
↓
返回推荐正确命令
```

### 6. 全权限 + Harness Guard

这派反而不喜欢：

```text
每执行一个命令都弹：
Allow?
```

他们想：

```text
Agent 拥有权限
+
Harness 做 deterministic guardrail
```

这其实是一个很重要的设计理念：

> **Safety 不应该完全靠 LLM 自律，也不一定要靠每步人工审批；可以放到 Tool Runtime 层。**

## 九、“Hermes 太主动”实际上形成了一个完整的权限控制流派

这是评论区出现次数最多的抱怨之一：

> “我只是问一句，你怎么直接开干了？”

各种民间解决方案都有。

有人在 SOUL 写：

```text
先问
一定要先问
不要上来就改
```

有人发明：

```text
如果消息以 qqqq 结束：
只回答
禁止执行
```


Pi 用户则做：

```text
ask mode
```

有人主张：

```text
plan mode
```

还有人干脆源码增加权限 gate。

于是你可以看到一个非常明确的梯度：

```text

↓

↓
Ask-to-act
↓
Act
↓
Autonomous
```

而 Hermes 原生的 “more active” 倾向比较靠右。

这恰好既是它的卖点，也是大量事故来源。

## 十、Pi / Oh-My-Pi 派：我不要“胖 Agent”，我要纯 Harness

评论里有人强推：

> “高强度 AI coding 的用户试试 pi；追求 Claude Code 体验用 oh-my-pi。”

这个我也核实了一下。

Pi 本身确实强调极简、可扩展的 agent harness，现在包括：

* coding agent CLI
* agent core
* unified LLM API
* TUI
* Web UI


而 Oh-My-Pi 是 Pi 的 batteries-included 分支，额外加了大量：

* LSP
* debugger
* browser
* subagents
* persistent Python
* optimized editing tools


所以评论区说：

> “Hermes 用得好的人最后可能干脆去 Pi。”

其背后的逻辑是：

```text
如果你已经愿意：
改 Skill
改 Tool
改 Loop
改 Permission
改 Memory
改 Prompt
```

那你其实已经不再需要一个“成品 Personal Agent”。

你真正想要的是：

> **可编程 Harness。**


## 十一、Superpowers 派：不要寄希望模型临场发挥，强制工程流程

评论里还吵到了 Superpowers。

支持者认为：

> 新模型越强，反而越应该有稳定流程，否则实际项目边界条件没确认就开始做。



Superpowers 确实是一套 Coding Agent workflow skills，包含：

```text
brainstorming
↓
writing plans
↓
git worktrees
↓
TDD
↓
subagent development
↓
code review
↓
verification
```


所以这派本质上相信：

> **Workflow > Agent personality**

也就是把 Claude Code 那类 agent 的隐藏工程经验“显式 Skill 化”。

评论里提到的 `grill me / gril me` 我目前没有搜到一个足够明确、可以确认就是他们讨论对象的主项目，所以这个名字暂时不要当作我已验证的项目；但语境上是在说另一套“先把需求拷问清楚再实施”的 Skill workflow。

## 十二、模型派：同一个 Harness，换模型人格都变了

评论区另一大主题不是 Agent，而是：

> **model × harness interaction。**

最典型的体验描述：

```text
DeepSeek + Hermes
→ 太积极
→ 问问题也直接干

GPT + Hermes
→ 反过来太爱确认

GLM
→ 更偏 Plan
```

另有人说：

> “ds api 就是喜欢蛮干；glm 反过来干啥都是 plan。”

这些属于**用户体验报告，不应该当作客观模型 benchmark**。

但它们揭示一个很重要的 Harness 问题：

```text
最终行为
≠ Model
≠ Harness

最终行为 =
Model
× System Prompt
× Tools
× Tool Schema
× Loop
× Context
× Permission
× Memory
× Training Adaptation
```

这也正是评论区最开始那句话：

> 不同 Agent 背后偷偷发的 prompt 不一样，你发一句“你好”并不只消耗几个 token。


## 十三、另一种实践哲学：专业任务和生活任务彻底分家

有一个评论非常完整：

```text
Hermes
→ 日常
→ 生活
→ 琐碎工作

Claude
→ 独立 Project
→ 专业复杂任务
```

原因就是：

> Hermes 的项目 Memory isolation 不方便，任务领域一多，相互污染之后幻觉很严重。


他进一步建立：

```text
Obsidian
```

作为跨 Agent 的 shared record：

```text
谁做了什么
为什么这么做
有什么影响
```

也就是说：

```text
Hermes Memory ≠ Single source of truth

OB / Git / docs
= Cross-agent source of truth
```

这个思路后面和“私有 Git 仓库给不同 Agent 接力”本质完全一致。


## 十四、所以评论区其实形成了三套终极架构

把上面所有玩法压缩后，真正有意义的是下面三个 archetype。

### A. Personal AI / Jarvis 路线

```text
                    ┌─ SOUL / Persona
                    ├─ User Memory
                    ├─ Hindsight/OpenViking/...
User
 ↓                  ├─ Skills
Hermes ─────────────┼─ Gateway
                    ├─ Browser
                    ├─ VPS
                    ├─ NAS / IoT
                    └─ Voice
```

适合：

> “我想有一个越用越懂我的长期 Agent。”

这里甚至可以合法地同时是：

**女友 + 秘书 + 管家 + VPS 运维。**

### B. Agent Manager / Company 路线

```text
                    ┌─ Claude Code
                    ├─ Codex
User → Hermes ──────┼─ OpenCode
       Manager      ├─ Browser Agent
                    ├─ Research Agent
                    └─ Workers
```

Hermes 自己尽量不执行重型任务。

它负责：

```text
Identity
Memory
Routing
Scheduling
Communication
Task decomposition
Result aggregation
```

### C. Clean Harness / Project Isolation 路线

```text
Project A → Claude Code / Pi
Project B → Codex
Project C → DSH
```

每个目录：

```text
AGENTS.md
docs/
skills/
git history
```

不要：

```text
global personality memory
global workflow memory
global vector memory
```

原则就是：

> **Context 越少越准；需要什么让 Agent 自己找。**

这是反 Hermes 派最强的论点。

## 最后，我觉得这 521 行评论真正讨论的是这张“技术地图”

不是：

> Hermes 好不好。

而是：

```text
Personal Agent
│
├── Identity
│   └── SOUL / Persona / RP
│
├── Memory
│   ├── Markdown Memory
│   ├── Memory Cards
│   ├── Hindsight
│   ├── Honcho
│   ├── Mem0
│   ├── OpenViking
│   ├── Smriti
│   └── Scope Recall
│
├── Knowledge
│   ├── Markdown Index
│   ├── RAG
│   ├── LLM Wiki
│   └── OpenViking Resources
│
├── Skills
│   ├── Workflow
│   ├── Browser Skill
│   ├── Ops Skill
│   └── Self-evolution Skill
│
├── Harness
│   ├── Agent Loop
│   ├── Tool Routing
│   ├── Permission
│   ├── Plan / Ask / Act
│   └── Context Management
│
├── Orchestration
│   ├── Subagents
│   ├── Claude Code
│   ├── Codex
│   ├── OpenCode
│   └── Workers
│
├── Interfaces
│   ├── CLI
│   ├── Web
│   ├── Feishu
│   ├── Telegram
│   └── Voice
│
└── Environment
    ├── Browser
    ├── VPS
    ├── NAS
    ├── HomeLab
    └── IoT
```

所以你最开始说“**自己改造 Hermes、外接 Mem0 等种种类型**”，实际上评论区已经给出了一条非常完整的进阶链：

> **改 SOUL → 改规则 → 整理 Skill → 做 Memory hygiene → 外接 Memory Provider → 做 project scope → 接 Browser/MCP → Hermes 管其他 Agent → 改源码 Harness → 最终变成自己的 Personal Agent OS。**

而另一群人则沿完全相反的方向：

> **关自动 Memory → 少写 prompt → 每项目隔离 → Skill 只保存 workflow → Agent 自己按需读文件 → 最后干脆 Pi/Claude Code。**

这两个方向恰恰是现在 Agent Harness 非常值得研究的两极：

**“长期人格化 Agent” vs “短生命周期、最小上下文 Worker”。**

评论区真正有意思的地方，不是谁赢，而是有人已经开始尝试把二者结合：

> **Hermes 做长期 Identity / Memory / Gateway / Manager；Claude Code、Codex、Pi 做无状态或弱状态的专业 Worker。**

这大概是整片评论区最值得提炼出来的架构思想。  

如果我们接着往下做，我觉得下一步最有价值的不是再泛泛总结评论，而是把评论区这些玩法整理成一张 **「Hermes 魔改技术树」**：从 Level 0 原版 Hermes，一直到 SOUL、Memory Provider、OpenViking、Browser MCP、Multi-Agent Manager、源码级 Harness 改造，并标出每一项“解决什么问题 / 值不值得你自己折腾 / 能从哪个开源项目抄作业”。这会和你前面研究 DSH、Claude Code、Pi/OMP 的 Harness 技术地图正好接起来。
