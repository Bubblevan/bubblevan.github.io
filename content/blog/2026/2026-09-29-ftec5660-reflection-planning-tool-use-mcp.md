今天下午的 FTEC5660 从系统抽象讲起，接着讨论 Reflection 和 Planning，最后用 LangChain 演示工具调用与 MCP。我按原始录音转写里的时间戳顺序整理课堂内容，用 `04 Reflection` 课件和 HW2 核对术语、操作步骤与作业要求；转写中的英文识别错误按上下文修正。

## 1. 先把复杂问题看成分层的输入—输出系统

### 1.1 从下一个 token 到 Agent

00:00，老师用系统工程的视角解释 abstraction：先把复杂任务拆成边界清楚的输入—输出方框，再把不同大小的方框组合起来。一个大系统可以由若干子系统构成，子系统又能继续拆分；关键是明确每个方框接收什么、产出什么，以及它在上层系统中的位置。

01:23，课堂把这个思路套到语言模型应用上，按抽象层级从小到大看：

1. **Next-token prediction**：输入前文，预测下一个 token。
2. **完整回答**：反复执行下一个 token 的预测，逐步生成一段回答。
3. **单 Agent**：把多轮模型调用、工具或其他组件组织起来，完成多步任务。
4. **Multi-agent system**：再把多个 Agent 组合起来，处理单个 Agent 难以独立完成的任务。

这样看，Agent 不是脱离语言模型的神秘新部件，而是在更高层把多个输入—输出过程组织起来的系统。

### 1.2 控制问题和设计问题不是同一种改法

06:17，老师把输入—输出方框推广到个人、公司和经济系统：公司把原料加工成产品，人也可以抽象成接收条件并做出行为的系统，经济体则由劳动、投资等输入产生总体产出。

在这个视角下，课堂区分了两类问题。**控制问题**是系统结构基本不变时，调整输入，让输出达到目标；**设计问题**则是改变组成部分及其相互作用方式，例如重新安排流程、制度或产品结构。两者最终都可能影响系统结果，但介入的位置不同：前者改输入，后者改系统内部的组织方式。

### 1.3 先定目标，再拆效果，最后挑工具

12:09，老师把问题求解顺序归纳成“目标—效果—工具”。先确定希望得到的终点，再问哪些中间效果有助于抵达终点，最后才从可用工具中挑选手段。课堂用 GDP 增长目标举例：如果目标是某个增长水平，可能的中间效果包括就业、工作条件、教育和金融科技发展；工具是否合适，要看它能不能带来这些效果。

14:51 又把工具和问题都看成节点。匹配时先检查工具是否可行，再比较成本和收益。这个次序很实用：先排除根本做不到的方案，再在可行方案中考虑效果、成本和维护负担，而不是因为手上有某个工具就硬把问题套给它。

## 2. 高频路径先做稳，响应时间不要变成填满的指标

### 2.1 把 80/20 当成排序启发式

20:05，老师用 Pareto 的 80/20 说法讨论 GenAI 产品的工作流设计：先找出频率高、模式稳定的请求，把这些核心路径做得可靠、便宜且可追踪；低频而复杂的长尾问题可以稍后再处理，或单独设计升级路径。

我把这里的 80/20 理解为**优先级启发式**，而不是每个产品都必须恰好满足的统计规律。实际比例仍要用产品自己的请求数据确认。 deterministic workflow 的优点是行为更稳定，也更容易控制单次成本和追查执行过程；代价是覆盖范围有限，遇到没设计过的情况仍要有合适的 fallback。

### 2.2 TTA 是约束，不是要用满的预算

28:48，课堂接着讲 Parkinson’s Law，并用 TTA（Time to Answer）说明指标设置的风险。如果把“最多十秒回答”误当成“应该花十秒回答”，系统可能为了用满时间而增加没有必要的步骤，例如多做一轮反思。

因此，TTA 更适合作为不能超过的约束；在满足质量要求的前提下，还要考虑减少延迟和运行成本。是否多加一步 Reflection，应该由它带来的可测量收益决定，而不是为了让响应时间接近上限。

## 3. Reflection：生成、评价、修改，再决定是否继续

### 3.1 反思循环怎样运行

31:59，课堂讨论怎样判断 Reflection loop 是否真的有用。课件把基本循环画成：先执行并产出初稿，再按准确性、一致性、完整性和约束条件等标准进行评价或批评，接着按反馈修改；如果仍未达到停止条件，就继续迭代。

反思可以由同一个 Agent 自查，也可以拆成 **Producer–Critic**：Producer 负责起草，Critic 按给定标准挑问题，再把结构化反馈交回 Producer 修改。两个角色分开，通常更容易聚焦评价标准；但它会增加调用、上下文和延迟，Critic 也可能把正确内容误判为错误。是否值得使用，要看评价标准是否清楚、反馈是否有用，以及改进是否抵得过成本。

课件中的信贷审批示例把循环展开得很具体：申请人的月收入是 5,000 美元，现有月供 1,500 美元，拟申请贷款月供 1,000 美元；规则要求包含新贷款后的每月总还款不超过收入的 40%。初稿漏掉新贷款，只按 1,500 美元计算；Critic 补上遗漏，得到 2,500 / 5,000 = 50%，超过 40%；修订后的结论是未通过自动检查，应交由贷款人员复核。

![Reflection 在信贷申请检查中的生成、批评与修订流程](/blog/2026/9-29/ftec5660-reflection-credit-review.png)

这张图也提醒我，Critic 不能只说“这里不够好”，它必须指出漏了什么、依据哪条规则、如何重新计算。否则后续修改没有可执行的反馈。

### 3.2 反思能否改善结果，需要按错误代价校准

31:59 的讨论用 TP、TN、FP、FN 四类结果来分析生成器和反思器的判断。应用场景不同，最需要压低的错误类型也不同；讨论风险时不能只说“准确率提高了”，还要先说明正类代表什么、各类错判会造成什么后果。

要做这类校准，需要有贴近实际任务、带标签的样例，并明确不同错误的代价。没有这些数据，仅凭几条看起来不错的输出，无法判断 Reflection 应该何时触发、Critic 的门槛该设多高。课件也列出适用场景：长文写作、摘要综合、计划检查和对话一致性维护；共同点是有相对清楚的评价标准，而且质量提升足以补偿额外耗时与计算。

### 3.3 课堂带出的 AI paradoxes

38:37，老师把 AI paradoxes 作为 HW2 Task 3 的讨论题引入。课堂转写里的两组矛盾现象是：模型能力和 benchmark 成绩持续进步，但人们仍难解释模型究竟如何、为何产生这些结果；生成式 AI 大量生产内容，同时人的注意力有限，而用户有时会信任 ChatGPT 的回答、却怀疑网上其他来源的信息。

作业要求写自己对 AI paradoxes 的反思，形式可以是文字、绘图或 AI 生成作品。题目没有规定必须把课堂提到的两组现象原样复述；后续写的时候要把观察到的矛盾讲清楚，并说明它为什么值得讨论。

## 4. Planning：把规划留给复杂长尾任务

44:11，课堂转到 Planning pattern。它针对的是低频、复杂、需要多个步骤或工具的请求：先根据目标生成执行计划，再按计划调用工具；必要时可以分层规划，也可以在执行中重新规划。

课堂把 Planning 视为确定性流程之外的兜底选择，而不是所有请求默认都要启动的环节。它更灵活，但规划本身具有随机性，会增加调用成本，也更难完全追踪。特别值得注意的是，计划可能是整条 Agent 链路的关键瓶颈：后续工具都按计划行动时，计划中的遗漏或顺序错误会传导到最终结果。因此，计划能力和规划模型的选择可能比普通摘要生成更直接地影响任务成败。

## 5. Tool Use：让模型决定调用什么，由程序执行

### 5.1 工具调用循环

01:01:17，课堂讲 Tool Use 怎样把 Agent 接到模型训练数据之外的能力上，例如实时数据、精确计算或第三方服务。传统方式是为各个 API 分别写 wrapper；如果更换服务提供方，就可能要改客户端代码。调用外部 API 还会带来费用、鉴权、可靠性和服务质量等实际约束，不能因为模型能发起工具调用就忽略这些成本。

01:24:27 的 LangChain tutorial 把一个工具定义为带有明确描述和类型提示的 Python 函数，再用 `@tool` 装饰器注册，并把可用工具绑定给模型。模型负责决定是否调用以及传入什么参数，Python 代码负责真正执行函数。

课堂演示了两个工具：通过 Yahoo Finance 查询股票 OHLCV 数据，以及执行计算器运算。核心循环可以按下面的顺序读：

1. 把用户请求和可用工具交给模型。
2. 模型返回普通回答，或返回一个/多个结构化 tool call。
3. Python 根据 tool call 执行相应函数，把执行结果追加到对话上下文。
4. 再把更新后的上下文交给模型；如果它继续要求调用工具，就重复执行。
5. 当模型不再返回 tool call 时，结束循环并返回最终回答。

01:42:14 用“苹果公司过去五个交易日收盘价的平均值”演示了多轮调用：模型先请求查询价格，程序取回数据，接着模型根据结果继续处理，最后给出答案。重要的是，模型提出工具调用并不等于工具已经运行；中间还需要程序读取参数、执行函数、把结果回传。

### 5.2 规划层放在工具执行循环之前

01:46:49，tutorial 在同一循环前增加了规划步骤：模型先把复杂请求分解成步骤，再逐步执行工具调用。把“计划”和“行动”分开后，可以分别查看计划错在哪里，还是某个工具调用或返回结果处理错了。计划依旧可能不合理，分层的价值是让错误更容易定位，而不是自动保证执行正确。

## 6. MCP：统一客户端和工具服务器之间的连接方式

01:13:07，课堂介绍 Model Context Protocol（MCP），把它比作 Agent 接工具时的通用连接标准。Agent 一侧作为 MCP client 发现服务器提供的工具，再按协议请求调用；工具实现和具体数据服务放在 MCP server 一侧。这样，客户端不必为每个服务器都写一套完全不同的发现和调用流程。

01:52:03 的 tutorial 连到预先部署的 SocialGraph MCP server，通过 HTTP 连接后自动发现六个工具：三项 Facebook 查询工具和三项 LinkedIn 查询工具。Notebook 使用异步客户端与 `async/await` 发起请求，再把发现到的工具交给 Agent，执行时仍沿用前面介绍的“请求工具—运行—回传结果”循环。

MCP 统一的是工具发现和通信接口，不会自动保证工具服务本身安全、可靠、免费或正确。身份验证、权限边界、调用成本和数据质量仍然要看具体 server 与服务配置；换服务也只有在服务器端确实提供了对应实现时，才可能不改客户端逻辑。

### 6.1 代码量变大，不等于产品价值变大

01:18:31，老师用一个很工程化的问题讨论 AI 生成代码：假设每写一行代码都有 \(\epsilon\) 的概率引入错误，代码越多，潜在缺陷机会也越多。老师进一步质疑只奖励代码量、功能数或论文数的评价方式，因为它可能鼓励堆复杂度，而不是让软件更可靠、更有用。对我来说，这和前面“先算收益是否值得调用 Reflection 或 Planning”是同一个取舍：新增组件也要算它带来的价值和维护成本。

### 6.2 TA 的 tutorial：从工具循环走到 MCP

01:24 左右，TA 从 LangChain 工具调用开始演示，再加上规划步骤，最后把工具移到 SocialGraph MCP server。Notebook 里展示了连接服务器、发现六个工具、异步调用 LinkedIn/Facebook 查询，再将工具结果回填给模型的完整链路。这个 tutorial 是 FTEC5660 HW2 的直接操作背景。Colab 访问方面，我课后已联系项目组并按要求填写了表单，这件事已处理；这堂课的录音没有提到 Individual Project 1 是否为小组项目，我还得单独向 TA 确认。

## 7. Individual Homework 02：先把个人作业边界和提交口径记牢

作业 PDF 首页写的是 Individual Homework 02，截止 **2026 年 10 月 20 日 23:59（HKT）**。它鼓励讨论，但明确要求每个人提交自己的工作；总分拆成 Task 1 CV verification agent（60 分）、Task 2 Fool the Verifier（20 分）、Report（10 分）和 Task 3 Reflection on AI paradoxes（10 分）。

作业仓库需要先 fork 到自己的 GitHub，再 clone；环境要求 Python 3.10 或以上，按 `requirements.txt` 建立虚拟环境并安装依赖。API key 放在本地 `.env` 的 `DEEPSEEK_API_KEY` 中，不能写进代码或推送到 GitHub；`.env` 已在 `.gitignore` 中。仓库提供 `hw2.py` 起始代码、`public_test/` 下的 7 份公开 CV 和标签，以及 `task2/` 目录。

### 7.1 Task 1：按社交资料核验 CV，并返回一个分数

输入是一批 CV PDF；每个文件要输出一个 `[0,1]` 的 reliability score。标签 1 表示 CV 资料与候选人的 LinkedIn / Facebook profile 一致；标签 0 表示至少有一项实质性错误。措辞差异本身不算错误，例如 degree 的近义表述或 seniority 相邻级别可接受。LinkedIn 是主要依据，作业测试数据里的 Facebook 资料与 LinkedIn 一致。

需要核验的范围限定在姓名、城市、任职经历（公司、职位、seniority、起止年份）、学历（学位、学校、专业、毕业年份）和技能。Job description、headline、hometown 不作为差异判据。候选人可能同名，因此要用地点、行业等线索识别正确 profile，不能找到第一个同名账户就结束。

实现上只填 `hw2.py` 中的 `build_agent(tools)` 和 `score_cvs(agent, cvs)`；允许在它们之前补 imports、常量和 helper functions，但不能改其下方提供的 PDF loading、MCP connection 和 scoring 代码。`build_agent` 创建模型、prompt 和 agent；`score_cvs` 为每个 CV 文件名返回一个 `[0,1]` 浮点数。单份 CV 的 API 或处理错误要单独捕获，返回该文件的分数，不能让整个批次崩溃。不能硬编码文件名、候选人姓名或 public labels。

作业只允许使用 `deepseek-v4-flash` 和 LangChain。所有核验证据必须来自课程指定的 SocialGraph MCP server（`https://ftec5660.ngrok.app/mcp`），不能再用网页搜索等其他数据源。共享服务器的并发量要控制在约 3 个 CV，可用 `asyncio.Semaphore(3)` 限流。

附录列出 6 个工具：Facebook 的 `search_facebook_users`、`get_facebook_profile`、`get_facebook_mutual_friends`，以及 LinkedIn 的 `search_linkedin_people`、`get_linkedin_profile`、`get_linkedin_interactions`。搜索结果可能是模糊匹配且不保证排序；同名候选人很多，应该用地点、行业等信息继续缩小范围。LinkedIn profile 是主要核验来源，不能只凭搜索结果摘要下结论。

本地先用 7 份公开样例运行：

```bash
python3 hw2.py --cv-folder public_test
```

程序会生成包含 `cv`、`score`、`correctness` 的 `results.csv`。`score > 0.5` 判为 valid，`score <= 0.5` 判为 has discrepancy。最终还会用约 20 份隐藏 CV 评估三次，Task 1 成绩取三次平均准确率；每次运行须在 30 分钟内结束。缺少分数、非数字或越界值都算错；程序崩溃、超时或没有产出 `results.csv`，该次为零分。提交前还要从 fresh clone 做端到端测试。

### 7.2 Task 2：做一份含真实错误的对抗 CV

这部分要为指定目标候选人 Kelly Tsang 准备一份最多两页的 PDF（作业给出的 LinkedIn `person_id` 和 Facebook `user_id` 均为 10001，Facebook 显示名为 “Kel Tsang”），至少包含一项虚假或夸大的信息；如果 CV 没有真实的错误或夸大内容，即使 verifier 给了高分也不得分。课程准备了 5 个使用相同模型与 MCP 数据源的 verifier，每个 verifier 若在三次运行中多数时候给出 `> 0.5`，得 4 分，最高 20 分。可以先用自己的 Task 1 agent 测试，PDF 写入 `task2/adversarial_cv.pdf`；Task 2 没有 ground-truth 标签，不要把本地试验输出当作评分结果。
