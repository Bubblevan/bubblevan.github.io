这次整理项目材料时，我发现自己真正需要的不是一张“项目进度备忘录”，而是一套之后能反复查阅的知识底座。小组项目同时涉及三维几何、传统算法、代码生成 Agent、CAD 软件接口和实验评测；如果只记住“有两份 PDF、六个 smoke tasks、几轮算法改进”，这些事实彼此之间仍然连不起来。

我把这份笔记从一个完整问题开始组织：给定一个不完整、有噪声的三维扫描结果，怎样恢复一个有意义、可执行、可编辑的 CAD 模型？回答这个问题，需要先理解输入几何和设计意图的差别，再看几何算法如何提供结构化证据，最后才是 Agent 如何调用 CAD 工具、生成程序并接受独立评测。项目中的两项工作——点云分割算法的迭代改进，以及从损坏几何生成参数化 CAD 程序——相关但并非已经合并成一条完整系统流水线。

## 这个任务要恢复的不是一张表面网格

三维逆向工程的输入可以是点云或网格，目标却未必只是得到一份看起来相似的表面。工程上更有用的结果通常还要说明哪些面构成零件、尺寸参数是什么、孔与主体之间有什么关系，以及这套几何能否通过一段程序重新生成。

几个表示之间的差异，决定了任务为什么困难：

| 表示 | 记录了什么 | 通常没有直接记录什么 |
| --- | --- | --- |
| 点云（point cloud） | 从表面采样得到的三维坐标，可能带法向和颜色 | 哪些点属于同一个面、该面属于何种解析几何 |
| 三角网格（mesh） | 顶点、三角形及其邻接关系，近似描述表面 | 一个弯曲区域原本是不是精确圆柱、圆孔半径是否为设计参数 |
| B-rep | 由面、边、顶点及拓扑关系定义的边界；面可以是平面、圆柱面或其他曲面 | 设计者当初按什么顺序创建这些几何特征 |
| 参数化 CAD 程序 / 特征历史 | 尺寸、约束以及草图、拉伸、切孔、倒角等构造关系 | 若原始设计过程没有保存，最终几何通常不足以唯一推出它 |

例如，一个长方体上有两个对称的圆孔。扫描网格可能只呈现很多三角形；设计者的模型却可能是一个矩形草图拉伸，再创建一个孔并镜像。另一个工程师也可以通过布尔减法分别挖出两个孔，得到几乎相同的最终形状。

因此，“从扫描中恢复 CAD”至少有两个层次：恢复几何结果，以及恢复有解释力的构造关系。后者通常不是单一答案。仅凭最终表面，不能断言最初的设计者一定采用了哪种特征顺序；更稳妥的研究目标是产出满足几何约束、可以执行并有合理参数结构的重建程序。

这也解释了为什么项目不能把“视觉上相似”直接当成“设计恢复成功”。模型可能复制了表面，却没有生成有效实体；也可能生成实体，但尺寸或位置偏差很大；即使几何相符，代码仍可能只是硬编码网格，改一个名义参数并不会得到有意义的局部变化。

## 几何分割把海量采样变成可推理的结构

点云里每个点都只是一个局部观测。要让后续程序推理更容易，常见前处理之一是把点归为平面、圆柱、球面、圆锥等几何基元（primitives），估计这些基元的参数，再判断它们如何相邻或相交。

以平面为例，RANSAC 会反复从数据中抽取少量点，生成候选平面，再计算有多少其他点落在距离阈值 ε 内。符合几何容差的点构成内点（inliers）；算法比较候选并保留得到较多支持的模型。圆柱、球和圆锥也可以采用相似的随机采样一致性思路，只是候选模型和拟合过程更复杂。

它不依赖一个针对所有零件提前训练好的神经网络，但输出仍会受扫描质量、采样密度、法向估计、阈值和候选评分方式影响。小的圆柱内壁可能因为点太少而没有被发现；同一平面可能被拆成多个区域；相邻而近似的面可能被并成一个；区域位置对了，也可能被标错几何类型。

RSI 报告把错误区分为几类，这比单看一个总分更有诊断价值：

| 失败类型 | 含义 | 例子 |
| --- | --- | --- |
| lost | 真实曲面没有被恢复 | 小孔内壁被当作残留点 |
| merged | 多个真实曲面被合并 | 两块相邻平面被识别成一个区域 |
| split | 一个真实曲面被分成多个区域 | 同一自由曲面被切成许多小片 |
| type mismatch | 大致找到了区域，但基元类型不正确 | 圆柱区域被识别成球面 |

几何摘要可以把几十万坐标压缩成可供程序处理的结构，例如“主体近似长方体、上表面有两个共轴圆柱孔、两孔关于中心线对称”。这让模型可以把一部分几何问题转成参数和关系推理；但若前处理漏掉了孔或错误合并曲面，后续 Agent 接收到的就是有偏差的证据。分割质量因此会影响 CAD 重建上限，而不是一项与最终任务无关的清理步骤。

## RSI 报告研究的是 Agent 改算法代码

项目材料中的 RSI（报告使用的名称）是一项点云基元分割实验。它把 Rust 版 Efficient RANSAC 作为基线，让 Coding Agent 根据失败报告修改传统算法，再通过自动化评测决定是否接受新版本。这里变化的是被测算法的程序代码，不是 Agent 的模型权重；因此它与 SFT 或强化学习训练不是同一种实验。

数据集包含 303 个机械零件，每个零件生成三种难度的点云，总计 909 个输入。按零件划分，250 个用于 tune，53 个用于 holdout；同一零件生成的不同难度样本不会跨越这两个集合。报告用 Hungarian 算法进行预测区域和真值区域的一对一匹配，匹配还要求 IoU 至少为 0.7，且基元类别正确。单个样本的区域恢复分，是有效匹配区域的 IoU 总和除以真值区域数；它不是“多少零件被完整还原”的百分比。

报告的四轮修改展示了 Agent 如何把错误统计转成明确的算法假设：

| 版本 | 修改 | Tune 分数 | Holdout 分数 | 观察到的结果 |
| --- | --- | ---: | ---: | --- |
| gen_0 | Efficient RANSAC 基线 | 0.3249 | 0.2785 | 起始结果 |
| gen_1 | 对主流程留下的点进行第二轮小区域提取（residual sweep） | 0.3638 | 0.3278 | 小区域 lost 显著减少；是主要早期提升来源 |
| gen_2 | 合并相邻且同类型的区域 | 0.3640 | 0.3281 | 提升很小；跨类型共识合并反而退步，因而回滚 |
| gen_3 | 按每个零件估计噪声并调整距离阈值 | 0.3688 | 0.3280 | Tune 改善而 Holdout 微降，显示阈值可能适应了 tune 数据 |
| gen_4 | 让所有候选基元竞争解释残差区域，限制特定类型重判 | 0.3877 | 0.3387 | type mismatch 减少，Holdout 三种难度均较基线提高 |

gen_1 的逻辑很直接：主流程为避免误检设置了较高的最小区域门槛，许多小面因此留在未分配点中。Agent 增加残留点二次提取，并针对这些小区域降低门槛；报告记录 lost 从 1,989 降到 566。Tune 从 0.3249 升至 0.3638，Holdout 从 0.2785 升至 0.3278，且有 16 个样本从零分变为正分、没有样本分数下降。

gen_2 尝试修补过分割：将邻接、法向接近、残差较小的同类型区域合并。Holdout 只增加 0.0003，说明“相邻且同类型”并不足以可靠判断两个区域原本是否属于同一曲面。报告还试过跨类型共识合并，净效果为负，随后回滚；这类负结果很有用，它说明失败模式不能总靠更宽松的局部规则解决。

gen_3 根据每个零件估计噪声，再选择距离容差。Tune 上升至 0.3688，Holdout 则从 0.3281 轻微降至 0.3280；最高难度层改善较多，但没有稳定地泛化。报告记录了在 tune 上校准阈值的过程，所以这轮更适合被理解为一次过拟合风险的实证，而不是一个已证明有效的通用策略。

gen_4 重新比较多个基元对残差区域的解释能力，并限制允许的类别改判方向，例如允许球面或圆锥候选在证据支持时改判为圆柱。type mismatch 从 489 降至 355；最终 Holdout 为 0.3387，比起点 0.2785 高 0.0602。报告仍记录了 3,442 个 split 错误，数量与 gen_1 后的 3,456 接近，说明自由曲面切分依然没有被这些改动解决。

这组实验的接受规则也需要一起读。Holdout 至少要比基线高 0.05，各难度层不能比基线低超过 0.01，Tune 分数要逐轮严格增加，Holdout 的逐样本累计结果不能出现净回退。Gen_4 的 Holdout 0.3387 达到报告中的总体门槛 0.3285，且三种难度都高于起点。

不过，Holdout 对修改者隐藏，并不自动意味着它是从未使用的最终测试集：Agent 改进流程反复用它决定候选是否通过，报告也将这些结果用于接受或回退。因此，0.3387 是这份实验流程的 Holdout 结果，不是完全独立的最终泛化证明。报告还指出，CGAL 6.2.1 的 0.3226、gen_0 的 0.3249 和 gen_4 的 0.3877 是在 tune 集上的比较；而 RANSAC 基线没有充分调参，初始几轮收益有可能部分来自补足基线调参不足。

还应保留报告附录里关于流程偏离的记录：冻结架构之后仍发生了门控调用，gen_1 的标签在 gen_2 期间被移动后又恢复，早期门控脚本也有缺陷。这些事实不会让数字自动失效，但会影响“严格按预注册合同运行”的说法。实验结论应限于：在这个算法模块、这套数据划分和迭代流程里，若干代码修改提高了分割指标；它还不能证明任意 Coding Agent 都能普遍地自主改进几何算法。

## Mesh2Code 要让 Agent 生成并运行 CAD 程序

Proposal 提出的另一项工作针对更靠近最终应用的问题：输入一份模拟受损的三维扫描，Agent 需要生成 Python 建模程序，执行后输出 CAD 实体，再与原始几何比较。

数据构造从已有的 CAD 模型开始。先将模型转成网格，再模拟噪声、遮挡、孔洞、表面平滑、降采样或细小特征丢失。完整 CAD 作为评分真值保留给离线验证器，Agent 只能看到受损输入和任务允许提供的信息。Proposal 计划从 CADGenBench 的编辑任务扩展；这一数据来源和扩展属于提案设计，不能误写成已经完成的大规模 Benchmark。

Agent 的执行过程可以概括为 inspect、write、run、revise：

1. Inspect：调用几何检查工具，观察包围盒、平面、孔、曲率或其他可用特征。
2. Plan：基于这些观测，选择草图、拉伸、切除、阵列等构造方式，并决定尺寸参数。
3. Write：写出调用指定 CAD SDK 的程序。
4. Run：在隔离环境里执行程序，检查是否生成有效实体；几何内核错误也作为反馈。
5. Revise：根据允许获得的诊断修改程序并重试。

下面仅是概念示意，并非项目已经验证过的某个 SDK 的真实 API：

~~~python
width = 60
height = 40
thickness = 8
hole_radius = 5
hole_offset = 12

part = make_box(width, height, thickness)
for x in (-hole_offset, hole_offset):
    part = cut_through_hole(part, center=(x, 0), radius=hole_radius)

export_step(part, "model.step")
~~~

关键点不是代码看起来像 CAD，而是它能否在指定内核中执行、是否形成有效实体、几何是否吻合，以及参数改变后模型是否按预期变化。若 Agent 只是把一个预先存在的 STEP 文件塞进输出，虽然可能复制出正确形状，却没有完成参数化重建；Proposal 因此禁止读取输入网格之外的文件、网络访问或直接嵌入预计算的 STEP/B-rep。

目前公开的 mesh2cad-smoke v0.3.1 包含六个独立 smoke tasks，覆盖 easy、medium、hard 难度，并使用原生 STEP 和冻结多边形参考两种几何表示。这适合验证任务启动、工具链、运行容器与评分流程是否能工作；六个案例不足以单独支撑稳定的研究结论。Proposal 计划进一步扩展到完整编辑任务集。

## CAD SDK 不只是库：它决定 Agent 怎么表达和修复操作

Proposal 计划比较 build123d、CadQuery 和 SimpleCADAPI。公平比较的目标是尽量固定模型、提示、任务、工具预算、运行资源和评分器，只改变 Agent 使用的 CAD 接口。研究问题是接口设计会不会影响生成、执行和修复成功率；现有材料没有证明 SimpleCADAPI 已经优于其他 SDK。

这里一个实际困难是拓扑命名问题（topological naming problem）。模型执行一次布尔运算或改变草图后，内核重新生成的边和面可能换序；脚本若依赖“第 12 条边”这样的索引，下一次运行中第 12 条边可能已不是原来那条。Agent 又常常需要根据失败反复改程序，因此不稳定的对象选择会造成连续的执行错误。

SDK 可以通过几何查询、语义标签、命名参数、参数表达式和结构化诊断，帮助 Agent 以“顶部附近、朝向某方向的边”等性质选择对象，而不只依赖偶然的索引。SimpleCADAPI 在提案中强调这些面向 Agent 的设计，但是否真的减少失败，必须由受控实验验证，不能从接口说明直接推出效果。

提案中的实验分两步：B1–B3 比较三个原版 SDK；B4 再让 Agent 根据训练任务中的运行记录改进 SimpleCADAPI 的文档、Skill、辅助函数、选择器或错误诊断，并在保留任务上评估。这个设计与 RSI 的共同点是“运行—定位失败—修改被测程序或工具—重新评测”；差别在于 RSI 修改几何分割实现，B4 计划修改 Agent 使用的工具环境。若同时换模型、调提示、改 SDK 和训练权重，即使分数上升，也很难知道是哪一项造成的。

## 评分需要拆成实体、几何、参数和成本

Proposal 的评分并非单一“准确率”。第一关是输出必须是有效 solid，而不只是开放曲面。之后检验体积差异门槛：ΔV 不高于 max(10⁻⁶ mm³, 0.001 × V_ref)。仅比较两个实体的总体积并不充分，因为位置不同的实体也可能有相同体积，所以提案还报告对称 Chamfer 距离。

Chamfer 通过两边各取 50,000 个面积加权表面采样点，计算预测表面到参考表面以及参考表面到预测表面的平均距离；配置不做额外对齐，因此摆放方向或位置错误也会反映在结果中。体积门槛与 Chamfer 是不同的检查项：前者是接受条件之一，后者作为几何差异指标单独报告。拓扑、参数可编辑性、工具调用数和 token 成本也应分别呈现，不能压成一个含义不清的准确率。

参数可编辑性可以用干预来测试：选一个具名参数，例如 width，把它从 60 改到 70 后重跑。若主体宽度按预期变化，而孔半径、厚度和对称关系保持不变，才说明参数对模型有清楚、局部的作用；若参数只是摆设，或者脚本背后是硬编码几何，程序可运行不等于模型可编辑。

Agent 与 Verifier 的信息边界同样重要。若生成过程中可以读取完整参考 CAD 或反复查询最终评分器，模型便可能利用答案搜索，而不是根据受损扫描重建。提案把评分器放在独立回放环境中，并限制提交程序读取网格以外文件、使用网络或嵌入参考实体；这类隔离规则是评测可信度的一部分，不是部署细节。

## 相关工作让项目贡献边界更清楚

我最初看到 Proposal 的相关工作描述时，容易把项目概括成“以前没有人从损坏扫描生成 CAD”。查阅论文原文后，这种说法太宽了，需要收窄。

| 工作 | 与项目相邻的部分 | 对本项目定位的提醒 |
| --- | --- | --- |
| [CAD-Recode（2024）](https://arxiv.org/abs/2412.14042) | 从点云生成 Python CAD 程序，研究草图与拉伸等构造序列 | 点云到代码生成已有先例，不应把这一点单独当作新颖性 |
| [CADReasoner（2026）](https://arxiv.org/abs/2603.29847) | 通过多视图与点云反馈迭代编辑可执行 CadQuery 程序，并在训练和评测中使用扫描模拟 | 它已经覆盖受损扫描场景；Proposal 中“相关工作只用干净合成采样”的概括需要修正 |
| [USDCraft（2026）](https://arxiv.org/abs/2610.11322) | 从部分几何证据生成并修订可执行程序，目标扩展到带关节与物理属性的 USD 资产 | 与几何证据、程序修订和仿真资产方向相邻，Real-to-Sim 主张要区分资产范围 |
| [CADGenBench](https://github.com/huggingface/cadgenbench) | 提供工程图生成与既有 STEP 编辑等 CAD 任务 | 是 Proposal 计划借用和扩展的数据任务来源，不等于 Mesh2Code 已完成完整基准 |

因此，目前更稳妥的研究定位是：建立面向损坏几何输入、可执行参数化程序输出的标准化 Agent 评测，并受控比较 CAD SDK 与可迭代改进工具接口的效果。这个定位仍需完整的文献检索和逐项对照，不能只凭几篇论文就宣称已经证明独特性。

同理，Proposal 把 Real-to-Sim 作为应用动机是合理的，但从表面几何恢复出实体，并不自动得到可直接用于机器人仿真的完整资产。机器人还需要关节关系、碰撞几何、质量和惯性等信息；这些属性无法仅从一个外表网格中确定。Proposal 将 articulation 标注及 MJCF/USD 等扩展放在后续阶段，文章也应保留这个边界。

## 我在项目里可以先做什么

我熟悉的部分主要是 LLM Agent、工具调用、Harness、评测和数据流程。相比一开始就重写 RANSAC 或实现大型三维视觉模型，我更适合先把单个任务从输入到评分跑通：Agent 看到了什么、可以调用哪些工具、脚本在哪里运行、失败信息如何返回、验证器实际检查什么。

据此，一个可讨论的切入点是 Benchmark Audit 与 Failure Analysis：检查 Agent 和 Verifier 是否有信息泄漏；整理失败究竟来自几何观测、设计关系推断、SDK 选择、内核执行还是代码修复；再固定模型、提示、预算、容器和评分器，建立 B1–B3 可复现基线。这是根据 Proposal 与我的经验提出的参与建议，不是已经得到组员或导师确认的分工。

对话里提到的约 300 个案例、GLM 轨迹和 Qwen SFT，也暂时只能列为待核实信息。两份项目 PDF 没有给出这些轨迹的确切格式、过滤标准、与 303 个零件数据集的关系，或 SFT 的训练和评测结果；在拿到代码、数据说明或实验日志之前，我不会把它写成已完成成果。

这项研究让我感兴趣的地方，是它把 Agent 的“会不会推理”变成可以逐步检查的工程问题：输入是什么，工具返回什么，程序能否运行，几何结果如何验证。三维几何是新的领域，但它与我做过的 Agent 系统有共同结构：语言模型负责提出和修订操作，外部工具承担精确计算，独立评测负责判断结果。下一步我需要先亲自跑通一个 smoke task，并沿着一条真实轨迹读完 inspect、生成、执行、报错和评分；在此之前，项目分工、完整数据规模及更大实验结果仍保持未确认。
