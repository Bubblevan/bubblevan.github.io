# 一次 Smoke 之后：EviEpoch 的 70.80、坏例定位与 GPT-4o-mini 修复

**记录时间：2026 年 10 月 29 日。** 这篇文章把两个连续的里程碑放在同一条复盘线上：先读官方 Smoke 的能力分数和线上请求记录，再用保存下来的数据在本地复现 Search 失败，最后把定位到的输入解析和证据披露问题修到真实模型请求返回 HTTP 200。

这不是一次“看到低分就改提示词”的经验总结。分数、服务稳定性、记忆检索和证据校验是不同层次的问题。每一项结论都标出它来自官方仪表盘、服务器日志、可重复的本地模型调用，还是仍待验证的推断。

## 先把结论边界说清楚

这次官方 Smoke 显示综合能力分 **70.80**。它说明这次运行的下游评测结果有明显强弱项，但不是 Full，也不是公开榜单成绩。AML 的协议把 Add 和 Search 留给参赛系统，回答生成、评审和分数聚合由平台控制；官方说明也区分 Smoke、Full 与审核发布流程。[官方评测说明](https://agentmemories.ai/evaluation) [Textual API 文档](https://agentmemories.ai/zh-cn/docs) [Leaderboard 仓库](https://github.com/AML-memory/agent-memory-leaderboard)

第二个里程碑是本地重放。我们捕获了 GPT-4o-mini 的 Search 完整请求消息和原始响应对象，并通过真实配置的 OpenAI-compatible endpoint 执行了多轮调用。最后一轮的服务端 Search 返回 200，但这不等于“所有 Smoke 坏例都修好了”，更不等于又跑了一次官方评测。

公开文章不会包含私有评测题目、gold answer、用户完整记忆、原始完整请求体或身份标识。完整模型调用记录保存在本机忽略目录 EviEpoch/logs 下，文章只展示定位问题必需的脱敏结构和长度。这样既能复盘解析器到底遇到了什么，也避免把评测样本和个人记忆写进公开 Git 历史。

## 里程碑一：官方 Smoke 给出的能力画像

### 总分与评测结果

| 项目 | 得分 |
|---|---:|
| 综合能力 | **70.80** |
| A · 显式事实召回 | 80.00 |
| B · 关系与多跳推理 | 100.00 |
| C · 时间与事件序列 | 60.00 |
| D · 记忆治理 | 53.33 |
| E · 个性化与关怀 | 100.00 |
| F1 · 摘要与压缩／长历史全局综合 | 0.00 |
| G · 上下文学习与执行 | 80.00 |
| H · 认识论安全与隐私 | 50.00 |
| I · 流式记忆 | 37.50 |

AML 把不同来源的数据映射到统一能力分类。下面按这次仪表盘实际出现的能力层级展开。分数是观测结果；本地日志中的具体问题则是候选解释。除非有逐题证据链，不把一个能力分数直接归因给某条请求。

### A · 显式事实召回：80.00

显式事实召回问的是：系统能否找回历史中明确说过的事实，而不是根据常识猜一个听起来合理的答案。

#### A1 · 单点事实／属性与来源回忆：66.67

单点属性和来源回忆要求检索到明确值，并能把事实放回正确的人、物或来源上下文。

本地汇总里有一类候选坏例：一个长选项问题，两次 Search 都没有返回证据；同一用户记忆中存在相关原文。这说明至少要继续检查长输入切分、选项词和记忆索引之间是否失配。由于文章不公开题目原文和记忆正文，目前只能称为“候选坏例”，不能据此断言唯一根因。

另一个候选是流式任务编号：对精确编号的查询没有命中，邻近编号查询却返回了另一任务的记忆。这更像标识符检索和相邻任务隔离问题，而不是语言语义能力不足。

#### A2 · 实体、角色、说话人、行动与归因：100.00

这次样本在实体和行动归因上得分很高，说明系统能处理一部分“谁做了什么”的问题。它不意味着实体消歧在所有长对话、多人对话或相似名称下都已解决；100 分在 Smoke 里仍只是当前样本上的结果。

### B · 关系与多跳推理：100.00

这一类看系统能否把散落在多段记忆里的证据连接起来。此次整体得分很高，说明关系聚合是当前版本的相对优势。

#### B1 · 跨片段／跨 session 多证据聚合：100.00

该项关注证据是否分散在不同片段或 session 中，以及 Search 是否把必要前提一并找回。

#### B2 · 因果链、路径与中间步骤恢复：100.00

该项关注的不只是两个实体有关联，还要能恢复路径中的中间步骤或因果链。分数高并不能证明所有长链都稳定，之后仍应通过公开数据集成对复测。

#### B4 · 受控开放域／常识补全：100.00

受控开放域项会考察记忆之外的有限常识能否在有边界的情况下参与推理。AML 的 Add/Search 只负责记忆证据；最终如何把证据和下游模型结合，仍由评测流程控制。对记忆服务来说，不能把“常识上合理”当成对历史事实的替代。

### C · 时间与事件序列：60.00

时间与事件能力要区分事件顺序、相对时间、状态变化和当前有效值。对 EviEpoch 而言，时间锚点是否在写入时保留、查询计划是否识别时间意图、Search 是否给出正确历史证据，都可能影响这类表现。

#### C1 · 日期、相对时间、间隔：46.67

本地候选坏例里出现过相对时间问题：叙述中存在相关经历，但对应查询没有拿到可用证据。潜在检查点包括相对日期归一化、消息时间戳来源、时间区间边界和查询时间锚点。

#### C2 · 事件顺序／阶段排序：40.00

这个分数提示我们不能只检索“相关事件”，还要确认事件顺序有证据支持。当前没有足够逐题材料把低分映射到某一条特定日志，因此先把它列为验证优先级，而不是直接调整全局时间排序。

#### C3 · 事件／立场轨迹变化：100.00

轨迹变化项得分高，说明这次样本对“某个事件或立场前后发生变化”的处理不错。它与 C1、C2 不是同一能力：能识别变化，不代表能精确计算相对日期或恢复完整顺序。

### D · 记忆治理：53.33

记忆治理关注新信息写入后如何保留旧状态、呈现当前状态，以及遇到冲突时是否妥善处理。不能把“新值覆盖”与明确要求隐私删除混为一谈。

#### D1 · 新值覆盖与当前状态：66.67

分数表明当前状态更新仍有空间。下一步应核对同一属性的多次陈述是否保留来源、时间和有效区间，避免简单地按最后写入时间覆盖所有历史。

#### D2 · 矛盾检测与冲突消解：40.00

这项较弱。后续实验要分别测试明确更正、不同时间下的有效值、相互矛盾但都来自用户的陈述，以及证据不足时的保留策略。不能为了提高召回把所有“旧值”都删掉，也不能把普通事实变化解释为隐私删除请求。

### F1 · 摘要与压缩／长历史全局综合：0.00

这是此次最突出的失败信号。它与单个事实召回不同：问题可能要求覆盖长历史中的多个主题、阶段或相互关系。只拿到最相似的一小段，不一定足以回答全局问题。

后续排查应把全局覆盖、证据集完整性和返回预算分开测量：查询计划是否识别 global 意图、候选阶段是否覆盖较早内容、Top-K 是否被近邻证据挤满、最终披露是否把互补片段压成不足的集合。不能单纯扩大所有查询的返回量，否则会把隐私和噪声问题带回来。

### E · 个性化与关怀：100.00

#### E1 · 偏好回忆与个性化遵循：100.00

此次样本中的偏好回忆表现很好，后续仍要验证偏好冲突和跨 session 更新。

#### E2 · 刻板／反刻板偏好鲁棒性：100.00

此分数说明样本中的反刻板偏好问题通过了评估；它不应被理解成所有身份和偏好组合都经过充分覆盖。

#### E3 · 个人背景、健康与心理关怀：100.00

这类能力通常需要同时考虑相关个人背景、语气和隐私边界。出于隐私原因，本文不复述对应评测材料。

### G · 上下文学习与执行：80.00

#### G1 · 领域知识推理：100.00

这次领域知识类表现较好。系统的职责仍是返回相关的历史证据，而不是在 Search 内生成最终答案。

#### G2 · 规则系统应用：20.00

这是显著薄弱点之一。后续应区分规则本身、前置条件、例外和触发条件是否都被 Add 保留，以及 Search 是否能把完整规则组作为互补证据返回。不要只通过重写答案提示词掩盖记忆证据缺失。

#### G4 · 经验数据发现与模拟：100.00

样本上的经验数据发现与模拟表现很好。后续仍要检查数据跨 session 分布时，是否能找全必要记录且不混入相邻任务。

### H · 认识论安全与隐私：50.00

#### H2 · 敏感信息最小披露／隐私：50.00

低于预期的分数不能靠放松证据校验来追。需要区分两类失败：拒绝过度导致该给的证据没给，和披露过度导致返回了不必要的敏感内容。后一类的修复不能是“多返回一点”。

### I · 流式记忆：37.50

#### I1 · 在线学习：35.71

在线学习关注系统在输入逐步到达时能否持续吸收新信息。之前提到的精确任务编号未命中、邻近编号误命中，是这一项值得检查的候选现象，但没有逐题评分链路时不把它等同于某个官方失败样本。

#### I2 · 内部迁移：50.00

内部迁移涉及从已积累的经验或记忆中迁移到后续任务。需要检查任务边界、session 边界、相似实体之间的串扰，以及有效证据是否能跨阶段复用。

### Smoke 分数之外：Add 可用性本身也有问题

服务器日志导出中，原始日志共 338 行；本次分析窗口覆盖 275 条记录。按该窗口的 API 状态统计：

| 路径 | HTTP 结果 | 记录数 |
|---|---:|---:|
| Add | 200 | 134 |
| Search | 200 | 48 |
| Add | 503 | 93 |

重试记录显示，大多数成功请求一次完成；另有一条请求经过 93 次尝试才成功。日志汇总中的一个长请求包含 5,185 个字符，经历 92 次 503 后才返回 200，总耗时约 3 小时 39 分 20.581 秒。这是服务稳定性和重试行为的问题，不能归到检索准确率上，也不能因为最后成功就当成容量已达标。

当时排查还发现没有可用的请求正文统计字段，因而服务器侧的低敏诊断日志适合回答“哪个阶段失败、持续多久、输入大约多长”，不适合替代本地受控数据复盘。日志中出现多少条状态行，也不等于有多少条独立记忆或多少次完整评测任务。

## 里程碑二：用真实模型调用复现 Search 的证据披露失败

### 实验边界和重放方式

本地重放基于代码提交 396dfb34e2ffed81f29016f9fddec2dfaed8c816，使用隔离的 SQLite 数据库和此前保存的一条同用户 Search 查询。Add 输入长度为 6,547 个字符，Add 返回 200，耗时 6.57 秒。第一次搜索的服务返回 503；第二次仍为 503。两次都在证据披露校验阶段失败，服务选择 fail closed，没有把无法验证的引用交给下游。

完整的 Search 模型消息和 SDK 原始响应对象从随后每次调用开始保存为本地 JSONL。第一次成功 Add 内部的模型 I/O 没有被当时的探针捕获，所以这里不假装拥有它的完整生成轨迹；Add 请求正文只留在本机私有审计日志。

### 四轮问题与第五轮通过

| 轮次 | 本轮发现 | HTTP 结果 | 实际操作 |
|---|---|---:|---|
| 初始重放 | Search 在 disclosure 阶段两次失败 | Add 200；Search 503、503 | 打开模型 I/O 探针并确认故障边界 |
| 第 1 轮 | 规划模型把枚举备选项原样输出成一个字符串，解析器无法把它当成单个排序轴 | 503 | 将提示词示例改为单一合法值，并明示枚举选择规则 |
| 第 2 轮 | disclosure 模型把原文中不连续的几段拼成一条长 quote；整条 quote 在来源中不是连续子串 | 503 | 明确要求每条 quote 必须是单段原文连续子串 |
| 第 3 轮 | 模型输出的四段分别为 17、102、77、136 个字符，其中三段末尾多了一个不属于原文的双引号 | 503 | 提示词继续明确禁止把 JSON 外的引号当作引用字符 |
| 第 4 轮 | 同一种末尾多一个引号的问题再次出现；单靠措辞没有消除这个输出缺陷 | 503 | 不再无限加强提示词，改为只对可证明安全的一种格式错误做精确修复 |
| 第 5 轮 | 去掉末尾单个多余引号后，每段都能在已选证据和原始 Add 来源中精确找到 | **200** | 保持严格来源校验，只接受精确子串，不做模糊匹配 |

第一轮的具体规划问题可以用脱敏 JSON 结构表达：

~~~json
{"order_by":"event|first_mention|record"}
~~~

这里的竖线是文档里表示“可选项”的写法，但模型把整段字面量写进 JSON。解析器只接受 event、first_mention、record 之一，因此报出 invalid ordering axis。修复点不是放宽解析器，而是把提示词示例改成单个合法值，并把选项规则写清楚。

第二轮的模型返回了一条约 4,799 字符的拼接 quote。离线定位发现，相关内容在来源中实际分成 2,926、861、1,011 和 1 个字符的精确片段，中间有不应被拼接的缺口。把不连续证据拼成一条 quote 会让来源证明失效；校验器拒绝它是正确行为。

第三轮和第四轮中，模型已经把内容拆成了四条，但其中三条各自多了一个末尾双引号。提示词约束更明确后，错误仍重复出现。这是一次有用的区分：格式约束有帮助，却不能保证模型每次都严格按格式输出。

第五轮的原始输出仍带有三个多余的末尾引号。修复只允许这一种很窄的情形：quote 长度大于 8，末尾是一个未匹配的引号字符；移除这一个字符后，结果必须同时是所选 evidence content 和权威 Add source content 的精确子串。其他情况照常拒绝。

关键逻辑的等价形式如下：

~~~python
if malformed_quote:
    recover_only_if_one_trailing_quote_is_unmatched()
    require_exact_substring_in_selected_evidence_and_source()
else:
    reject_closed()
~~~

这里没有相似度匹配、标点重写、空白归一化或自行补字。返回的仍是原始证据，不在 Search 里生成最终答案。离线审计还确认三处被修复的 quote 在修复后都能精确匹配所选 evidence 与原始来源。

### 代码具体改了什么

代码改动已提交到 EviEpoch 的 codex/reliable-memory-retrieval 分支，提交为 7a841282030f0c0b7b53b723c2a5eef28ce569f4。

- eviepoch/ingest/extraction.py：把规划提示词中的排序轴示例从“多个备选项组成的字面字符串”改为单个合法枚举值，并明确枚举选择规则。
- eviepoch/providers/client.py：要求每条 quote 是来源中的单段、逐字、连续子串；非连续内容必须拆成多条；不允许把引用分隔符引号加进内容。
- eviepoch/retrieval/disclosure.py：对单个末尾多余引号增加精确匹配恢复，且必须同时匹配选中证据与原始来源。其余 malformed quote 继续 fail closed。
- tests/test_memory_improvements.py：添加排序轴解析和末尾引号恢复的回归测试。

### 真实调用、测试和已知限制

第五轮 Search 返回 HTTP 200，耗时 **16.045 秒**，使用 3 次 chat completion 和 1 次 embedding 调用，返回 4 条 evidence，共 402 个字符。此处记录的是一次真实本地模型调用结果，不是 mock。

这轮迭代合计的应用侧计数为 20 次 chat、7 次 embedding、30,789 个输入 token 和 3,810 个输出 token。中转服务没有提供可核验的账单金额，因此本文不编造美元成本。完整单轮请求和响应保存在本机 EviEpoch/logs/disclosure-io-20261029-*.jsonl；初始 Add 的模型级输入输出未捕获，属于记录缺口。

回归验证命令：

~~~powershell
python -m unittest discover -s tests -p test_memory_improvements.py -v
git diff --check
~~~

实际结果是 38 项测试通过，用时 3.97 秒；git diff --check 通过。这些是本地回归测试，不是官方 Smoke 或 Full。

仍未解决或尚未证明的事项：

1. 一条早先保存的精确流式任务编号查询还没有在修复后重新跑，不能据第五轮 Search 200 推断 Streaming 全部恢复。
2. F1、C1/C2、D2、G2 和 H2 的官方得分都没有用这一轮 disclosure 修复重新测量。
3. 修复覆盖的是两个可复现的解析边界问题，不代表 GPT-4o-mini 的所有格式错误都能自动修复。
4. Search 延迟仍包含多个模型阶段。16 秒的一条记录不是并发容量结论。
5. 本轮没有触发官方 Smoke 或 Full，也没有使用私有题目内容做新的官方任务。
