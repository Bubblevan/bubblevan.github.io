## 今日总结
### Stablepay
今天必须把PPT做完。

你可以把一次支付想成一句话：

“**我是 Agent A，我现在要给 Skill B 付 3 USDC，这件事是我自己授权的，而且这条请求不是别人拿旧包重放的。**”

Payment Service 里你提到的那几个词，都是在保护这句话。

**1. 幂等是什么**

幂等就是：

- **同一个支付请求，用户点两次、网络重试两次，系统也只能算一笔。**

最典型场景：
- 客户端点了“支付”
- 服务端其实已经收到了
- 但前端超时，以为没成功，又发一次

如果没有幂等，就会扣两次钱。

你们这里的做法是：
- 客户端带一个 `X-Idempotency-Key`
- 服务端再把 `agent_did + skill_did + client_key` 做一次哈希，变成内部幂等键
- 先查这个键有没有处理过
- 如果处理过，而且请求内容一样，就返回之前结果
- 如果同一个键，但请求内容不一样，就拒绝

- [payment_service.go](D:/MyLab/StablePay/payment-service/internal/application/service/payment_service.go:100)
- [payment_service.go](D:/MyLab/StablePay/payment-service/internal/application/service/payment_service.go:103)
- [payment_service.go](D:/MyLab/StablePay/payment-service/internal/application/service/payment_service.go:321)
- [validator.go](D:/MyLab/StablePay/payment-service/internal/domain/service/validator.go:135)

你可以把它理解成：
- **“这次支付的流水号”**
- 同流水号只认一次

**2. nonce 是什么**

`nonce` 可以理解成：

- **这次请求的“一次性随机编号”**

它的目的不是区分“是不是同一笔业务”，而是区分：

- **这是不是一条别人偷来的旧签名请求**

因为签名这件事有个天然风险：
- 你今天签了一次“给 3 USDC”
- 别人把这整包请求复制下来
- 明天再发一遍

如果系统只看“签名对不对”，那旧包也还是对的，就会被重放。

所以要额外加：
- 时间戳 `timestamp`
- 一次性随机数 `nonce`

然后系统记住这个 nonce 用过没有。  
用过了，再来一次就拒绝。

你们代码里：
- 网关会把 `did + nonce + timestamp + path + method` 组成指纹
- 做 SHA-256
- 写入 nonce store
- 再次出现就视为 replay

所以你可以这样记：

- **幂等：防“同一笔业务被重复处理”**
- **nonce / 防重放：防“旧签名请求被复制重发”**

这两个很像，但不是一回事。

**3. 防重是什么**

你前面说的“防重”，严格讲有两种：

1. **防重复支付**
也就是幂等

1. **防重放攻击**
也就是 nonce + timestamp + 签名

很多人口语里把这俩混着说，所以你会觉得绕。

更准确地说：

- **幂等防的是“业务重复执行”**
- **nonce 防的是“签名包重复利用”**

**4. 组业务签名载荷是什么**

因为签名不能对“空气”签，必须签一个明确字符串。

**那既然 API Gateway 已经验过了，为什么还需要第二次？**

因为这两层职责其实不同。

**网关验签**
验的是：
- 这个 HTTP 请求是不是 DID 持有者发来的
- 请求有没有被改
- 有没有重放

这是“入口安全”。

**Payment Service 再验一次**
更理想的作用是：
- 再确认“支付业务内容本身”的签名是对的
- 防止以后出现绕过网关的内部调用
- 防止多入口接入时只靠网关一处兜底
- 让业务服务本身具备自证能力，而不是完全信任上游

这是“业务安全”。

你可以把它理解成：

- **网关像小区门口保安**
- **Payment Service 像银行柜台**
- 保安查过身份证，不代表银行柜台就该永远不核人

**现在缺这层的实际后果是什么？**

1. **如果所有流量都必须经过 API Gateway**
风险没那么大，因为网关已经拦住大多数非法请求。

2. **如果将来有人内部直调 Payment Service**
那就危险了，因为 Payment Service 自己会“默认签名都对”。

3. **从架构一致性上看**
现在存在“文档和图里说 Payment 调 DID 验签”，但实际代码里没真正生效，会误导答辩和后续维护者。

所以更准确的话是：

- **当前系统的签名安全主要靠 API Gateway 落地；Payment Service 内预留了业务侧验签接口，但尚未真正接 DID RPC，因此这层 defense-in-depth 还没补齐。**

**再把 Blockchain Adapter 重新讲明白，不绕弯**

你上次觉得云里雾里，是因为“签名”其实有两种，必须拆开。

一笔 Solana USDC 转账里，至少有两个重要角色：

1. **谁的钱被转走**
也就是 token owner / authority  
这里是买家

2. **谁付这笔交易的 SOL 手续费**
也就是 fee payer  
这里是平台热钱包

你们设计的精髓就在于：

- **买家授权花自己的 USDC**
- **平台只帮忙付链上 gas**
- **平台不替买家决定花不花钱**

**具体流程是：**

**第一步：客户端本地组交易草稿**
插件会组出一笔 SPL Transfer：
- 从买家 ATA
- 到卖家 ATA
- authority 是买家
- fee payer 是热钱包

见 [tx_builder.ts](D:/MyLab/StablePay/stablepay-openclaw-plugin/src/tx_builder.ts:72)

**第二步：客户端本地先签“交易消息”**
不是签一个随便字符串，而是签：
- `tx.serializeMessage()`

见 [tx_builder.ts](D:/MyLab/StablePay/stablepay-openclaw-plugin/src/tx_builder.ts:103)

这一步的意义是：

- **买家明确授权：这笔链上转账我同意**

然后把买家的签名塞进交易：
- [tx_builder.ts](D:/MyLab/StablePay/stablepay-openclaw-plugin/src/tx_builder.ts:115)

此时得到的是：

- **部分签名交易**
- 买家已签
- 热钱包还没签

**第三步：服务端收到部分签名交易**
Blockchain Adapter 判断：
- 如果 `signed_tx_base64` 存在，说明这是用户已授权的交易
- 就进入 `client_partial_signed` 模式

见 [transfer_cmd_service.go](D:/MyLab/StablePay/blockchain-adapter/app/service/transfer_cmd_service.go:81)

**第四步：热钱包只补 fee payer 签名**
HotWallet 会先检查：
- 交易第一个 account key，也就是 fee payer
- 必须真的是热钱包自己

见 [hotwallet_impl.go](D:/MyLab/StablePay/blockchain-adapter/infrastructure/blockchain/hotwallet_impl.go:82)

然后只对“等于热钱包公钥”的 signer 返回私钥，做 partial sign：
- [hotwallet_impl.go](D:/MyLab/StablePay/blockchain-adapter/infrastructure/blockchain/hotwallet_impl.go:90)

这一步的意义是：

- **平台只同意“我来付手续费”**
- **并没有替买家签“我同意转出 USDC”**

**第五步：把完整签名交易发到 Solana**
见 [transfer_cmd_service.go](D:/MyLab/StablePay/blockchain-adapter/app/service/transfer_cmd_service.go:134)

**一句话总结这套签名机制**
你可以直接背：

- **客户端先用买家钱包对转账消息签名，证明“用户同意花自己的 USDC”；服务端热钱包再只补手续费签名，证明“平台同意代付 gas”。这样用户授权和平台补贴被拆成两把钥匙，既安全又符合业务分工。**

**为什么不能由服务端直接全签？**
因为那就意味着：
- 服务端要么拿到买家私钥
- 要么假装成买家授权

这两件事都不应该发生。

### 你们现在这版是什么

### 更“正规”的 W3C DID 实现一般长什么样

严格的 W3C DID 世界里，核心不是只有一个字符串，而是 **DID Document**。

一个更完整的 DID Document 一般会长成这样：

```json
{
  "id": "did:example:123",
  "controller": "did:example:123",
  "verificationMethod": [
    {
      "id": "did:example:123#key-1",
      "type": "Ed25519VerificationKey2020",
      "controller": "did:example:123",
      "publicKeyMultibase": "z6Mk..."
    }
  ],
  "authentication": [
    "did:example:123#key-1"
  ],
  "assertionMethod": [
    "did:example:123#key-1"
  ],
  "keyAgreement": [
    "did:example:123#key-2"
  ],
  "service": [
    {
      "id": "did:example:123#profile",
      "type": "ProfileService",
      "serviceEndpoint": "https://example.com/profile/123"
    }
  ]
}
```

它通常包含几类东西：

1. **`id`**
DID 本身

2. **`verificationMethod`**
这个 DID 有哪些公钥、各自什么类型、怎么编码

3. **`authentication`**
哪些 key 可以用于“登录/身份认证”

4. **`assertionMethod`**
哪些 key 可以用于“声明/签发”

5. **`keyAgreement`**
哪些 key 用于加密通信

6. **`capabilityInvocation / capabilityDelegation`**
哪些 key 可以调用或委托某种能力

7. **`service`**
这个 DID 还挂了哪些外部服务端点

### 你们轻量版和正规版的根本区别

**你们现在：**
- “这个 DID 对应哪个公钥”
- “这个 DID 现在是不是 active”
- “能不能验证这个签名”

**正规版：**
- “这个 DID 有多少把 key”
- “每把 key 的用途是什么”
- “有没有轮换过”
- “有没有控制者委托”
- “有没有服务发现能力”
- “能不能解析成标准 DID Document 给第三方系统使用”

### 为什么说你们是轻量版

因为你们当前基本没有完整展开：
- `verificationMethod`
- `authentication`
- `assertionMethod`
- `service`
- DID resolution / DID Document 输出

你们现在更像：

- **“用 DID 语法包装 Solana 公钥，并提供状态与验签服务”**

这不是错，反而很务实。  
只是如果你要从 W3C 角度去答辩，必须知道：

- **你们实现的是 DID 的“身份标识 + 验签核心”，不是完整的标准化 DID 文档生态。**

### 那“重量级实现”会多哪些能力

如果往正规方向走，通常会增加：

- **DID Resolution**
输入 `did:solana:xxx`，输出标准 DID Document

- **多密钥支持**
不是只有 1 把公钥，可能有认证 key、支付 key、恢复 key

- **密钥轮换**
旧 key 失效，新 key 接管，但 DID 本身不变

- **服务端点**
比如这个 DID 对应的支付网关、profile、messaging endpoint

- **可验证声明**
比如这个 DID 是否绑定某商家身份、是否通过某种 KYC、是否有某权限

- **委托与 capability**
Agent A 是否被 Owner 委托执行支付

**Payment**

- 轻量版：DID = 公钥身份 + 状态 + 验签
- 正规版：DID = 可解析文档，里面有 key 用途、服务端点、委托和标准语义
