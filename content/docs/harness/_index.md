Harness 不等于“大模型原理合集”。这里记录模型之外的任务运行层：loop、state、tool contract、权限、sandbox、MCP、skills、subagent、重试、日志、人工接管和结果验证。

子页面的内容主要从 [OpenClaw](openclaw/) 开始。Pi、Claude Code、Hermes 和 dsh 目录只有在出现实际调研或实现笔记后再加入入口页。

我原本对 Vibe Coding 工程化的理解，大致可以概括成一套还算朴素的流程：

先写 PRD，明确究竟要解决什么问题；再写 TRD，把数据结构、模块边界和技术路线说明白；然后将工作拆成六到八个规模适中的子任务，一个一个交给 Coding Agent。每完成一项就运行测试、检查 Diff，再根据结果决定下一步。

它至少解决了两个非常常见的问题：一是人自己都没有把需求想清楚，Agent 只能围绕模糊目标自由发挥；二是任务跨度太大，Agent 在一次上下文中同时规划、实现和验证太多东西，做到后面逐渐忘记最初的约束。

所以我认为：所谓 AI-Native 软件工程，主要就是把过去藏在人脑里的需求和技术方案写成更严格的 Spec，再把它们拆成 Agent 可以逐步完成的任务。

但读完 OpenAI 的 [Harness Engineering](https://openai.com/index/harness-engineering/) 以后，我发现这套理解只覆盖了问题的一部分。

PRD、TRD、Spec 和 Exec Plan 主要回答的是：

> Agent 要做什么？什么状态才算完成？应该按照什么顺序推进？

它们并没有自动回答另外一组问题：

* Agent 从哪里找到实现所需的历史决策？
* 如果关键约束只存在于 Slack、Google Docs 或某个人脑中怎么办？
* 修改代码以后，Agent 怎样知道真实应用已经恢复正常？
* 单元测试通过，但 UI 仍然无法操作怎么办？
* “启动速度必须低于 800 ms”这种要求，Agent 到底怎样亲自验证？
* 如果 Agent 每天高速生成大量代码，谁来阻止架构和文档逐渐漂移？
* 当 Agent 反复犯同一种错误时，我们应该继续修改 Prompt，还是改造它所处的环境？

## 一百万行代码不是最重要的东西

OpenAI 在文中称，他们用大约五个月构建了一个内部产品，代码量达到约一百万行，累计合并了约 1500 个 Pull Request。团队最初只有三名工程师，后来增加到七名。更引人注意的是，OpenAI 表示这个项目中没有一行代码由人类直接编写，并估计开发耗时约为传统手工开发方式的十分之一。

“Codex 已经可以写一百万行代码”并不夸张，但 **人类不能在 Agent 卡住时顺手替它把代码补完** 很夸张。

这和我们平时使用 Coding Agent 的方式并不完全相同。

在普通工作流里，Agent 如果连续尝试几次仍然没有修好问题，人类通常会接管：亲自改掉那几行代码，再把结果交还给 Agent。这样做当然很高效，但它也会遮住一个更深层的问题——Agent 为什么会在这里卡住？

可能是模型能力不够，也可能不是。

它可能找不到正确的架构文档；可能看不到真实浏览器中的错误；可能无法查询日志和性能指标；可能不知道某种跨层依赖在这个项目里是被禁止的；也可能完成修改以后，没有任何工具帮助它判断问题是否真的解决。

如果人类每次都直接接管，这些环境缺口就不会被修复。下一次遇到类似任务，Agent 仍然会在相同位置失败。

OpenAI 采用的是另一种处理方式：当 Codex 遇到困难，人类首先检查的不是“我应该替它写哪段代码”，而是“它还缺少什么”。

缺工具，就让 Codex 构建工具；缺文档，就补充可发现的文档；约束只存在于 Review 意见里，就把它变成 Lint 或结构测试；无法判断修改结果，就开放浏览器、日志、指标和 Trace，让它获得真实的运行时反馈。

于是，一次 Agent 失败不再只是某个任务没有完成，也变成了对开发环境的一次诊断：

```text
Agent 在哪里需要人类接管
        ↓
环境中可能缺少什么能力
        ↓
把缺失能力补进代码库或工具链
        ↓
让下一次 Agent 运行可以自行通过
```

从这个角度看，如果人类不能用亲自写代码掩盖 Agent 的失败，那么团队就不得不持续改造 Agent 工作所依赖的环境。

当然，OpenAI 给出的规模、效率和“零人工代码”都是这篇内部实践文章的自述，不能直接当成经过独立验证的行业基准。这套结果显然依赖 OpenAI 当时使用的模型、基础设施、测试体系、应用形态和团队经验。原文自己也明确提醒，这种端到端行为高度依赖该代码库的具体结构和工具，不能假设它会自然泛化到其他项目。

但它确实提供了一个很有意思的观察窗口：

> 当代码生成不再是整个流程中最稀缺的环节，人类工程师的主要工作对象会转移到哪里？

## 人类没有退出软件工程

如果只看到“代码全部由 Codex 生成”，很容易顺着它想象出一种极端分工：

```text
人类负责提需求
Agent 负责完成其他一切
```

但从 OpenAI 的描述看，人类工程师的职责远不只是提交一个 Prompt，然后等待产品自动出现。

他们仍然要决定：

* 哪些用户问题更值得优先处理；
* 怎样把模糊反馈转化为可以验证的验收标准；
* 哪些结果虽然测试通过，却不符合产品意图；
* 什么架构边界必须长期维持；
* 哪些 Review 意见值得升级为全局规则；
* 哪些失败应该通过补工具解决；
* 哪些判断不能自动化，需要重新交给人。

变化并不是人类停止了软件工程，而是工作的抽象层次上移了。

过去，一位工程师发现某个接口的输入结构经常被误用，可能会在这次 Code Review 里指出问题，再亲自改正实现。下一次另一个人犯错时，再提醒一次。

在 Agent-first 的代码库里，更有杠杆的做法是继续向上追问：

1. 这个输入结构能不能在系统边界处直接解析？
2. 能不能用 Schema 让错误输入无法悄悄进入内部？
3. 能不能写一条静态检查，禁止 Agent 继续猜测数据形状？
4. 检查失败以后，错误信息能不能直接告诉 Agent 应该如何修复？
5. 这条规则的原因是否需要进入架构文档？

人类的一次判断由此不再只修复一处代码，而是有机会进入整个系统的反馈机制，持续作用于后续的每一次 Agent 运行。

这也是我认为 Harness Engineering 最值得注意的变化：

> 人类工程师不只是验收 Agent 生成的结果，也开始设计能够持续塑造这些结果的环境。

当然，这并不意味着每一条 Review 意见都应该变成 Lint，也不意味着人的判断可以被完全编码。

有些东西天然适合机械执行，例如模块依赖方向、Schema 边界、结构化日志格式和文件大小限制。有些东西则仍然需要人在具体语境中判断，例如产品取舍、交互感受、架构迁移的成本，以及多个正确方案之间哪个更值得长期投入。

真正的变化不是“判断消失了”，而是团队开始区分：

* 哪些判断应该由人持续保留；
* 哪些判断已经足够稳定，可以被编码成系统不变量；
* 哪些失败不是本次实现偶然出错，而是环境仍然缺少支撑。

## Harness Engineering 到底是什么

“Harness”直译过来可以是马具、安全带或者线束。放在 Agent 系统中，可以把它理解成模型外部的一整套支撑和控制结构。

不过，如果只把 Harness 理解成“给模型挂上几个工具”，仍然有些狭窄。

一个 Agent 可以拥有 Shell、浏览器、代码搜索、Git 和数据库权限，但工具只解决了“可以执行哪些动作”。它没有保证 Agent：

* 知道什么时候应该使用哪个工具；
* 能找到与当前任务相关的知识；
* 能观察动作造成的真实结果；
* 能判断结果是否违反项目边界；
* 失败以后知道应该重试、回滚还是寻求人类判断；
* 长期运行时不会不断放大代码库里的坏模式。

因此，我更愿意给它一个工作性的定义：

> **Harness Engineering 是对 Agent 工作环境的设计：让它能够找到正确知识、执行真实动作、观察动作结果、受到稳定约束，并根据反馈继续修正。**

这个定义可以进一步压缩成五个动词：

| 动作 | 它解决的问题                            |
| -- | --------------------------------- |
| 找到 | Agent 是否知道应该去哪里获得可信知识？            |
| 行动 | Agent 是否能启动应用、修改代码并操作真实环境？        |
| 观察 | Agent 是否能看到 UI、日志、指标和 Trace？      |
| 约束 | Agent 是否会被架构边界、Schema、Lint 和测试限制？ |
| 修正 | 失败后能否重新定位、修改、重启并验证？               |

这五个动作共同组成一个闭环：

![智能体工程闭环的五个动作](/images/harness-five-action-loop.png)

如果只有“找到”，它会变成一套更复杂的知识库。

如果只有“行动”，Agent 可能只是更快地执行错误操作。

如果只有“测试”，它又可能只会围绕有限的断言进行局部优化。

如果缺少恢复过程，任何一次环境异常都需要人类重新接管。

Harness 真正有价值的地方，是把这些能力连接起来，让 Agent 不再只经历：

```text
读取需求 → 生成代码
```

而是经历：

```text
读取需求与仓库知识
→ 修改
→ 启动真实系统
→ 执行用户路径
→ 查询运行信号
→ 根据约束判断
→ 失败后继续修改
→ 将结果和决策留在仓库
```

这也解释了为什么 OpenAI 的文章花了大量篇幅讨论看起来并不像“模型能力”的东西：

* 为什么 Codex 需要独立的 Worktree；
* 为什么它需要操作 Chrome DevTools；
* 为什么日志、指标和 Trace 应该能被 Agent 查询；
* 为什么巨大的 `AGENTS.md` 反而会失败；
* 为什么知识必须进入代码仓库；
* 为什么架构依赖需要由自定义 Lint 执行；
* 为什么高速生成以后还要持续进行垃圾回收。

这些东西没有直接让基础模型变聪明。

它们做的是另一件事：减少模型必须依靠猜测才能继续工作的地方，并让错误更早、更明确地反馈回来。

所以，与其把 Harness Engineering 理解成一种新的 Agent 框架，我更愿意把它看作一个环境问题：

**如果今天真的规定“人类不能亲自下场补代码”，为了让 Agent 仍然能够长期维护一个真实软件，代码库周围还缺什么？**

### 先让 Codex 看得见软件

前面把 Harness Engineering 压缩成了五个动作：找到、行动、观察、约束和修正。

其中最容易被忽略的，其实是“观察”。

我们平时使用 Coding Agent，经常会看到一种颇为熟悉的完成报告：

> 已经修改相关实现，并补充测试。
> 所有测试均已通过。
> 该问题现已解决。

它听起来很完整：代码改了，测试跑了，结果也是绿色的。但如果任务涉及一个真实运行的软件，这些信息仍然不足以证明用户遇到的问题已经消失。

一次前端修改完全可能出现以下情况：

* TypeScript 编译通过，但按钮实际上无法点击；
* 组件单测通过，但真实页面的导航路径已经断裂；
* DOM 结构看起来正确，浏览器控制台却持续报错；
* API 返回成功，但界面状态没有重新渲染；
* 某个 Modal 可以打开，却无法通过键盘或关闭按钮退出；
* 页面截图没有明显异常，但执行一次交互以后状态就错了。

这些错误并不一定说明测试没有价值。更准确地说，是代码层面的验证与用户实际经历的软件之间仍然隔着一段距离。

人类工程师通常会自然地补完这段距离：启动应用、打开浏览器、进入目标页面、点击几次，再观察结果是否符合预期。因为这套动作过于自然，我们甚至不会把它单独当成开发基础设施的一部分。

但 Agent 不会自动拥有这种能力。

如果它只能看到源代码、测试输出和终端，那么“我已经修改文件”就是它最容易确认的状态；至于“用户问题已经解决”，则存在于它无法直接观察的运行环境中。

于是，Agent 很容易把前者误当成后者。

这也是 Harness Engineering 与单纯代码生成拉开差距的地方：不仅要让 Agent 有能力修改软件，也要让它能够接触修改后的软件。

#### Browser 工具的重点不是“会点击网页”

OpenAI 为 Codex 提供了操作 Chrome DevTools 的能力，让它可以启动应用、定位页面、操作 UI、读取 DOM、保存截图，并检查浏览器运行期间产生的事件。

单独看这些功能，很容易把它归入 Browser Agent 或 RPA：

> 以前是人点击浏览器，现在让 Agent 代替人点击。

但 OpenAI 图中真正值得注意的不是 Codex 会不会点击，而是这些动作被组织成了一套重复执行的验证流程。

![Codex 通过 Chrome DevTools 验证修改结果](/images/harness-chrome-devtools-validation.png)

首先，Codex 选择目标页面并清空控制台，避免之前积累的错误信息干扰这一次验证。随后，它记录修改前的页面状态，再执行需要验证的用户操作路径。

在交互过程中，应用产生的运行时事件也会被记录。操作完成后，Codex 再保存一次页面状态，将修改前后的结果进行比较。

如果结果不符合预期，它会继续修改代码、重新启动应用，然后重跑相同的验证过程。

整套流程可以概括为：

```text
定位目标页面
→ 清理旧状态
→ 保存修改前快照
→ 执行用户路径
→ 收集运行时事件
→ 保存修改后快照
→ 应用修复并重启
→ 重新运行同一套验证
```

这里最关键的是最后一步。

如果 Agent 每次修改以后只随机操作几下页面，那么它获得的不过是一次新的观察。只有当它能够重放同一条用户路径，并用相同标准重新检查结果时，修改前后的状态才具有可比性。

也就是说，Browser 工具在这里不是一个孤立的“网页操作能力”，而是软件验证回路的一部分：

> **修改代码只是中间动作。Agent 还必须重新进入发生问题的环境，重放问题，并证明这一次结果发生了改变。**

这与传统自动化测试的方向并不冲突。

区别在于，测试通常需要人类提前把输入和断言编码下来；而有了浏览器工具以后，Agent 还可以处理一部分尚未沉淀成稳定测试、却能通过真实用户路径复现的问题。

例如，一条 Bug 报告可能只写着：

> 修改设置后返回首页，再次进入设置页面，刚才的选项没有保存。

Agent 可以先通过浏览器复现这条路径，观察请求、页面状态和控制台事件，然后再决定问题应该在哪一层修复。修改后，它重新执行完全相同的路径，检查状态是否保留。

如果这类问题足够稳定且足够重要，最终仍然应该补成自动化测试。Browser 验证并不是用来代替测试，而是帮助 Agent 打通从模糊故障报告到可重复验证之间的距离。

我原先会把“Agent 操作浏览器”主要理解成另一条技术路线：Browser Agent 负责搜索、填写表单或者执行办公 RPA；Coding Agent 则负责修改代码。

OpenAI 这里给出的连接方式更有意思：

> 浏览器并不一定是 Coding Agent 之外的另一个应用场景，它也可以成为 Coding Agent 的眼睛。

不过，浏览器主要暴露的是软件的外部行为。很多问题即使最终表现在 UI 上，其原因也藏在服务内部。

页面没有更新，可能是前端状态错误；可能是接口返回了旧数据；也可能是请求已经失败，只是错误没有显示在页面上。

要让 Agent 继续向内部定位，就需要另一组传感器。

#### Logs、Metrics 和 Traces 也可以直接给 Agent 看

Logs、Metrics 和 Traces 原本就是现代软件工程中常见的可观测性基础设施。

它们分别从不同角度描述系统：

| 信号      | 主要回答的问题               |
| ------- | --------------------- |
| Logs    | 发生了什么事件？输入、错误和上下文是什么？ |
| Metrics | 某项行为发生了多少次，延迟和错误率怎样？  |
| Traces  | 一次请求经过了哪些组件，时间消耗在哪里？  |

过去，我们通常会说这些数据是“给开发者和 SRE 排查问题用的”。

OpenAI 做的事情，是把它们也变成 Codex 可以主动查询的环境接口。

![向 Codex 开放完整的可观测性栈](/images/harness-observability-stack.png)

在这张图中，应用会产生 HTTP 日志、OTLP 指标和 OTLP Trace。这些信号通过本地 Vector 进行分发，分别进入日志、指标和链路追踪服务。

Codex 随后可以通过 LogQL、PromQL 和 TraceQL 查询这些数据，进行关联和推理。

这里不必过度关注 VictoriaLogs、VictoriaMetrics 或某一种查询语言。它们是 OpenAI 在这个项目中选择的实现载体，不是 Harness Engineering 的必要定义。

真正重要的结构是：

```text
应用产生运行信号
        ↓
信号进入可查询的观测系统
        ↓
Codex 主动查询、关联并推理
        ↓
修改代码并重启应用
        ↓
重新执行 workload
        ↓
再次查询信号
```

Agent 因此不再只能通过测试输出猜测系统内部发生了什么。

假设一个页面加载缓慢，单看 UI，Codex 只能确认“这个页面似乎比较慢”。有了 Trace，它可以继续观察：

* 时间主要消耗在浏览器、API 还是数据库；
* 是每个请求都慢，还是某一条路径偶发变慢；
* 同一个操作是否触发了重复请求；
* 哪个 Span 占据了主要延迟；
* 修改以后瓶颈是否真的消失。

如果问题表现为错误率升高，它可以查询 Metric；如果某一条请求失败，则继续从 Trace 找到相关日志；如果日志显示数据形状异常，再返回代码和 Schema 检查边界。

这使得 Agent 的工作方式开始接近一个真正排查软件故障的工程师，而不只是围绕报错文本生成补丁。

因此，我现在更愿意把 Observability 理解成 Agent 的环境传感器。

浏览器告诉它用户看到了什么，日志告诉它系统记录了什么，指标告诉它整体行为怎样变化，Trace 则帮助它把一次用户操作与内部执行路径连接起来。

这些信息共同缩短了“修改代码”与“判断修改是否成立”之间的距离。

#### Spec 中的要求，怎样变成 Agent 可以验证的事实

这也让 Harness Engineering 与前面的 SDD 重新连接起来。

假设 TRD 或验收标准中写着：

> 应用必须快速启动。

这句话表达了一个正确方向，却没有告诉 Agent 什么叫“快速”。

稍微进一步，可以把它改成：

> 本地开发环境的冷启动时间不得超过 800 ms。

现在目标已经可测量，但 Agent 仍然需要知道：

* 如何启动应用；
* 从哪个时间点开始计算；
* 哪个指标代表启动完成；
* 在什么机器和配置下测试；
* 应该查询哪一个 Metric；
* 测量需要重复几次；
* 偶发超时应该怎样处理。

只有当这些条件被连接到真实运行信号时，验收标准才进入完整闭环：

```text
Spec 中的自然语言目标
        ↓
被定义为可测量的运行时信号
        ↓
Agent 执行统一 workload
        ↓
查询结果并与阈值比较
        ↓
未通过则修改并重新验证
```

这里有一个很容易忽略的差别。

在普通 SDD 流程里，我们可能已经把“启动时间低于 800 ms”写进验收条件。Agent 实现结束以后，也可能在总结中声称自己完成了性能优化。

但如果环境没有提供统一的启动命令、指标定义和查询入口，它就未必真正测量过这个结果。验收标准虽然存在，却仍然只是上下文中的一句自然语言。

因此，Spec 与 Harness 并不是两种竞争方法。

Spec 负责把“快速”变成“低于 800 ms”；Harness 再负责让 Agent 能够启动服务、产生 Metric、读取结果，并在失败以后继续修改。

可以将它们的关系写成：

```text
Spec：什么结果才算正确
Harness：怎样让 Agent 亲自获得关于结果的证据
```

这也是我在读这部分时产生的一个认识变化。

以前我会把验收标准写得是否明确，当成 Agent 能否完成任务的主要决定因素。现在看来，明确只是第一步。

> **如果验收标准没有对应到 Agent 可以访问的环境信号，它仍然可能是一条无法自行核实的要求。**

#### 闭环不等于消除了人的判断

不过，给 Codex 浏览器和完整可观测性栈，并不意味着软件质量已经能够被完全自动验证。

首先，Agent 能验证什么，仍然取决于我们向环境中暴露了什么。

如果测试路径没有覆盖真正的失败条件，Agent 即使完整重跑，也只能证明那条有限路径通过了。错误可能藏在不同权限、不同数据规模或不同浏览器状态下。

其次，能够测量不等于指标本身正确。

把“启动速度低于 800 ms”写成 Metric 很容易，但如果用户真正关心的是首次可交互时间，而我们测量的是进程完成初始化的时间，Agent 完全可能把错误指标优化得很好。

类似的问题还包括：

* 截图相似不代表交互体验正确；
* 没有控制台错误不代表产品行为符合预期；
* 平均延迟达标可能掩盖严重的尾部延迟；
* UI path 通过不代表无障碍体验合格；
* 测试环境稳定不代表生产环境不会失败；
* Agent 可能针对现有断言局部优化，而没有解决根本问题。

即使 Agent 可以读取截图，它也很难仅凭像素判断一个页面是否真正“好用”。布局可能没有破损，但信息层级依然混乱；按钮确实能点击，但交互过程仍然令人困惑。

这些仍然涉及产品感觉、审美和具体语境中的判断。

因此，Harness Engineering 的目标不应被理解成“把所有质量判断自动化”。

更准确的说法是：

> 它扩大了 Agent 能够自行获得证据、自行发现错误和自行完成验证的范围，从而减少那些原本只是因为工具缺失而必须交给人的工作。

人在这里并没有消失。

人仍然需要决定：

* 哪些用户路径最值得验证；
* 什么指标真正对应产品目标；
* 哪种失败风险不可接受；
* 什么结果虽然测试通过，却仍然不够好；
* 什么时候继续自动修正已经不再划算；
* 什么时候问题涉及新的产品或架构判断，应当停止并升级。

OpenAI 的 Harness 不是通过取消人类判断来提高自治水平，而是尽量把那些已经可以明确表达和重复执行的判断接入反馈循环，只在真正需要判断的地方再交还给人。

让 Codex 看得见软件，解决的是“修改以后发生了什么”。

接下来还有另一个同样重要的问题：

> 在修改之前，Codex 怎样知道这个项目为什么会被设计成现在这样？

浏览器、日志和 Trace 可以告诉它系统正在做什么，却不能自动告诉它团队三个月前为什么否决另一种架构，也不能告诉它某项安全约束究竟来自哪里。

要回答这些问题，还需要让 Codex 找得到知识。

### 再让 Codex 找得到知识

浏览器、日志、指标和 Trace 解决的是一个运行时问题：

> Agent 修改代码以后，怎样知道真实软件发生了什么？

但它们无法自动回答另一个问题：

> Agent 修改代码以前，怎样知道这个项目为什么被设计成现在这样？

假设 Codex 在仓库里看到两种都能工作的实现方式。第一种更短、更符合它从公共代码中学到的常见写法；第二种看起来稍微繁琐，却是团队为了安全边界、兼容性或者未来迁移而刻意选择的方案。

如果这个取舍只存在于三个月前的一次 Slack 讨论里，Agent 很可能会选择第一种。

从当前代码看，它的实现甚至可能完全合理。只有经历过那次讨论的人才知道：这恰好重新引入了团队曾经解决过的问题。

面对这种失败，我们很容易得出一个直觉性的结论：

> Agent 缠在这里，是因为它获得的上下文还不够多。

然后开始不断扩充 `AGENTS.md`：

* 增加项目背景；
* 增加编码规范；
* 增加目录说明；
* 增加历史决策；
* 增加常见错误；
* 增加依赖库的使用方式；
* 增加测试和部署流程；
* 增加每个模块的特殊规则。

起初，这种做法往往确实有效。Agent 之前不知道的约束被补进上下文，下一次便可能不再犯相同错误。

但随着文件越来越大，一种新的失败模式开始出现：信息都在那里，Agent 却不一定能正确使用。

#### 更大的 `AGENTS.md` 为什么会失败

OpenAI 也经历过这个阶段。

他们最初试图把越来越多的项目知识集中写进一个庞大的 `AGENTS.md`，希望 Codex 开始工作时能够一次性掌握整个仓库。

这听上去很合理。既然 Agent 只能依据上下文推理，那么给它更多上下文似乎总比给得更少好。

但原文最终总结了四类问题。

第一，**它会持续消耗有限的上下文预算**。

一个大型入口文件会在每次任务开始时占据大量 Token，无论当前任务是否真的需要其中的全部信息。修复一个前端按钮，可能同时加载数据库迁移规范、后端遥测约定和发布流程。

这些内容本身没有错，只是和当前任务无关。

上下文窗口即使越来越大，也不意味着可以不考虑信息密度。Agent 仍然要在大量文字中分辨哪些内容与当前修改直接相关。无关规则越多，真正关键的约束越可能被淹没。

第二，**当所有内容都被标记为重要时，实际上就没有明确的优先级了**。

一个庞大的 `AGENTS.md` 往往由许多局部经验逐渐堆积而成：

> 遇到 A 时必须这样做。
> 修改 B 时需要特别注意。
> 过去 C 曾经引发问题。
> 所有实现都应遵循 D。
> 除非出现 E，此时应该采用另一种方式。

每条规则单独看都可能合理。但当它们在同一个平面上同时出现，Agent 就需要自己判断：

* 哪条规则适用于当前模块；
* 哪条只是历史背景；
* 哪条规则优先级更高；
* 两条建议冲突时应当相信谁；
* 某个例外是否仍然有效。

此时，更多指导不一定产生更强的导航能力。Agent 可能退化成局部模式匹配：在庞杂文本中找到几个与当前任务措辞相近的段落，然后围绕它们展开实现。

第三，**大文档会悄悄腐烂**。

代码已经完成重构，文档仍然描述旧目录；依赖库升级了，使用示例还停留在旧版本；临时迁移规则早已失效，却没有人记得删除。

最危险的不是明显缺失的文档，而是一份看起来完整、实际上已经过时的文档。

缺少信息时，Agent 至少可能继续搜索或提出疑问。面对一条措辞明确但已经失效的规则，它反而更容易充满信心地走向错误方向。

第四，**单一大文档很难进行机械检查**。

谁负责维护其中哪一部分？哪条规则最后一次核实是什么时候？它是否链接到对应的设计决策？文中提到的模块和命令是否仍然存在？哪些内容已经被新的规范取代？

当所有知识挤在一个 Blob 里，这些问题很难自动回答。

最终，`AGENTS.md` 会逐渐变成一座规则坟场：每当 Agent 犯错，就往里面再加一条提醒；但很少有人重新判断旧规则是否仍然必要，以及这些规则是否应该转移到更合适的载体中。

这让我重新理解了所谓“上下文不足”。

Agent 出错当然可能是因为缺少信息，但还有另一种情况：

> 信息已经存在，只是没有被组织成它能够在正确时机发现、判断和验证的结构。

所以 OpenAI 的解决办法不是继续扩大入口文件，而是重新定义它的职责。

#### `AGENTS.md` 应该是一张地图，而不是百科全书

OpenAI 后来把 `AGENTS.md` 收缩到大约一百行。

这并不意味着项目知识减少了。恰恰相反，更多知识被写进了仓库，只是不再被强制塞进每一次 Agent 运行的初始上下文。

`AGENTS.md` 开始承担一种更接近“内容目录”的作用：

* 这个代码库解决什么问题；
* 最关键的不变量是什么；
* 顶层架构文档在哪里；
* 产品规范放在哪里；
* 当前执行计划应该去哪里寻找；
* 修改以后运行哪些验证命令；
* 遇到安全、前端或可靠性问题时继续阅读什么；
* 哪些内容由程序自动生成，不能手工修改；
* 哪些目录或文件存在特殊限制。

更详细的知识则进入结构化的 `docs/`：

```text
AGENTS.md
ARCHITECTURE.md
docs/
├── design-docs/
│   ├── index.md
│   ├── core-beliefs.md
│   └── ...
├── exec-plans/
│   ├── active/
│   ├── completed/
│   └── tech-debt-tracker.md
├── generated/
│   └── db-schema.md
├── product-specs/
│   ├── index.md
│   ├── new-user-onboarding.md
│   └── ...
├── references/
│   ├── design-system-reference-llms.txt
│   ├── nixpacks-llms.txt
│   └── uv-llms.txt
├── DESIGN.md
├── FRONTEND.md
├── PLANS.md
├── PRODUCT_SENSE.md
├── QUALITY_SCORE.md
├── RELIABILITY.md
└── SECURITY.md
```

这样一来，Agent 开始工作时不必一次读完整个知识库。

它只需要先获得一张稳定的地图，然后根据任务逐层深入：

```text
当前要修改用户注册流程
        ↓
从 AGENTS.md 找到产品规范入口
        ↓
读取 new-user-onboarding.md
        ↓
根据索引找到相关设计决策
        ↓
查看当前活跃的执行计划
        ↓
只加载与本次任务有关的约束
```

这套结构的价值并不只是节约 Token。

更重要的是，它把“所有规则平铺在一起”改造成了“知识拥有明确位置和进入路径”。

架构问题去 `ARCHITECTURE.md` 或设计文档中寻找；产品行为以产品规范为准；进行中的复杂工作记录在活跃执行计划里；已经完成的计划被归档，保留当时的决策历史；数据库结构等可再生成事实，则由工具更新，而不是依赖人手维护。

因此，`AGENTS.md` 不再试图回答 Agent 可能提出的所有问题。

它只负责回答一个更重要的问题：

> **遇到这种问题，下一步应该去哪里看？**

如果只能从 OpenAI 这篇文章里先抄一个设计，我现在反而最想先抄这个。

不是为自己的项目建立一座越来越复杂的 Agent 宪法，而是先检查入口文件中哪些内容是真正的全局规则，哪些内容应该被移动到按需读取的知识层。

好的 `AGENTS.md` 不应该让 Agent 一次性理解整个项目，而应该让它不容易在项目里迷路。

#### 渐进式披露不等于“多建几个文件夹”

OpenAI 将这种方式称为 Progressive Disclosure，也就是渐进式披露。

但这个概念很容易被形式化地理解成：

> 不要写一个大文件，拆成很多小文件就好了。

如果只是机械地把五千行 `AGENTS.md` 切成五十个 Markdown 文件，问题并没有真正解决。

过去 Agent 面对的是一份无法区分优先级的大文档；现在它面对的可能是五十个命名含糊、互相重复、彼此矛盾的小文档。

它仍然不知道应该先看哪一份，也不知道冲突时谁才是真实来源。

真正的渐进式披露至少需要建立三种关系。

第一种是**任务与知识入口之间的关系**。

例如：

| 当前任务   | 首要知识入口                    |
| ------ | ------------------------- |
| 修改领域模型 | `ARCHITECTURE.md` 与对应设计文档 |
| 调整产品行为 | 对应 `product-specs/`       |
| 继续复杂任务 | `exec-plans/active/`      |
| 修改数据库  | 自动生成的 Schema 与迁移规范        |
| 处理安全问题 | `SECURITY.md`             |
| 修改前端交互 | `FRONTEND.md` 与设计系统参考     |

这不是要求 Agent 死板地按表执行，而是提供一个可靠的搜索起点。

第二种是**不同知识来源之间的优先关系**。

如果产品规范和旧执行计划发生冲突，应该相信谁？如果生成的数据库 Schema 与手写文档不一致，哪个才是事实？已经完成的历史计划能否覆盖当前架构？

没有这些规则，结构化文档仍然可能成为另一种信息迷宫。

通常可以明确：

* 代码和自动生成事实描述当前状态；
* 已批准的产品规范定义目标行为；
* 活跃计划描述正在发生的变更；
* 已完成计划主要用于解释历史决策；
* 设计文档描述长期架构意图；
* 入口文档只负责导航，不重复覆盖各处内容。

第三种是**知识与验证方式之间的关系**。

一份文档不仅要说“系统应该怎样”，还应尽量说明：

* 这项结论最后一次何时核实；
* 哪个模块实现了它；
* 用什么测试或命令验证；
* 哪些情况会使该文档失效；
* 谁或什么流程负责更新它。

如果缺少这些关系，“渐进式披露”就容易退化成单纯的文件整理。

所以，它真正解决的不是文件长度，而是上下文路由：

> Agent 不需要同时知道所有内容，但必须知道当前需要什么、从哪里获得，以及怎样判断它仍然可信。

这和我在 Hi-Agent 里学习的 Context Budget、Selector、Compiler 其实可以接上。

当时关注的是一次模型调用中，哪些 `ContextItem` 应当被选择、哪些可以丢弃，以及如何在 Token Budget 中保留 Required 内容。那仍然主要发生在运行时 Context Pipeline 内部。

OpenAI 这里则把同一个问题向外扩展到了整个仓库：

```text
运行时 Context Engineering
解决“一次调用应该装入哪些内容”

Repository Knowledge Design
解决“这些内容平时存在哪里、怎样被发现、如何保持可信”
```

两者并不是同一个层面，却共享同一种思想：不要把所有内容无差别塞给模型，而要设计明确的选择、优先级和丢弃机制。

不过，要让 Agent 真正找到正确知识，还有一个更现实的前提——这些知识首先必须处于它能看到的地方。

#### Codex 看不见的东西，就像不存在一样

OpenAI 原文中有一张我认为非常值得留下来的图。

![Codex 无法访问的知识无法参与运行时推理](/images/harness-limits-of-agent-knowledge.png)

图的下方列出了三类常见的组织知识：

* Google Docs 中的产品优先级与规划；
* Slack 消息中达成的安全共识；
* 某位工程师掌握的隐性架构方向。

对人类团队而言，这些知识当然存在。

参与过讨论的人记得为什么做出某个选择；新员工遇到问题，可以在 Slack 里搜索，或者直接询问那位负责架构的同事。

但对一次运行中的 Codex 来说，事情没有这么自然。

如果它只能访问当前代码仓库，那么 Google Docs、Slack 历史和人脑中的判断都处在它的上下文边界之外。它既不知道这些内容存在，也不知道应该停下来向谁提问。

于是就会出现一种很有迷惑性的错误：

Agent 并不是无视了架构决策，而是这个决策从未进入它可以访问的世界。

假设团队曾经在 Slack 里达成共识：

> 出于审计要求，所有外部数据在进入业务层以前都必须经过显式 Schema 解析，不能在内部依赖动态字段探测。

三个月以后，Codex 为一个新接口编写实现。代码库中恰好还残留着几个旧的动态探测例子，而安全共识没有进入仓库。

从 Agent 能看到的证据出发，模仿现有代码是一个很自然的选择。人类 Review 时却会认为：

> 我们不是早就明确禁止这样写了吗？

问题在于，“我们早就明确过”和“Agent 能发现这项决定”完全是两件事。

OpenAI 因此提出了一个听起来很绝对、实际上很务实的原则：

> 从 Codex 的角度看，它在运行时无法访问的内容就不存在。

这并不是一个关于哲学意义上“知识是否存在”的判断，而是关于工程可用性的判断。

一项决策如果要持续影响未来的 Agent 修改，就必须被编码成 Agent 可以访问的工件，例如：

* Markdown 设计文档；
* 产品规范；
* Schema；
* 类型定义；
* 执行计划；
* 测试；
* Lint；
* 可生成的参考资料。

这里最值得注意的词不是 Markdown，而是 Repository-local 和 Versioned。

知识进入仓库以后，才能与代码一起获得：

* 版本历史；
* 修改记录；
* 所有权；
* Review；
* 交叉链接；
* 自动检查；
* 与实现同步演化的可能性。

那场让团队统一架构方向的 Slack 讨论，如果最后没有留下可发现的决策记录，对三个月后运行的 Agent 来说，就像一场从未发生过的会议。

这也解释了为什么单靠更强的代码搜索无法完全解决问题。

Agent 可以非常擅长阅读仓库，但它不可能从代码中可靠恢复所有设计原因。同一种实现可能来自安全要求、历史兼容、临时迁移，也可能只是某位工程师当时随手写的。

代码能告诉 Agent“现在是什么”，却不总能告诉它“为什么必须这样”。

因此，Repository as System of Record 的意义，是让那些需要持续影响未来实现的知识拥有正式、可访问的位置。

但这马上会引出一个反方向的问题：

> 难道以后每条 Slack 消息、每次会议和每份 Google Docs 都要复制进代码仓库吗？

显然不是。

#### 应该进入仓库的是决策，不是全部聊天记录

如果将“Codex 看不见的东西就不存在”理解成“把组织中的所有信息都导入仓库”，很快会重新制造一座更大的信息垃圾场。

一次设计讨论中可能包含：

* 最初的模糊设想；
* 已经被否决的路线；
* 对问题的重复澄清；
* 临时假设；
* 与最终决策无关的分支；
* 已经过期的时间安排；
* 参与者基于不完整信息作出的意见；
* 最终结论和成立条件。

真正需要持续影响未来实现的，通常不是完整对话，而是经过整理的决策工件。

例如，一场长达两小时的架构讨论，最后可以沉淀成一份简短的 ADR 或设计文档：

```markdown
# 决策：所有外部输入在边界处解析

## 当前状态
Accepted

## 背景
多个上游接口的数据结构不稳定，内部动态探测造成静默错误。

## 决策
所有外部输入必须先经过显式 Schema 解析，再进入业务层。

## 被否决的方案
在各个调用点使用可选字段和默认值兜底。

## 原因
这种方式会把数据不一致扩散到内部，且难以观察。

## 验证
对应结构测试与 Schema 测试必须通过。

## 重新评估条件
上游接口统一并由类型化 SDK 完整覆盖。
```

它没有保留会议里的每句话，却保留了未来 Agent 真正需要的内容：

* 最后决定了什么；
* 为什么这样决定；
* 替代方案为什么被否决；
* 怎样验证；
* 在什么条件下可以重新讨论。

可以将仓库知识分成两类：

| 应该沉淀       | 不必原样搬运      |
| ---------- | ----------- |
| 最终架构决策     | 完整聊天流水      |
| 当前有效的不变量   | 重复表达的个人意见   |
| 约束成立的原因    | 与结果无关的讨论分支  |
| 关键失败及其教训   | 每一次中间尝试     |
| 被否决方案的核心理由 | 已失效的临时假设    |
| 更新条件和责任边界  | 无人维护的长篇会议纪要 |

这里也不能走向另一个极端：为了追求“干净”，把所有失败过程都删除，只留下一个看起来从一开始就很正确的结论。

如果被否决方案很可能再次被提出，或者失败原因并不能直接从最终代码中看出，就应该保留它。

否则，未来的 Agent 可能重新提出同一个方案，再重复一遍已经付出过的试错成本。

因此，知识整理不是单纯的信息压缩，而是一种面向未来行动的选择：

> 哪些内容会改变下一个实现者的决策？

只有会改变未来判断、约束或验证方式的内容，才值得进入长期知识系统。

这也与普通项目文档存在一点区别。

面向人的文档可以依赖一些默认背景：作者知道新同事在不确定时会来询问，团队也能通过口头沟通补齐缺口。

面向 Agent 的文档则需要更明确地表达状态和边界，因为 Agent 很可能不会意识到自己缺失了某段隐性知识。

例如，不应只写：

> 一般情况下推荐使用新接口。

而要说明：

* 旧接口是否仍被允许；
* 哪些模块暂时属于例外；
* 新代码是否必须采用新接口；
* 迁移完成的判定条件是什么；
* 对应检查是否已经存在。

知识只有在能够影响实际选择时，才真正进入 Harness。

不过，即使我们精心整理了决策，新的问题仍然存在：这些文档同样会随着代码变化而过期。

如果不能解决这一点，Repository-local knowledge 反而可能成为 Agent 最可信、也最危险的错误来源。

#### 文档也需要自己的测试和垃圾回收

“把知识写进仓库”并不是终点。

假设 `ARCHITECTURE.md` 仍然声称项目采用旧的三层结构，而代码半年前已经迁移到新的领域分层；或者产品规范中链接的测试已经被删除，示例命令也无法运行。

Agent 读到这些信息时，很难像有经验的人类工程师那样凭直觉判断：

> 这份文档看起来已经很久没人维护了，我最好再问一下。

如果它被标记为正式规范，Agent 反而可能赋予它很高权重。

因此，OpenAI 不仅把知识迁移到结构化 `docs/`，还为知识系统本身建立了检查机制。

可以机械验证的内容包括：

* 索引中引用的文档是否存在；
* 文档之间的交叉链接是否有效；
* 每份设计文档是否声明状态；
* 活跃执行计划是否仍然有人负责；
* 完成的计划是否已经归档；
* 文档提到的文件、模块和命令是否存在；
* 自动生成内容是否与当前代码一致；
* 某些重要文档是否超过更新期限；
* 产品领域和架构层是否存在明显知识空缺。

OpenAI 还提到一个定期运行的 doc-gardening Agent。它会寻找那些不再反映真实代码行为的过时文档，并发起修复 Pull Request。

这个设计让我觉得有意思的地方是：文档不再只是“写给 Agent 看的材料”，文档维护本身也被纳入了 Agent 工作流。

```text
代码和产品发生变化
        ↓
知识与实现开始偏离
        ↓
检查器或整理 Agent 发现异常
        ↓
发起文档修复
        ↓
通过 Review 和验证
        ↓
更新后的知识继续服务未来任务
```

这和代码测试的思想非常接近。

测试并不能证明程序永远正确，但它可以让一部分已经明确的预期在每次变更后重新执行。文档检查也无法判断每一句描述是否仍然准确，却可以让链接、状态、结构、所有权和生成事实不再完全依赖人工记忆。

更进一步说，文档应该尽量与证据相连。

例如，与其在文档里孤立地写：

> Service 层不能直接依赖 UI。

不如同时链接：

* 对应的架构决策；
* 实施这一规则的结构测试；
* 违规时运行的检查命令；
* 允许例外的正式流程。

这样，Agent 读到的不只是一条自然语言建议，还能找到它如何被验证。

我原本会把代码库文档理解成 Agent 的“外部记忆”。这个类比并非完全错误，但读到这里以后，我觉得还应该再加一个限定：

> 没有索引、状态、验证和清理机制的外部记忆，只会把遗忘问题变成过时信息问题。

真正有用的仓库知识系统，不只是把更多内容记下来，而是同时设计：

* 什么值得被记住；
* 它应该存在哪里；
* 什么任务会读取它；
* 与其他来源冲突时谁优先；
* 怎样判断它仍然有效；
* 什么时候应该更新或删除。

这也是为什么大型 `AGENTS.md` 最终会失败，而结构化的 Repository Knowledge 更接近 Harness Engineering。

前者主要尝试通过一次性注入解决问题；后者则把知识的产生、发现、选择、验证和维护都看作长期运行的系统。

不过，到这里仍然只解决了一半。

文档可以告诉 Agent：

> 不要让 UI 直接访问 Repository。

但如果当前修改中跨层调用恰好是最短的实现路径，Agent 仍然可能忽略这句话，或者认为本次场景属于例外。

对于那些真正不能被随意违反的规则，仅仅写在文档里还不够。

下一步要做的，是把一部分工程品味从自然语言说明转化为每次修改后都会重新执行的机器约束。

### 把工程品味编译成机器规则

前面建立的仓库知识系统，主要解决了两个问题：

* Agent 应该去哪里寻找知识；
* 那些会影响未来实现的决策，怎样长期留在仓库中。

但“Agent 能找到一条规则”和“Agent 每次都能遵守这条规则”，仍然不是一回事。

假设 `ARCHITECTURE.md` 已经明确写着：

> UI 层不能直接访问 Repository，所有业务操作必须通过 Service。

Codex 也确实读过这份文档。

但在某次具体修改中，UI 组件只差一次数据库查询就能完成功能。直接调用 Repository 是当前最短、最容易让测试通过的方案。如果代码库中恰好还残留着几个类似写法，Agent 就可能判断：

* 这条规则只是一般建议；
* 当前任务可能属于合理例外；
* 现有代码已经证明这种调用被项目接受；
* 为这次小修改增加 Service 接口显得过于繁琐。

于是，它提交了一份局部正确、整体上却在侵蚀架构的实现。

人类在 Code Review 中看到以后，可以再次留言：

> 不要从 UI 直接访问 Repository，请把业务逻辑移动到 Service。

这当然可以修好当前 PR，但没有解决下一次问题。只要同样的局部诱因再次出现，Agent 就可能重新作出相同选择。

OpenAI 在 Harness Engineering 中给出的方向是：

> 对那些真正不能被随意违反的不变量，不要只提醒 Agent，而要让违规实现直接失败。

#### 对 Agent 而言，最可靠的规则不是“曾经读过”

自然语言文档擅长解释：

* 为什么存在这条架构规则；
* 它解决过什么历史问题；
* 哪些方案曾经被否决；
* 哪些场景可能属于例外；
* 未来在什么条件下可以重新评估。

但文档并不天然具有执行力。

即使 Agent 已经在上下文中读过规则，随着任务推进，它仍然可能：

* 忘记早期出现的约束；
* 错误理解规则的适用范围；
* 被附近的旧代码示例影响；
* 为了让当前测试通过而选择局部最短路径；
* 将一个历史遗留实现误认为推荐模式。

这不一定是 Agent 独有的问题。人类工程师也会忘记规范，也会在赶进度时跨层调用。区别在于，Agent 生成代码的速度更快、并行度更高，同一种偏差也可能在更短时间内扩散到更多地方。

因此，单纯增加文档提醒并不是最稳定的解决办法。

如果某条规则已经足够明确，并且可以通过代码结构判断，那么更可靠的做法是将它转化成每次修改后都会重新运行的检查。

继续使用前面的例子。自然语言规则是：

```text
UI 不得直接依赖 Repository。
```

它可以被进一步写成一条结构测试：

```python
def test_ui_does_not_import_repository_layer():
    violations = find_imports(
        source_layer="ui",
        forbidden_layer="repository",
    )
    assert violations == []
```

这里的伪代码并不重要，真正发生的变化是：

```text
修改前：
Agent 阅读规则
→ Agent 自己判断是否适用
→ 人类在 Review 中发现违规
→ 要求返工

修改后：
Agent 修改代码
→ 结构测试自动执行
→ 非法依赖立即失败
→ 错误信息指出正确边界
→ Agent 在交付前自行修复
```

规则从一种依赖注意力的建议，变成了环境中稳定存在的反馈。

这也是我理解 Harness Engineering 时很重要的一点：

> **对 Agent 而言，最可靠的规则不是它“曾经在上下文里读过”的规则，而是每一次修改以后都会重新执行的规则。**

文档当然仍然需要存在。结构测试负责说“你越界了”，设计文档负责解释“为什么这里是一条边界”。

两者承担的任务不同。

如果只有结构测试，Agent 可能知道当前实现不合法，却不知道这条限制背后的设计意图；如果只有文档，它可能理解原则，却无法保证每一次局部实现都遵循原则。

比较理想的组合是：

```text
设计文档：解释原因和长期意图
        ↓
架构规则：定义可以机械判断的不变量
        ↓
Lint / 结构测试：在每次变更后执行
        ↓
错误信息：把修复方向重新注入 Agent 上下文
```

这里已经不只是“为代码增加更多测试”。

它是在把组织的部分工程判断编译进 Agent 所处的环境。

#### 严格架构不是为了好看，而是为了缩小搜索空间

OpenAI 在文章中展示了一套层次严格的领域架构。

![具有显式横切边界的分层领域架构](/images/harness-layered-domain-architecture.png)

在每个业务领域内部，代码大致沿着固定方向依赖：

```text
Types → Config → Repo → Service → Runtime → UI
```

认证、连接器、遥测和 Feature Flag 等横切关注点，则通过 `Providers` 这样的显式接口进入系统。最终由 `App Wiring + UI` 完成组合。

原图中的具体命名未必适用于所有项目。

不是每个仓库都需要拥有完全相同的六层，也不是照着建立几个同名目录，就完成了 Agent-first 架构。真正值得注意的是，OpenAI 不只规定了有哪些模块，还规定了模块之间允许出现哪些边。

换句话说，架构不再只是下面这种抽象描述：

> 项目采用分层架构，各模块应当保持低耦合。

而是变成可以检查的依赖图：

```text
Types 可以被 Config 使用
Config 可以被 Repo 使用
Repo 可以被 Service 使用
Service 可以被 Runtime 使用
Runtime 可以被 UI 使用

反方向依赖不允许出现
横切能力必须经过规定接口
```

这看起来比“让 Agent 自己选择最合适的实现”更死板，却能解决一个很实际的问题：缩小 Agent 的搜索空间。

假设仓库有十个模块，而任何模块理论上都可以直接调用其他模块。Agent 实现一个功能时，就需要在大量可能路径中作出选择：

* UI 是否直接调用 Repository？
* 是否把逻辑放进 Runtime？
* Config 能否读取 Service 状态？
* 新功能应该进入公共 Utils，还是留在业务域内部？
* 横切逻辑是否可以随手 import？

其中很多路径在短期内都能工作，甚至都能通过现有测试。Agent 很容易选择离当前文件最近、改动量最小或者现有示例最多的方案。

但如果架构已经规定了合法依赖方向，那么 Agent 面对的就不再是任意图，而是一组有限路径。

例如，UI 需要访问持久化数据时，它不必在整个仓库里猜测应该调用谁。合法路径已经被收缩为：

```text
UI → Runtime → Service → Repo
```

它仍然需要决定具体接口如何设计，却不再需要判断能不能跳过中间层。

这就是严格边界对 Agent 的另一层价值：

> 它不只是禁止错误方案，也减少了模型必须依靠品味和猜测作出的选择数量。

这与类型系统有一点相似。

类型系统不会替工程师写出正确业务逻辑，但它可以排除一批不合法程序。剩下的搜索空间更小，错误也更容易在靠近产生的位置暴露。

架构测试起到的也是类似作用：它无法证明一个设计优秀，却可以让某些已知会破坏系统连贯性的方案无法静默进入代码库。

我以前也容易把这种严格的架构模型理解成“大团队病”。

毕竟，当一个项目只有一两个人、代码量也不大时，为每个业务领域划分固定层次，再编写专门的依赖检查，似乎显得过于正式。很多团队确实是在代码库已经非常庞大、跨团队协作不断产生混乱以后，才开始补这些规则。

但在 Agent 高吞吐环境里，因果关系可能反过来。

过去可以等到数百名工程师时再解决的问题，在大量 Agent 持续生成代码时，可能更早出现。因为架构腐化取决的不只是团队人数，也取决于代码变化的速度和并行程度。

当一天可以产生过去一周甚至一个月的代码变更时，“项目现在还小”不一定意味着可以推迟所有结构约束。

当然，这也不意味着个人 Toy Project 一开始就该建立十层架构和几十条自定义 Lint。

更合理的判断是：

* 只对已经明确、反复出现的边界建立约束；
* 约束数量随真实问题增长；
* 不为了模仿大型工程而制造空洞分层；
* 每条规则都应能够说明它在防止什么具体退化。

严格架构的价值不来自形式复杂，而来自它是否消除了一个反复消耗 Agent 和人类注意力的错误空间。

#### 把重复出现的 Review 意见写进 Lint

从文档到结构测试的过程，还可以用一个更直接的问题来判断：

> 同一条 Review 意见，人类已经说过多少次？

如果一位工程师不断在 PR 里留言：

* 不要在这里手写重试逻辑；
* 外部数据必须先经过 Schema；
* 日志不能直接拼接字符串；
* UI 不能绕过 Service；
* 不要在每个模块复制同一个 Helper；
* 新文件不能继续放进这个已经过大的目录；
* 修改产品行为以后必须同步更新对应规范；

那么这些内容可能已经不再是一次性的品味判断，而是某种稳定规则。

继续依赖人工 Review，会产生两个问题。

第一，人类需要不断重复相同劳动。

第二，规则的执行会受到审查者、时间压力和上下文的影响。同一种违规在一个 PR 里被指出，在另一个 PR 里可能被遗漏。Agent 因此很难从反馈中形成稳定预期。

OpenAI 的做法是将一部分“品味不变量”编码成自定义 Lint 和结构测试，例如：

* 结构化日志要求；
* Schema 与类型的命名约定；
* 文件大小限制；
* 模块依赖规则；
* 特定平台的可靠性要求；
* 外部数据必须在边界处解析；
* 不允许通过猜测字段形状进行“YOLO 式”探测。

这类自定义检查和普通代码格式化工具有所不同。

格式化器主要统一表面表达，例如缩进、引号和换行。OpenAI 所描述的检查则开始承载项目自己的架构知识：

```text
通用 Lint：
“这个变量没有使用。”

项目 Lint：
“UI 层不能直接导入 Repository；
请在对应 Service 中定义业务操作，
再由 Runtime 暴露给 UI。”
```

后一种错误信息不仅指出代码不符合规则，还把修复路径注入了 Agent 当前上下文。

这件事在人类工作流里可能没有那么显眼。

人类工程师看到一个简短的错误码，可以主动搜索内部 Wiki、询问同事，或者凭经验推断应该怎样修复。Agent 如果只收到一句“非法依赖”，可能会不断尝试其他同样错误的变体。

因此，自定义 Lint 的报错信息最好明确包含：

* 违反了哪条规则；
* 当前依赖为什么不合法；
* 允许的依赖方向是什么；
* 对应设计文档在哪里；
* 通常应该将逻辑移动到哪一层；
* 如果确实需要例外，应通过什么流程处理。

例如：

```text
ARCH001：UI 层不得直接导入 Repository。

原因：
UI 只负责展示与交互，持久化访问必须经过 Service，
否则权限、事务和遥测逻辑会被绕过。

修复：
1. 在当前业务域的 Service 中增加对应操作；
2. 由 Runtime 组合该 Service；
3. UI 只调用 Runtime 暴露的接口。

参考：
docs/design-docs/layered-domain-architecture.md
```

对于人类来说，这是一条友好的诊断信息；对于 Agent 来说，它更像一个在错误发生时按需出现的微型 Skill。

这比把同样内容永久塞进 `AGENTS.md` 更有效率。

因为 Agent 只有真正触犯这条规则时，才会把详细解释加载进当前上下文。没有相关修改时，这段知识不会占用注意力。

它正好形成另一种渐进式披露：

```text
平时：
入口文档只声明“架构边界由结构测试执行”

发生违规时：
检查器提供与当前错误直接相关的详细指导
```

所以，Lint 在 Agent 工作流里不只是警察，也是一种 Context Router。

![把工程品味编译成机器规则](/images/harness-taste-to-rules.png)

它利用 Agent 的实际行为决定何时暴露哪条知识。

同一思路也可以用于自己的项目。

比如在 CS336 A1 仓库里，“不要把实现写进 `tests/` 和 `tests/adapters.py`”目前主要是一条自然语言约束。它确实应当出现在 `AGENTS.md` 或任务说明里，因为这是作业的关键边界。

但如果未来 Agent 多次违反这一约束，就可以把它升级成机械检查：

```python
def test_student_implementation_stays_outside_tests():
    forbidden_changes = find_student_implementations_under("tests/")
    assert forbidden_changes == []
```

或者在提交检查中直接拒绝对受保护文件的修改。

这样，规则就经历了三个层次：

```text
任务说明：
告诉 Agent 不要修改 adapters.py

入口文档：
将它声明为全局高优先级边界

机械检查：
一旦修改，立即失败并给出正确实现目录
```

这正是 Harness Engineering 可以迁移到小型学习项目中的地方。

不一定需要搭建庞大的智能体基础设施。先把最容易反复发生、最确定不能接受的一类错误变成自动反馈，就已经是在建设 Harness。

不过，随着越来越多的人类经验被编码成规则，也会自然出现另一种诱惑：

> 既然规则能提高 Agent 的稳定性，是否应该把所有实现方式都规定下来？

OpenAI 的答案并不是这样。

#### 强制不变量，而不是微观管理实现

Harness Engineering 中有一句很值得单独拿出来的话：

> 通过强制执行不变量，而不是对实施过程进行微观管理，让 Agent 能够快速交付，同时不削弱系统基础。

这句话其实给“约束应该加到什么程度”划了一条边界。

所谓不变量，是无论采用哪种具体实现，都必须长期成立的条件。例如：

* 外部输入必须在系统边界处解析；
* UI 不能直接访问持久化层；
* 跨领域调用必须经过显式接口；
* 关键操作必须产生结构化日志；
* 数据库迁移必须可回滚；
* 某类安全数据不得进入普通日志；
* 修改核心产品行为必须拥有对应测试。

这些规则关注的是系统不能失去什么性质。

至于这些性质如何实现，则可以给 Agent 留出空间。

以“在边界处解析数据”为例，团队可以强制要求：

```text
不可信外部数据在进入业务逻辑以前，
必须被转换为内部已知的数据形状。
```

但不必进一步规定：

* 所有模块必须使用同一个函数名；
* 每个 Schema 必须按照完全相同的代码模板编写；
* 必须使用某个特定库；
* 每一种错误都必须采用同样的控制流；
* 所有实现必须具有相同文件布局。

OpenAI 原文提到，模型似乎偏好 Zod，但团队强制的是“在边界处解析”这个不变量，而不是指定必须使用 Zod。

这一区别很重要。

如果连具体实现步骤都被完全规定，Agent 就不再是在边界内寻找解决方案，而是在填写模板。随着需求变化，规则系统本身也会变得极其笨重：任何合理的新实现都可能先被旧规则阻止。

反过来，如果只写一些非常抽象的原则：

> 保持代码整洁。
> 遵循最佳实践。
> 保持模块低耦合。

它们又几乎无法机械执行，也不能有效缩小搜索空间。

比较合适的粒度位于两者之间：

| 约束层级  | 示例              | 是否适合强制 |
| ----- | --------------- | ------ |
| 空洞价值观 | 保持良好架构          | 否      |
| 系统不变量 | UI 不得直接依赖 Repo  | 是      |
| 边界行为  | 外部输入必须经过 Schema | 是      |
| 验证要求  | 修改行为必须通过对应集成测试  | 是      |
| 具体实现  | 必须使用某个局部函数结构    | 通常不必   |
| 表达细节  | 每段代码必须写成同一风格    | 谨慎     |

这可以概括为一种“中央约束、局部自主”的方式：

```text
中央层面明确：
哪些边界不能越过
哪些性质必须保留
哪些验证必须通过

局部实现允许：
选择合理抽象
组织内部代码
比较不同方案
根据上下文完成重构
```

它和领导一个大型工程团队有些相似。

平台团队不会逐行规定每个业务团队怎样实现功能，却会统一身份认证、数据边界、遥测接口和发布要求。在这些稳定边界内，业务团队拥有足够的自主空间。

Agent 也是如此。

它需要清楚知道哪些地方没有谈判空间，也需要在剩余空间里发挥模型本身的推理和实现能力。

因此，Harness 的目标不是用越来越多的规则把 Agent 困住，而是把人的注意力从重复检查稳定边界中释放出来。

真正需要人参与的，应当是那些规则无法预先编码的判断：

* 这个功能是否值得做；
* 当前抽象是否匹配未来方向；
* 两个都正确的方案哪个更合适；
* 现有不变量是否已经不再适用；
* 某项例外是否值得改变全局规则；
* 产品体验是否达到了可以接受的水平。

而那些已经被确认了几十次、每次答案都相同的问题，则没有必要继续依赖人类逐个提醒。

这也解释了为什么 AI 时代没有让软件架构和工程纪律失去意义。

恰恰相反，当代码生成速度增加以后，代码库更需要明确区分：

* 什么可以自由变化；
* 什么必须保持稳定；
* 什么应由文档解释；
* 什么应由机器强制；
* 什么仍需要人的判断。

不过，即使 Agent 的每一次修改都符合架构边界，代码库也不一定会一直保持整洁。

它仍然可能在合法范围内重复发明辅助函数、复制次优模式、扩展过时抽象，并让文档逐渐偏离实现。

换句话说，边界可以阻止一部分错误，却无法自动阻止长期熵增。

当 Agent 真正开始高速、持续地产生代码以后，下一个问题不再只是“如何让这一次修改正确”，而是：

> 如何防止一千次各自合理的修改，最终把代码库推向一种没有人设计过的形状？

## 当 Agent 开始高速工作，新的敌人是熵

有了结构化文档、分层架构、自定义 Lint 和结构测试，一个 Agent-first 代码库看起来似乎已经相当稳固。

Agent 能找到项目知识，能够通过浏览器和可观测性工具验证修改，也无法轻易跨越那些已经被编码成测试的架构边界。

但这些机制主要保证的是：

> 某一次修改没有违反我们已经明确知道的不变量。

它们无法保证一千次局部合理的修改叠加起来，代码库仍然保持原来的连贯性。

假设某个 Agent 为了完成任务，新增了一个只有十几行的辅助函数。它没有跨层依赖，也通过了全部测试。从当前 PR 看，这个实现几乎没有任何问题。

但仓库里也许已经存在另一个功能相近的公共工具，只是名字不完全一样，位置也不容易发现。Agent 没找到它，于是重新实现了一份。

下一次，另一个 Agent 在附近看到这个新函数，便把它当成当前模块的惯用模式，又写出第三份变体。

再过一段时间，三个辅助函数分别处理了略有不同的边界情况。此时即使人类发现重复，也很难再简单合并，因为每一份都已经拥有自己的调用者和行为差异。

没有任何一次提交明显错误，代码库却在慢慢失去统一性。

这就是 OpenAI 在高吞吐 Agent 开发中遇到的另一个问题：**熵**。

### Agent 会复制好模式，也会复制坏模式

Coding Agent 很依赖仓库中的现有模式。

当它需要新增一个接口、组件或测试时，通常会先搜索附近是否存在类似实现，然后模仿项目已有的组织方式。这本来是一种非常有价值的能力。

它可以让 Agent：

* 遵循本地命名习惯；
* 复用项目内部抽象；
* 采用已经验证的测试方式；
* 减少凭空发明新的代码风格；
* 写出更像“这个仓库原本就有”的实现。

但这种能力有一个天然限制：Agent 不会自动知道某个现有模式究竟是推荐范例，还是尚未来得及清理的历史遗留。

从它看到的代码出发，两者可能同样真实。

于是，Agent 不只会复制代码库中的好模式，也会复制其中不够理想的部分：

* 一个临时 Helper 可能被当成公共惯例；
* 一次为了兼容旧版本留下的特殊写法，可能出现在新模块里；
* 已经准备废弃的接口，因为拥有大量调用示例，反而比新接口更容易被 Agent 找到；
* 某个模块里偶然出现的重复逻辑，可能继续扩散到其他模块；
* 一份结构不够好的测试，可能成为后续测试的模板；
* 文档中已经过时的术语，可能重新进入代码和注释。

这不是模型简单地“不够聪明”。

从统计上看，一个在仓库里出现几十次的模式，本来就比一条只在设计文档里出现一次的理想规则更容易影响下一次生成。

甚至可以说，代码库本身也是 Prompt 的一部分。

![坏模式在代码库中的自我放大](/images/harness-entropy-amplification.png)

`AGENTS.md`、设计文档和任务说明是显式上下文；搜索结果、相邻文件和历史实现则构成了隐式上下文。Agent 会同时从两者中判断“这个项目通常怎样写代码”。

如果显式规范说：

> 新实现必须复用共享工具。

但 Agent 在附近连续看到五个各自手写的辅助函数，它接收到的信号就是矛盾的。

人类工程师也会受到这种影响。新入职的开发者往往通过模仿现有代码学习项目习惯。如果仓库里充满历史妥协，他们也可能把妥协当成设计。

区别仍然在吞吐量。

人类团队中的坏模式可能经过数周才复制到几个地方；Agent 可以在多个并行任务中迅速重复同一种写法。等到人类发现，它可能已经从一个局部例外变成了仓库中的多数模式。

而 Agent 又会继续把“多数模式”视为更强的证据。

于是形成一种自我强化：

```text
仓库中出现一个次优模式
        ↓
Agent 将它当成项目惯例
        ↓
更多任务复制该模式
        ↓
它在代码库中的占比提高
        ↓
后续 Agent 更确信这就是正确写法
```

这也解释了为什么只在文档里写“请复用公共工具”可能仍然不够。

对于 Agent 来说，仓库中大量存在的现实模式，往往比一条孤立的文字规范更有说服力。

因此，保持代码库本身的可读性和一致性，不只是为了照顾人类维护者，也是为了控制未来 Agent 获得的训练样例。

OpenAI 在原文中提出，他们首先优化的是代码对 Codex 的可读性。这个说法容易被误解成“代码不再需要给人看”，其实更接近：

> 代码库必须让下一次进入的 Agent 能够从现有结构中推断出正确的项目惯例。

这包括：

* 推荐模式应当清晰、集中且容易搜索；
* 已废弃实现不能长期与新方案并列；
* 相同概念不应拥有大量互相竞争的表达；
* 例外需要被明确标记，而不是悄悄混在普通代码中；
* 关键抽象需要拥有足够清晰的边界和命名；
* 代码、文档和检查器给出的信号不能长期互相冲突。

从这个角度看，技术债务不再只是“未来人类改起来比较痛苦”。

它还会污染下一次 Agent 推理所依赖的环境。

坏模式如果不被及时处理，就会不断产生新的坏模式。这正是熵会在 Agent 高吞吐代码库中加速积累的原因。

### 从“周五大扫除”转向持续垃圾回收

OpenAI 最初仍然使用了一种很传统的解决办法：由人类定期清理 Agent 留下的残渣。

原文提到，团队一度需要把每周五，也就是一周大约 20% 的时间，用来处理所谓的 “AI slop”。

这里的 AI slop 并不一定是完全不能运行的垃圾代码。

更常见的可能是：

* 功能已经正确，但出现了重复抽象；
* 测试通过，却采用了仓库中正在淘汰的模式；
* 为局部任务新增了不必要的包装层；
* 文档已经跟不上实现；
* 同一个概念出现多套命名；
* 小型 Helper 在各处重新实现；
* 临时兼容逻辑没有在迁移结束后删除；
* 每个 PR 单独看都合理，组合起来却使架构逐渐变形。

集中安排一天清理，短期内当然有效。

人类可以浏览一周积累的修改，识别哪些内容“虽然没错，但越来越不对劲”，再进行统一重构。

问题是，这种方式无法随着 Agent 吞吐量一起扩展。

如果 Agent 的生成速度继续提高，人类每周五面对的就不再是少量需要整理的代码，而是一整周已经互相依赖的局部决策。越晚清理，重构成本越高；重构范围越大，验证风险也越高。

一个原本只需删除的重复 Helper，可能已经产生几十个调用点。一个错误命名可能已经进入 API、测试、文档和监控指标。一个临时架构例外，也可能已经被其他 Agent 当成先例。

OpenAI 因此将维护方式从集中大扫除，改成了更接近垃圾回收的持续过程。

他们开始把一部分主观但稳定的工程偏好写成“黄金原则”，例如：

* 优先使用共享工具，而不是重复手写辅助函数；
* 在系统边界验证数据，而不是在内部猜测字段形状；
* 不让历史例外继续扩散成新模式；
* 让同一种概念尽量拥有统一实现；
* 让未来 Agent 能从代码库中发现明确而一致的范例。

这些原则再由后台 Codex 任务定期执行。

Agent 会扫描仓库中的偏差，更新质量评分，并针对具体问题发起范围有限的重构 PR。许多修改足够小，可以在较短时间内完成 Review 和合并。

![持续垃圾回收与小额偿还技术债务](/images/harness-continuous-garbage-collection.png)

于是，维护过程从：

```text
积累一周技术债务
        ↓
人类集中浏览和判断
        ↓
发起大范围重构
        ↓
重新验证大量行为
```

转变为：

```text
持续扫描已知偏差
        ↓
发现一类局部问题
        ↓
生成小范围修复
        ↓
运行相关验证
        ↓
快速审查与合并
        ↓
继续扫描
```

这里的“垃圾回收”类比很准确。

内存垃圾回收不会等程序耗尽全部内存，再要求开发者暂停系统、手动寻找每个无用对象。它会持续识别不再需要的内容，并逐步回收空间。

代码库维护也可以采用类似思路：不要让技术债务积累到必须进行一次痛苦的大重构，而是在偏差刚刚出现、影响范围仍然较小时不断偿还。

当然，代码中的“垃圾”不像内存对象那样容易判断。

一个看似重复的 Helper 可能承担了不同语义；一段旧代码可能仍然服务某个兼容场景；两个相近抽象也可能不应该被强行合并。因此，后台维护 Agent 不能只依靠表面相似度任意重构。

适合自动或半自动清理的，仍然应该是那些已经有清晰原则和验证方式的问题，例如：

* 使用已经废弃的 API；
* 违反统一命名规则；
* 重复实现已有公共工具；
* 文档链接失效；
* 完成的迁移残留旧入口；
* 文件持续超过项目规定的复杂度上限；
* 同类模块缺少已经成为标准的测试；
* 架构质量评分中明确可检测的退化。

而对于“这个抽象是否真的值得统一”之类仍然需要设计判断的问题，Agent 最多可以提出候选 PR，不能因为它能修改代码就默认它有权决定新的全局方向。

因此，这套垃圾回收机制依然是 Harness 的延伸：

```text
黄金原则定义希望保持的性质
        ↓
扫描工具把原则转化成可发现信号
        ↓
Agent 生成范围有限的修复
        ↓
测试和 Review 约束修改
        ↓
新的代码库状态影响未来 Agent
```

它不是让 Agent 自由清理自己生成的所有内容，而是让人类已经形成的品味能够被持续应用。

这里产生了一个很有意思的闭环。

最开始，人类在 Review 中发现坏模式；如果同类问题不断出现，就将它总结成原则；如果原则足够稳定，就将其转化成 Lint、扫描器或质量规则；后台 Agent 再根据这些规则修复已有偏差。

```text
一次具体问题
→ 人类判断
→ 可复用原则
→ 机械规则
→ 持续扫描
→ 自动或半自动修复
```

人的一次判断，因此可能影响未来成千上万行代码。

这或许才是 OpenAI 所说“人类工作抽象层次上移”最具体的含义之一。

人不再亲自修改每一处重复实现，而是决定：

* 什么算重复；
* 哪种共享抽象值得推广；
* 哪些例外应当保留；
* 扫描器能在哪些范围内自动修复；
* 什么修改必须升级给人审查。

当代码生成变得越来越便宜时，真正稀缺的东西也开始变化。

过去，团队可能担心功能做不完、代码写得太慢；在 Agent 高吞吐环境里，新的瓶颈可能是：

* 人类来不及审查所有变化；
* 代码库来不及吸收这些变化；
* 架构共识来不及追上局部实现；
* 文档来不及反映真实状态；
* 次优模式在被发现前已经大量复制。

因此，Agent-first 工程追求的不能只是更高的生成吞吐量。

它还必须同步提高：

* 错误发现速度；
* 偏差修复速度；
* 知识更新速度；
* 技术债务偿还速度；
* 人类判断被系统复用的速度。

否则，Agent 生成代码越快，只是让代码库更快到达需要大规模重构的状态。

### 我暂时不会照抄 OpenAI 的快速合并哲学

高吞吐量还让 OpenAI 改变了另一项传统工程习惯：对合并等待成本的判断。

原文提到，他们尽量减少阻塞式合并门，PR 的生命周期很短。某些偶发测试失败会通过后续重跑和修复解决，而不是让所有进展无限期等待。

OpenAI 给出的逻辑大致是：

> 在 Agent 吞吐量远高于人类注意力的系统中，纠错成本可能很低，而等待成本可能很高。

这套判断不是没有道理。

假设一个 Agent 可以在几分钟内完成以下动作：

1. 发现主分支构建失败；
2. 定位引入失败的提交；
3. 复现问题；
4. 生成修复；
5. 运行验证；
6. 发起补丁 PR；
7. 在通过检查后自动合并。

那么等待一个偶发测试被人工排查数小时，可能确实比先合并、再快速纠正更加昂贵。

传统流程中的某些强阻塞门，本来就是为了应对人类修复周期长、上下文恢复昂贵、出错后无人持续观察的问题。如果这些成本因 Agent 而显著下降，流程自然可以重新计算。

但这是整篇文章里我最不准备直接照抄的一点。

因为“纠错成本低于等待成本”并不是由 Agent 存在自动推出的结论。它依赖一组很强的前提：

* 测试能够较快发现回归；
* 构建失败会被持续监测；
* 变更能够定位到具体提交；
* 修复和回滚足够便宜；
* 不同任务之间有良好隔离；
* Agent 有权限也有能力完成恢复；
* 发布基础设施支持灰度或快速回退；
* 错误不会立即造成难以逆转的损失。

缺少这些条件时，低阻塞合并不会带来更高吞吐，只会把验证工作推迟到更危险的位置。

尤其在以下系统中，错误成本很难被概括成“再发一个修复 PR”：

* 医疗决策；
* 支付和清算；
* 身份认证与权限；
* 数据删除与迁移；
* 安全边界；
* 隐私和合规；
* 会直接影响真实设备的控制系统。

例如，一个普通 UI 样式错误进入内部开发环境，可能只需要几分钟就能修复；但一次错误的数据迁移即使很快发现，也可能已经破坏无法重新生成的数据。

这里不能只比较：

```text
修复代码需要多久
```

还要比较：

```text
错误被发现以前会产生什么后果
这些后果是否可逆
恢复是否只涉及代码
是否需要人工核查真实世界状态
```

所以，更完整的工程判断应该是：

[
\text{预期纠错成本}
=============

\text{错误发生概率}
\times
(\text{发现延迟}+\text{影响范围}+\text{恢复成本})
]

而等待成本则包括：

[
\text{等待成本}
===========

\text{阻塞时间}
\times
(\text{受阻任务数量}+\text{上下文切换成本})
]

OpenAI 的环境可能通过高度自动化显著降低了发现延迟和恢复成本，因此得出了“减少阻塞更划算”的局部结论。

普通项目不能只看到结论，却忽略他们为降低纠错成本建设的整套 Harness。

这其实与前面所有内容互相呼应。

只有当 Agent 已经能够：

* 验证当前代码库状态；
* 复现问题；
* 操作真实应用；
* 查询日志、指标和 Trace；
* 修改并重启系统；
* 检测构建失败；
* 回应 Review；
* 在必要时升级给人；
* 完成可靠回滚或修复；

“先保持流动，再快速纠正”才可能是一种经过基础设施支撑的策略。

如果 Agent 连问题是否真正修好都无法自行验证，却先取消人工合并门，那不是 Harness Engineering，而是单纯放弃质量控制。

因此，我更愿意把 OpenAI 的快速合并理解成一个结果，而不是起点：

```text
先建设强反馈和恢复能力
        ↓
降低单次错误的发现与纠正成本
        ↓
再重新评估哪些阻塞门仍然值得保留
```

而不是：

```text
因为 Agent 写代码很快
        ↓
所以减少检查、加快合并
```

这两种顺序看起来只差一点，工程含义却完全相反。

前者用更强的反馈系统替代一部分等待；后者只是用乐观假设替代验证。

对我现在的项目而言，更现实的实践仍然是：

* 保留确定性的测试门；
* 对受保护文件和关键架构边界保持强约束；
* 让低风险文档、格式和局部重构拥有更快流程；
* 逐步补齐自动复现、运行时验证和恢复能力；
* 等纠错成本真的下降以后，再讨论取消哪些阻塞。

这也是读 Harness Engineering 时很容易被顺序误导的地方。

看到最终状态，我们可能会模仿：

* 短 PR 生命周期；
* Agent 自动 Review；
* 自动修复 CI；
* 更少的阻塞门；
* 自动合并。

但 OpenAI 真正先投入建设的是：

* 可访问的知识；
* 可操作的开发环境；
* 可查询的运行状态；
* 可执行的架构约束；
* 可持续的质量清理；
* 失败后的恢复能力。

如果没有前面这些能力，最后那套高吞吐流程只剩下速度，没有控制。

所以，我不会把“等待成本高于纠错成本”当成 Agent 时代的新定律。

它更像一道需要用项目现实条件回答的题：

> 在我的代码库里，错误能多快被发现？影响是否可逆？恢复能否由 Agent 可靠完成？如果答案还不清楚，那么等待仍然可能比盲目纠错便宜。

到这里，OpenAI 这篇文章的几个主要部分已经能够拼在一起：

* Browser 和 Observability 让 Agent 看见修改结果；
* Repository Knowledge 让它找到实现背景；
* 架构规则让它不能轻易越过边界；
* 垃圾回收让代码库在高速生成后仍然保持连贯；
* 强反馈与恢复能力，才可能进一步改变合并经济学。

这也终于允许我们回到文章开头的问题：

> 如果我已经会先写 PRD、TRD，再把任务拆成六到八步，那么 Harness Engineering 到底还增加了什么？

答案并不是再写一份更详细的 Spec。

它增加的是从“意图已经表达清楚”到“Agent 能够在真实环境中持续兑现这份意图”之间缺失的整套控制系统。

## 从 Spec 到 Harness：它们不是同一个层次

现在回头看，我最初采用的那套流程——先写 PRD、TRD，再拆成六到八个子任务——依然是正确的。

问题只在于，我曾经把它误认为 Agent-first 软件工程的完整形态。

实际上，这套方法主要优化的是 Agent 收到任务的方式：

* PRD 尽量说清产品目标；
* TRD 描述技术路线与边界；
* 验收标准定义什么叫完成；
* 任务拆分控制单次工作的规模；
* 每完成一步就测试和 Review。

它将原本模糊的一句话需求，转化成一系列可以逐步执行的工程工件。

```text
“帮我把这个功能做好”
        ↓
明确用户问题
        ↓
定义目标行为
        ↓
设计技术方案
        ↓
拆成有限任务
        ↓
逐项实现与验收
```

这是 SDD 最有价值的地方：先让需求和决策成为显式的 Spec，再让实现围绕 Spec 展开。

但一份完整的 Spec 并不会自动创造执行条件。

假设 PRD 已经准确描述了用户问题，TRD 也明确写出架构方案，验收标准甚至精确到了响应时间和错误率。Agent 仍然可能因为下面这些原因失败：

* 找不到与本次修改有关的历史决策；
* 不知道项目中的哪个文档才是当前事实来源；
* 无法启动真实应用并复现问题；
* 看不到浏览器控制台和运行时状态；
* 不能查询日志、指标和 Trace；
* 不知道自己的实现跨越了架构边界；
* 测试虽然通过，却没有覆盖真实用户路径；
* 文档已经过期，但仍被当成有效规范；
* 失败以后缺少回滚、重试和恢复机制；
* 仓库中的旧模式不断诱导它复制技术债务。

这些都不是继续细化 PRD 就能解决的问题。

如果一个 Agent 看不到浏览器，那么在 PRD 里增加十段 UI 说明也不会赋予它验证页面的能力；如果安全约束只存在于某位工程师脑中，再详细的任务拆分也无法让 Agent 自动发现；如果架构边界没有被机械执行，那么 TRD 里的“保持分层”仍然可能在局部实现中被绕过。

所以，我现在会把 Agent-first 软件工程拆成几个相互连接、但职责不同的层次。

| 层次                        | 它回答的问题                  | 典型工件                                  |
| ------------------------- | ----------------------- | ------------------------------------- |
| Spec / SDD                | 要做什么？什么算完成？             | PRD、TRD、Spec、验收标准                     |
| Planning                  | 应按什么顺序推进？               | Exec Plan、子任务、进度与决策日志                 |
| Context Engineering       | Agent 此刻应知道什么？从哪里找？     | `AGENTS.md`、文档索引、检索与渐进式披露             |
| Harness Engineering       | Agent 怎样行动、观察结果并从失败中恢复？ | Shell、Browser、Worktree、日志、指标、Trace、CI |
| Architecture / Guardrails | 哪些边界不能随意越过？             | Schema、依赖规则、Lint、结构测试                 |
| Evaluation                | 怎样证明结果成立？               | 单测、集成测试、端到端测试、运行时验证、Review            |
| Maintenance               | 高速生成后怎样控制熵？             | 文档整理、质量评分、清理 Agent、技术债务追踪             |

这张表并不是 OpenAI 原文给出的标准分层，而是我为了定位 Harness Engineering 所作的整理。

现实系统中的边界也不会这么整齐。例如，结构测试既属于 Guardrail，也属于 Evaluation；Exec Plan 既是 Planning 工件，也会成为后续 Context；Observability 既支持运行时行动，也为评测提供证据。

但这种划分至少可以避免把所有方法都塞进“提示词工程”或者“Vibe Coding 最佳实践”这个大筐里。

### Spec 解决意图，Harness 解决行动条件

可以先把它们压缩成最简单的区别：

> **Spec 告诉 Agent 什么结果才算正确；Harness 让 Agent 有条件产生、观察并验证这个结果。**

比如，Spec 可以规定：

> 用户在修改个人设置并刷新页面后，选项必须保持；接口 P95 延迟不得超过 200 ms；失败时界面必须显示明确提示。

Harness 则需要提供：

* 相关产品规范和历史设计决策；
* 启动前端与后端的标准命令；
* 可隔离运行的 Worktree 或开发环境；
* 操作真实页面的浏览器工具；
* 可以重放的用户路径；
* 查询接口延迟的 Metric；
* 定位失败请求的 Log 和 Trace；
* 修改后的重启与重跑能力；
* 失败时恢复到安全状态的机制。

如果只有 Harness，没有 Spec，Agent 虽然能行动、观察和修正，却不知道应该朝哪个目标收敛。

如果只有 Spec，没有 Harness，Agent 虽然知道目标，却可能没有能力判断自己是否到达目标。

两者的关系更像目标与控制系统：

```text
Spec：定义目标状态
        ↓
Plan：提出达到目标的步骤
        ↓
Context：提供当前决策所需的信息
        ↓
Tools：让 Agent 对环境施加动作
        ↓
Feedback：返回动作产生的真实结果
        ↓
Guardrails / Evaluation：判断是否偏离目标
        ↓
未通过则重新规划和修正
```

这时，最初那种“让 Agent 一次生成代码”的开环，才真正变成反馈控制意义上的闭环。

开环流程大致是：

```text
需求
→ Agent 推理
→ 生成代码
→ 任务结束
```

闭环流程则是：

```text
目标
→ 获取相关知识
→ 规划动作
→ 修改环境
→ 观察真实结果
→ 根据约束和验收标准判断
→ 修正
→ 再次观察
```

这里的关键区别不是多了几步形式，而是系统的后续动作会受到真实输出影响。

如果测试失败、页面状态不对、Metric 超过阈值或者结构检查发现越界，Agent 就不能继续按照原计划宣称任务完成，而要把反馈重新送回下一轮决策。

因此，Harness Engineering 不是在 SDD 之外再增加一套互不相干的方法论。

它是在追问 SDD 的后半句：

> 当目标和验收标准已经写清楚以后，怎样让 Agent 真正获得完成和验证它们所需的环境？

### Context Engineering 也不只是记忆和检索

这套分层也让我重新定位了 Context Engineering。

以前提到 Context，我首先想到的是一次模型调用内部的事情：

* Token Budget 有多少；
* 哪些信息必须保留；
* 哪些信息可以裁剪；
* 多条 Context Item 怎样排序；
* 历史对话怎样压缩；
* 检索结果怎样选取；
* 最终怎样编译成模型 Payload。

这也是我在 Hi-Agent 中实现 Context Budget、Selector、Compiler、Formatter 和 Trace 时主要处理的问题。

可以把它称为**调用级 Context Engineering**：

```text
候选上下文
→ 选择
→ 排序
→ 裁剪
→ 格式化
→ 送入模型
```

OpenAI 的 Harness Engineering 又暴露出它的上一层问题：

> 候选上下文本身从哪里来？

如果架构决策只在 Slack，如果产品规范分散在多个无人维护的 Google Docs，如果失败原因只存在于上一次会话，那么 Selector 再聪明也选不到这些信息。

所以，Repository Knowledge Design 更像是**仓库级 Context Engineering**：

```text
组织中的原始知识
→ 提炼为决策和规范
→ 进入可版本化的仓库工件
→ 建立索引与优先级
→ 标记状态与验证方式
→ 在具体任务中按需读取
```

再向下一层，Context Compiler 才负责将其中一部分装入具体模型调用。

这三层可以连起来理解：

| 层次                          | 主要问题                 |
| --------------------------- | -------------------- |
| Knowledge Capture           | 哪些组织知识值得长期沉淀？        |
| Repository Navigation       | Agent 怎样发现当前任务需要的知识？ |
| Runtime Context Compilation | 在有限 Token 中实际送入哪些内容？ |

这也是为什么“大型 `AGENTS.md`”不是一个理想的终局。

它试图绕过中间两层：把捕获到的所有知识直接注入每次运行。知识不再需要路由，代价则是上下文膨胀、优先级稀释和维护困难。

真正成熟的设计不是让 Agent 永远携带所有知识，而是让它能在需要时稳定找到正确知识。

### Evaluation 也必须从“测试通过”扩展到“证据链成立”

同样，Evaluation 不能只理解成运行一组测试。

测试当然是最重要的验证工具之一，但 Harness Engineering 所展示的验证链条更宽：

* 单元测试证明局部函数满足断言；
* 集成测试证明多个组件能够共同工作；
* 结构测试证明实现没有违反架构边界；
* Browser 验证证明真实用户路径能够执行；
* Logs 帮助确认运行中没有隐藏错误；
* Metrics 证明性能和可靠性目标达到阈值；
* Traces 解释一次请求经过了哪些组件；
* Review 判断机器断言没有覆盖的产品和设计问题。

因此，“测试全绿”与“任务完成”之间不应该被直接画上等号。

更可靠的完成条件应当是：

> 与本次任务风险相匹配的证据已经形成，并且这些证据共同支持验收标准。

例如，修改一个纯函数，单元测试可能已经足够；修复一个前端交互问题，则至少还应重放对应 UI path；调整请求链路性能，就需要 Metric 或 Trace；修改模块边界，结构测试比视觉验证更重要。

不是每个任务都要把所有验证工具运行一遍，而是需要选择真正能证明该任务成立的证据。

可以将它写成一条简单原则：

```text
验证方式应当由风险和验收标准决定，
而不是由 Agent 最容易运行什么决定。
```

这也是 Harness 与 Evaluation 的交界处。

Evaluation 定义需要什么证据；Harness 负责让 Agent 有能力产生并读取这些证据。

### Maintenance 决定这套方法能否活过第一个版本

最后是最容易被 SDD 流程忽略的 Maintenance。

PRD、TRD 和任务拆分天然围绕一次变更展开：

* 这次要做什么；
* 这次怎样实现；
* 这次怎样验收。

但一个长期运行的 Agent-first 代码库还要面对：

* 完成的计划怎样归档；
* 已失效的规范怎样撤销；
* 临时例外什么时候清理；
* 新的 Review 经验怎样沉淀；
* 文档怎样跟随代码更新；
* 质量指标怎样持续检查；
* Agent 复制出的坏模式怎样尽早阻断；
* 技术债务怎样在规模扩大前偿还。

如果缺少这一层，Agent 每次都可能正确完成局部任务，代码库却仍然逐步腐烂。

因此，真正完整的 Agent-first 流程不是：

```text
写 Spec
→ 拆任务
→ 生成代码
→ 测试通过
→ 结束
```

而更接近：

```text
写 Spec
→ 建立执行计划
→ 提供可导航知识
→ 在真实环境中行动
→ 获得运行时反馈
→ 执行结构与行为验证
→ 记录决策和结果
→ 更新仓库知识
→ 持续扫描偏差
→ 为下一次 Agent 运行改善环境
```

最后几步看起来不直接产生功能，却决定了第十次、第一百次修改是否仍然可以保持同样效率。

这也是 Harness Engineering 比普通“使用 Coding Agent 的技巧”更值得积累的地方：它不只讨论怎样让当前任务成功，还讨论怎样让代码库越来越适合未来的 Agent 工作。

## 总结与实践

理解到这里以后，很容易产生另一个冲动：为自己的项目照着 OpenAI 的结构搭一整套平台。

建立完整的 Observability Stack，编写几十条自定义 Lint，部署多个后台 Agent，接入 Browser、自动 Review、自动修复 CI，再建设文档评分和自动合并系统。

但这很可能又走向另一种形式的过度工程。

OpenAI 的系统服务于一个约一百万行代码、拥有高 Agent 吞吐量的真实内部产品。它所承担的建设成本和维护成本，未必适合一个学习项目或者个人开源仓库。

如果我现在把完整复刻这套 Harness 当成新项目，很可能花大量时间建设 Agent 基础设施，却没有足够复杂的真实任务来验证它是否有价值。

更合适的方式，是先从自己已经反复遇到的问题里选择三个最小实验。

### 实验一：把 `AGENTS.md` 从说明书改成地图

第一个实验成本最低，也和我现在的项目最相关。

目标不是简单删短 `AGENTS.md`，而是重新划分知识职责：

```text
AGENTS.md
├── 项目目标与当前范围
├── 不可违反的全局约束
├── 关键目录导航
├── 常用验证命令
├── 活跃执行计划入口
├── 架构和产品规范入口
└── 特殊任务的继续阅读路径
```

详细内容则进入对应位置：

```text
docs/
├── architecture/
├── product-specs/
├── decisions/
├── exec-plans/
│   ├── active/
│   └── completed/
├── references/
└── generated/
```

这个实验真正需要验证的不是文件是否变得更漂亮，而是 Agent 的行为是否改善。

可以选取几类过去经常出现的问题：

* 修改了不该修改的适配层；
* 没有读取任务对应的 Contract；
* 重复实现已有组件；
* 忽略了活跃计划中的范围限制；
* 使用了已经废弃的目录或接口。

然后比较改造前后：

* Agent 是否能主动打开正确文档；
* 是否减少了无关上下文加载；
* 是否更少修改错误文件；
* 是否减少重复追问；
* 是否仍然遗漏关键约束；
* 当文档冲突时能否找到优先级。

例如，在 CS336 A1 里，入口文件不需要完整解释 Tokenizer、Transformer 和 Optimizer 的全部知识。它只需要明确：

* 学生实现位于 `cs336_basics/`；
* 不得把实现写入 `tests/`；
* `tests/adapters.py` 只负责连接测试与实现；
* 每个任务应阅读哪个作业说明；
* 应运行哪些测试验证；
* 遇到失败时先检查哪些接口契约。

具体模块的数学推导、实现笔记和实验记录则应进入更深层文档。

如果这项改造有效，说明导航型入口确实比百科全书式入口更适合当前仓库；如果没有改善，也要检查问题究竟出在结构设计、文档命名，还是 Agent 根本没有遵循导航入口。

这才是一次 Harness 实验，而不只是整理 Markdown。

### 实验二：为一个 Web 任务补上 Browser 验证闭环

第二个实验是选择一个范围很小、能够明确复现的 Web 问题，让 Coding Agent 不以“代码已修改、测试已通过”为终点。

完整任务可以要求它：

1. 启动应用；
2. 打开指定页面；
3. 按步骤复现问题；
4. 保存修改前状态；
5. 检查控制台与相关请求；
6. 修改代码；
7. 重启或热更新应用；
8. 重新执行同一路径；
9. 保存修改后状态；
10. 报告修改前后的证据。

例如，可以选择 Hugo 博客中的一个具体交互或布局问题：

> 在移动端打开某篇包含宽表格的文章，页面出现横向溢出；修复后重新打开相同视口，确认正文不再超出容器，并且桌面端布局不受影响。

这个任务的验收不能只写：

> CSS 已经调整。

而应当包括：

* 固定的页面 URL；
* 固定的移动端视口；
* 修改前溢出状态；
* 修改后的页面截图；
* 页面宽度与元素边界；
* 控制台是否出现新错误；
* 桌面端回归检查。

这样，Agent 的工作过程才从代码生成变成环境闭环：

```text
复现
→ 观察
→ 修改
→ 重启
→ 重放
→ 比较
→ 验证
```

这个实验可以直接检验：Browser 工具究竟只是让 Agent 多点了几下网页，还是确实减少了“测试通过但真实页面仍然错误”的情况。

### 实验三：把一条重复 Review 意见变成机械检查

第三个实验不追求建立完整架构 Linter，只选择一条已经足够明确、并且确实反复出现的规则。

例如：

> 不允许把学生实现写进 `tests/` 或 `tests/adapters.py`。

这条规则具备几个适合机械化的条件：

* 判断标准清楚；
* 违规位置明确；
* 几乎不存在合理例外；
* 一旦违反，就会破坏作业测试与实现之间的边界；
* 人类每次给出的 Review 结论基本相同。

它可以被实现成：

* 受保护路径检查；
* Git Diff 检查；
* 自定义测试；
* 提交前 Hook；
* CI 规则。

检查失败时，不应只返回：

```text
Protected file modified.
```

而应提供足够的修复信息：

```text
禁止在 tests/ 和 tests/adapters.py 中实现作业功能。

请将实现放入：
A1/assignment1-basics/cs336_basics/

tests/adapters.py 只负责：
1. 导入你的实现；
2. 根据测试参数实例化对象；
3. 加载 reference weights；
4. 调用并返回结果。
```

这条信息与当前违规直接相关，所以只在需要时进入 Agent 上下文。

它既是一条 Guardrail，也是一种按需指导。

如果这一条规则能够稳定阻止同类错误，再继续观察其他反复出现的 Review 意见：

* 哪些已经足够稳定，可以机械化；
* 哪些仍然依赖具体语境；
* 哪些应该进入文档，而不是测试；
* 哪些其实说明当前架构本身不够清晰。

这样，Harness 会从真实失败中逐步生长，而不是根据一张理想架构图一次性设计完成。

## 我暂时不会照抄什么

与三个最小实验相比，OpenAI 原文中的一些机制目前更适合记下来，而不是立刻复制：

* 大规模 Agent-to-Agent Review；
* 高吞吐、低阻塞合并；
* 完整的本地 Logs、Metrics、Traces 栈；
* 自动创建并合并垃圾回收 PR；
* 多个后台 Agent 持续扫描代码库；
* 端到端处理 Bug、录制视频、回应 Review 和合并代码；
* 为所有产品领域建立完整质量评分体系。

这些东西未必不适合个人项目，只是需要用真实瓶颈证明其建设成本。

如果仓库目前每周只有几次修改，就没有必要先建设一个不断扫描技术债务的 Agent 集群；如果项目根本没有稳定的端到端测试，自动合并更不是优先级；如果性能问题尚未成为验收要求，也不必为了模仿 OpenAI 而部署完整遥测栈。

我现在更愿意采用一条保守的增长原则：

> 每当 Agent 在同类问题上第二次或第三次需要人类接管，就判断这是否暴露了一个可以补进 Harness 的稳定缺口。

可能的答案是：

* 缺少一个文档入口；
* 缺少一条结构检查；
* 缺少一个标准命令；
* 缺少一种运行时信号；
* 缺少可重复的测试 Fixture；
* 缺少失败恢复步骤；
* 也可能只是模型这一次推理失败，不值得建设新的全局机制。

Harness 不应该变成“Agent 每犯一次错，就永久增加一条规则”。

否则它很快会重蹈大型 `AGENTS.md` 的覆辙：局部补丁不断累积，最终形成另一套无人敢删、无人能理解的复杂系统。

每次新增机制前，至少应该问：

1. 这类失败是否重复发生？
2. 它造成的成本是否足够高？
3. 根因是模型推理、知识缺失、工具缺失，还是约束缺失？
4. 新机制能否被机械验证？
5. 它会不会限制大量本来合理的实现？
6. 谁负责维护它？
7. 未来在什么条件下可以删除？

这也是 Harness Engineering 本身需要纪律的地方。

我们不能一边批评代码库中的熵，一边在代码外围制造一套同样不断膨胀的规则、脚本和 Agent。

## 读完以后，我真正改变的理解

回到最开始的问题：Harness Engineering 是 SDD 之后又一个短暂流行的新名词吗？

至少从 OpenAI 这篇文章看，我不太愿意把它理解成一种可以直接安装的框架，也不觉得它会替代 Spec、测试或者软件架构。

它更像是一组围绕 Agent 重新组织工程环境的原则：

* 把需要持续生效的知识放进 Agent 可以访问的仓库；
* 用索引和渐进式披露代替无限膨胀的入口文件；
* 让 Agent 能够启动和操作真实软件；
* 把 Logs、Metrics 和 Traces 也开放为环境反馈；
* 将稳定的工程品味转化为 Lint 和结构测试；
* 在明确边界内保留实现自主权；
* 将代码库漂移视为需要持续回收的熵；
* 先降低发现和修复错误的成本，再重新讨论合并速度；
* 只在真正需要判断时把任务交还给人。

它没有让软件工程纪律消失。

变化的是，纪律越来越多地体现在支撑代码生成的结构中，而不只体现在人亲手写出的代码中。

我原本把 AI-Native 开发主要理解成：

> 人先把 PRD、TRD 和任务拆清楚，再让 Agent 提高实现效率。

现在我会在后面再补一句：

> 还要让仓库向 Agent 暴露正确知识、真实环境、可执行约束和验证反馈，使它能发现自己何时失败，并在失败以后继续修正。

如果只能从这篇文章中先抄一个设计，我不会先搭多 Agent 编排，也不会立即部署完整的可观测性平台。

我会先把 `AGENTS.md` 从说明书改成地图。

接着选择一个真实 Web 问题，让 Coding Agent 自己完成一次“复现—修改—重启—重放—验证”。

最后，再把一条已经重复出现的 Review 意见变成机器检查。

这三个实验都很小，却分别对应 Harness 最基本的三个问题：

| 实验              | 要验证的问题              |
| --------------- | ------------------- |
| 导航型 `AGENTS.md` | Agent 能不能找到正确知识？    |
| Browser 验证闭环    | Agent 能不能观察并证明修改结果？ |
| Review 规则机械化    | 人的稳定判断能不能被系统持续执行？   |

至于 Agent-to-Agent Review、高吞吐合并和自动垃圾回收，我暂时只把它们记录下来。

OpenAI 已经证明它们可以在自己的代码库和基础设施中工作，但这还不能说明我的项目已经值得承担同样的建设成本。

读到这里，我暂时不会把 Harness Engineering 理解成某个固定技术栈。

它更像一个持续追问：

> Agent 下一次还需要人类接管的地方，究竟是不可替代的判断，还是尚未被工程化的环境缺口？

前者应当继续留给人。

后者，才是 Harness Engineering 真正开始的地方。
