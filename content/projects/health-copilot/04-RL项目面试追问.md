> 这是**项目经历边界与研究设想**，不是 RL 训练报告。PPO/GRPO/DPO 等通用原理见[通用 Agent/LLM 八股](/projects/health-copilot/05-agent-llm通用八股/)；项目路线见[首页](/projects/health-copilot/)。

## 必须先背：项目没有做 RL

Health-Copilot roadmap 中 M11 Learned Harness Policy / Post-training 仍是 future，未启动。仓库没有 Health-Copilot 的 SFT、DPO、PPO、GRPO 或 GSPO 训练 run，也没有可报告的训练前后 benchmark delta。不能把本地 Qwen3 GGUF 推理、RAG prompt、RRF weight grid、Agent 多次调用或 memory synthetic suite 叫 RL。

### 面试官问“你在项目里做了什么 RL？”

**准确回答**：

> 我目前没有在 Health-Copilot 上训练或评估 RL/post-training policy。我的已完成经历是检索实验、受限 Agent Runtime、Memory/Context contracts 和小型 Agent Team 对照。RL 是 M11 的 future direction，还没有 rollout、reward、policy update 或 held-out post-training result。我可以解释如果要做，如何把一个有可验证 reward 的 decision problem 定义出来，但不会把计划当经历。

说“没有做”不是减分项；被追问公式时再去[通用八股](/projects/health-copilot/05-agent-llm通用八股/)讲算法，不要把理论熟悉度冒充训练经验。

## 哪些结果不是 RL

| 项目活动 | 为什么不等于 RL |
| --- | --- |
| Qwen3-8B 生成 retrieval bridge | 一次固定 prompt inference；没有 reward feedback 后的 policy update |
| DEV 上选 RRF `k/weights` | 离线有限网格的 retrieval configuration selection，不是 policy gradient |
| Agent 根据 observation 选 tool/final | inference-time action selection；没有训练 policy |
| Memory ADD/UPDATE/DELETE/NOOP contract | runtime 接收并校验显式操作，没有学习写入策略 |
| M8 三次重复 trial | evaluation replication，不是 rollout training |
| PPO/GRPO 的公式或论文阅读 | 理论学习，不是训练经历 |

## 如果未来真做，可能怎样形式化

可研究的方向不是“为了简历跑个 GRPO”，而是受限的 **memory/harness policy**：

```text
state s_t:
  当前任务目标、已有 typed memory、provenance、时间有效性、Context budget
action a_t:
  ADD / UPDATE / DELETE / NOOP，或选择哪些 ContextItem 投影
runtime:
  仍执行 consent、scope、sensitivity、expiry、evidence 和 budget hard constraints
reward:
  held-out task usefulness − stale retrieval penalty − privacy/scope violation penalty
trajectory:
  多轮合成/公开任务 state transition，而不使用真实患者数据
evaluation:
  对照 deterministic policy、no-memory、recent-history；测 utility、stale/leakage、budget、cost
```

这只是可检验的 formulation 候选，**不是当前实现**。其中 privacy/consent/safety 不适合只交给 reward 学；必须保留 runtime hard gate。若 reward 只奖励短期 QA correctness，可能鼓励过度记忆、保存敏感信息或从偶然相关记录投机答题。需要分解 reward、offline holdout、人工/独立 grader 和反事实案例。

RAG retrieval policy 也可以研究何时用 closed-book、BM25、dense 或 team，但本项目之前的 router/result 不能直接当成 RL 训练数据；必须先检查 action coverage、counterfactual outcome、reward leakage 和 query split，再决定是否值得学 policy。手工调阈值或在 DEV 上选网格仍然是 conventional model selection。

## 高频追问的安全答法

### “你们为什么不直接对 memory policy 做 GRPO？”

因为目前没有足够可靠的 rollout/reward 数据和独立 held-out task，也没有先证明 learned policy 比 deterministic policy 带来用户价值。M10 先把 provenance、expiry、scope、write authority 和 context projection 做成可验证底座；不应让训练去学习绕过本来必须是硬约束的隐私/安全规则。

### “memory 任务的 reward 怎么避免 reward hacking？”

只用回答正确率会诱导把更多内容记下来、把高频项当成相关项，甚至保存敏感信息。要把任务成功、记忆精确率、stale retrieval、cross-scope/deleted leakage、context cost 分开度量；对 privacy/scope violation 设 runtime veto，而不是仅扣 reward。评估应在不同轨迹与数据来源上 hold out，并人工抽查 reward 与真实目标是否一致。

### “RRF 权重是 policy learning 吗？”

不是。它是在 DEV 上对预先声明的小型超参数 grid 做 selection；没有 gradient、policy rollout 或 reward-based optimization。报告应叫 DEV configuration selection。

### “项目里有没有做 SFT/RLVR？”

没有。我们固定现成 GGUF 模型做 inference；未微调权重、未构造 RLVR training loop，也没有优化模型参数。若未来探索 RLVR，先需要可自动验证且不易被投机的 retrieval/memory outcomes，再建立新 protocol。

### “那这篇为什么放在项目面试文档里？”

因为面试官可能会从 Agent/Multi-Agent/Memory 延伸问 policy learning。最专业的回应是明确当前实现边界，说明已经有怎样的可验证 substrate，以及什么时候才值得进行学习型优化。

## 学习路线（不等于项目实现）

先在通用八股区掌握 SFT vs DPO vs online RL、policy gradient、PPO clipped objective、GRPO group-relative advantage、KL/reference policy、reward hacking、entropy/KL/clip diagnostics。之后再读：

1. PPO 原论文，弄清 likelihood ratio、clipping 和 advantage。
2. DPO 原论文，弄清 preference pair 如何消去显式 reward-model/RL loop，以及它并非“完全没有隐含目标”。
3. DeepSeekMath/GRPO 论文，弄清 group baseline 的 memory trade-off 与 reward normalization 边界。
4. GSPO 原文与官方训练报告，区分 sequence-level ratio 与常见 token-level GRPO，避免只背缩写。
5. M10 的 Memory-R1/MemAct source alignment，再问：哪些 memory action 真的应该学习，哪些必须由 deterministic authorization policy 拦住？

核心回答不是“我用了 GRPO”，而是：**目前没有训练；如果做，会先写清 state/action/reward、强制约束、baseline 和 unseen eval，再决定算法。**
