# 悦动体育 00：基础概念与阅读方法

## 第一课

阅读一个真实项目时，最容易卡住的地方通常不是语法，而是代码中的概念没有对上号：看到 method 不知道它和路径有什么关系，看到 data 不知道它最终会落到哪里，看到 Authorization 不知道它是在证明身份还是决定权限。

所以“能读 TypeScript/JavaScript”“知道 HTTP、JSON、JWT 和关系型数据库”它们正是我们要在正文里补齐的基础。我们只从悦动体育已经存在的代码出发，一边看项目，一边认识这些概念。

读完以后，你应该能够完成四件事：

1. 从 C 端或 B 端的一段请求中，指出 method、path、header 和 body。
2. 解释 JSON 如何承载预约参数，以及它和 JWT 为什么不在同一个位置。
3. 看懂普通用户认证、后台管理员认证和角色授权之间的边界。
4. 从 venue → court → session → session_reg 找到一条业务数据链，并理解预约代码为什么要使用锁和事务。

本文使用的源码范围包括：

| 工程 | 目录 | 本篇观察点 |
| --- | --- | --- |
| 后端 | yuedong_nestjs | 全局路由前缀、认证守卫、场次服务、Prisma 数据模型 |
| C 端 | yuedong-v2-frontend | uni.request、请求头、Token、查询参数 |
| B 端 | yuedong_front | Fetch 封装、Bearer Token、管理员请求 |

## 读后端前，先把技术栈的台阶摆出来

第一次打开后端仓库时，容易把“语言、框架、数据库工具”看成一件事。它们其实处在不同层次：

| 名词 | 先记住什么 | 在本文中的位置 |
| --- | --- | --- |
| JavaScript | 浏览器和 Node.js 都能执行的语言 | 前端请求工具使用它 |
| TypeScript | 在 JavaScript 上增加类型标注的语言 | NestJS 后端使用它 |
| Node.js | 让 JavaScript/TypeScript 能在服务器运行的运行时 | 后端进程运行在这里 |
| NestJS | 组织后端模块、controller、service 和 guard 的框架 | 负责把请求分发到业务代码 |
| MySQL | 真正保存表、行和关系型数据的数据库 | 保存用户、场馆、场次、订单 |
| Prisma | 让 TypeScript 代码按 model 查询 MySQL 的 ORM | 代码中的 prisma.session.findMany |
| Redis | 适合快速读写键值的独立存储 | 预约锁、缓存等能力会用到它 |
| JWT | 放在请求中的一种身份凭据格式 | 由 AuthGuard/AdminGuard 验证 |

这里先把 Prisma 说清楚。Prisma 不是数据库，它更像是 TypeScript 和 MySQL 之间的翻译层：schema.prisma 描述 model 与关系，代码调用 prisma.session.findMany，Prisma 再把这次查询转换成数据库能执行的语句。你现在不需要先学会 SQL 优化，也不需要背完 Prisma API；只要先能分辨“数据存在哪里”和“代码通过什么工具访问它”。

同样，NestJS 里的 controller 和 service 也不是两个数据库表。controller 负责接住路由参数，service 负责组织业务规则；guard 在请求进入业务代码前做身份检查。后文会用场次查询把这三层连起来。

读这些代码时，先只认三个 JavaScript/TypeScript 动作就够了：

~~~ts
const options = { method: 'GET', data: { venueId: 12 } };
const result = await request(options);
return result.data;
~~~

第一行创建一个对象，第二行调用函数并等待结果，第三行取出结果中的字段。TypeScript 可能再给对象和函数加类型，但不会改变这三个基本动作。先能读懂这类结构，再逐步认识 NestJS、Prisma 和 MySQL，技术栈就会变成一层层可定位的工具，而不是一堵墙。

先看一张总图：之后看到某一段代码时，我们就能知道它在三端链路中的位置是什么。

![悦动体育三端与后端边界](/projects/yuedong-sports/yuedong-00-three-repositories.png)

图中客户端只通过 API 与后端交互，数据库、缓存和支付服务由后端协调。图里的英文标签是为了保持技术名词稳定；具体接口路径以源码为准。

> 本篇的阅读顺序是：先看一条请求，再看请求中的身份信息，最后追到数据库。不要一上来就从 43 个 model 里猜业务；先让一条请求把这些概念串起来。

## 1. 先看懂一条请求

### 1.1 HTTP 请求：方法、路径、头和正文

HTTP 请求可以先拆成四个观察点：

| 部分 | 它回答的问题 | 在悦动体育中的例子 |
| --- | --- | --- |
| method | 想对资源做什么 | GET 查询，POST 提交 |
| path | 想访问哪类资源 | /api/venues、/api/sessions/reserve |
| header | 请求携带哪些额外信息 | Content-Type、Authorization |
| body | 这次提交的结构化数据是什么 | 预约日期、场次、数量等 |

在 C 端的统一请求工具里，前端先把相对路径和 API 基址拼成完整地址，再准备请求头：

~~~js
const fullUrl = url.startsWith('http') ? url : CONFIG.API.BASE_URL + url;
  
// 构建请求头
const requestHeaders = {
  'Content-Type': 'application/json',
  ...header
};
~~~

随后这些参数会被交给 uni.request：

~~~js
const response = await uni.request({
  url: fullUrl,
  method,
  data,
  header: requestHeaders
});
~~~

这里的 method、url、data 和 header 不是四种不同的请求，而是同一个 HTTP 请求的不同组成部分。把它们放在一起看，才容易理解页面按钮最后是怎样触发后端逻辑的。

后端在 main.ts 中设置了全局前缀：

~~~ts
app.setGlobalPrefix('api');

const port = process.env.PORT ?? 8080;
await app.listen(port, '0.0.0.0');
~~~

这意味着 controller 中写的 venues 或 sessions，对外访问时会带上 /api。B 端模块又通过 RouterModule 注册了 business 路由前缀：

~~~ts
RouterModule.register([
  {
    path: 'business',
    module: AdminModule
  },
  {
    path: 'business',
    module: MerchantModule
  },
  {
    path: 'business',
    module: SessionModule
  }
]);
~~~

因此，阅读路径可以先看成一封从客户端寄往后端的请求：方法和路径决定它要做什么，header 和 JSON body 携带额外信息。

![HTTP 请求的四个组成部分](/projects/yuedong-sports/yuedong-00-http-request-anatomy.png)

图中的 POST /api/bookings 只是概念示例，不是悦动体育当前已核实的具体接口；项目中的真实路径仍以 controller 与模块路由拼接结果为准。

在当前项目中，下面几种请求表达的是不同动作：

| 请求 | 初步阅读 |
| --- | --- |
| GET /api/venues | 查询 C 端可以展示的场馆资源 |
| GET /api/sessions/venue/:venueId | 查询某个场馆下的场次 |
| POST /api/sessions/reserve | 提交预约操作，可能改变场次或订单状态 |
| GET /api/business/venues | 从 B 端路由前缀进入后台场馆管理接口 |

GET 通常表达读取，参数常常出现在 query string；POST 通常表达提交一项业务动作，数据更多放在 body 中。最终是否改变数据，仍然要以 controller 和 service 的实现为准。

#### 用一段请求做定位

假设你在页面里看到一个“预约”按钮，可以按下面的顺序定位：

1. 找到按钮事件调用的 request 函数。
2. 记录 method、path、query、body 和是否需要认证。
3. 用 main.ts 的全局前缀补出对外路径。
4. 找到 sessions 相关 controller，再进入 service。
5. 最后确认 service 修改了哪些 session、order 或 registration 数据。

此时不要先问“这个按钮用了哪个组件”，而要先记录：

- 请求的完整路径是什么？
- method 是读取还是提交？
- body 中有哪些字段？
- 是否需要 Authorization？
- 后端 controller 把请求交给了哪个 service？

这五个问题会把页面阅读带到业务链路，而不是停留在按钮样式。

#### 面试官可能会问

**Q：在悦动体育中，POST /api/sessions/reserve 的 method、path、header、body 分别负责什么？**

**A：** POST 表示提交一次会产生业务处理的动作；path 表示请求进入 /api 下的 sessions reserve 资源；header 携带 Content-Type 或 Authorization 等元信息；body 携带预约场次、数量等业务输入。/api 由后端全局前缀补上，最终局部路径还要回到 controller 确认。

**追问：为什么不能只看页面上的按钮名称判断接口行为？**

因为按钮名称是 UI 文案，真正的读写行为由 method、controller 和 service 的实现决定。面试时我会继续追踪请求如何进入 controller，以及 service 是否修改了 session、order 等数据。

源码定位：yuedong-v2-frontend/utils/request.js:33-64、yuedong_nestjs/src/main.ts:23-26、yuedong_nestjs/src/business/business.module.ts:26-67。

### 1.2 JSON：请求和响应之间的结构化载荷

上一节里出现了 data。如果它只是一个没有结构的字符串，后端就很难稳定地读取“场次 id”“预约数量”“会员卡号”这些字段。JSON 解决的是正文内部的结构问题。

在 C 端请求工具里，data 作为对象交给 uni.request，请求头声明正文采用 JSON：

~~~js
const requestHeaders = {
  'Content-Type': 'application/json',
  ...header
};

const response = await uni.request({
  url: fullUrl,
  method,
  data,
  header: requestHeaders
});
~~~

JSON 能表达对象、数组、字符串、数字、布尔值和 null。例如，一次预约的请求正文可以长这样：

~~~json
{
  "sessionIds": [1024, 1025],
  "quantity": 1,
  "cardNumber": null
}
~~~

上面是为了理解结构写的示意数据，不代表本文已经从 Network 面板确认了当前线上请求的完整字段。实际字段要以调用处、DTO 和 controller 为准。DTO 是 Data Transfer Object，数据传输对象；在这里先把它理解成“约束和承载请求字段的对象或类”。项目代码中，SessionService.reserveSessions 的方法参数包含 sessionId、openid 和可选的 cardNumber；预约相关 DTO 还需要继续与调用方交叉核对。

响应也可以使用 JSON：

~~~json
{
  "message": "Successfully get sessions",
  "statusCode": 200,
  "data": [
    {
      "sessionId": 1024,
      "date": "2026-09-10",
      "startTime": "18:00",
      "endTime": "19:00",
      "price": 80,
      "status": "available"
    }
  ]
}
~~~

后端的 service 会把数据库字段映射成前端更容易消费的对象。例如 getSessions 查询 session 时，同时 include 场地名称和类别，然后返回 sessionId、startTime、capacityUsed 等字段。这里有两个重要区别：

1. 数据库字段名、后端返回字段名和前端使用字段名可以不同，但转换必须发生在明确的代码位置。
2. Content-Type: application/json 说明正文的媒体类型，不等于它自动保证字段一定正确。

可以把 HTTP 和 JSON 的分工画成两条线：

![JWT 凭据与 JSON 业务输入在请求中的位置](/projects/yuedong-sports/yuedong-00-json-jwt-separation.png)

上图中的 name 和 amount 只是帮助理解 JSON 结构的示例字段，不是悦动体育已确认的业务契约。真正阅读项目时，仍然要把调用方、DTO 和 controller 放在一起核对。

因此，JSON body 和 JWT 不是一回事。预约数量属于业务数据，应该进入 body；身份凭据通常放在 Authorization header。下一节会把这两条线分开。

#### 面试官可能会问

**Q：Content-Type: application/json 和 Authorization: Bearer ... 同时出现在一个请求中时，分别解决什么问题？**

**A：** Content-Type 描述 body 的媒体类型，让服务端知道正文按 JSON 解析；Authorization 携带身份凭据，供认证 guard 验证请求者。一个解决“正文怎么读”，一个解决“请求来自谁”，两者不能互相替代。

**追问：JSON 字段名对不上时，HTTP 层会自动帮我们转换吗？**

不会。字段映射必须由 DTO、controller、service 或专门的适配代码明确完成。比如前端传 venueId、后端读取 venue_id，不能因为两者都是 JSON 字段就假设框架会自动转换。

源码定位：yuedong-v2-frontend/utils/request.js:35-64、yuedong_nestjs/src/consumer/session/session.service.ts 中 getSessions 和预约方法。

## 2. 再解释“谁在请求”

### 2.1 JWT：通过 Authorization header 随请求传递的凭据

登录成功后，客户端通常需要在后续请求中带上某种凭据。悦动体育的代码使用 Bearer Token 形式的 Authorization header；其中 Token 的具体内容由 JWT 机制承载。后面代码里的 payload 可以先理解为 Token 验证后得到的载荷对象，里面放着 openid 或 username 这样的身份字段。

> 面试回答建议：先给出一句结论，再落到悦动体育的具体代码，最后主动说清楚当前证据没有覆盖什么。这样比只背“JWT 是无状态认证”更能说明你真的读过项目。

C 端请求工具的认证分支是：

~~~js
if (needAuth) {
  const token = uni.getStorageSync('token');
  if (token) {
    requestHeaders.Authorization = `Bearer ${token}`;
  } else {
    console.warn('⚠️ 需要认证但token不存在');
  }
}
~~~

B 端的 API 封装也做了同样的事情：

~~~js
getHeaders() {
  const headers = {
    'Content-Type': 'application/json'
  };

  const token = this.getToken();
  if (token) {
    headers['Authorization'] = `Bearer ${token}`;
  }

  return headers;
}
~~~

这里的格式可以先按“字段名 + 认证方案 + Token 值”来读。Bearer 是当前请求采用的认证方案，后面的字符串才是实际交给后端验证的 Token。

后端 AuthGuard 通过空格拆分 header，只接受类型为 Bearer 的第一段：

~~~ts
private extractTokenFromHeader(request: any): string | undefined {
    const [type, token] = request.headers.authorization?.split(' ') ?? [];
    return type === 'Bearer' ? token : undefined;
}
~~~

普通用户的认证流程随后会验证 Token，并从 payload 中取出 openid，再到数据库寻找用户：

~~~ts
const payload = this.jwtservice.verify(token);
const { openid } = payload;

if (!openid) {
    throw new HttpException('Authorization failed', HttpStatus.UNAUTHORIZED);
}

const user = await this.userService.findUser(openid);
if (!user) {
    throw new HttpException('Authorization failed', HttpStatus.UNAUTHORIZED);
}

request.openid = openid;
~~~

这段代码能确认的事实是：当前 guard 会验证 Token、读取 openid、查询用户，并把 openid 放到 request 上供后续业务使用。仅凭这些文件，不能推断 JWT 使用了哪一种签名算法、密钥如何轮换，也不能把 Token 解码等同于验证成功。

#### 认证流程的四个检查点

1. 客户端有没有从存储中取到 Token？
2. 请求头是不是 Authorization: Bearer <token>？
3. 后端能不能验证 Token？
4. payload 中的 openid 是否对应数据库中的用户？

任何一步失败，都不应该继续把请求当成已登录用户的操作。

#### 面试官可能会问

**Q：为什么预约数量不应该放进 Authorization，而应该放在 JSON body？**

**A：** 预约数量是本次业务动作的输入，属于 JSON body；Token 是证明请求身份的凭据，属于 Authorization header。把业务参数塞进认证字段，会让认证层和业务层失去边界，也不符合这套请求工具和 guard 的读取方式。

**追问：JWT 解码成功，是否就说明请求一定可信？**

不一定。解码只是把字符串还原成 payload；当前 AuthGuard 还会验证 Token，并根据 payload 中的 openid 查询真实用户。是否过期、签名是否有效、用户是否存在，都要看验证和查询结果。

源码定位：yuedong-v2-frontend/utils/request.js:41-49、yuedong_front/src/api/index.js:66-77、yuedong_nestjs/src/auth/auth.guard.ts:61-89。

### 2.2 认证和授权是两个动作

“认证”回答：你是谁？  
“授权”回答：你作为这个人，能不能做当前这件事？

在悦动体育里，普通用户和后台管理员并不是同一种身份上下文。AuthGuard 读取 payload 中的 openid，随后查用户；AdminGuard 读取 payload 中的 username，查询 admin 表，并检查管理员状态和角色。

![普通用户与后台管理员的认证授权边界](/projects/yuedong-sports/yuedong-00-authentication-authorization.png)

图中把认证和授权拆成两段：先确认凭据对应哪个身份，再决定这个身份能否访问当前 API。实际是否挂载了哪个 guard，还需要回到每个 controller/module 核对。

管理员 guard 的核心逻辑可以缩成下面这段：

~~~ts
const payload = this.jwtService.verify(token);
const { username } = payload;

const admin = await this.prisma.admin.findUnique({
    where: { username }
});

if (!admin) {
    throw new HttpException('授权失败', HttpStatus.UNAUTHORIZED);
}

if (admin.status !== true) {
    throw new HttpException('账号已被禁用', HttpStatus.FORBIDDEN);
}

const requiredRoles = this.reflector.get<string[]>('roles', context.getHandler());
if (requiredRoles && requiredRoles.length) {
    if (!requiredRoles.includes(admin.role)) {
        throw new HttpException('权限不足', HttpStatus.FORBIDDEN);
    }
}
~~~

对应关系可以这样记：

| 层次 | 当前代码中的观察 |
| --- | --- |
| 认证 | 验证 Bearer Token，读取 openid 或 username |
| 身份查询 | userService.findUser(openid) 或 prisma.admin.findUnique |
| 状态检查 | 管理员 status !== true 时返回 403 |
| 角色授权 | 将 handler 上的 roles 与 admin.role 比较 |
| 业务身份传递 | 将 request.openid 或 request.admin 放入请求对象 |

这里有一个值得在后续复盘中继续追踪的边界：当前快照的普通用户 AuthGuard 将 /api/business/.* 放在完全豁免认证路径中，而 AdminGuard 自己又实现了管理员 Token、账号状态和角色检查。这只能说明两个 guard 的代码行为不同，不能直接推断每个 B 端接口最终都安全或不安全。要得出结论，还要逐个确认 controller/module 使用了哪一个 guard。

这就是项目阅读中“事实”和“判断”的区别：

- [源码事实]：某个 guard 的白名单正则包含 /api/business/.*。
- [需要继续验证]：所有 B 端业务接口是否都经过 AdminGuard。
- [不能直接推出]：看到 B 端有登录页，就认为接口已经受保护。

#### 用一个检查清单阅读权限代码

- 请求是普通用户 API 还是后台 API？
- Token payload 中用的是 openid 还是 username？
- guard 是否查询了数据库中的真实身份？
- 是否检查账号状态？
- 是否读取 handler 上的角色要求？
- controller 是否真的挂载了预期的 guard？
- 未登录和无权限是否分别返回 401 与 403？

#### 面试官可能会问

**Q：管理员 Token 验证成功，但 admin.status 为 false，这属于认证失败还是授权结果失败？**

**A：** Token 能被验证，说明身份凭据本身通过了；但管理员账号已被禁用，AdminGuard 返回 403 Forbidden，属于授权阶段拒绝访问。若没有 Token 或 Token 验证失败，才是认证阶段的 401。

**追问：前端把某个菜单隐藏起来，能不能代替后端授权？**

不能。隐藏菜单只改变界面展示，调用者仍然可以直接构造 HTTP 请求。真正的权限判断必须在后端 guard 或业务服务中完成，并且需要检查 controller 是否确实挂载了预期的 guard。

源码定位：yuedong_nestjs/src/auth/auth.guard.ts:61-104、yuedong_nestjs/src/auth/admin.guard.ts。

## 3. 最后看懂数据落在哪里

### 3.1 表、行、主键和外键表达业务关系

关系型数据库可以先用四个词开始：

- 表：一类对象的集合，例如场地或场次。
- 行：表中的一条具体记录，例如“2026-09-10 18:00 的 3 号场”。
- 主键：唯一标识一行记录的字段，例如 session_id。
- 外键：把一张表中的记录指向另一张表，例如 session.court_id 指向 court.court_id。

悦动体育的 Prisma schema 里，court 负责描述场地，session 负责描述可被预约的具体时间段。court 的关键字段如下：

~~~prisma
model court {
  court_id          Int      @id @default(autoincrement()) @db.UnsignedInt
  venue_id          Int      @db.UnsignedInt
  category          court_category
  name              String   @db.VarChar(20)
  status            court_status @default(available)
  capacity          Int?
  venue             venue    @relation(fields: [venue_id], references: [venue_id], onDelete: Cascade)
  session           session[]
}
~~~

一条 court 记录只能说明“哪一个场地”，还不能说明“哪一天、几点到几点”。这些信息在 session：

~~~prisma
model session {
  session_id            Int      @id @default(autoincrement()) @db.UnsignedInt
  venue_id              Int      @db.UnsignedInt
  court_id              Int      @db.UnsignedInt
  date                  DateTime @db.Date
  start_time            DateTime @db.Time(0)
  end_time              DateTime @db.Time(0)
  price                 Decimal  @db.Decimal(10, 2)
  capacity_total        Int?
  capacity_used         Int      @default(0)
  status                session_status?
  event_id              Int?
  court                 court    @relation(fields: [court_id], references: [court_id])
  venue                 venue    @relation(fields: [venue_id], references: [venue_id])
  session_reg           session_reg[]
}
~~~

因此可以把一条普通预约资源读成一条关系链：

![场馆、场地、场次与预约记录的数据关系](/projects/yuedong-sports/yuedong-00-relational-model.png)

图中的连线表达表之间的关系；主键、外键和具体字段仍以 Prisma schema 为准。它不是页面目录，而是一次预约会穿过的业务数据结构。

这不是单纯的目录层级，而是业务关系：

| 数据 | 在业务中的含义 |
| --- | --- |
| venue | 一个体育场馆 |
| court | 场馆中的一块具体场地 |
| session | 该场地在某个日期和时间段的可预约资源 |
| session_reg | 用户对某个场次的一次登记/预约关系 |
| order | 与这次预约关联的交易记录 |

session 同时拥有 capacity_total 和 capacity_used，说明项目既要支持无容量的单场占用，也要支持有容量的场次。当前 SessionService.reserveSessions 会明确拒绝把有容量场次交给普通的无容量预约接口处理，这种“先区分业务类型，再进入不同库存逻辑”的做法值得在后续文章继续展开。

#### 从数据库字段反推页面字段

后端 getSessions 查询场次时，会 include court 的 name 和 category，然后把数据库字段转换成接口对象：

~~~ts
return sessions.map((session) => ({
    sessionId: session.session_id,
    courtId: session.court_id,
    date: this.formatDate(session.date),
    startTime: this.formatTime(session.start_time),
    endTime: this.formatTime(session.end_time),
    price: parseFloat(session.price.toString()),
    status: session.status,
    name: session.court.name,
    category: session.court.category,
    capacityTotal: session.capacity_total,
    capacityUsed: session.capacity_used
}));
~~~

这里就能看到三种命名之间的转换：

| 数据库字段 | 接口字段 | 处理 |
| --- | --- | --- |
| session.session_id | sessionId | 直接改成前端常用的驼峰命名 |
| session.start_time | startTime | 同时格式化时间 |
| session.capacity_used | capacityUsed | 保留容量统计语义 |

以后如果页面显示“场地名称”“剩余容量”或“已预约”，可以沿着返回对象反查数据库，而不是凭字段名猜测。

#### 面试官可能会问

**Q：为什么 court 和 session 不能合并成一张简单的“场地表”？**

**A：** 一个 court 会在很多日期和时间段重复提供资源。court 描述相对稳定的场地本身，session 描述一次具体时间资源；拆开后，日期、价格、状态和容量可以独立变化，也能让预约关系指向具体时间段。

**追问：Prisma model 是数据库本身吗？**

不是。MySQL 才是保存表和行的数据库，Prisma 是 TypeScript 访问 MySQL 的 ORM；schema.prisma 用 model 描述数据结构和关系，prisma.session.findMany 是代码侧的查询调用。

源码定位：yuedong_nestjs/prisma/schema.prisma:37-52、schema.prisma:374-400、yuedong_nestjs/src/consumer/session/session.service.ts 的 getSessions。

### 3.2 事务：把一次业务修改变成可回滚的数据库操作

预约不是简单地把一行 status 改成 reserved。至少要同时考虑：

1. 场次是否存在。
2. 场次是否仍然可预约。
3. 这次请求是否拿到了正确的库存控制权。
4. 状态更新是否全部成功。
5. 预约登记和订单相关写入是否应该一起成功。

SessionService.reserveSessions 的外层先使用场次锁，内部再进入 Prisma transaction：

![预约竞争中的锁、事务与条件更新](/projects/yuedong-sports/yuedong-00-transaction-race.png)

这张图把“两个请求同时抢同一个场次”的结果画出来：锁负责协调进入顺序，事务负责成组提交，条件更新负责确认数据库中的状态仍然是 available。图中的单赢家是并发控制示意，具体锁实现仍要继续阅读 booking-inventory.service.ts。

~~~ts
return await this.bookingInventoryService.withSessionLocks(
    sessionId,
    async () =>
        await this.prisma.$transaction(async (tx) => {
            const sessions = await tx.session.findMany({
                where: {
                    session_id: { in: sessionId }
                }
            });

            // 校验场次存在、状态和业务类型
            // ...

            const updateResult = await tx.session.updateMany({
                where: {
                    session_id: { in: sessionIds },
                    status: 'available',
                    capacity_total: null
                },
                data: {
                    status: 'reserved'
                }
            });

            if (updateResult.count !== sessionIds.length) {
                throw new HttpException(
                    '场次已被其他用户预订，请刷新后重试',
                    HttpStatus.BAD_REQUEST
                );
            }

            // 后续创建订单、登记预约等操作仍使用 tx
        })
);
~~~

这里有两个容易混淆的“保护”：

| 机制 | 主要解决什么问题 |
| --- | --- |
| withSessionLocks | 在业务入口处协调同时操作同一批场次的请求 |
| $transaction | 让同一组数据库读写作为一个整体提交或回滚 |
| updateMany 的条件 | 只有仍为 available 的记录才允许被更新 |
| updateResult.count | 用实际更新行数判断是否有竞争请求先一步完成 |

如果查询时看到场次可用，随后更新时它已经被别人抢走，条件更新的计数就不会等于期望数量。代码会抛出异常，事务中的写入不会以“半成功”的状态继续向下提交。

这仍然不是完整的并发理论。当前本文只确认了代码中存在锁、transaction、条件更新和结果计数检查；锁的实现细节、MySQL 隔离级别、重试策略和外部支付回调的一致性，会在后续库存与订单专题中单独分析。

#### 面试官可能会问

**Q：为什么不能只先 findMany 看见所有场次都是 available，然后无条件 updateMany？**

**A：** 两个请求可能同时读到 available。更新时必须把“仍然可用”作为条件，并检查实际更新数量；否则第二个请求可能覆盖第一个请求的结果，出现超卖或状态错乱。

**追问：Redis 锁和数据库事务分别解决什么问题？**

Redis 锁主要协调多个请求不要同时进入同一批库存操作；数据库事务保证这一批数据库读写要么整体提交，要么在异常时回滚。两者不是同一个层次，也不能因为有事务就自动得到完整的分布式锁语义。

源码定位：yuedong_nestjs/src/consumer/session/session.service.ts:395-510、yuedong_nestjs/src/common/inventory/booking-inventory.service.ts。

## 4. 用四个概念阅读 Yuedong 源码

### 4.1 用 Controller → Service → Data 找一条后端请求

到这里，可以把一次“查询场次”请求完整走一遍。

#### 第一步：从客户端确认请求形状

C 端统一请求工具负责拼接 URL、准备 header，并调用 uni.request。请求可能是：

~~~text
GET /api/sessions/venue/12?startDate=2026-09-10&endDate=2026-09-10
~~~

这里的日期过滤参数在 GET 请求的 query string 中，而不是 JSON body。

#### 第二步：从 controller 确认入口

后端 SessionController 将局部路径写成：

~~~ts
@Controller('sessions')
export class SessionController {
    constructor(private readonly sessionService: SessionService) {}

    @Get('venue/:venueId')
    async getSessions(
        @Param('venueId') venueId: string,
        @Query('category') category?: string,
        @Query('startDate') startDate?: string,
        @Query('endDate') endDate?: string
    ): Promise<Message> {
        const sessions = await this.sessionService.getSessions(
            Number(venueId),
            false,
            category,
            startDate,
            endDate
        );

        return {
            message: 'Successfully get sessions',
            statusCode: 200,
            data: sessions
        };
    }
}
~~~

@Controller('sessions') 与 @Get('venue/:venueId') 拼起来是 /sessions/venue/:venueId；再加 main.ts 的全局 /api，就得到客户端看到的 /api/sessions/venue/:venueId。

#### 第三步：进入 service 看业务规则

SessionService.getSessions 先按 venue_id 查询，再根据日期和类别拼接 where 条件：

~~~ts
const where: any = {
    venue_id: venueId
};

if (startDate || endDate) {
    const dateCondition: any = {};
    // 解析 startDate / endDate，并检查区间
    where.date = dateCondition;
} else if (onlyFuture) {
    where.date = {
        gte: new Date()
    };
}

const sessions = await this.prisma.session.findMany({
    where,
    include: {
        court: {
            select: {
                name: true,
                category: true
            }
        }
    },
    orderBy: [{ date: 'asc' }, { start_time: 'asc' }]
});
~~~

#### 第四步：最后才看 data model

service 使用 prisma.session.findMany，说明查询落在 session model；include.court 又说明页面需要场地名称和类别。此时再回到 schema，看 session.court_id 与 court.court_id 的关系，数据链就闭合了。

#### 面试官可能会问

**Q：如果让你现场说明 GET /api/sessions/venue/:venueId 的执行链路，你会怎么回答？**

**A：** 我会先从 C 端请求工具确认 method、路径和 query；然后由 main.ts 的全局前缀拼出 /api；SessionController 的 sessions 与 venue/:venueId 组成局部路由，并把参数传给 SessionService.getSessions；service 再通过 Prisma 查询 session，并 include court，最后把数据库字段映射成前端对象返回。

**追问：为什么排查接口问题时不建议只看 controller？**

因为 controller 往往只负责接参数和组织响应，日期过滤、状态判断、库存检查以及数据库写入通常在 service 或更下层。只看 controller，容易误把“路由能进来”当成“业务已经正确”。

### 4.2 读完基础概念后，下一篇从三端边界开始

基础概念的目的不是让你背名词，而是让后面的项目复盘有共同坐标：

| 后续复盘问题 | 本篇提供的坐标 |
| --- | --- |
| C 端为什么请求 /api/...？ | HTTP path 与全局前缀 |
| B 端为什么出现 /api/business/...？ | 模块路由前缀 |
| 登录后每次请求为什么要带 Token？ | JWT 与 Authorization header |
| 普通用户和后台管理员为什么不能混用？ | 认证身份与授权角色 |
| 一个场次为什么能被多人同时抢？ | session 资源与并发更新 |
| 预约为什么要做锁和 transaction？ | 业务原子性与数据库一致性 |

下一篇将从三个工程的边界开始。三端关系已经在本文开头的架构图中呈现，这里只保留文字说明：

- yuedong_nestjs：给 C 端提供用户、场馆、场次、预约等 API，也给 B 端提供后台运营、审核、订单等 API。
- yuedong-v2-frontend：面向普通用户的 UniApp 小程序。
- yuedong_front：面向管理员和商户的 Vue 3 管理台。

这三端不是“前端一份、后端一份、后台一份”这么松散。它们通过以下契约互相约束：

- URL 和 HTTP method 必须匹配。
- JSON 字段必须能被双方正确解析。
- Token 的身份上下文必须对应正确的 guard。
- 数据库状态变化必须能被页面正确展示。
- 库存、支付和订单状态不能只在某一端自说自话。

#### 本篇复盘

1. 先从一个页面动作找到 API 调用。
2. 记录 method、path、header、query 和 body。
3. 找到 controller，确认路由如何拼接。
4. 找到 service，记录真正的业务判断。

#### 面试官可能会问

**Q：如果一个 B 端页面能打开，并且浏览器里保存了 admin token，是否就足以证明后台接口已经正确授权？**

**A：** 不够。还需要检查请求是否真的带上 Bearer Token、接口是否挂载 AdminGuard、Token 中的 username 是否能查到管理员、管理员是否启用，以及 handler 的角色要求是否匹配。页面能打开只说明前端路由可达，不等于后端资源授权通过。

**追问：你会如何证明自己理解了这个项目，而不是只背了技术名词？**

我会现场画出一条真实请求：从客户端 method 和 path 开始，经过 controller、service、Prisma model，再补上身份检查和并发控制。然后指出哪些是源码确认的事实，哪些还需要继续核对，而不是直接把所有行为说成已经验证。

## 本篇小结

现在可以把 00 篇压缩成一条可执行的阅读路线：

HTTP 请求 → JSON body / response → Authorization + JWT → AuthGuard / AdminGuard → venue / court / session → lock + transaction + conditional update → Controller → Service → Data。

这条路线同时也是悦动体育后续复盘的主线。遇到新功能时，先判断它处在哪一层；遇到异常时，先问请求、身份、数据和并发中的哪一个环节出了问题。
