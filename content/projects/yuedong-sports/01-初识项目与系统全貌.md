# 悦动体育 01：初识项目与系统全貌

## 这篇先解决“我到底在读什么”

打开悦动体育时，最先让人迷路的通常不是某一行 TypeScript，而是三个仓库、两套前端、一个后端、许多业务名词同时出现：

| 工程 | 入口形态 | 主要读者 |
|---|---|---|
| yuedong-v2-frontend | UniApp C 端小程序 | 运动用户 |
| yuedong_front | Vue/Vite B 端网页 | 商户、场馆或平台运营人员 |
| yuedong_nestjs | NestJS 后端 | 两端共同依赖的业务 API |

这篇不把“会读 TypeScript/JavaScript”“知道 HTTP、JSON、JWT、关系型数据库”列为 prerequisite。00 已经把这些词放进正文，本篇会继续把它们接到真实项目：请求从哪里进入，为什么 B 端多一层 business，用户和管理员为什么不是同一种授权上下文，场馆如何一步步变成可预约场次，最后怎样区分“文档写了能运行”和“我们真的验证过能运行”。

如果你刚读完 00，可以把 00 当作概念词典，把本篇当作第一张项目地图：[悦动体育 00：基础概念与阅读方法](00-基础概念与阅读方法)。

本篇的阅读结论先写在这里：

1. 三个仓库不是三个独立练习，而是 C 端、B 端和后端在代码层面的三块边界。
2. 后端默认从 /api 进入，B 端业务模块进一步组织在 /business 路径下。
3. C 端用户和 B 端管理员都可能携带 Bearer token，但后端建立的身份上下文不同。
4. Venue、Court、Price Plan、Session 和 Order 共同解释了“资源怎样变成交易”。
5. 当前源码、配置和部署文档足够建立地图，但还不能替代三端 E2E、并发库存和支付回调测试。

下面的“已验证”“推断”“选择”“待验证”不是装饰。它们是复盘里最重要的边界：我知道什么，我根据什么推断，以及下一步还要补什么。

## 1. 这篇 Day01 要解决什么阅读问题

### 1.1 三个仓库对应三个用户入口，但共同落到一个业务内核

先不要从文件数量开始。先问三个问题：

- 谁在使用这个入口？
- 这个入口能发起什么业务动作？
- 动作最终由哪个后端和哪类数据承接？

C 端 pages.json 已经把用户入口暴露出来：首页、场馆、场次、活动、约球、订单和会员等能力都从这里进入。B 端则有自己的 Vue 页面、路由、登录状态和 API client。后端 AppModule 同时装配认证、业务、数据库、缓存、支付和文件能力，BusinessModule 又把运营侧模块集中组织起来。

因此，“三个仓库是一条系统”是一个基于源码组织的项目地图。它不表示三端共享 UI，也不表示项目已经拆成微服务。当前能验证的是：两套前端都通过 HTTP 请求访问后端，后端在一个应用入口里承载共同的业务领域。

![悦动体育三端与共享业务内核](/projects/yuedong-sports/yuedong-01-system-boundaries.png)

图里的 C Client、B Admin 和 Backend 先只当作三个观察位置：用户从哪里来，运营从哪里来，业务规则在哪里汇合。右侧的 Venue、Court、Session、Order、Event、Membership 是领域入口，不是完整模型清单。

再用边界表把它说得更具体：

| 入口 | 面向谁 | 主要动作 | 不应该直接碰什么 |
|---|---|---|---|
| C 端小程序 | 普通用户 | 发现、预约、报名、约球、购买权益 | MySQL、Redis、支付密钥 |
| B 端网页 | 商户或平台人员 | 配置场馆、场地、价格、场次、活动、订单 | 小程序本地存储和页面生命周期 |
| NestJS 后端 | 三端之间的业务中枢 | 鉴权、校验、库存、订单、支付、数据访问 | 把权限只交给前端菜单 |

这里有一个容易被忽略的判断：两端都能显示订单，不代表两端有同样的订单权限。C 端可能只看自己的订单和凭证，B 端可能按商户、场馆或平台范围查询；最终范围要回到 guard、角色和 service 验证。

#### 面试官可能会问

**Q：为什么说悦动体育是“一条系统”，而不是三个独立项目？**

**A：** 三个仓库分别承担 C 端、B 端和后端职责。两套前端通过 API 访问同一个 NestJS 后端，后端再连接共同的业务数据和基础设施。这个结论来自仓库分工、前端请求封装、后端模块注册和数据库模型，而不是只看目录名称。

**追问：这是不是说明它是微服务架构？**

**A：** 不能这样推断。当前证据更接近“两个前端加一个 NestJS 后端应用”，后端内部有多个模块，并不等于多个独立部署的服务。是否拆分成微服务，要看独立进程、部署单元、服务间通信和运行证据。

源码定位：yuedong-v2-frontend/pages.json、yuedong_front/src/views/HomeView.vue、yuedong_nestjs/src/app.module.ts、yuedong_nestjs/src/business/business.module.ts。

### 1.2 初识文章必须从可验证的问题开始，而不是从功能清单开始

参考 Day01 PDF，可以把学习顺序排成背景、项目业务、架构、功能、环境、结构、源码阅读、调试测试。这里吸收的是“先搭地图，再下钻”的编排，不复制与悦动体育无关的电商内容。[Day01-初识项目_知识小册子.pdf](D:/MyLab/Yuedong/Day01-初识项目%20_%20知识小册子.pdf)

所以本篇不从“系统有多少页面”开始，而是从一组能回到证据的问题开始：

| 问题 | 首要证据 | 得到的结论 |
|---|---|---|
| 请求从哪里进后端 | main.ts | 全局前缀和监听端口 |
| 为什么 B 端有 business | BusinessModule | 模块级路由归类 |
| 谁在访问接口 | AuthGuard/AdminGuard 和前端 token 逻辑 | 两类身份上下文 |
| 场馆怎样变成可预约资源 | schema.prisma、controller/service | 领域物化链 |
| 项目怎样运行 | docker-compose、部署文档、build 脚本 | 运行和构建边界 |
| 哪些结论还不稳 | 日志、测试、抓包和真实数据 | 证据缺口 |

本篇使用五类标签：

| 标签 | 意义 |
|---|---|
| 已验证 | 当前源码、配置、schema 或文档直接能看到 |
| 推断 | 多个已验证事实组合出的合理解释 |
| 选择 | 为了学习路径做的编排决定 |
| 待验证 | 已经知道需要实测，但本轮没有运行证据 |
| 未知 | 当前没有足够资料作结论 |

例如，main.ts 明确写了全局 api 前缀，这是“已验证”；“三个仓库共同落到一个业务内核”是对多份证据的“推断”；先讲请求再讲订单，是本篇的“选择”；“完整预约链已经跑通”在没有日志时就是“未知”，不能写成成果。

#### 面试官可能会问

**Q：为什么项目复盘不能只写“有用户端、管理端、后端、订单和支付”？**

**A：** 这只是功能名，不能说明请求入口、路由拼接、数据关系、权限边界和运行证据。复盘要让每个判断都能回到文件或运行结果，并把事实、推断和缺口分开。

**追问：源码证据和运行证据有什么区别？**

**A：** 源码证据说明“代码准备怎样做”，运行证据说明“在某个环境、某个数据和某次命令下实际发生了什么”。部署文档写了 health 检查命令，不等于本轮已经拿到健康响应。

源码定位：Day01 PDF、当前 01 Shape 的证据账本和本篇引用的各工程配置文件。

## 2. 从启动文件得到后端边界

### 2.1 全局 /api 前缀和 8080 监听决定请求入口

第一次读 NestJS，不必先把整个框架学完。先把 main.ts 当成“后端进程的启动说明书”：它创建应用、设置全局能力、决定路由前缀，并开始监听端口。

悦动体育后端当前入口中的关键代码是：

~~~ts
app.setGlobalPrefix('api');

const port = process.env.PORT ?? 8080;
await app.listen(port, '0.0.0.0');
~~~

这三行分别回答三个问题：

- 所有 controller 路由默认从 /api 开始。
- 如果环境变量 PORT 没有覆盖，后端使用 8080。
- 进程监听所有网卡地址，而不是只监听本机回环地址。

所以 controller 中的局部路径不是最终 URL。假设某个 controller 局部路径是 venues，对外地址至少要先考虑 /api/venues；若它属于 B 端模块，还要继续检查是否存在 /business。

这一步也解释了为什么 00 要先教 HTTP。method、path、header 和 body 是请求的不同组成部分；main.ts 决定 path 的全局外壳，前端 request 封装决定它最终发向哪个 base URL。

遇到 404 时，建议按下面顺序查：

1. 浏览器或小程序发出的完整 URL。
2. main.ts 是否加了 /api。
3. 所属模块是否又加了 /business。
4. controller 的局部路径和 HTTP method。
5. 进程是否真的监听了当前端口。

#### 面试官可能会问

**Q：只看到 controller 中的局部路径，为什么不能直接把它当成完整接口地址？**

**A：** NestJS 可以在应用级和模块级增加路由前缀。当前项目 main.ts 设置全局 /api，B 端业务模块还会注册 /business，因此完整地址要把这些配置和 controller 局部路径一起拼出来。

**追问：8080 是固定端口吗？**

**A：** 不是。代码从 process.env.PORT 读取端口，8080 是缺省值；Docker Compose 还可能把宿主机端口映射到容器 8080。

源码定位：yuedong_nestjs/src/main.ts。

### 2.2 B 端的 /business 由模块路由注入

在后端代码里看到 BusinessModule，最有价值的第一问不是“这个模块有多少行”，而是“它给请求增加了哪一层边界”。

BusinessModule 使用 RouterModule.register，把多个运营模块挂在 path: business 下。当前能看到的模块包括 Admin、Merchant、MerchantVenue、Court、PricePlan、Event、Session、BusinessOrder、Membership 和 Message。

核心结构可以简化为：

~~~ts
RouterModule.register([
  { path: 'business', module: AdminModule },
  { path: 'business', module: MerchantModule },
  { path: 'business', module: MerchantVenueModule },
  { path: 'business', module: CourtModule },
  { path: 'business', module: PricePlanModule },
  { path: 'business', module: EventModule },
  { path: 'business', module: SessionModule },
  { path: 'business', module: BusinessOrderModule },
  { path: 'business', module: MembershipModule },
  { path: 'business', module: MessageModule }
]);
~~~

因此，看到 /api/business/... 时，可以先把阅读范围缩到 BusinessModule，再按模块名称找到 controller 和 service。business 是路由归类，不是一个独立后端，也不是一个万能 CRUD controller。

这里要特别区分两件事：

| 代码位置 | 它解决的问题 |
|---|---|
| RouterModule | 请求归入哪组模块 |
| AuthGuard/AdminGuard | 请求者身份如何建立 |
| Roles 或角色判断 | 请求者属于哪种权限类别 |
| service 数据范围 | 这个调用者能读写哪些商户或场馆 |

看到 path: business 只能确认运营侧入口的组织方式，不能自动推出“所有管理员都能访问所有数据”。

#### 面试官可能会问

**Q：BusinessModule 的 path: business 解决了什么，又没有解决什么？**

**A：** 它把多个运营侧模块统一组织到 /business 路由前缀下，便于定位和区分 C/B 接口；它没有自动决定角色权限、数据范围和每个接口的业务规则，这些还要看 guard、角色和 service。

**追问：/api/business/venues 和 /api/venues 是同一接口吗？**

**A：** 不能仅凭资源名判断是同一个接口。它们的全局资源词可能相同，但所属模块、权限上下文、返回字段和数据范围都可能不同，需要继续追 controller 和 service。

源码定位：yuedong_nestjs/src/business/business.module.ts。

### 2.3 C 端 JWT 和 B 端管理员角色是两套授权上下文

“两端都带 token”很容易让人得出错误结论：它们是不是同一种用户，只是页面不同？当前源码提示的答案是否定的。

C 端 request.js 在 needAuth 为真时从小程序 storage 取 token；B 端 api/index.js 从 localStorage 取 jwt_token。两端都使用 Bearer 形式传递凭据，但后端的 guard 处理对象不同：

- AuthGuard 面向 C 端用户方向，建立 openid 相关的用户上下文。
- AdminGuard 面向 B 端管理员方向，围绕 username 查询管理员，并携带角色或数据范围。

对初学者，可以把四个词拆成四个问题：

| 词 | 它回答什么 |
|---|---|
| JWT | 凭据以什么格式携带 |
| Authorization | 凭据放在请求的哪个位置 |
| AuthGuard/AdminGuard | 后端怎样检查并建立身份上下文 |
| 角色/数据范围 | 这个身份允许做什么、能看到哪类数据 |

概念代码可以这样理解：

~~~ts
// 这是帮助阅读的概念化表达，不是完整 guard 实现
request.openid = user.openid;
request.admin = admin;
~~~

前端隐藏菜单只是用户体验。真正的安全边界仍然在后端 guard、角色校验和 service 数据范围。C 端把 userId 放进 body，也不能代替后端从认证上下文确认“当前调用者是谁”。

还可以顺手检查 app.module.ts。当前后端同时装配 TypeORM 的 MySQL 连接、PrismaModule、全局 JwtModule、ScheduleModule、BusinessModule 以及其他支付、对象存储和基础设施模块。这说明“技术栈”不是一堵墙，而是一组不同层次的工具：

| 层次 | 当前项目中的例子 | 先学到什么程度 |
|---|---|---|
| 语言/运行时 | TypeScript、JavaScript、Node.js | 能读对象、函数、async/await |
| Web 框架 | NestJS | 知道 main、module、controller、service、guard |
| 数据访问 | Prisma、TypeORM | 能看 model、where、create、update |
| 数据存储 | MySQL、Redis | 知道持久化数据与快速键值/锁的区别 |
| 客户端 | UniApp、Vue、Vite、Pinia | 能定位页面、请求封装和状态 |

这也是为什么 00 要把 Prisma 解释成“TypeScript 与 MySQL 之间的翻译层”：现在看到 PrismaModule 或 schema.prisma 时，不需要先背完 ORM，只要先定位“它访问哪个 model，读写了什么数据”。

#### 面试官可能会问

**Q：C 端 JWT 和 B 端 JWT 都使用 Bearer 形式，为什么仍然要区分 AuthGuard 和 AdminGuard？**

**A：** Bearer 只是凭据的传递形式。当前项目两类 guard 建立的上下文不同：C 端围绕用户 openid，B 端围绕管理员 username、角色和数据范围。传递方式相同，不代表业务身份和授权范围相同。

**追问：前端路由守卫能不能代替后端权限校验？**

**A：** 不能。前端路由守卫只控制页面体验，攻击者仍可直接调用接口。后端必须从认证上下文和角色/数据范围重新校验。

源码定位：yuedong_nestjs/src/auth/auth.guard.ts、yuedong_nestjs/src/auth/admin.guard.ts、yuedong-v2-frontend/utils/request.js、yuedong_front/src/api/index.js。

## 3. 用业务领域验证系统地图

### 3.1 用户发现资源，运营者维护资源

如果只按仓库读，C 端和 B 端会像两本书。换成领域对象视角，就能看到它们其实是在描述同一套资源的两面。

| 领域词 | C 端问题 | B 端问题 |
|---|---|---|
| Venue | 用户能否发现、定位、查看详情 | 谁维护、审核、上下架 |
| Court | 哪块具体资源可选 | 类型、容量、状态怎样配置 |
| Session | 哪个日期和时间可预约 | 如何生成、调整、锁定、核销 |
| Event | 用户如何查看和报名 | 谁创建、审核、维护报名容量 |
| Order | 用户看到什么状态和凭证 | 客服如何查询、退款、对账 |
| Membership | 用户拥有什么权益 | 商户怎样售卖和查看使用情况 |

C 端 pages.json 能看到 venue、event、meetup、order、membership 等用户入口；后端 BusinessModule 又能看到 merchant、venue、court、price、session、event、order、membership、message 等运营模块。名称重复不代表代码重复，更可能代表同一领域对象的读写视角不同。

先用“使用”和“维护”分开思考：

- 用户在 C 端关心场馆是否开放、场次是否可用、价格是多少。
- 运营人员在 B 端还要关心归属商户、审核状态、营业时间、价格策略和数据范围。
- 两者的最终规则都不能只看页面，而要回到后端 controller/service。

活动和约球也要单独保留。它们都可能有日期、人数和报名，但不能因为 UI 都出现“报名”按钮，就直接把它们当成普通场次库存。

#### 面试官可能会问

**Q：为什么 C 端和 B 端是同一领域的两种视角？**

**A：** C 端围绕发现、预约和使用资源，B 端围绕配置、审核和运营资源。两端的入口不同，但都通过后端访问 Venue、Court、Session、Order 等共同领域对象。

**追问：看到 C 端和 B 端都有 venue 字段，应该怎样判断是不是重复建模？**

**A：** 先看它是在读模型、写模型、DTO 还是权限过滤中；再比较字段、关联和 service 行为，不能只因为名字相同或不同就下结论。

源码定位：yuedong-v2-frontend/pages.json、yuedong_nestjs/src/business/business.module.ts、yuedong_front/src/views/HomeView.vue。

### 3.2 Venue → Court → Price Plan → Session 是资源物化链

第一次看到 43 个 model 和 41 个 enum 时，很容易想从头背 schema.prisma。这个做法的性价比很低。更好的入口是先找一条能解释用户动作的最小链：

**Venue → Court → Price Plan → Session**

- Venue：经营地点。
- Court：场馆内可被配置和预约的具体资源。
- Price Plan：按星期、时间段或规则描述价格。
- Session：把某个场地在某一天、某个时间段的资源具体化，成为用户真正竞争的库存。

schema.prisma 当前能找到 venue、court、price_plan_detail、session，以及注册、订单、支付等关联模型。后端 README 还明确记录了 TypeORM 和逐步迁移到 Prisma 的状态。所以本篇不把“用了 Prisma”写成“一切都已经 Prisma 化”，而是保留混合 ORM 的事实。

![Venue 到 Session 的资源物化链](/projects/yuedong-sports/yuedong-01-domain-chain.png)

图中 Price Plan 是规则，Session 才是可被查询、锁定、预约的时间资源。这两个概念混在一起，会直接影响后面理解“改价格”和“抢库存”为什么是不同问题。

读这条链时，每遇到一个字段都问四个问题：

1. 这是哪个 Venue？
2. Venue 下面是哪一个 Court？
3. 这个 Court 在当前日期/时间套用哪条 Price Plan？
4. 最终的 Session 是否还有容量、状态和可预约条件？

“物化”可以理解成把规则落成具体记录。价格策略本身不是用户点击的库存；系统需要通过生成任务、service 或其他逻辑，把规则变成 Session。当前项目是否所有场次都按同一方式生成、价格修改是否自动影响未来场次，还要继续读 service 和任务代码，不能从 model 名称直接推断。

#### 面试官可能会问

**Q：为什么用户预约时通常要落到 Session，而不能只传 venueId？**

**A：** venueId 只表示经营地点，不能表达具体日期、时间、场地和库存。Session 才把这些条件物化成用户真正竞争的资源记录。

**追问：Price Plan 和 Session 的关系是什么？**

**A：** Price Plan 描述价格规则，Session 描述某个时间点的实际资源。规则怎样生成或同步到 Session，要看当前 service、定时任务和数据状态，不能把两者当成同一张表。

源码定位：yuedong_nestjs/prisma/schema.prisma、yuedong_nestjs/README.md。

### 3.3 Order 连接预约、支付、退款和资金流水

Session 解释“竞争什么资源”，Order 解释“一次交易发生了什么”。当前 schema.prisma 中能找到：

| 模型方向 | 复盘时先问什么 |
|---|---|
| order | 这次交易的主身份和总体状态是什么 |
| order_item、order_snapshot | 买了什么、下单时的价格和业务快照是什么 |
| payment_order、payment_allocation | 钱何时进入，如何分配 |
| refund_order | 退款请求、状态和结果如何记录 |
| fund_flow | 平台、商户和退款之间的资金事实如何留痕 |

因此，Order 不是“支付成功后的一行 status”。一次普通场次预约可能同时涉及 Session、预约登记、订单项和支付；会员购买会连接产品与会员卡；退款又需要观察库存释放、退款事实和资金流。

项目中已经存在这些模型和相关枚举，这足以证明交易事实被拆开建模；但它还不能证明支付回调已经幂等、对账一定正确、所有状态流转都被测试覆盖。模型存在是源码证据，回调重复时的实际行为需要测试和日志。

![订单、支付、退款与资金流的阅读位置](/projects/yuedong-sports/order-state.svg)

读订单时，可以沿时间顺序追：

1. 用户选择 Session，系统是否创建 Order。
2. Order item 或 snapshot 如何保存业务与价格。
3. 支付成功回调如何更新支付事实和订单状态。
4. 退款发生时，哪些记录新增，哪些库存释放。
5. fund flow 如何为平台或商户保留可追踪记录。

#### 面试官可能会问

**Q：为什么不能只在 order 表里放一个 status？**

**A：** 一次交易还要表达买了什么、当时的价格快照、支付事实、退款事实和资金流。单一 status 无法完整保留可追溯信息，也很难解释回调重复、部分退款或多业务订单项。

**追问：schema 中有 payment_order 和 refund_order，是否就能证明支付回调安全？**

**A：** 不能。它只能证明模型层准备保存这些事实；还需要检查回调入口、唯一约束、幂等键、状态机、事务和实际重试日志。

源码定位：yuedong_nestjs/prisma/schema.prisma、yuedong_nestjs/README.md。

## 4. 三端请求链如何被前端实际拼出来

### 4.1 C 端 request.js 统一 baseURL、token 和错误分支

C 端的统一请求层是理解小程序业务的好入口。页面不需要每次都重复写域名、JSON header、token 和错误提示，而是把这些协议细节交给 utils/request.js。

核心逻辑可以按下面几段读：

~~~js
const fullUrl = url.startsWith('http')
  ? url
  : CONFIG.API.BASE_URL + url;

const requestHeaders = {
  'Content-Type': 'application/json',
  ...header
};

if (needAuth) {
  const token = uni.getStorageSync('token');
  if (token) {
    requestHeaders.Authorization = 'Bearer ' + token;
  }
}
~~~

随后 request.js 把这些配置交给 uni.request：

~~~js
const response = await uni.request({
  url: fullUrl,
  method,
  data,
  header: requestHeaders
});
~~~

当前实现还包含几个值得复盘的分支：

- 2xx 和 304 按成功处理。
- 401 会清理 token、userInfo、hasUserInfo，并触发 tokenExpired。
- 502 具备带等待时间的重试逻辑，maxRetries 默认是 2。
- config.js 把 venues、sessions、events、meetup、orders、membership 等 endpoint 集中管理。

这段封装的优点是跨页面一致；风险是调用者容易忘记真实请求细节。调试时仍要回到 request.js，确认完整 URL、needAuth、header、状态码和重试分支。

还要留意环境配置：当前 local 使用 localhost:8081/api，而 development、testing、production 的配置指向生产域名；小程序 develop、trial、release 的映射也需要结合实际构建产物和发布流程验证。环境名写在代码里，不等于数据隔离和发布隔离已经完成。

#### 面试官可能会问

**Q：C 端为什么要有统一 request.js？它可能带来什么风险？**

**A：** 它统一 baseURL、JSON header、token、错误处理和重试逻辑，减少页面重复代码。风险是封装隐藏真实请求细节，错误的环境配置或过宽的重试策略会把问题放大。

**追问：502 为什么可以考虑重试，401 为什么不应该简单重试？**

**A：** 502 更像网关或短暂上游不可用，短暂等待后重试可能成功；401 表示身份凭据无效或过期，继续带同一个 token 重试通常没有意义，还可能造成更多无效请求。

源码定位：yuedong-v2-frontend/utils/config.js、yuedong-v2-frontend/utils/request.js。

### 4.2 B 端 API client 与 Vite proxy 对齐本地开发路径

B 端有另一套请求边界：浏览器页面运行在 Vite 开发服务器，API client 默认以 /api 为前缀，Vite 再把本地请求代理到后端。

从 api/index.js 可以先抓住三个动作：

~~~js
const baseURL = '/api';
const token = localStorage.getItem('jwt_token');

headers.Authorization = 'Bearer ' + token;
~~~

从 vite.config.js 可以抓住两个环境事实：

~~~js
server: {
  port: 3344,
  proxy: {
    '/api': {
      target: 'http://localhost:8080'
    }
  }
}
~~~

本地开发时，可以把浏览器地址、代理和后端地址分三层想：

1. 浏览器打开 localhost:3344。
2. 页面发出同源的 /api/business/... 请求。
3. Vite 把 /api 请求转给 localhost:8080。
4. NestJS 再按全局 /api 和业务模块路由寻找 controller。

Vite proxy 不是后端路由，NestJS 的 /api 也不是浏览器代理。遇到 B 端 404 或跨域错误，应分别检查浏览器 Network、vite.config.js、后端监听端口和 NestJS 路由。

另外，B 端生产 base 是 /admin/。这意味着“开发时页面根路径”和“生产时站点挂载路径”是两个问题；静态资源、路由 history fallback、API 反向代理都要一起验收。

#### 面试官可能会问

**Q：Vite proxy 和 NestJS 的 /api 前缀分别负责什么？**

**A：** Vite proxy 解决本地浏览器到后端服务的转发，NestJS 的 /api 是后端真正注册的全局路由前缀。前者不是后端路由，后者也不是浏览器代理。

**追问：B 端 router 已经保护页面了，为什么 API 还要带 token？**

**A：** router 只保护页面导航，直接调用 API 仍然可能绕过页面。API client 带 token，后端 AdminGuard 和 service 再验证身份、角色与数据范围。

源码定位：yuedong_front/package.json、yuedong_front/vite.config.js、yuedong_front/src/api/index.js、yuedong_front/src/stores/auth.js、yuedong_front/src/router/index.js。

### 4.3 用一次“查看场馆/选择场次”串起页面、API 和服务

到这里，可以用一条低风险的查询链把前面的概念串起来。选择“查看某场馆某天的场次”，是因为它同时包含页面入口、请求封装、路由、身份、领域对象和数据访问，但不像支付回调那样一开始就陷入复杂状态。

一条可重复使用的源码阅读卡如下：

| 顺序 | 记录什么 | 你要找的证据 |
|---|---|---|
| 1 | 页面入口 | pages.json、页面事件、按钮回调 |
| 2 | method/path/data | C 端 request.js 或 B 端 api/index.js |
| 3 | 完整 API 前缀 | main.ts 和 BusinessModule |
| 4 | 身份上下文 | needAuth、Bearer、AuthGuard/AdminGuard |
| 5 | controller | 局部路由、DTO、参数解析 |
| 6 | service | 可用性、日期、价格、库存和权限规则 |
| 7 | data | venue/court/session/order 的读写、事务或缓存 |

可以把一次查询按这个顺序复原：

1. 页面拿到 venueId 和日期。
2. request.js 拼出 baseURL 加相对路径，按需补 Authorization。
3. NestJS 用 /api 前缀找到场次 controller。
4. controller 把输入交给 DTO 或 service。
5. service 根据 venueId、日期和状态读取 Session，必要时关联 Court 或价格数据。
6. response 以 JSON 返回，页面把结果渲染成时间格。

![C/B 请求进入共享后端的阅读链](/projects/yuedong-sports/yuedong-01-request-chain.png)

图中的 Auth Guard、Business Module、Service 和 Database 是定位顺序的视觉提示，不是一次请求必经的全部实现细节。某个查询是否需要认证、是否使用 Redis、是否经过事务，都要以对应 controller/service 为准。

这里的 Controller → Service → Data 可以先按“门口、规则、存取”理解：

- controller 把 HTTP 世界翻译成后端函数参数。
- service 组织领域规则和跨模型动作。
- Prisma/TypeORM 把代码中的 model 操作翻译成数据库查询。

遇到 Prisma，不要停下来先学完 Prisma。先记下 model、where 条件、create/update 对象、事务边界和返回值，再补 ORM 语法。这样技术栈不再是一堵墙，而是一条可以逐层下钻的路径。

#### 面试官可能会问

**Q：面试时怎样解释一次“查看场次”请求在悦动体育后端的阅读路径？**

**A：** 我会从 C 端页面事件找到 request.js，拼出 baseURL 和 API 前缀；后端由 controller 接收请求，guard/DTO 处理身份和输入，service 组织场馆、场地、场次和价格规则，最后通过 Prisma/TypeORM 访问 MySQL，必要时使用 Redis 等基础设施。具体字段和是否命中缓存，还要回到对应实现与日志。

**追问：如果你不熟 Prisma，能继续定位吗？**

**A：** 可以。先把 Prisma 当作数据访问工具，记录调用的是哪个 model、筛选条件是什么、写入了什么、是否在事务中，再针对这些调用补 Prisma 语法。阅读路径比先背 API 更重要。

源码定位：三端页面与请求封装、yuedong_nestjs/src/main.ts、yuedong_nestjs/src/business/business.module.ts、yuedong_nestjs/prisma/schema.prisma。

## 5. 环境、调试和测试边界

### 5.1 后端 Docker、MySQL、Redis 和 health 接口构成可运行基础

后端不是只启动一个 Node 进程。docker-compose.yml 把 app、MySQL 和 Redis 放进一套本地/部署基线：

~~~yaml
services:
  app:
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy
    ports:
      - app host port to container 8080
    environment:
      DATABASE_HOST: mysql
      DATABASE_PORT: 3306

  mysql:
    image: mysql:8.0

  redis:
    image: redis:latest
~~~

这里的 host port to container 8080 是为了避免把 compose 默认值伪装成一段脱离上下文的配置；当前文件实际使用 APP_PORT 可覆盖的端口映射，容器内后端仍是 8080。app 依赖 MySQL 和 Redis 的 healthy 状态，MySQL 使用 8.0，Redis 开启持久化和健康检查。

DEPLOYMENT_DOCKER.md 还给出了环境文件准备、deploy/status 脚本和 curl /api/health 的检查路径。这是可复现运行的文档基线，但不是本轮的运行结果。

![App、MySQL、Redis 与健康检查的运行基线](/projects/yuedong-sports/yuedong-01-runtime-baseline.png)

检查服务至少分三层：

| 层次 | 观察点 | 能否直接推出业务可用 |
|---|---|---|
| 进程层 | app 是否监听 8080 | 不能 |
| 依赖层 | MySQL、Redis 是否 healthy | 不能 |
| 业务层 | health、登录、查询、预约和订单是否符合预期 | 只有这一层接近业务验收 |

容器 healthy 只说明进程或依赖的基础状态。迁移是否执行、数据库是否有数据、token 是否有效、预约库存是否有并发保护，都需要另外验证。

#### 面试官可能会问

**Q：app、MySQL、Redis 都 healthy，能否直接说明预约功能可用？**

**A：** 不能。还要验证数据库迁移、登录、场馆/场次查询、库存写入、订单、支付和失败回滚。健康检查是进程/依赖证据，不是完整业务验收。

**追问：为什么 app 依赖 MySQL 和 Redis healthy，而不是只 depends_on 容器启动？**

**A：** 容器“启动”不一定意味着服务已经可以接受连接。healthy 条件至少能减少应用启动早于依赖 ready 的竞态，但仍然需要应用自身处理连接失败和迁移问题。

源码定位：yuedong_nestjs/docker-compose.yml、yuedong_nestjs/DEPLOYMENT_DOCKER.md。

### 5.2 Hugo 内容构建入口与业务应用构建入口必须分开

这篇笔记最终要进入 Hugo 项目，但 Hugo 构建和悦动业务应用构建是两条不同的验证链。

用户已经指定 Hugo 可执行文件为：

~~~text
D:/MyLab/Hugo/hugo.exe
~~~

项目内部的 npm run build 会指向这套 Hugo 入口。它可以验证 Markdown front matter、图片资源、站点模板和静态输出；它不能证明 NestJS、C 端、B 端、MySQL、Redis 或支付接口已经工作。

| 验证动作 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 隔离 Hugo build | 01 Markdown 和图片可以渲染 | 三端 API 可用 |
| C/B npm build | 前端代码可以打包 | 后端业务逻辑正确 |
| NestJS start | 后端进程可以启动 | 数据库内容和并发预约正确 |
| Docker health | 进程/依赖达到健康条件 | 全链路业务验收 |
| E2E/集成测试 | 某条业务链在指定数据下实际工作 | 所有生产场景都无问题 |

本轮会单独验证 01 的 Hugo 输出，再记录项目现有 full build 的结果。如果 full build 被仓库内其他历史 Markdown/YAML 问题阻断，要把阻断文件写出来，而不是把它误判成 01 内容错误。

#### 面试官可能会问

**Q：为什么 Hugo build 通过不能说明悦动体育项目运行成功？**

**A：** Hugo 只处理文档站的 Markdown、图片和模板。悦动业务还需要分别验证 C/B 前端、NestJS、MySQL、Redis、认证和业务接口，它们属于不同的构建或运行证据。

**追问：如果 full build 失败，你会怎样判断责任边界？**

**A：** 先看错误文件和行号，再用隔离内容目录只构建 yuedong-sports，判断 01 是否自身可渲染。若隔离构建通过而 full build 被其他文件阻断，就把两者分别记录。

**A：** 当前还缺三端完整启动和 E2E、真实 response 样本、并发库存测试、支付回调幂等验证、生产安全验收和完整角色矩阵。每项都有具体下一步：启动并迁移、抓请求、并发 reserve、重放回调、比较不同管理员数据范围并检查日志。

**追问：为什么要主动讲这些未知？**

**A：** 因为源码结构不等于运行结果。主动区分证据边界，能避免把“我读到了”夸大成“我验证了”，也能把后续复盘任务变成可执行的测试计划。

源码定位：当前 01 Shape 的 C13/C14 证据缺口，以及 yuedong_nestjs 的部署和测试文档。

## 结语：先拥有地图，再选择下一条下钻路径

现在重新打开三个仓库，建议不要从所有页面或所有 model 开始。先沿着下面的顺序定位：

1. 入口：C 端页面或 B 端页面事件。
2. 请求：method、path、data、Authorization。
3. 路由：main.ts 的 /api，BusinessModule 的 /business。
4. 身份：AuthGuard 还是 AdminGuard。
5. 领域：Venue、Court、Session、Order 或 Event。
6. 业务：controller → service → Prisma/TypeORM。
7. 证据：源码事实、运行事实和仍然未知的部分。

如果下一篇要继续下钻，最自然的两条路径是：

- C 端：从查看场次进入一次预约，研究库存、事务、锁和订单。
- B 端：从后台场次或价格配置进入管理请求，研究管理员数据范围和资源物化。

01 的第一张地图到这里闭合：先定位三个入口，再拼后端边界；接着用领域链解释可预约资源和交易；最后把运行、构建和证据缺口分开。后续文章不必重新介绍三个仓库，而可以直接沿着一条真实请求继续往下读。
