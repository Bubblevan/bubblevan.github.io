# 悦动体育 02：从业务场景到接口契约——场馆场次查询与预约

## 1. 先限定一条能讲清楚的预约业务

## 2. 从页面动作提取业务规则

预约接口接收的是 sessionId，而用户在页面上首先看到的是场馆。因此，读路径至少要经过“场馆 → 场次”两个层次。VenueController 提供场馆列表、详情和 :id/sessions；SessionController 又提供 venue/:venueId 查询，前端 config.js 目前把 VENUE_SESSIONS 配成 sessions/venue/:id。

schema.prisma 中 session 同时保存 venue_id、court_id、date、start_time、end_time、price、status 和容量字段。它不是一个只存“时间字符串”的页面对象，而是后续预约写入要锁定、检查并产生 session_reg 的资源记录。

```typescript
    @Controller('sessions')
    export class SessionController {
        @Get('venue/:venueId')
        async getSessions(
            @Param('venueId') venueId: string,
            @Query('category') category?: string,
            @Query('startDate') startDate?: string,
            @Query('endDate') endDate?: string
        ): Promise<Message> {
            const sessions = await this.sessionService.getSessions(
                Number(venueId),
                false,
                category,
                startDate,
                endDate
            );
        }
    }

```

| 页面动作 | 前端配置 | 后端入口 |
|---|---|---|
| 查场馆列表 | VENUES: /venues | VenueController @Get() |
| 查场馆详情 | VENUE_DETAIL(id) | VenueController @Get(':id') |
| 查场次 | VENUE_SESSIONS(id) = /sessions/venue/:id | SessionController @Get('venue/:venueId') |
| 另一种场馆场次路径 | 未作为 C 端主配置 | VenueController @Get(':id/sessions') |



SessionController 暴露了 reserve、reserve-capacity/:sessionId 和 reserve-membership/:sessionId 三个写入口。普通预约方法会拒绝混入 capacity_total 不为空的场次；容量预约专门检查容量并执行 capacity_used 的原子占用；会员卡预约还要检查卡归属、卡类型、状态、有效期、剩余次数和场馆范围。

这三个入口的差异来自业务约束，而不是为了让 API 看起来更复杂。普通场次的关键结果是把 available 状态改为 reserved；容量场次需要在剩余容量大于零时递增 capacity_used；会员卡分支还要把资格校验和使用记录放在同一个数据处理过程中。

```typescript
    @Post('reserve')
    @Post('reserve-capacity/:sessionId')
    @Post('reserve-membership/:sessionId')

```

|---|---|---|

普通预约的 service 代码在检查场次后会创建 order，并继续创建订单项和 session_reg；会员卡预约还会记录会员卡使用。预约 service 负责资源占用和业务事实；外部收款由 payment service 处理。

PaymentOrderService 以 out_trade_no 查找或创建 payment_order，维护 payment_allocation，并在支付成功后更新支付单、分摊和订单，再创建资金流水和 payment success job。RefundOrderService 则维护 refund_order，退款成功后创建退款资金流水并投递退款任务。它们说明预约、支付和退款是相连的状态边界，不是一个同步函数的单一返回值。

## 3. 把业务规则翻译成接口契约

先把 controller 中的相对路径和前端 config.js 放在一起，再加上 01 已经建立的 /api 前缀，才能得到面向客户端的 URL。前端当前把场次查询配置成 /sessions/venue/:id，SessionController 也有 @Get('venue/:venueId')；同时 VenueController 还有 @Get(':id/sessions')，两条路径并列存在，后续结合调用关系统一主路径。

接口表的作用不是把代码抄一遍，而是暴露契约缺口；两个“按场馆查场次”的路径要通过前端调用、真实请求和提交历史统一主路径。

```typescript
    // yuedong-v2-frontend/utils/config.js
    VENUES: '/venues',
    VENUE_DETAIL: (id) => '/venues/' + id,
    VENUE_SESSIONS: (id) => '/sessions/venue/' + id,
    SESSIONS_RESERVE: '/sessions/reserve',

    // yuedong_nestjs/src/consumer/session/session.controller.ts
    @Controller('sessions')
    @Get('venue/:venueId')

```

| 方法 | 目标 URL | 代码入口 | 备注 |
|---|---|---|---|
| GET | /api/venues | VenueController @Get()、config VENUES | 场馆列表 |
| GET | /api/venues/:id | VenueController @Get(':id')、config VENUE_DETAIL | 场馆详情 |
| GET | /api/sessions/venue/:venueId | SessionController @Get('venue/:venueId')、config VENUE_SESSIONS | C 端当前主配置 |
| GET | /api/venues/:id/sessions | VenueController @Get(':id/sessions') | 与上一条存在路径差异 |
| POST | /api/sessions/reserve | SessionController @Post('reserve')、config SESSIONS_RESERVE | 普通预约 |
| POST | /api/sessions/reserve-capacity/:sessionId | SessionController @Post('reserve-capacity/:sessionId') | 容量预约 |
| POST | /api/sessions/reserve-membership/:sessionId | SessionController @Post('reserve-membership/:sessionId') | 会员卡预约 |



普通预约 controller 从 Body 中读取 SessionReservationDto，从 @Openid() 读取 openid，再把这两类数据传给 service。会员卡预约还从路径读取 sessionId，从 MembershipReserveDto 读取 cardNumber；openid 不是用户在 body 里随意提交的业务字段，而是由鉴权上下文交给 controller 的身份信息。

成功和失败也属于接口契约的一部分。当前 controller 返回的 Message 至少包含 message、statusCode、data 或 error；错误分支使用 error.status 或默认 500。这个结构可以帮助前端判断结果；完整 Message 类型、全局异常过滤器和各 endpoint 的实际 JSON 应通过接口测试补齐。

```typescript
    @Post('reserve')
    async reserveSessions(
        @Body() dto: SessionReservationDto,
        @Openid() openid: string
    ): Promise<Message> {
        try {
            const result = await this.sessionService.reserveSessions(
                dto.sessionId,
                openid,
                dto.cardNumber
            );
            return {
                message: 'Success',
                statusCode: 200,
                data: result
            };
        } catch (error) {
            return {
                message: 'Error',
                statusCode: error.status || 500,
                error: error.message || 'Internal Server Error'
            };
        }
    }

```

| 输入位置 | 示例字段 | 来源 |
|---|---|---|
| path | sessionId | URL 中的参数，controller 转为 Number |
| body | sessionId、cardNumber | DTO 或匿名对象 |
| identity | openid | @Openid() |
| response success | message、statusCode、data | controller 返回值 |
| response error | message、statusCode、error | controller catch 分支 |



阅读预约接口时，不能停在“它接收一个 DTO”。普通入口把 dto.sessionId、openid 和 dto.cardNumber 依次传给 reserveSessions；容量入口把路径 sessionId 转成数字，把 openid 和可选 cardNumber 传给 reserveCapacitySession；会员卡入口则把 dto.cardNumber 放在 service 的第二个参数位置。

这层映射让 service 可以直接围绕业务参数工作；DTO 定义和全局校验管道则应通过接口测试补齐。

```typescript
    @Post('reserve-capacity/:sessionId')
    async reserveCapacitySession(
        @Param('sessionId') sessionId: string,

        );
    }

```

## 4. 从接口反推数据模型和不变量

schema.prisma 里 venue 关联 court 和 session，court 关联 price_plan_detail 和 session，session 又反向关联 venue 与 court。这个关系说明 C 端看到的 session 不是凭空出现的页面数组，而是依附于场馆和场地的具体时间资源。

price_plan_detail 保存 court_id、weekday、start_time、end_time、price 和 status；session 则保存 date、start_time、end_time、price 和预约状态。本文用这组字段解释资源如何从运营配置走到 C 端查询，批量生成任务放到资源同步专题。

![悦动体育预约数据模型](/projects/yuedong-sports/yuedong-02-booking-data-model.png)



普通预约先判断场次状态是否为 available，再用 updateMany 限定 status = available 且 capacity_total = null，成功更新的数量必须等于请求数量。这个 affected count 是一个数据库写入结果，帮助代码判断检查之后是否有其他请求抢先改变了场次。

容量预约的 service 走另一条路径：它要求 capacity_total 不为空，先计算剩余容量，再用带有 status = available、capacity_total IS NOT NULL 和 capacity_used < capacity_total 条件的原子 SQL 增加 capacity_used。更新结果为 0 时，代码重新查询并返回容量已满或场次不可预约。

Redis 锁可以降低同一资源的并发冲突，但它不替代数据库条件更新。BookingInventoryService 只负责按 session ID 组织锁的获取和释放；真正改变场次状态或容量的事实仍然写在 transaction 内的数据库操作中。

![悦动体育预约临界区](/projects/yuedong-sports/yuedong-02-booking-critical-section.png)

```typescript
    async withSessionLocks<T>(sessionIds: number[], callback: () => Promise<T>): Promise<T> {
        const locked = await this.lockMany(
            Array.from(new Set(sessionIds))
                .sort((a, b) => a - b)
                .map((id) => 'booking:session:' + id)
        );
        try {
            return await callback();
        } finally {
            await this.releaseMany(locked);
        }
    }

    const updateResult = await tx.session.updateMany({
        where: {
            session_id: { in: sessionIds },
            status: 'available',
            capacity_total: null
        },
        data: { status: 'reserved' }
    });

```

普通场次：status = available 且 capacity_total = null，成功后把 status 改为 reserved。

容量场次：capacity_total 有值，只有 capacity_used < capacity_total 时才允许原子增加 capacity_used。

两类场次都需要在写入结果不符合预期时返回失败，而不是继续创建成功预约事实。



把普通场次想成一个只能被一个人占用的格子，把容量场次想成一个还能逐个减少剩余名额的计数器。两者都需要判断“当前还能不能占用”，但写入动作不同，所以 service 分支和数据库条件也不同。

锁、transaction 和条件更新分别承担不同保护职责；并发正确性要通过并发用例、隔离级别和故障恢复测试观察。

session_reg 至少连接 session_id、user_id、order_id，并可关联 membership_card_id；它回答的是“谁预约了哪个场次，属于哪张订单”。order 则保存 user_id、money、status、order_type、venue_id、business_date 和 paid_at 等查询字段，面向的是交易事实。

order_item 和 venue_order_item 把通用订单明细与场馆预约明细拆开。venue_order_item 还保存 session_id、court_name、sport_category、start_time、end_time 和 snapshot，这些字段让历史订单不必完全依赖场次当前名称和价格。

预约 service 还会构建 session snapshot 和 order metadata，并在事务里创建 order、session_reg、订单项或会员卡使用记录；metadata 承担历史和查询补充信息；字段迁移时要配套回放和对账脚本。

```typescript
    const sessionRegs = sessions.map((session) => ({
        session_id: session.session_id,
        user_id: openid,
        membership_card_id: membershipCard.card_id,
        is_free_booking: true,
        order_id: order.order_id
    }));

    await tx.session_reg.createMany({
        data: sessionRegs,
        skipDuplicates: true
    });

```



## 5. 追踪预约写入的实现路径

controller 的职责在这里很明确：它不查询场次，也不直接修改订单，而是把 HTTP 形状转换成 service 可以使用的业务参数。以会员卡入口为例，sessionId 从路径进入，cardNumber 从 DTO 进入，openid 从装饰器进入，三个值随后传到 reserveWithMembershipCard。

这层分工让后续代码可以脱离 HTTP 细节讨论资格、库存和订单。读者阅读新功能时，可以先从 controller 找输入，再跳到同名 service 方法，最后向下找 transaction、锁和 Prisma model；这正是 01 已经建立的请求阅读路径在一个真实写接口中的应用。

```typescript
    @Post('reserve-membership/:sessionId')
    async reserveWithMembershipCard(
        @Param('sessionId') sessionId: string,
        @Body() dto: MembershipReserveDto,
        @Openid() openid: string
    ): Promise<Message> {
        try {
            const result = await this.sessionService.reserveWithMembershipCard(
                Number(sessionId),
                dto.cardNumber,
                openid
            );
            return {
                message: '会员卡预定成功',
                statusCode: 200,
                data: result
            };
        } catch (error) {
            return {
                message: error.message || '会员卡预定失败',
                statusCode: error.status || 500,
                error: error.message || 'Internal Server Error'
            };
        }
    }

```



普通预约从 withSessionLocks(sessionId, callback) 开始，callback 内再调用 prisma.$transaction。锁的作用是让同一组 session ID 的竞争请求先在 Redis 层排队或失败；transaction 的作用是把一次业务写入中的多条数据库操作放到同一事务边界内。

普通场次的核心写入不是先 update 再无条件相信结果，而是把 status = available 和 capacity_total = null 写进 updateMany 的 where 条件，并检查 count。容量场次则把 capacity_used < capacity_total 写进原子 SQL 的 where 条件；两者都保留了数据库层的最后判断。

```typescript
    return await this.bookingInventoryService.withSessionLocks(
        sessionId,
        async () =>
            await this.prisma.$transaction(async (tx) => {
                const sessions = await tx.session.findMany({
                    where: { session_id: { in: sessionId } }
                });

                const updateResult = await tx.session.updateMany({
                    where: {
                        session_id: { in: sessionId },
                        status: 'available',
                        capacity_total: null
                    },
                    data: { status: 'reserved' }
                });

    if (updateResult.count !== sessionId.length) {
        throw new HttpException(
            '场次已被其他用户预订，请刷新后重试',
            HttpStatus.BAD_REQUEST
        );
    }
            })
    );

```

同一个 sessionId 的锁 key 形如 booking:session:123；锁获取失败时返回资源繁忙。

普通场次的 updateMany count 少于请求数量时，代码会重新查询状态并返回请刷新后重试。

容量场次的原子 SQL 更新为 0 时，代码重新查询并区分场次不可预约和容量已满。



Redis 锁像是让同一资源的请求先经过一个窄门，减少同时进入关键代码的请求；数据库条件更新像是进入数据库后再次核对资源是否仍满足占用条件。两者解决的是不同层次的问题，不能把其中一个的存在解释成另一个已经完成。

锁获取失败时，BookingInventoryService 返回资源繁忙的 409；普通场次更新数量不足时，service 重新查询并返回场次被其他用户预订；容量原子更新为 0 时，service 区分不可预约和容量已满。失败方式本身就是接口设计的一部分。

普通预约会在 transaction 中查询多个 session，构建场次快照和订单 metadata，创建 order，随后创建场次预约记录和场馆订单项。容量预约在占用一个名额后也会继续创建订单及其预约记录；会员卡预约还会创建 membership_card_usage，并按卡类型扣减次数或保留时限卡的使用语义。

场次状态只是资源占用结果；订单查询、退款审核、用户预约列表和会员卡使用记录还需要独立事实，并在事务设计中保持关联。

```typescript
    const order = await tx.order.create({
        data: {
            order_id: orderId,
            user_id: openid,
            money: 0.0,
            status: 'paid',
            order_type: 'venue',

```



PaymentOrderService 先按 out_trade_no 查找已有支付单，再创建或更新支付单和 payment_allocation。收到成功结果后，它在一次 transaction 中更新 payment_order、allocation 和符合条件的 order，再创建 payment fund flow 并加入支付成功任务。

重复回调按支付单状态提前返回；退款单也记录 refund_id、out_refund_no 和成功状态。渠道签名、重试时序和退款后的资源释放应列为支付专题的测试项。

![悦动体育预约与交易边界](/projects/yuedong-sports/yuedong-02-trade-boundary.png)

```typescript
    if (payment.status === 'success') {
        this.logger.log('支付单已处理成功，跳过重复回调');
        return payment;
    }

    await this.prisma.$transaction([
        this.prisma.payment_order.update({
            where: { payment_id: payment.payment_id },
            data: { status: 'success' }
        }),
        this.prisma.payment_allocation.updateMany({
            where: { payment_id: payment.payment_id },
            data: { status: 'paid' }
        }),
        this.prisma.order.updateMany({
            where: { order_id: { in: orderIds } },
            data: { status: 'paid' }
        })
    ]);

```

## 7. 面试复盘

下面集中整理项目中最容易被追问的设计问题，回答按“实现—依据—验证”展开。

### 1. 为什么 02 不从“悦动体育一共有多少模块”开始？

**回答：** 因为本文要复盘一次可追踪的预约业务；模块只有放进用户动作和数据变化中，才容易解释接口与设计选择。

**依据：** Day02 以具体业务任务推进，当前源码又能直接给出场馆、场次和预约入口，因此选择这条切片。

### 2. 看到 withSessionLocks，能否直接回答“系统已经通过并发测试”？

**回答：** 它说明源码接入了 Redis session 锁；并发测试还要通过具体场景观察。

**依据：** 代码证据支持“调用锁”；测试或运行日志才支持“在某组并发条件下的结果”。

### 3. 用户为什么不能直接调用 POST /api/sessions/reserve 而跳过场馆和场次查询？

**回答：** 因为预约需要具体的 sessionId，查询阶段还要让用户看到日期、时间、价格、场地和当前可用状态。

**依据：** SessionController 的预约方法接收 sessionId；schema 中这些展示和资格判断字段属于 session。

### 4. 为什么不能把容量预约直接复用普通预约的 status = reserved？

**回答：** 容量场次允许多个用户占用同一场次，需要维护 capacity_used 与 capacity_total；普通场次则是一个可用资源被一次占用。

**依据：** session schema 同时有容量字段；普通和容量 service 的实现分别执行状态更新和原子容量递增。

### 5. 预约成功是否等于支付成功？

**回答：** 不等于。预约 service 可以创建订单和预约记录；支付成功还需要 payment_order 的渠道回调处理。

**依据：** session service 与 PaymentOrderService 位于不同服务类，后者单独处理支付单、订单状态和支付成功队列。

### 6. 看到 @Get('venue/:venueId') 后，能否直接把它写成 /api/venues/:id/sessions？

**回答：** 不能。最终路径还要结合 controller 前缀、全局前缀和前端配置；项目存在两种相近路径。

**依据：** SessionController 与 VenueController 的装饰器文本不同，config.js 又明确使用 sessions/venue/:id。

### 7. 为什么不允许前端在 body 中传一个 openid 来代表当前用户？

**回答：** 因为当前用户身份应来自鉴权上下文；如果直接信任 body，用户可以尝试替换成别人的 openid。

**依据：** controller 显式从 @Openid() 接收身份，并把它传给 service；body 中不设置可信身份字段，鉴权上下文提供的 openid 直接传入 service。

### 8. price_plan_detail 和 session 为什么不能被当作同一张表？

**回答：** 前者更像场地的时间/价格规则，后者是某个具体日期上可被查询和预约的资源实例。

**依据：** schema 中两者字段和关系不同；session 还拥有 status、capacity_used 和 session_reg 关系。

### 9. 为什么 updateResult.count 不等于请求数量时要报错？

**回答：** 因为至少有一个场次没有在仍为 available 且无容量的条件下成功更新，可能是并发请求已经占用或输入混入了错误类型。

**依据：** updateMany 带条件执行，count 只反映满足条件并被修改的记录数。

### 10. 为什么已经有 session.status，还要新增 session_reg？

**回答：** status 表达场次资源当前是否可占用；session_reg 保存具体用户、订单和场次之间的预约事实，两者查询目的不同。

**依据：** schema 同时定义 session.status 与 session_reg.user_id/order_id；service 也会在更新场次后创建 session_reg。

### 11. Controller 为什么不直接把 Prisma 查询写在 @Post 方法里？

**回答：** 当前代码把 HTTP 解析/响应包装交给 controller，把业务规则、锁、事务和数据写入交给 service，职责更容易按请求链追踪和测试。

**依据：** SessionController 只调用 SessionService 的方法；锁与 transaction 出现在 session.service.ts。

### 12. 有了 Prisma transaction，为什么还要 withSessionLocks？

**回答：** transaction 负责数据库操作的一致性边界，Redis 锁负责跨请求协调同一 session 资源的竞争；它们不承担同一个职责。

**依据：** booking-inventory.service.ts 只管理 Redis key；session.service.ts 在锁 callback 内调用 $transaction。

### 13. 会员卡预约为什么还会创建 order，而不是只扣减卡次数？

**回答：** 当前代码把会员卡预约也记录为交易事实，并关联订单项、session_reg 和 membership_card_usage，方便查询和后续处理。

**依据：** reserveSessions 的会员卡分支创建免费订单、会员卡使用记录、session_reg 和 venue order items。

### 14. 支付回调幂等在当前代码里体现在哪里？

**回答：** service 先按 out_trade_no 找支付单；如果状态已经是 success，就跳过后续更新、资金流水和队列任务。

**依据：** 同一个外部支付单号可以再次进入 handlePaymentSuccess，但 success 分支提前返回。

### 15. 面试官问“容量场次如何避免超卖”，当前最准确的回答是什么？

**回答：** 当前代码在 session lock 和 transaction 内，用带 status、capacity_total、capacity_used 条件的原子 SQL 增加 capacity_used，并根据更新结果判断失败；并发压测用例再补充成功率与冲突结果。

**依据：** 代码证据来自 reserveCapacitySession 与 BookingInventoryService；并发压测应补充成功率与冲突结果。

### 16. 如果面试官追问“你真的做过这个并发方案吗”，应该怎样回答？

**回答：** 可以说明当前代码使用了 Redis session 锁、Prisma transaction 和数据库条件更新；并发压测再补充吞吐量与冲突结果。

**依据：** 源码回答实现方式，运行日志回答并发结果。

### 17. 为什么普通预约和容量预约有不同接口？

**回答：** 普通场次用 available → reserved 的状态占用，容量场次需要在 capacity_used < capacity_total 时原子递增；service 分成两个入口。代码证据是 session.service.ts 的 reserveSessions 和 reserveCapacitySession。并发正确性由并发用例补充。

### 18. session.status 和 session_reg 有什么区别？

**回答：** status 表达资源当前能否继续被占用，session_reg 记录用户、场次和订单之间的预约事实。schema 和预约写入代码同时使用它们，不能用一张表替代另一个语义。

### 19. 如何处理重复支付回调？

**回答：** 按 out_trade_no 找到结构化支付单后，如果状态已经是 success 就提前返回；否则在 transaction 内更新 payment_order、allocation 和 order，并在成功后投递资金流水和队列任务。单元 spec 已覆盖重复成功回调跳过；渠道重试时序放入支付专题。

### 20. 你发现过什么接口设计问题？

**回答：** 当前代码和配置中存在 /sessions/venue/:id 与 /venues/:id/sessions 两种形状，主路径应结合前端调用、真实请求和提交历史统一。

### 21. 支付成功是不是预约成功的必要条件？

**回答：** 不能把两者合并回答。预约 service 会创建订单和预约记录，支付 service 再根据渠道结果更新 payment_order、allocation 和 order；会员卡或免费订单还可能走不同的付款语义。是否允许“先占位后支付”，取决于订单状态与产品流程。
