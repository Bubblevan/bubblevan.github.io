# 悦动体育 03：从 43 个 Prisma Model 反推领域模型与一致性约束



面对一千多行 `schema.prisma`，最容易陷入的误区是从第一张 `model` 开始逐表背字段。这样能记住名字，却很难回答一个更重要的问题：这张表到底在保存哪一种业务事实？

这篇复盘把当前悦动体育后端的 43 个 model、41 个 enum 先重排成四张学习地图：资源域、交易域、活动社交域和会员域。然后沿着“规则 → 物化事实”“订单 → 业务明细 → 历史快照”“商品 → 权益 → 使用记录”三条主线，观察唯一约束、外键、事务和测试分别能保证什么。

文中的代码片段就地解释模型和写入边界，文末集中整理面试复盘。



## 1. 先把大 schema 变成领域地图

### model 数量是导航信号，不是领域模型答案

> **先记住：** `schema.prisma` 当前有 43 个 model、41 个 enum。这个统计说明项目规模较大；业务分组还要结合表之间的关系。

03 不从第一行 `model admin` 开始逐表朗读，而是先建立一个导航问题：这张表是在描述可运营的资源、一次业务事实、两个对象之间的关系，还是某个历史快照？只有分类之后，字段和约束才有解释位置。

我选择先把 43 个 model 还原成领域地图，再逐层解释规则、事实、订单和一致性边界。本文把当前 schema 暂时切成四个主域：资源域、交易域、活动社交域和会员域。merchant、venue、court、session 属于资源链；order、payment、refund、fund_flow 属于交易链；event、meetup 及其报名/收藏/评论属于活动社交链；membership_product、membership_card、membership_card_usage 属于权益链。这里先按四个主域建立阅读地图，服务文件仍按模块组织。

**例子**

- `price_plan_detail` 更像“按星期和时间段定价的规则”，不是用户最终预约的记录。
- `session_reg` 更像“某个用户对某个场次产生的一次预约事实”，不是场次当前状态的替代物。
- `venue_order_item` 是订单中的场馆业务明细，不能因为名字里有 order 就当成订单主表。
- `order_snapshot` 保存历史展示所需的快照，不能拿它推断当前场馆名称一定没有变化。

**检查清单**

- [ ] 先统计 model、enum、关系表和快照表，再决定阅读顺序。
- [ ] 每读一张表，先回答它保存的是资源、规则、事实、关系还是快照。
- [ ] 不把“领域分组”写成代码已经拆成独立服务。

### 用实体、事实、关系和快照四个词重排 schema

> **先记住：** 实体表描述可被持续引用的对象；事实表记录发生过的业务动作；关系表连接两个对象并常用组合主键；快照表保存某个时刻的展示或补充数据。这个分类来自当前模型关系，是本文的阅读工具。

`venue`、`court`、`event` 这些表比较像实体：它们有自己的身份、状态和生命周期。`session_reg`、`event_reg`、`membership_card_usage` 则是在记录“谁对什么资源做了什么”，它们的价值不只是被页面展示，还要留下可追溯事实。`event_favor`、`meetup_favor`、`match_tag_relation` 把两个对象连接起来，重复关系需要由组合主键或唯一约束阻止。

订单明细和快照又是另一层。订单主表需要稳定地支持状态、金额和归属查询，业务明细需要表达场馆/活动/会员商品的不同字段，快照则保存下单时的名字、时间、价格或扩展信息。把它们全部塞进一个 JSON 看起来灵活，但会牺牲结构化查询、约束和历史解释能力。

| 分类 | 当前例子 | 它保存的事实 | 读者要问的问题 |
|---|---|---|---|
| 实体 | venue、court、event、membership_card | 一个可被持续引用的对象 | 身份、状态和生命周期是什么？ |
| 规则/配置 | price_plan_detail、membership_product | 如何生成资源或权益 | 修改规则会影响哪些未来数据？ |
| 业务事实 | session_reg、event_reg、membership_card_usage | 一次预约、报名或使用 | 是否允许重复？如何退款/取消？ |
| 关系表 | event_favor、meetup_favor、match_tag_relation | 两个对象的连接 | 组合主键是否表达唯一性？ |
| 快照/扩展 | order_snapshot、metadata、registration_fields | 某时刻的历史补充 | 未来还能否解释这段 JSON？ |

```prisma
model session_reg {
  reg_id     Int    @id @default(autoincrement())
  session_id Int
  user_id    String
  order_id   String

  @@unique([session_id, user_id, order_id])
}

model order_snapshot {
  order_id     String @id
  session_ids  Json?
  venue_name   String?
  booking_time String?
}
```

**例子**

- `venue` 是持续存在的资源实体，`session_reg` 是用户与某个场次之间发生过的预约事实。
- `order_snapshot` 记录历史展示需要的当时数据，而不是用来替代当前 `venue` 或 `court` 的主数据。



### 先写证据状态，再写领域结论

> **先记住：** 源码回答字段、关系、枚举和 service 调用；运行与测试回答并发、迁移和数据行为。

阅读源码时可把结论分成四种状态：verified 是可以直接定位的实现；inferred 是从多个文件关系推导出的解释；chosen 是本文为了学习选取的分组或主线；planned/unknown 是后续验证项。

例如，`membership_card_usage` 的唯一约束表达了重复组合边界；它能降低同卡重复使用同一场次的风险，实际扣次行为还要结合 service、事务和并发用例观察。





## 2. 资源域——从价格规则到可预约场次

### merchant、venue、court 是资源归属层级

> **先记住：** `merchant` 是运营归属，`venue` 是面向用户的场馆，`court` 是场馆内部可以配置价格和生成场次的具体资源。

同一个“预约场馆”页面，后端至少需要回答三件不同的事：谁负责运营它、用户看到的场馆是什么、场馆里哪一块具体资源被预约。把三层混成一个表，会让价格、维护状态、场馆审核和订单归属互相污染。

当前 schema 用 `merchant_id` 连接场馆归属，用 `venue_id` 连接 court；B 端 API 也把场馆、场地和价格计划拆成不同入口。这个拆分说明它们是不同的运营动作，服务边界仍按实际模块组织。

```prisma
model court {
  court_id  Int          @id @default(autoincrement())
  venue_id  Int
  category  court_category
  status    court_status @default(available)
  capacity  Int?
  venue     venue        @relation(fields: [venue_id], references: [venue_id])
  session   session[]
}
```

**例子**

- 商户可以管理多个场馆；场馆可以下挂多个 court；每个 court 再生成自己的价格计划和 session。
- 用户页面展示“某场馆”，库存扣减时却必须落到具体 `court_id` 和 `session_id`，否则无法区分同馆的不同场地。



### price_plan_detail 是规则，session 是被物化的时间库存

> **先记住：** `price_plan_detail` 描述星期、时间段和价格规则；`session` 是某个具体日期上可查询、可锁定、可预约的资源实例。价格计划同步服务会把规则物化为未来场次。

如果每次用户打开页面都根据星期和价格规则临时计算，后端还要在预约时重新确认同一套计算结果，历史价格和已预约资源也更难被解释。当前实现把规则和实例拆开：B 端维护价格计划，生成服务为未来日期创建 session，C 端查询 session 并把 sessionId 交给预约接口。

这是一种“规则 → 物化事实”的设计。它换来了更容易查询和预约的 session，也引入了同步问题：价格计划修改后，哪些未来 session 可以更新，哪些已被预约或锁定必须保留。

```typescript
const priceDetails = await this.prisma.price_plan_detail.findMany({
    where: { court_id: courtId, status: 'available' },
    orderBy: [
        { weekday: 'asc' },
        { start_time: 'asc' },
        { end_time: 'asc' }
    ]
});

await this.prisma.session.create({
    data: {
        venue_id: court.venue_id,
        court_id: courtId,
        date: dateOnly,
        start_time: startTime,
        end_time: endTime,
        price,
        status: 'available',
        capacity_total: court.capacity ?? null
    }
});
```

**例子**

- 规则：周三 19:00-20:00，价格 80 元。
- 物化实例：2026-09-09，某个 court，19:00-20:00，当前状态 available。
- 交易事实：用户在该 session 上产生一条 session_reg，并通过 order 关联付款或会员权益。

### 已预约日期保护了什么一致性

> **先记住：** 生成服务会识别已有场次以及 reserved/locked 状态的日期；有预约或锁定事实的日期不能被简单删除后重建。

价格计划同步看起来像一次批量更新，但它实际上会触碰已经暴露给用户的资源。如果某一天的 session 已经产生预约，直接删除并重建会改变 sessionId、丢失关联或让历史订单无法对应原来的资源。因此当前服务先统计受保护日期，再跳过这些日期；无预约的旧场次才可能被清理后按新规则生成。

当前生成服务会跳过 reserved/locked 日期；其他占用状态则放入验证矩阵继续检查。

```typescript
const datesWithReservedSessions = new Set<string>();

for (const session of existingInRange) {
    const date = this.toUTCDateStr(new Date(session.date));
    if (session.status === 'reserved' || session.status === 'locked') {
        datesWithReservedSessions.add(date);
    }
}

if (datesWithReservedSessions.has(dateStr)) {
    skippedDaysCount++;
    continue;
}
```

**检查清单**

- [ ] 修改规则前先找出已预约、已锁定或已被其他业务占用的日期。
- [ ] 不用 delete + recreate 覆盖仍被业务事实引用的 session。
- [ ] 给同步任务增加“跳过数量、生成数量、失败数量”的日志或结果。
- [ ] 对跨时区的 date、start_time、end_time 设计独立测试。





## 3. 交易域——订单不是一张大 JSON

### order 是交易聚合入口，不是所有细节的容器

> **先记住：** `order` 保存用户、金额、状态、业务类型、商户/场馆/活动归属、业务日期和支付时间等高频交易字段；具体细节继续由明细表、事实表和快照承载。

订单主表需要支持列表、详情、支付状态和商户运营查询，所以 `order_type`、`venue_id`、`event_id`、`business_date`、`paid_at` 等字段被提取出来。它们让常用筛选不必每次解析一段 JSON，也让 B 端订单列表能够按业务日期、状态和资源归属组织结果。

但 order 仍然不应该吞掉所有细节。一个订单可能包含多个 session、活动报名人或会员商品；这些对象的结构和生命周期不同，应该通过明细表、事实表或快照继续表达。

| 订单层次 | 保存什么 | 适合回答的问题 |
|---|---|---|
| `order` | 金额、状态、用户和业务归属 | 这笔交易现在处于什么阶段？ |
| 业务明细 | 场次、活动参与人或会员商品字段 | 这笔交易具体买了什么？ |
| `order_snapshot` | 下单时的展示信息 | 当时用户看到的名称、时间和价格是什么？ |

```prisma
model order {
  order_id       String      @id
  user_id        String
  money          Decimal
  status         order_status
  order_type     order_type?
  merchant_id    Int?
  venue_id       Int?
  event_id       Int?
  business_date  DateTime?   @db.Date
  paid_at        DateTime?
  metadata       String?     @db.Text

  session_reg    session_reg[]
  event_reg      event_reg[]
}
```



### order_item、业务明细和 snapshot 分别服务什么查询

> **先记住：** `order_item` 负责通用金额与数量，业务明细表负责领域字段，snapshot 负责下单时不可变展示；三者共同把交易事实从大 JSON 中拆出来。

场馆订单需要 sessionId、courtName、sportCategory、start/end time 等信息；活动订单需要 eventId 和参与人数；会员商品订单需要 productId、卡类别、范围和时长/次数。把这些字段都塞进统一 order_item 会产生大量可空列，塞进 metadata 又会失去结构化约束。

因此当前模型使用 `order_item` 作为公共层，再用 `venue_order_item`、`event_order_item`、`membership_order_item` 表达各自业务结构。`order_snapshot` 则承担低频历史展示数据，例如下单时的场馆名称、预约时间和批量支付信息。这样，即使场馆名称或价格策略以后变化，历史订单仍有机会展示当时的语义。

| 模型 | 责任 | 不应该替代谁 |
|---|---|---|
| `order_item` | 公共数量、单价、总价和状态 | 具体业务明细 |
| `venue_order_item` 等 | 保存各业务类型的结构化字段 | 订单主状态 |
| `order_snapshot` | 保存历史展示快照 | 当前资源主数据 |

```typescript
const item = await tx.order_item.create({
    data: {
        order_id: orderId,
        item_type: 'venue',
        venue_id: session.venue_id,
        business_date: session.date,
        quantity: 1,
        unit_amount: session.price,
        total_amount: session.price,
        status: 'active'
    }
});

await tx.venue_order_item.create({
    data: {
        item_id: item.item_id,
        session_id: session.session_id,
        court_id: session.court_id,
        court_name: session.court?.name,
        start_time: session.start_time,
        end_time: session.end_time,
        snapshot: { price: session.price }
    }
});
```

**例子**

- 公共金额：quantity、unit_amount、total_amount、status。
- 场馆明细：session_id、court_name、sport_category、start_time、end_time。
- 活动明细：event_id、participant_count、registration_type。
- 历史快照：下单时的 venue_name、booking_time、session_ids。

### payment_order、refund_order、fund_flow 是资金状态边界

> **先记住：** 支付渠道单号、支付状态、退款审核/渠道状态和资金发生记录是不同事实；它们不能只压缩成一个 `order.status`。

`order.status` 表达业务订单处于待支付、已支付、已完成或退款相关阶段；`payment_order` 记录渠道单号、支付金额、渠道交易号和通知原文；`refund_order` 记录退款申请、审核、渠道退款单号及退款状态；`fund_flow` 记录资金方向、金额、关联支付/退款单和业务日期。

这套拆分让重复支付回调、部分分摊和退款审计有独立落点，也意味着状态变化不应该用一个字段代替所有事实。源码能确认这些模型和 service 边界，但退款后是否释放具体资源、队列重试如何排序，还需要集成日志和故障测试。

| 事实 | 典型字段 | 主要问题 |
|---|---|---|
| `order` | `status`、`paid_at` | 业务交易是否完成？ |
| `payment_order` | `out_trade_no`、渠道交易号 | 渠道支付是否成功、回调是否重复？ |
| `refund_order` | 退款申请与渠道状态 | 退款是否受理、成功或失败？ |
| `fund_flow` | 方向、金额、关联单号 | 钱最终如何流转与对账？ |

```prisma
model payment_order {
  payment_id             String               @id
  out_trade_no           String               @unique
  status                 payment_order_status @default(initiated)
  total_amount           Decimal
  channel_transaction_id String?
  raw_notify             Json?
}

model refund_order {
  refund_id         String              @id
  order_id          String
  out_refund_no     String              @unique
  apply_status      refund_apply_status
  channel_status    refund_channel_status
  refund_amount     Decimal
}
```

**检查清单**

- [ ] 分别记录业务订单、支付渠道、退款审核/渠道和资金流水状态。
- [ ] 用 out_trade_no、out_refund_no 处理外部单号幂等边界。
- [ ] 对同一支付回调重复进入、部分订单分摊和退款失败分别测试。
- [ ] 不把已有 enum 和字段拆分直接描述成渠道时序已经验证。





## 4. 活动与社交域——动态表单和关系表

### event 把内容、审核、报名和资源关联放在同一聚合周围

> **先记住：** `event` 保存活动的内容、时间、价格、容量和状态；`event_audit`、`event_image`、`event_reg`、标签关系表分别保存审核、内容资源、报名事实和分类关系；`event.session` 还可以关联场次资源。

一个活动页面同时承担“被创建”“待审核”“展示图片”“接受报名”“关联场馆/场次”等多种动作。如果把审核记录、图片排序和报名数据都塞进 event，event 的主表会变成一个不可维护的混合对象。当前 schema 通过一对多关系把这些事实拆开，又通过 event.status、audit_status、is_hidden、is_deleted 等字段表达当前可见性和生命周期。

本文把 event 周围的相关表作为一个阅读上的聚合边界；具体事务范围结合 event service 和报名 service 判断。

**例子**

- 审核事实：谁在何时对活动执行 approve/reject。
- 展示资源：cover/detail 图片、排序和删除。
- 报名事实：user、event、order、registration_fields、status。
- 资源关系：event 可与 venue 和 session 连接，但不是普通场次预约的同一事实。



### registration_fields 是灵活性，也是数据解释成本

> **先记住：** `event.registration_fields` 描述动态表单，`event_reg.registration_fields` 保存报名时提交的数据；这种设计降低了每种活动都建新列的成本，但需要字段版本或历史快照策略。

不同活动可能需要姓名、水平、紧急联系人、装备尺码等不同字段。使用 JSON 可以让运营台动态增加报名字段，避免为每一种活动改 schema；报名记录也把当时的填写结果保留下来，而不是只保存一组固定列。

动态字段与报名记录分离后，历史 JSON 的解释依赖字段定义；表单版本号、历史回放和校验兼容应纳入表单演进设计。

```prisma
model event {
  event_id             Int   @id @default(autoincrement())
  registration_fields  Json?
  event_reg            event_reg[]
}

model event_reg {
  reg_id              Int    @id @default(autoincrement())
  event_id            Int
  user_id             String
  order_id            String
  registration_fields Json
  status              event_reg_status @default(active)
}
```

**检查清单**

- [ ] 区分表单定义和报名提交数据。
- [ ] 给动态 JSON 保留字段 key、版本或生成时间的解释入口。
- [ ] 测试表单新增、删除、改名后旧报名数据仍能展示。
- [ ] 不把 JSON 灵活性写成“无需校验”。



### meetup、favor、comment、reg 展示关系表的价值

> **先记住：** 收藏、报名、标签等多对多关系适合用独立关系表表达；评论还可能通过 parent_id 形成自关联。组合主键让同一用户和同一对象的关系天然唯一。

如果把所有用户的收藏名单放进 meetup，一条约球记录会不断增长，查询和删除也会变复杂。`meetup_favor` 把 user_id 与 meetup_id 作为一条关系事实，`@@id([meetup_id, user_id])` 直接表达“同一用户不能重复收藏同一条约球”。`meetup_reg` 使用同样思路表示报名，`meetup_comment` 则额外通过 parent_id 支持回复关系。

这种关系表不是“多余的中间表”，而是把一个可查询、可约束、可审计的事实单独建模。它也要求 service 在删除用户或 meetup 时明确外键级联和历史保留策略。

| 关系表 | 连接对象 | 额外语义 |
|---|---|---|
| `meetup_favor` | 用户 + 约球 | 是否收藏，组合主键防重复 |
| `meetup_reg` | 用户 + 约球 | 是否报名以及报名状态 |
| `meetup_comment` | 用户 + 约球/评论 | `parent_id` 支持回复层级 |

```prisma
model meetup_favor {
  meetup_id Int
  user_id   String
  meetup    meetup @relation(fields: [meetup_id], references: [meetup_id])
  user      user   @relation(fields: [user_id], references: [openid])

  @@id([meetup_id, user_id])
}
```

**例子**

- 用户 A 收藏 meetup-100，会生成一条 `(meetup_id=100, user_id=A)` 关系事实。
- 用户 A 回复用户 B 的评论，新增评论记录并通过 `parent_id` 指向原评论，而不是把回复文本拼回 meetup 主表。

## 5. 会员域——商品、权益卡和使用事实

### product、card、usage 分别代表规则、权益和事实

> **先记住：** `membership_product` 是商户配置的商品规则，`membership_card` 是用户购买/激活后的权益，`membership_card_usage` 是一次入场或场次使用事实。

商品可以设置 entry/session 类别、有效期、总次数、单馆/连锁范围和购买/使用限制；卡片保存用户、产品、起止日期、状态和剩余次数；使用记录则保存 venue、session、order、usage_date 和 usage_type。三者合并后，商品规则会被每次使用覆盖，用户拥有的权益也无法和已经消耗的事实区分。

`remaining_times` 是卡片当前的可用余额，`membership_card_usage` 是余额变化的业务凭据。余额适合快速判断，使用记录适合追溯和对账；两者不应该互相替代。

| 层次 | 主要问题 | 当前模型 |
|---|---|---|
| 商品规则 | 卖什么、适用哪个场馆、多少天/次 | membership_product |
| 用户权益 | 谁拥有、何时生效、还剩多少、当前状态 | membership_card |
| 使用事实 | 哪天、哪个场馆、哪一场次、以何种方式使用 | membership_card_usage |



### 激活会员卡是跨表状态变化

> **先记住：** 会员卡激活会读取卡片、商品和用户已有权益，可能合并同产品有效卡、计算日期/次数，再在 transaction 中更新或删除多条记录。

会员卡的状态不是孤立字段。激活时要确认卡属于当前用户，读取产品的 card_category、duration_days、total_times 和 scope，再判断用户是否已经有同产品有效卡。时间卡可能延长 end_date，次数卡可能合并 remaining_times；如果多表变化中途失败，部分更新会产生难以解释的权益。

当前 service 用 Prisma transaction 包住这类跨表操作；卡片合并、外键删除失败、重复点击和退款恢复可作为后续测试用例。

```typescript
return await this.prisma.$transaction(async (tx) => {
    const card = await tx.membership_card.findUnique({
        where: { card_id: cardId },
        include: { membership_product: true }
    });

    const existingActiveCard = await tx.membership_card.findFirst({
        where: {
            user_id: openid,
            product_id: card.membership_product.product_id,
            status: 'active'
        }
    });

    // 根据卡类型合并权益或更新激活状态
    return tx.membership_card.update({
        where: { card_id: cardId },
        data: { status: 'active', start_date: new Date() }
    });
});
```

**例子**

- 时间卡激活：读取产品有效期，计算新的 `end_date`，再与已有同产品有效卡合并或更新。
- 次数卡激活：读取 `total_times` 和已有 `remaining_times`，在同一事务里决定新卡创建、合并或拒绝。

**检查清单**

- [ ] 激活前确认卡片归属、产品状态和当前有效期。
- [ ] 明确时间卡与次数卡的合并规则。
- [ ] 将更新卡片、删除旧卡和生成返回结果放进同一事务边界。
- [ ] 测试重复激活、卡片已过期、外键删除失败和退款回滚。

### 会员使用唯一约束表达了哪些业务边界

> **先记住：** 当前 `membership_card_usage` 通过 `(card_id, usage_date, venue_id, usage_type, session_id)` 与 `(card_id, session_id)` 两组唯一约束表达不同重复边界；约束能阻止特定重复组合，不能自动完成资格校验、扣次和退款回滚。

入场卡和场次卡的使用语义不同。入场记录关注某张卡在某天、某馆是否已经使用；场次卡关注某张卡是否已经绑定某个 session。把所有使用场景只用一个布尔字段表达，会丢掉日期、场馆和 session 维度。

唯一约束表达记录级边界；service 还要检查卡状态、有效期、scope、usage_type 和场次关系，并把余额更新与 usage 记录放在同一事务中。

| 唯一边界 | 防止的重复 | 还要由 service 判断的内容 |
|---|---|---|
| `card_id + usage_date + venue_id + usage_type + session_id` | 同卡在同日/同馆/同类型的重复使用记录 | 卡是否有效、是否在范围内 |
| `card_id + session_id` | 同卡重复绑定同一场次 | 场次是否可用、是否需要扣次 |

```prisma
model membership_card_usage {
  card_id    Int
  venue_id   Int
  usage_type membership_card_usage_usage_type
  session_id Int?
  usage_date DateTime @db.Date

  @@unique([card_id, usage_date, venue_id, usage_type, session_id])
  @@unique([card_id, session_id])
}
```





## 6. 一致性复盘——数据库能保证到哪一步

### 约束要分成数据库层、service 层和测试层

> **先记住：** 数据库层约束值域、唯一性、关系和查询入口；service 层表达跨表资格、状态转换和事务；测试层验证并发、异常、迁移和真实边界。三层各有边界。

`@@unique` 适合表达数据库可以判断的重复组合，`enum` 适合限定状态值域，`@@index` 适合告诉数据库常用查询方向，外键负责关联和删除策略。它们是底层结构约束，不会自动判断“这个会员卡是否属于当前用户”或“这个价格修改是否应该避开已预约日期”。

service 层把多个查询和写入放进业务过程，transaction 让一组数据库变化具有原子边界；测试层则需要故意制造重复请求、失败回滚、时间边界和历史数据，才能证明代码在异常路径下的行为。

| 层次 | 适合保证 | 还要补的内容 |
|---|---|---|
| schema/数据库 | 唯一、外键、值域、索引 | service 里的跨表业务流程 |
| service/事务 | 资格、状态转换、多表原子写入 | 并发与故障场景的测试 |
| 测试/运行 | 特定输入、并发和故障条件下的结果 | 未覆盖的输入与环境 |

```typescript
await this.prisma.$transaction(async (tx) => {
    await tx.membership_card_usage.create({ data: usageData });
    await tx.membership_card.update({
        where: { card_id: cardId },
        data: { remaining_times: { decrement: 1 } }
    });
});
```

**检查清单**

- [ ] 先问这个约束能否由单条 SQL 判断。
- [ ] 跨表资格和状态转换放进 service/transaction。
- [ ] 对并发、重复、回滚和历史数据设计可重复测试。
- [ ] 把“代码路径存在”与“测试已经运行通过”分开记录。



### 时间、软删除和级联关系是隐藏的领域规则

> **先记住：** DATE、TIME、DATETIME、JSON 的选择影响查询和时区；软删除字段影响“是否还能被展示/操作”；Cascade 与 SetNull 影响删除后历史关系如何保留。

`session.date` 是业务日期，`start_time/end_time` 是时段，订单和通知还会使用 DateTime；如果在 API 边界没有固定转换规则，同一个场次可能在不同时区被算到不同日期。生成服务已经用 UTC 日期边界处理场次生成，这可以作为需要单独测试的真实案例。

删除也不是简单的 boolean。venue、event 等模型有 is_deleted/deleted_at 等软删除字段，同时部分外键使用 Cascade，session 与 event 的关联又可能 SetNull。这样做可以让历史订单保留部分事实，也可能让查询出现“资源还在关系里但当前不可见”的边界，需要明确各接口的过滤规则。

```prisma
model event {
  is_deleted Boolean   @default(false)
  deleted_at DateTime?
  session    session[]
}

model session {
  date      DateTime @db.Date
  start_time DateTime @db.Time(0)
  end_time   DateTime @db.Time(0)
  event_id   Int?
  event      event? @relation(fields: [event_id], references: [event_id], onDelete: SetNull)
}
```

**例子**

- `session.date` 适合表示业务日，`start_time/end_time` 适合表示日内时段，支付时间则需要完整的 `DateTime`。
- 活动被软删除后，C 端列表可能不再展示，但历史订单详情仍需要依据快照和关联策略保留可解释信息。

**检查清单**

- [ ] 为业务日期、时间段和真实时间点分别定义输入/输出格式。
- [ ] 测试 UTC 边界、夏令时/服务器时区差异和跨日时段。
- [ ] 记录软删除后 C 端、B 端、订单详情各自应该看到什么。
- [ ] 逐一检查 Cascade 是否会误删历史事实，SetNull 是否会留下可解释的孤儿关系。



### 用验证矩阵结束，而不是用“表都看完了”结束

> **先记住：** 数据库复盘的终点不是列出所有表，而是为每个关键不变量指定验证方式：schema 检查、service 单测、集成测试、迁移回放、并发测试或运营日志。

验证矩阵要覆盖跨表链，而不是只测单个 CRUD。资源域要验证价格修改是否保护已预约 session；交易域要验证 metadata 与结构化字段在历史订单上是否一致；活动域要验证表单变化后旧报名仍可解释；会员域要验证重复激活、并发扣次和退款恢复。

面试回答按“schema/service 做了什么—关键字段、约束或 transaction—如何验证”组织，回答项目中的工程判断，而不是背诵“范式、索引、事务”的名词。

| 场景 | 证据方式 | 验证方式 |
|---|---|---|
| 价格计划修改覆盖已预约日期 | session generation integration test | 代码分支，运行集成测试 |
| order.metadata 与结构化字段不一致 | migration replay + reconciliation script | 兼容读取，运行回放与对账 |
| 动态报名字段改版后读取历史报名 | fixture + form version test | 补充历史版本样本 |
| 同一会员卡重复使用同一场次 | unique constraint + concurrent test | schema 约束，运行并发测试 |
| 会员卡激活合并中途失败 | transaction rollback test | service transaction，运行回滚测试 |
| venue/event 软删除与历史订单展示 | API contract test | 删除字段与关系，运行端到端测试 |

**例子**

- 看到“价格同步会保护已预约日期”时，至少要准备一条已预约 fixture、一条普通未来场次和一次同步前后对比。
- 看到“唯一约束能防重复使用”时，还要并发提交两次请求，检查一条成功、一条被数据库约束拒绝，以及余额是否只扣一次。

**检查清单**

- [ ] 每条关键结论都绑定一个可复现的验证方式。
- [ ] 区分源码已有分支、单元测试覆盖和集成/线上证据。
- [ ] 对迁移、并发、时区、删除和回滚单独建用例。
- [ ] 面试回答中主动说出需要补充的边界用例。





> **03 的复盘结论：** 数据库模型不是表名清单，而是业务事实的分层。schema 负责声明值域、唯一性、关系和查询入口；service/transaction 负责跨表资格与状态变化；测试和运行证据负责回答并发、迁移、回滚、时间边界与删除策略是否真的成立。

## 7. 面试复盘

下面集中整理项目中最容易被追问的设计问题，回答按“实现—依据—验证”展开。

### 1. 为什么 03 不从第一张 model 逐个讲到最后一张？

**回答：** 因为表的顺序是文件组织，不是业务理解顺序；先按事实和关系建立领域地图，才能知道字段为什么存在。

**依据：** 当前 schema 同时包含资源、交易、活动、会员和运营模型，逐表阅读会丢掉跨表关系。

### 2. 为什么 session_reg 不能被简单理解为 session 的附属字段？

**回答：** 因为 session.status 表示资源当前状态，session_reg 记录用户、订单与场次之间发生过的预约事实；它们的查询目的和生命周期不同。

**依据：** schema 同时定义了 session 的状态字段和 session_reg 的 user/order 外键。

### 3. 看到 @@unique 后，能不能直接说业务不会重复？

**回答：** 不能。它能证明数据库声明了一个唯一边界，但还要确认写入路径、事务、异常处理和历史数据是否都经过这条约束。

**依据：** schema 是数据库设计证据，真实重复请求和错误处理属于运行/测试证据。

### 4. 为什么价格计划不直接挂在 venue 上？

**回答：** 因为真正被定价和生成场次的是具体 court；同一个场馆内不同场地可以有不同运动类型、容量和时段价格。

**依据：** price_plan_detail 通过 court_id 关联 court，session 也通过 court_id 关联资源。

### 5. session 是不是 price_plan_detail 的另一种名字？

**回答：** 不是。price_plan_detail 是可复用的定价规则，session 是绑定具体日期和当前状态的可交易资源实例。

**依据：** 两个 model 的字段、关系和 service 使用方式不同；生成服务会从前者创建后者。

### 6. 为什么价格计划同步不能无条件删除未来七天的 session？

**回答：** 因为其中可能已经存在预约或锁定事实；删除重建可能改变资源身份、断开订单关联，甚至覆盖用户已经购买的权益。

**依据：** 当前生成服务显式区分 datesWithReservedSessions 和 datesWithSessions。

### 7. order_type、venue_id、business_date 为什么要从 metadata 里提到结构化字段？

**回答：** 因为它们是高频查询和运营筛选字段，结构化后能直接过滤、建立索引，也减少每次解析 JSON 的成本。

**依据：** schema 为这些字段增加了独立列和索引，order.service 仍保留 metadata 兼容读取。

### 8. 为什么 venue_order_item 还要保存 court_name，而不是永远 join 当前 court？

**回答：** 因为订单需要保留下单时的展示事实；当前 court 名称可能被运营修改，历史订单不应完全依赖现在的资源表。

**依据：** schema 同时提供 court_id、court_name 和 snapshot 字段。

### 9. 为什么支付成功不能只执行 order.update({ status: 'paid' })？

**回答：** 因为还需要记录渠道支付单、订单分摊、资金流水和重复回调状态；这些事实的生命周期和订单状态不同。

**依据：** schema 独立定义 payment_order、payment_allocation、fund_flow，payment service 也围绕它们处理回调。

### 10. 为什么 event 需要 event_audit，而不是只在 event.status 上记录 approved？

**回答：** status 只能表示当前状态，audit 记录谁做了什么审核动作及原因，便于追溯状态变化。

**依据：** schema 同时定义 event.audit_status 与 event_audit.action/reason/auditor_id。

### 11. registration_fields 使用 JSON 后，为什么还需要表单版本化？

**回答：** 因为 JSON 只保存数据，不自动保存字段含义；表单变化后需要知道历史值对应哪一版字段定义。

**依据：** event 和 event_reg 都有 registration_fields，但 schema 没有直接证明完整的版本回放策略。

### 12. 为什么不在 meetup 表上增加 favor_count 和 favor_user_ids？

**回答：** 计数和用户集合的写入竞争、查询和去重都更难处理；独立关系表可以按 user_id/meetup_id 查询并用组合主键约束重复关系。

**依据：** 当前 schema 使用 meetup_favor 及其组合主键表达收藏事实。

### 13. remaining_times 和 usage 记录为什么要同时存在？

**回答：** remaining_times 方便快速判断当前余额，usage 记录保留每次消耗的业务事实，便于审计、退款和对账。

**依据：** schema 同时为 membership_card 和 membership_card_usage 建模，并通过 session/venue/order 关联使用场景。

### 14. 为什么会员卡激活不能只更新 status = active？

**回答：** 因为激活还涉及产品规则、起止日期、剩余次数、已有同产品权益和可能的合并/删除，多表变化需要事务保持一致。

**依据：** consumer membership service 在 transaction 中查询产品和已有卡，再处理日期与次数。

### 15. membership_card_usage 的唯一约束能不能单独证明会员卡不会被超额使用？

**回答：** 不能。它只能防止满足这些字段组合的重复记录，剩余次数、有效期、并发扣减和退款恢复仍需要 service、事务与测试共同保证。

**依据：** 唯一约束覆盖记录重复，不覆盖 remaining_times 的数值变化和跨请求竞争。

### 16. 数据库有唯一索引后，为什么还要在 service 里做重复检查？

**回答：** service 可以给出更明确的业务错误并避免无意义写入，数据库唯一索引则作为并发和遗漏路径下的最后边界；二者职责不同。

**依据：** service 负责资格和状态语义，schema 负责唯一约束，错误路径仍需测试。

### 17. 为什么字段类型和删除策略也属于领域模型，而不是纯数据库实现细节？

**回答：** 因为它们决定业务日期如何解释、历史订单是否保留、关联资源删除后是否还能追溯，最终会改变接口返回和运营流程。

**依据：** 当前 schema 同时使用 DATE/TIME/DateTime、软删除字段和多种 onDelete 策略。

### 18. 面试官问“你如何证明这个数据库模型可靠”，最准确的回答是什么？

**回答：** 先说明 schema 的字段、关系和唯一约束，再说明 service 的事务/状态校验，最后列出已运行的测试和待补的迁移、并发、故障用例；不能只说“用了 Prisma 和事务”。

**依据：** 数据库结构、业务写入和运行验证分别属于不同证据层。
