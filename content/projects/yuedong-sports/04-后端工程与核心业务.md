# 悦动体育 04：NestJS 后端工程与核心业务——从模块组装到业务落库

Day05 的正文推进顺序是“需求分析 → 接口统计 → 数据结构 → 接口实现”。把这个顺序放回悦动体育，04 最适合回答另一个问题：这些接口为什么能在同一个 NestJS 应用里工作？

这篇不把 NestJS 当成一套需要先背完的框架 API，而是从后端进程启动开始，顺着真实代码往下读：`main.ts` 负责启动，`AppModule` 负责组装，`consumer` 和 `business` 提供两类业务入口，`common` 提供 Prisma、订单、权限和 OSS 等公共能力，具体的 Controller 和 Service 再把场馆、活动、会员与订单写成业务事实。

读完之后，应该能用一条完整路径解释：一个 B 端管理员创建场馆时，谁验证身份，谁检查商家，谁决定事务边界，哪几张表被写入，响应又是在哪里包装的。

> **本篇任务卡**
>
> 把“B 端管理员创建场馆”当成一次正式开发任务来读。输入是管理员身份和场馆表单，交付是一个处于待审核状态的场馆，以及一条能够追溯申请人的审核记录。完成标准不是记住 `@Controller` 或 `@Injectable`，而是能从请求入口走到数据库写入，并说清每个失败分支在哪里结束。
>
> - 先找到最终请求路径和权限边界；
> - 再确认 DTO、service 业务校验和事务写入；
> - 最后用“未授权、商家不存在、名称重复、创建成功”四种结果验收。

## 1. 先把 NestJS 应用看成一棵依赖树

### `main.ts` 负责把应用放到网络上

初学者容易把 `main.ts` 当成普通入口文件，然后直接跳去找业务方法。实际上它负责的是“应用怎么启动”，而不是“用户怎么预约”。

![图：从 main.ts、AppModule、consumer/business 模块到 Prisma/MySQL 的后端组装路径。](/projects/yuedong-sports/yuedong-04-backend-architecture.png)

悦动的启动入口可以压缩成下面这几步：

```typescript
// yuedong_nestjs/src/main.ts
import { NestFactory } from '@nestjs/core';
import { AppModule } from './app.module';

async function bootstrap() {
    const app = await NestFactory.create(AppModule);

    app.enableCors({
        origin: [
            'http://localhost:5173',
            'http://localhost:3000',
            'http://localhost:3344',
            'https://yuedongjump.com'
        ],
        credentials: true,
        methods: ['GET', 'POST', 'PUT', 'DELETE', 'PATCH', 'OPTIONS'],
        allowedHeaders: ['Content-Type', 'Authorization', 'Accept', 'Origin']
    });

    app.setGlobalPrefix('api');

    const port = process.env.PORT ?? 8080;
    await app.listen(port, '0.0.0.0');
}

bootstrap();
```

这里有三个对读接口很重要的结果：

| 代码 | 作用 | 阅读时要联想到什么 |
|---|---|---|
| `NestFactory.create(AppModule)` | 创建 NestJS 应用实例 | 下面的模块、controller、provider 从哪里装进来 |
| `setGlobalPrefix('api')` | 给接口统一增加 `/api` | `@Controller('venues')` 不等于最终 URL |
| `listen(port, '0.0.0.0')` | 监听端口并接受请求 | 前端 base URL、端口和容器暴露端口是否一致 |

所以 `@Controller('venues')` 如果属于 C 端模块，常见最终路径会是 `/api/venues`；如果属于 B 端模块，还要继续合并 `business` 路由前缀。

### `AppModule` 是依赖的总装配点

NestJS 的 `@Module` 可以先翻译成四个普通概念：

- `imports`：这个模块需要使用哪些其他模块。
- `controllers`：哪些类负责接收 HTTP 请求。
- `providers`：哪些 service、guard 或工具可以被 NestJS 注入。
- `exports`：哪些 provider 可以被其他模块继续使用。

悦动的根模块把基础设施和业务入口放在同一个应用中：

```typescript
// yuedong_nestjs/src/app.module.ts
@Module({
    imports: [
        ConfigModule.forRoot({ isGlobal: true, envFilePath: '.env' }),
        PrismaModule,
        TypeOrmModule.forRoot({
            type: 'mysql',
            host: process.env.DATABASE_HOST || 'localhost',
            port: Number(process.env.DATABASE_PORT || 3306),
            database: process.env.DATABASE_NAME || 'yuedong',
            synchronize: false,
            timezone: '+08:00',
            dateStrings: true
        }),
        ScheduleModule.forRoot(),
        JwtModule.register({
            global: true,
            secret: process.env.JWT_SECRET || 'default_secret',
            signOptions: { expiresIn: '3d' }
        }),
        VenueModule,
        SessionModule,
        OrderModule,
        EventModule,
        UserModule,
        MeetupModule,
        ConsumerMembershipModule,
        BusinessModule,
        MerchantVenueModule,
        WxpayModule,
        OssModule,
        GeoModule
    ],
    controllers: [AppController, HealthController],
    providers: [
        AppService,
        VenueCleanupTask,
        { provide: APP_GUARD, useClass: AuthGuard }
    ]
})
export class AppModule {}
```

这里有一个很适合初学者的观察点：配置里同时出现 `TypeOrmModule.forRoot` 和 `PrismaModule`，但业务 service 大量注入的是 `PrismaService`。因此不能只看依赖包名称就判断“项目使用了什么”，要沿着实际的 `constructor` 和 `prisma.xxx` 调用确认数据访问路径。

`PrismaModule` 本身很小，但它被声明为全局模块：

```typescript
// yuedong_nestjs/src/common/prisma/prisma.module.ts
@Global()
@Module({
    providers: [PrismaService],
    exports: [PrismaService]
})
export class PrismaModule {}
```

这段代码的工程意义是：业务模块可以直接注入同一个 Prisma 数据访问入口，具体 service 不需要重复创建数据库客户端。

### 全局 guard 和 middleware 先于业务方法出现

`AppModule` 通过 `APP_GUARD` 注册用户侧 `AuthGuard`，并把日志与清理 middleware 应用到所有路由：

```typescript
// yuedong_nestjs/src/app.module.ts
providers: [
    AppService,
    VenueCleanupTask,
    {
        provide: APP_GUARD,
        useClass: AuthGuard
    }
]

// module.configure
configure(consumer: MiddlewareConsumer) {
    consumer
        .apply(LoggerMiddleware, CleanerMiddleware)
        .forRoutes('*');
}
```

`AuthGuard` 先看请求路径：登录、注册、健康检查、OSS 等路径有自己的放行规则；公开 GET 也可以放行，但如果请求带了合法 token，guard 仍会尝试解析 `openid` 并挂到 request 上。需要登录的请求则必须带 `Bearer` token，JWT 中的 `openid` 还要能查询到用户。

```typescript
// yuedong_nestjs/src/auth/auth.guard.ts
const token = this.extractTokenFromHeader(request);

if (!token) {
    throw new HttpException('Unauthorized', HttpStatus.UNAUTHORIZED);
}

const payload = this.jwtservice.verify(token);
const { openid } = payload;
const user = await this.userService.findUser(openid);

if (!openid || !user) {
    throw new HttpException('Authorization failed', HttpStatus.UNAUTHORIZED);
}

request.openid = openid;
return true;
```

到这里可以形成第一条阅读路径：

> `main.ts` 启动应用 → `AppModule` 装配依赖 → middleware/guard 处理请求 → controller 接收业务动作

## 2. consumer、business 与 common 如何共存

### 目录是业务入口提示，不是微服务地图

悦动后端大致可以按下面三类目录阅读：

| 目录 | 典型模块 | 主要调用者 | 关注点 |
|---|---|---|---|
| `consumer` | user、venue、session、event、meetup、membership | C 端用户 | 查询、预约、报名、收藏、会员购买 |
| `business` | admin、merchant、venue、court、price-plan、event、session、order、membership | B 端运营人员 | 配置、审核、发布、订单处理、核销 |
| `common` | prisma、order、inventory、oss、sms、message、queue | 多个业务模块 | 可复用的基础设施和公共业务能力 |

这三类代码被 `AppModule` 放入同一个 NestJS 应用。它们是职责和入口的划分，是否形成独立服务要看独立进程、部署单元和运行配置。

![图：consumer 与 business 两类业务入口共同进入 NestJS Application，再复用 Prisma、Permission、OSS 与 Message。](/projects/yuedong-sports/yuedong-04-module-boundaries.png)

例如消费端场次模块声明自己的 controller 和 service，同时导入订单与库存模块：

```typescript
// yuedong_nestjs/src/consumer/session/session.module.ts
@Module({
    imports: [OrderModule, InventoryModule],
    controllers: [SessionController],
    providers: [SessionService, PrismaService],
    exports: [SessionService]
})
export class SessionModule {}
```

B 端场馆模块则把权限、OSS、场次和消息能力组合起来：

```typescript
// yuedong_nestjs/src/business/venue/venue.module.ts
@Module({
    imports: [
        PrismaModule,
        PermissionModule,
        OssModule,
        forwardRef(() => SessionModule),
        MessageModule
    ],
    controllers: [MerchantVenueController, VenueAuditController],
    providers: [MerchantVenueService, VenueAuditService],
    exports: [MerchantVenueService, VenueAuditService]
})
export class MerchantVenueModule {}
```

两段 module 的区别不在于写法，而在于它们服务的入口和依赖不同：C 端 session 需要用户预约相关能力，B 端 venue 需要管理员权限、图片上传、场次矩阵和审核消息。

### `RouterModule.register` 把 B 端模块挂到同一个前缀

`@Controller` 只提供局部路径。B 端的完整前缀在 `BusinessModule` 中集中注册：

```typescript
// yuedong_nestjs/src/business/business.module.ts
@Module({
    imports: [
        AdminModule,
        MerchantModule,
        MerchantVenueModule,
        CourtModule,
        PricePlanModule,
        EventModule,
        SessionModule,
        BusinessOrderModule,
        MembershipModule,
        MessageModule,
        RouterModule.register([
            { path: 'business', module: AdminModule },
            { path: 'business', module: MerchantModule },
            { path: 'business', module: MerchantVenueModule },
            { path: 'business', module: CourtModule },
            { path: 'business', module: PricePlanModule },
            { path: 'business', module: EventModule },
            { path: 'business', module: SessionModule },
            { path: 'business', module: BusinessOrderModule },
            { path: 'business', module: MembershipModule },
            { path: 'business', module: MessageModule }
        ])
    ]
})
export class BusinessModule {}
```

因此，B 端场馆 controller 的：

```typescript
@Controller('venues')
export class MerchantVenueController {}
```

与 `main.ts` 的 `/api`、`BusinessModule` 的 `/business` 组合后，形成 `/api/business/venues` 这一类地址。C 端的 `@Controller('venues')` 没有 `business` 这一层，形成 `/api/venues`。

读 B 端接口时可以固定做三次拼接：

1. 找 `main.ts` 的全局前缀。
2. 找 `RouterModule.register` 的模块前缀。
3. 找 controller 装饰器和方法装饰器的局部路径。

### 用户身份、管理员身份与资源范围是三层判断

有 token 只说明请求带了凭据，不等于它能操作任意场馆。B 端 controller 通常还会出现 `AdminGuard` 和 `@Roles`：

```typescript
// yuedong_nestjs/src/business/venue/venue.controller.ts
@Post()
@UseGuards(AdminGuard)
@UsePipes(ZodValidationPipe)
@Roles('platform_admin', 'merchant_admin')
async createVenue(
    @AdminInfo() adminInfo: AdminInfoInterface,
    @Body() dto: VenueCreateDto
): Promise<Message> {
    if (
        adminInfo.role === 'merchant_admin' &&
        dto.merchantId !== adminInfo.merchantId
    ) {
        throw new HttpException('无权为其他商家创建场馆', HttpStatus.FORBIDDEN);
    }

    const venue = await this.venueService.createVenue(dto, adminInfo.id);
    return {
        message: '创建场馆成功',
        statusCode: HttpStatus.CREATED,
        data: venue
    };
}
```

`AdminGuard` 验证管理员 JWT 中的 `username`，查询管理员状态，并把需要的上下文挂到 request：

```typescript
// yuedong_nestjs/src/auth/admin.guard.ts
const payload = this.jwtService.verify(token);
const { username } = payload;
const admin = await this.prisma.admin.findUnique({
    where: { username }
});

if (!admin || admin.status !== true) {
    throw new HttpException('授权失败', HttpStatus.UNAUTHORIZED);
}

const requiredRoles = this.reflector.get<string[]>(
    'roles',
    context.getHandler()
);

if (requiredRoles?.length && !requiredRoles.includes(admin.role)) {
    throw new HttpException('权限不足', HttpStatus.FORBIDDEN);
}

request.admin = {
    id: admin.id,
    username: admin.username,
    role: admin.role,
    merchantId: admin.merchant_id,
    venueId: admin.venue_id
};
```

角色判断之后还有资源范围判断。`PermissionService.validateVenuePermission` 把三种关系写得很清楚：平台管理员直接通过，商家管理员查询 `merchant_id`，场馆管理员比较自己的 `venueId`。

```typescript
// yuedong_nestjs/src/common/utils/permission.service.ts
async validateVenuePermission(
    adminInfo: AdminInfoInterface,
    venueId: number
): Promise<boolean> {
    if (adminInfo.role === 'platform_admin') {
        return true;
    }

    if (adminInfo.role === 'merchant_admin') {
        const venue = await this.prisma.venue.findFirst({
            where: {
                venue_id: venueId,
                merchant_id: adminInfo.merchantId
            }
        });

        if (!venue) {
            throw new HttpException('无权操作此场馆', HttpStatus.FORBIDDEN);
        }
        return true;
    }

    if (
        adminInfo.role === 'venue_manager' &&
        adminInfo.venueId === venueId
    ) {
        return true;
    }

    throw new HttpException('无操作权限', HttpStatus.FORBIDDEN);
}
```

这三层可以整理成一句话：

| 层次 | 回答的问题 | 代码位置 |
|---|---|---|
| JWT 身份 | 你是谁？ | `AuthGuard` / `AdminGuard` |
| 角色 | 你属于哪类调用者？ | `@Roles`、`admin.role` |
| 数据范围 | 你能操作哪条资源？ | `PermissionService`、service 查询条件 |

## 3. 用“创建场馆”读懂 Controller → Service → Prisma

### Controller 负责接住请求

前面的模块图有了入口，但还没有回答一次请求怎样落库。先看 B 端创建场馆的调用链：

![图：创建场馆从 AdminGuard、VenueCreateDto 到 MerchantVenueService、Prisma transaction 和 Message response 的请求链。](/projects/yuedong-sports/yuedong-04-venue-request-flow.png)

这里的分层不是为了让目录看起来整齐，而是让每个问题有固定的落点：

| 问题 | 主要负责者 |
|---|---|
| 请求是不是管理员？ | `AdminGuard` |
| 角色能不能进入这个 handler？ | `@Roles` |
| body 的字段格式对不对？ | `VenueCreateDto` + `ZodValidationPipe` |
| 商家是否存在、名称是否重复？ | `MerchantVenueService` |
| 场馆和审核记录是否一起写入？ | Prisma transaction |
| 客户端收到什么结构？ | Controller 的 `Message` |

Controller 的主体只做编排：拿到 `adminInfo` 和 DTO，调用 service，把结果放进统一响应。

### DTO 校验与业务校验是两件事

`VenueCreateDto` 不是把 Prisma 的 `venue` model 原样搬到请求里，而是描述“创建场馆这个动作允许携带什么数据”。

```typescript
// yuedong_nestjs/src/business/venue/dto/venue-create.dto.ts
const schema = z
    .object({
        name: z.string().min(2).max(20),
        addr: z.string().min(5).max(50).optional(),
        category: z
            .array(z.nativeEnum(court_category))
            .min(1)
            .refine((arr) => arr.length === new Set(arr).size),
        tel: z.string().regex(/^1[3-9]\d{9}$/).optional(),
        latitude: z.number().min(-90).max(90).optional(),
        longitude: z.number().min(-180).max(180).optional(),
        businessHoursStart: z.string().optional(),
        businessHoursEnd: z.string().optional(),
        merchantId: z.number().positive()
    })
    .refine(
        (data) => {
            if (data.businessHoursStart && !data.businessHoursEnd) return false;
            if (data.businessHoursEnd && !data.businessHoursStart) return false;
            if (data.businessHoursStart && data.businessHoursEnd) {
                const start = data.businessHoursStart.split(':').map(Number);
                const end = data.businessHoursEnd.split(':').map(Number);
                return start[0] * 60 + start[1] < end[0] * 60 + end[1];
            }
            return true;
        },
        { message: '营业时间必须同时提供且结束时间更晚' }
    );
```

可以按“请求进来时能不能判断”来分：

| 校验 | 示例 | 需要访问数据库吗？ |
|---|---|---:|
| 类型和值域 | 名称长度、电话格式、经纬度范围 | 否 |
| 跨字段关系 | 营业开始和结束时间同时出现，且开始更早 | 否 |
| 资源存在 | `merchantId` 对应的商家存在 | 是 |
| 当前业务唯一性 | 同一个商家下场馆名称不能重复 | 是 |
| 事务关系 | 场馆和审核记录作为一次写入 | 是 |

DTO 先把输入形状收窄，service 再用数据库中的事实完成业务判断。

### `createVenue` 是“校验 + 事务 + 审核事实”

`MerchantVenueService.createVenue` 的核心路径可以浓缩为：

```typescript
// yuedong_nestjs/src/business/venue/venue.service.ts
async createVenue(dto: VenueCreateDto, applicantId: number) {
    if (!dto.merchantId) {
        throw new HttpException('商家ID不能为空', HttpStatus.BAD_REQUEST);
    }

    const merchant = await this.prisma.merchant.findUnique({
        where: { id: dto.merchantId }
    });

    if (!merchant) {
        throw new HttpException('商家不存在', HttpStatus.BAD_REQUEST);
    }

    const existingVenue = await this.prisma.venue.findFirst({
        where: {
            name: dto.name,
            merchant_id: dto.merchantId
        }
    });

    if (existingVenue) {
        throw new HttpException('场馆名称已存在', HttpStatus.BAD_REQUEST);
    }

    return this.prisma.$transaction(async (tx) => {
        const venue = await tx.venue.create({
            data: {
                name: dto.name,
                addr: dto.addr || null,
                category: dto.category as any,
                business_hours_start: parseTimeToUtcDate(dto.businessHoursStart),
                business_hours_end: parseTimeToUtcDate(dto.businessHoursEnd),
                status: 'pending',
                merchant_id: dto.merchantId
            }
        });

        await tx.venue_audit.create({
            data: {
                venue_id: venue.venue_id,
                audit_type: 'creation',
                applicant_id: applicantId,
                action: 'pending'
            }
        });

        return this.toVenueResponse(venue);
    });
}
```

这段代码有三个值得记住的工程判断：

1. `merchant` 查询把外键从“一个数字”变成真实归属。
2. 名称查重把用户体验更好的业务错误提前返回。
3. `venue` 和 `venue_audit` 一起进入 transaction，审核链条不会只剩一条孤立的场馆记录。

Controller 最后统一包装成 `Message`：

```typescript
// yuedong_nestjs/src/common/interfaces/message.ts
export default interface Message {
    message: string;
    statusCode: number;
    data?: any;
    error?: string;
}
```

因此，读接口时要把“业务返回对象”和“HTTP 外壳”分开：service 返回场馆业务结果，controller 再决定 `message`、`statusCode`、`data` 或 `error` 怎么交给前端。

### 把创建场馆写成一份接口契约

天机学堂 Day02 先把页面动作拆成接口，再进入数据结构。对悦动的创建场馆任务，也可以先写一份足够让前后端并行的最小契约：

| 项目 | 当前代码中的事实 |
|---|---|
| 请求路径 | `/api/business/venues`；`/api` 来自全局前缀，`/business` 来自路由注册，`venues` 来自 controller |
| 请求方法 | `POST` |
| 请求体 | `name`、`merchantId`、`category`，以及可选地址、电话、经纬度和营业时间 |
| 成功写入 | `venue.status = pending`，同时创建 `venue_audit`，记录 `applicant_id` 和 `action = pending` |
| 失败分支 | 管理员身份或资源范围不通过、商家不存在、名称重复、DTO 格式不合法 |
| 返回外壳 | `Message`，包含 `message`、`statusCode`，成功时附带 `data`，失败时附带 `error` |

请求体可以先用一个最小例子固定双方对字段的理解：

```json
{
  "name": "滨江羽毛球馆",
  "merchantId": 12,
  "category": ["badminton"],
  "addr": "滨江区某路 88 号",
  "businessHoursStart": "09:00",
  "businessHoursEnd": "22:00"
}
```

这份契约还没有替代 DTO 和 service。它的作用是先把“前端提交什么、后端承诺写入什么、失败时用户会看到什么”固定下来，后续读代码时每一行都能回到这张表。

## 4. 资源业务如何从配置落成可运营数据

### 场馆、场地、价格计划和场次是一条协作链

03 解释了 `venue`、`court`、`price_plan_detail`、`session` 分别保存什么；04 换一个视角，看它们由哪些 service 动作串起来：

> 场馆归属 → 创建场地 → 生成价格详情 → 生成未来场次 → C 端查询和预约

创建场地不是单纯的 `court.create`。`CourtService.createCourt` 会先确认场馆存在，再检查类别是否属于场馆支持范围，最后根据容量决定默认价格计划：

```typescript
// yuedong_nestjs/src/business/court/court.service.ts
const venue = await this.prisma.venue.findUnique({
    where: { venue_id: dto.venueId }
});

if (!venue) {
    throw new HttpException('场馆不存在', HttpStatus.NOT_FOUND);
}

const venueCategories = Array.isArray(venue.category)
    ? venue.category
    : typeof venue.category === 'string'
      ? JSON.parse(venue.category)
      : [];

if (!venueCategories.includes(dto.category)) {
    throw new HttpException(
        `场地类别 "${dto.category}" 不属于该场馆的运动类别`,
        HttpStatus.BAD_REQUEST
    );
}

return this.prisma.$transaction(async (tx) => {
    const court = await tx.court.create({
        data: {
            name: dto.name,
            venue_id: dto.venueId,
            category: dto.category,
            status: 'available',
            capacity: dto.capacity ?? null
        }
    });

    if (court.capacity == null) {
        await this.pricePlanService.createDefaultPriceDetails(
            court.court_id,
            tx
        );
    } else {
        await this.pricePlanService.createCapacityDefaultIntervals(
            court.court_id,
            tx
        );
    }

    return court;
});
```

无容量场地更像一个时间段只能被一笔预约占用；有容量场地需要按名额计数。这里先由场地配置决定资源类型，再由价格计划 service 创建不同的默认时段，后续生成服务才有规则可以执行。

### 场地状态变化会向下游 session 传播

运营人员把场地改成维护或关闭时，C 端仍然可能持有已经生成的 session。如果只改 `court.status`，下游场次还可能继续显示为可用。

```typescript
// yuedong_nestjs/src/business/court/court.service.ts
const updatedCourt = await this.prisma.court.update({
    where: { court_id: courtId },
    data: { status: dto.status }
});

if (dto.status !== 'available') {
    await this.prisma.session.updateMany({
        where: {
            court_id: courtId,
            status: 'available',
            capacity_used: 0
        },
        data: { status: 'locked' }
    });
}

return this.mapCourt(updatedCourt);
```

删除场地也有前置条件：只能删除维护中的场地，并且今天及之后不能存在已经使用容量的场次。父资源的管理动作因此会检查下游业务事实。

### 价格计划同步是有保护条件的批处理

`price_plan_detail` 更像规则；`session` 则是绑定某个具体日期、时间和价格的可运营实例。修改规则时，service 要在“配置变化”和“已经暴露给用户的实例”之间做选择。

第一步找受保护日期：

```typescript
// yuedong_nestjs/src/business/price-plan/price-plan.service.ts

    courtId: number,
    startDate: Date,
    endDate: Date,
    tx?: any

    const bookedSessions = await prismaClient.session.findMany({
        where: {
            court_id: courtId,

            session_reg: { some: {} }

        select: { date: true }

        ...new Set(bookedSessions.map((s) => formatDate(s.date)))

```

第二步遍历目标日期，保护日期跳过，其他日期按“已存在则更新，不存在则创建”处理：

```typescript
// yuedong_nestjs/src/business/price-plan/price-plan.service.ts
for (const date of targetDates) {
    const dateStr = formatDate(date);

    if (protectedDates.includes(dateStr)) {
        continue;
    }

    const existingSession = await tx.session.findFirst({
        where: {
            court_id: courtId,
            date,
            start_time: startTime,
            end_time: endTime
        }
    });

        await tx.session.update({
            where: { session_id: existingSession.session_id },
            data: { price, start_time: startTime, end_time: endTime }

    } else {

                venue_id: court.venue_id,

```

这里的关键不是循环语法，而是 `protectedDates` 这个业务判断：有预约记录的日期已经进入交易事实，配置同步要保留它的身份和关联。后续 05 会继续展开这个资源链中的并发、事务和时间问题。

## 5. 活动业务如何把内容、审核和报名串起来

### 创建活动同时处理地点、时间和报名表单

活动创建比普通内容发布多几层业务：时间要合法，地点可以来自场馆或自定义地址，活动还要有容量、价格、报名类型和动态表单。

```typescript
// yuedong_nestjs/src/business/event/event.service.ts
async createEvent(dto: EventCreateDto, organizerId: number) {
    const startTime = this.parseDateTimeInput(dto.startTime, '开始时间');
    const endTime = this.parseDateTimeInput(dto.endTime, '结束时间');

    if (startTime <= new Date()) {
        throw new HttpException('开始时间必须晚于当前时间', HttpStatus.BAD_REQUEST);
    }

    if (endTime <= startTime) {
        throw new HttpException('结束时间必须晚于开始时间', HttpStatus.BAD_REQUEST);
    }

    let venueSnapshot: any = null;
    if (dto.venueId) {
        venueSnapshot = await this.prisma.venue.findUnique({
            where: { venue_id: dto.venueId }
        });

        if (!venueSnapshot) {
            throw new HttpException('场馆不存在', HttpStatus.NOT_FOUND);
        }
    }

    return this.prisma.$transaction(async (tx) => {
        const registrationFields =
            dto.registrationFields || this.generateDefaultRegistrationForm();

        const event = await tx.event.create({
            data: {
                title: dto.title,
                type: dto.type,
                category: dto.category ?? null,
                venue_id: venueSnapshot?.venue_id ?? null,
                addr: dto.address ?? venueSnapshot?.addr ?? null,
                creator_name: dto.creatorName,
                creator_tel: dto.creatorTel,
                creator_wechat: dto.creatorWechat,
                description: dto.description,
                start_time: startTime,
                end_time: endTime,
                capacity: dto.capacity,
                price: dto.price,
                registration_type: dto.registrationType ?? 'online',
                registration_fields: registrationFields as any,
                audit_status: 'pending',
                status: 'pending',
                organizer_id: organizerId
            }
        });

        return event;
    });
}
```

可以把活动创建字段分成四组：

| 字段组 | 例子 | 作用 |
|---|---|---|
| 内容 | `title`、`description`、`type` | 活动页面展示什么 |
| 时间地点 | `start_time`、`end_time`、`venue_id`、`addr` | 活动在哪里、什么时候发生 |
| 交易容量 | `capacity`、`price`、`registration_type` | 怎么报名、是否付费 |
| 生命周期 | `status`、`audit_status`、`organizer_id` | 谁创建、能否发布、是否公开 |

这解释了为什么 `createEvent` 是一个 service 方法：它同时协调输入转换、父资源读取、默认表单和主表写入。

### 发布申请和平台审核是两次动作

活动的 `status` 与 `event_audit` 不是重复字段。前者回答“现在能不能被展示/报名”，后者记录“谁在什么时候提交或处理了什么发布动作”。


### 动态报名表单的灵活性由状态规则收口

`registration_fields` 使用 JSON 后，不同活动可以定义不同字段，但表单公开之后，字段结构还要保持稳定。`EventRegistrationService` 把这条规则放在 service 中：

```typescript
// yuedong_nestjs/src/business/event/event-registration.service.ts
async checkEventCanModifyForm(eventId: number): Promise<void> {
    const event = await this.prisma.event.findUnique({
        where: { event_id: eventId },
        select: { status: true }
    });

    if (!event) {
        throw new HttpException('活动不存在', HttpStatus.NOT_FOUND);
    }

    if (['open', 'ongoing', 'closed'].includes(event.status)) {
        throw new HttpException(
            '活动已发布，不允许修改报名表单',
            HttpStatus.FORBIDDEN
        );
    }
}
```

添加字段时还要读取原表单，检查字段 id 和排序值不能重复，再把完整表单写回：

```typescript
// yuedong_nestjs/src/business/event/event-registration.service.ts
async addRegistrationField(
    eventId: number,
    fieldData: CreateRegistrationFieldDto
) {
    await this.checkEventCanModifyForm(eventId);

    const currentForm = await this.getRegistrationForm(eventId);
    if (!currentForm?.fields) {
        throw new HttpException('活动表单不存在', HttpStatus.NOT_FOUND);
    }

    if (currentForm.fields.some((field) => field.id === fieldData.id)) {
        throw new HttpException('字段ID已存在', HttpStatus.CONFLICT);
    }

    if (currentForm.fields.some((field) => field.order === fieldData.order)) {
        throw new HttpException('字段排序已存在', HttpStatus.CONFLICT);
    }

    const updatedForm = {
        fields: [...currentForm.fields, fieldData]
    };

    this.validateFormData(updatedForm);

    return this.prisma.event.update({
        where: { event_id: eventId },
        data: { registration_fields: updatedForm as any },
        select: {
            event_id: true,
            title: true,
            registration_fields: true
        }
    });
}
```

这里的阅读重点是执行顺序：状态检查 → 读取旧表单 → 字段级检查 → 整体表单检查 → 写回 JSON。灵活字段没有绕过业务规则，只是把结构从固定列变成了 service 维护的配置。

### 会员入场不是一次普通 update

会员入场的业务动作要检查卡片是否存在、是否属于目标场馆、是否过期，以及今天是否已经在这个场馆入场。它最后写入的是 `membership_card_usage` 事实。

```typescript
// yuedong_nestjs/src/business/membership/membership.service.ts

    cardNumber: string,
    venueId: number,
    adminInfo: AdminInfoInterface
) {
    return this.prisma.$transaction(async (tx) => {
        const membershipCard = await tx.membership_card.findUnique({
            where: { card_number: cardNumber },
            include: {
                membership_product: true,
                user: {
                    select: {
                        openid: true,
                        username: true,
                        phone: true
                    }
                }
            }
        });

        if (!membershipCard) {
            throw new HttpException('会员卡不存在', HttpStatus.NOT_FOUND);
        }

        if (membershipCard.membership_product.card_category !== 'entry') {
            throw new HttpException(
                '只有时限卡可以用于扫码入场',

            throw new HttpException(

                HttpStatus.BAD_REQUEST
            );

            throw new HttpException(

                HttpStatus.BAD_REQUEST
            );
        }

                card_id: membershipCard.card_id,
                venue_id: venueId,
                usage_type: 'entry',
                usage_date: todayDate
            }
        });

        if (existingEntry) {
            throw new HttpException(

        }
```

会员卡表表达“用户拥有的权益”，使用表表达“这次权益已经发生了什么”。公共 Prisma transaction 提供写入工具，会员 service 负责入场语义。

### BullMQ、Cron 与消息让后端拥有时间维度

HTTP 请求返回后，后端仍可能有支付后处理、订单过期、退款后处理、场次生成、消息通知和软删除清理。悦动使用 BullMQ 队列和 NestJS schedule 把这些动作从请求线程中拆出来。

![图：同步 HTTP 请求、BullMQ 队列/processor 与 Cron 后台任务的分工。](/projects/yuedong-sports/yuedong-04-async-tasks.png)

队列服务建立三条队列，并用固定 jobId 组织任务：

```typescript
// yuedong_nestjs/src/common/order-queue/order-queue.service.ts
constructor(private readonly configService: ConfigService) {
    const connection = {
        host: this.configService.get('REDIS_HOST', '127.0.0.1'),
        port: Number(this.configService.get('REDIS_PORT', 6379)),
        password: this.configService.get('REDIS_PASSWORD') || undefined,
        db: Number(this.configService.get('REDIS_DB', 0))
    };

    this.paymentQueue = new Queue('order-payment', { connection });
    this.expireQueue = new Queue('order-expire', { connection });
    this.refundQueue = new Queue('order-refund', { connection });
}

async addOrderExpireJob(orderId: string, expireAt: Date) {
    const delay = Math.max(0, expireAt.getTime() - Date.now());

    await this.add(
        this.expireQueue,
        'order.expire',
        { orderId },
        { delay, jobId: `order:${orderId}:expire` }
    );
}

private async add(queue: Queue, name: string, data: any, opts = {}) {
    await queue.add(name, data, {
        attempts: 5,
        backoff: { type: 'exponential', delay: 1000 },
        removeOnComplete: 1000,
        removeOnFail: false,
        ...opts
    });
}
```

队列适合“以后处理”的事件，Cron 适合“按时间周期扫描”的动作。比如场馆清理任务每天凌晨 2 点执行：

### 本篇验证清单

在进入面试复盘前，可以按下面的顺序检查这条请求链。这里记录的是验收动作，不把源码中没有运行过的结果写成已经通过：

| 验收场景 | 输入或操作 | 应观察的结果 |
|---|---|---|
| 未登录或无管理员身份 | 不携带有效管理员上下文访问创建接口 | 请求在 guard 层结束，不进入 service |
| 商家不存在 | `merchantId` 指向不存在的商家 | service 返回业务错误，不产生场馆记录 |
| 名称重复 | 同一商家再次提交相同 `name` | 查重分支结束，不新增第二个场馆 |
| 创建成功 | 提交合法表单 | `venue` 与 `venue_audit` 一起出现，场馆状态为 `pending` |
| 事务异常 | 在两次写入之间制造数据库异常 | 两张表都不留下半条创建结果 |

验收时要同时看 HTTP 响应和数据库事实：响应说明客户端得到了什么，数据库记录说明业务是否真的完成。两者不能互相替代。

## 7. 面试复盘

### 1. 为什么 `main.ts` 不是业务逻辑的起点？

**回答：** `main.ts` 负责创建 NestJS 应用、配置 CORS、设置 `/api` 前缀和监听端口；业务逻辑从 controller 和 service 开始。先看启动入口，可以确定后续接口的网络外壳。

**依据：** `NestFactory.create(AppModule)`、`app.setGlobalPrefix('api')`、`app.listen(...)`。

### 2. `imports`、`providers`、`controllers`、`exports` 分别做什么？

**回答：** `imports` 引入依赖模块，`controllers` 接收请求，`providers` 提供可注入的 service/工具，`exports` 把 provider 暴露给导入方。它们共同描述一个模块的依赖边界。

**依据：** `AppModule`、`PrismaModule`、`OrderModule` 的 `@Module` 配置。

### 3. 为什么说 `consumer` 和 `business` 不是两个微服务？

**回答：** 它们是同一个 NestJS 应用中的两类业务目录和路由入口，都由 `AppModule` 组装；目录分工不自动等于独立进程或独立部署。

**依据：** `AppModule` 同时 imports C 端模块与 `BusinessModule`，`BusinessModule` 再注册多组 B 端模块。

### 4. `/api/business/venues` 是怎样拼出来的？

**回答：** `/api` 来自 `main.ts` 的全局前缀，`/business` 来自 `RouterModule.register`，`/venues` 来自 `@Controller('venues')`。方法上的 `@Get`、`@Post` 还会继续追加局部路径。

**依据：** `main.ts`、`business.module.ts`、`business/venue/venue.controller.ts`。

### 5. `AuthGuard` 和 `AdminGuard` 有什么区别？

**回答：** `AuthGuard` 面向用户身份，解析 JWT 中的 `openid` 并写入 request；`AdminGuard` 面向管理员身份，解析 `username`、查询管理员状态和角色，并写入 `request.admin`。

**依据：** `auth.guard.ts` 的 `openid` 查询与 `admin.guard.ts` 的管理员查询。

### 6. `@Roles` 能不能单独完成场馆数据范围权限？

**回答：** 不能。`@Roles` 只判断角色是否允许进入 handler；商家管理员能操作哪些场馆，还要由 `PermissionService` 查询 `merchant_id`，场馆管理员还要匹配 `venueId`。

**依据：** `Roles` decorator、`AdminGuard` 的角色检查、`validateVenuePermission`。

### 7. Controller 为什么不直接写 Prisma 查询？

**回答：** Controller 更适合负责路由、参数、guard、DTO 和响应包装；Service 负责商家存在、名称查重、事务和业务错误。这样同一规则可以被其他入口复用，测试也更容易按职责组织。

**依据：** `MerchantVenueController.createVenue` 调用 `MerchantVenueService.createVenue`。

### 8. DTO 校验和 Service 业务校验有什么区别？

**回答：** DTO 校验处理字段类型、长度、格式和跨字段输入关系；Service 校验需要访问数据库的事实，例如商家是否存在、名称是否重复、场馆是否属于管理员范围。

**依据：** `VenueCreateDto` 的 Zod schema 与 `createVenue` 的 merchant/venue 查询。

### 9. 创建场馆为什么要同时写 `venue` 和 `venue_audit`？

**回答：** `venue` 保存场馆实体，`venue_audit` 保存创建申请和申请人。场馆初始为 `pending`，后续审核需要这条动作记录，因此两者放入同一个 transaction。

**依据：** `tx.venue.create` 与 `tx.venue_audit.create`。

### 10. 创建场地时为什么会生成默认价格计划？

**回答：** `court` 只描述具体场地，价格计划描述可重复使用的星期/时间段规则。创建场地后生成默认规则，未来的场次生成服务才有输入；容量场地和独占场地还会走不同默认时段。

**依据：** `CourtService.createCourt` 根据 `court.capacity` 调用两个价格计划方法。

### 11. 修改场地状态为什么还要更新 session？

**回答：** C 端真正查询和预约的是 `session`。场地进入非 `available` 状态时，把可用且尚未使用容量的 session 锁定，才能让父资源状态传递到下游交易对象。

**依据：** `updateCourtStatus` 中的 `session.updateMany`。

### 12. 价格计划同步为什么要保护已有预约日期？

**回答：** 已有预约的 session 已经进入业务事实，直接删除重建会改变 session 身份并影响关联订单。同步服务先查询 `session_reg`，保护这些日期，再处理其他日期的更新或创建。

**依据：** `getProtectedDates` 与 `syncSessionsFromPricePlan`。

### 13. `event.status` 和 `event_audit` 为什么要分开？

**回答：** `event.status` 表示活动现在是否 pending、open、ongoing 或 closed；`event_audit` 记录发布申请、审核者、动作和原因。一个表示状态，一个保存状态变化的业务过程。

**依据：** `publishEvent` 创建审核申请，`auditEvent` 在 transaction 中更新状态和审核记录。

### 14. 为什么活动发布申请和平台审核是两个动作？

**回答：** 组织者点击发布表达“请求公开”，平台管理员审核表达“平台做决定”。分开后才能记录申请者、审核者和处理原因，也能让平台管理员直接发布、组织者走待审核路径。

**依据：** `publishEvent` 的角色分支与 `auditEvent` 的平台管理员检查。

### 15. `registration_fields` 使用 JSON 后，为什么还要限制修改时机？

**回答：** JSON 提供了活动表单的灵活结构，但活动公开后，参与者看到的字段需要保持稳定。service 先检查活动状态，再检查字段 id/order 和整体表单，最后写回 JSON。

**依据：** `EventRegistrationService.checkEventCanModifyForm` 与 `addRegistrationField`。

### 16. 公共 `OrderService` 和领域 service 如何分工？

**回答：** `OrderService` 负责多个业务都需要的订单查询、状态处理和公共交易流程；场次、活动、会员 service 负责自己的资格判断、资源关系和领域事实。公共层提供骨架，领域层保留语义。

**依据：** `OrderModule` 导出 `OrderService`/`OrderItemService`，各业务模块通过 imports 注入公共能力。

### 17. 会员入场为什么需要 `membership_card_usage`？

**回答：** `membership_card` 表示用户拥有的权益，`membership_card_usage` 记录某次入场事实。入场要检查状态、场馆范围和当天重复，再写 usage，不能只修改卡片主表。

**依据：** `MembershipService.entryWithMembershipCard` 的 transaction 与 `membership_card_usage.create`。

### 18. 为什么订单要拆成 `order_item` 与业务明细？

**回答：** `order_item` 提供统一的金额、数量和订单关联；`venue_order_item`、`event_order_item` 等明细保存各自的 session、活动或参与人数。这样订单列表统一，业务查询仍保留专属字段和快照。

**依据：** `OrderItemService.createVenueItems` 与 `createEventItem`。

### 19. BullMQ 和 Cron 分别适合解决什么问题？

**回答：** BullMQ 适合把一次业务产生的后续动作放入队列，例如支付成功、订单过期和退款成功；Cron 适合按固定时间扫描或生成，例如软删除清理和场次生成。

**依据：** `OrderQueueService` 的三条队列、`VenueCleanupTask` 的 `@Cron`、`SessionGenerateService` 的启动与定时入口。

### 20. 如果面试官问“你如何证明这套后端设计可靠”，应该怎样回答？

**回答：** 先说明模块和请求链，再指出角色/数据范围、DTO、service 条件和 transaction 的具体位置；然后按业务列出状态转换、重复操作、并发、支付、退款、时间和后台任务的测试用例。代码结构说明设计意图，测试和运行结果回答行为是否符合预期。

**依据：** 04 的模块/业务代码，以及 `event-visibility.spec.ts`、`event-delete.spec.ts`、`order-event-filter.spec.ts` 等 focused spec；05 继续补充并发、支付、退款和时间专题。
