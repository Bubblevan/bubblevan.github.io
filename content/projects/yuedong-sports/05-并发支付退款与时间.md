# 悦动体育 05：并发、支付、退款与时间——把业务事实做成可重试的流程

04 解释了悦动后端怎样启动、怎样组装模块，以及 Controller、Service 和 Prisma 怎样把一次业务动作落进数据库。05 接着追问一个更容易在真实系统里出问题的问题：当两个用户同时预约、微信支付通知重复到达、退款要恢复多个资源、后台任务执行失败，系统怎样保持状态可解释？

这篇的切入口来自 Day06 对点赞系统的分析。那份小册子把一个看似简单的功能拆成通用、独立、并发和安全几个要求。把这个分析方法放回悦动，业务对象不再是点赞，而是场次、活动名额、会员卡次数、支付单和退款单。技术名词也不再是散落的“Redis、事务、MQ”，而是一组各守一层的控制点：

![悦动体育 05：四类不可靠问题](/projects/yuedong-sports/yuedong-05-concurrency-map.png)

| 问题 | 悦动里的例子 | 主要控制点 |
|---|---|---|
| 资源竞争 | 两个人抢同一个普通场次，或同时消耗最后一个容量 | Redis 锁、条件更新 |
| 重复事件 | 微信重复发送支付/退款通知，队列任务被重复投递 | 状态短路、唯一标识、幂等处理 |
| 跨系统延迟 | 微信已经成功，本地报名和容量处理还没完成 | 结构化订单、BullMQ、补偿扫描 |
| 时间边界 | 订单过期、场次业务日期、支付时间跨越时区 | 字段语义、UTC 工具、契约测试 |

读完之后，我希望自己能用一条完整链路回答：资源在哪里被占用，数据库在哪里做最后裁决，支付成功记录在哪里，异步任务失败后谁来接手，退款怎样把资源归还，以及“某一天”和“某一个瞬间”怎样避免混在一起。

> **本篇任务卡**
>
> 把一笔场馆预约当成一条会被打断、重复和延迟的业务链。先解决容量为 1 时的竞争，再把同一套“事实、状态、重试”语言迁移到微信支付、退款和时间处理。完成标准不是列出 Redis、事务和 BullMQ，而是能指出每个组件保护的对象、失败后留下的记录，以及下一次重试怎样知道自己该跳过什么。
>
> - 资源竞争：两个请求不能同时占用最后一个名额；
> - 重复事件：同一个支付或退款通知只能推进一次本地事实；
> - 异步失败：队列任务失败后仍有稳定 ID、重试和扫描入口；
> - 时间边界：业务日期、时段和支付瞬时不会被同一种解析方式混淆。

## 1. 先把四类“不可靠”分开

### 两个用户同时抢最后一个名额

假设一个活动场次容量是 1，数据库初始值如下：

~~~text
capacity_total = 1
capacity_used  = 0
~~~

最直观的实现是先查询，再在 TypeScript 中加一，最后写回数据库：

~~~typescript
const session = await prisma.session.findUnique({
    where: { session_id: sessionId }
});

if (session.capacity_used >= session.capacity_total) {
    throw new BadRequestException('容量已满');
}

const nextUsed = session.capacity_used + 1;
await prisma.session.update({
    where: { session_id: sessionId },
    data: { capacity_used: nextUsed }
});
~~~

问题在于，findUnique 和 update 之间不是一个不可分割的动作。A 请求读到 0，B 请求也读到 0；A 写入 1，B 随后也写入 1。最终数据库看起来只用了 1 个名额，但实际上已经答应了两个用户。

这类 bug 不是“代码跑错了”，而是代码对并发时序做了错误假设。只要请求可以同时执行，就不能把“我刚刚查到的值”当作写入时仍然成立的事实。

### 先把竞态写成可回放的失败现场

为了让“两个用户抢最后一个名额”不只停留在概念上，可以把它记录成一组最小回放：

| 时刻 | 请求 A | 请求 B | 数据库中的 `capacity_used` |
|---|---|---|---:|
| t0 | 读取容量 | 读取容量 | 0 |
| t1 | 得到 `0 < 1` | 得到 `0 < 1` | 0 |
| t2 | 写入 `1` | 尚未写入 | 1 |
| t3 | 已经返回成功 | 也写入 `1` | 1，但两个请求都认为自己成功 |

这张表揭示了错误结果：数据库里的数字没有变成 2，所以只看最终值会误以为系统安全；真正丢失的是第二个请求本应收到的“竞争失败”。验收时至少要记录请求数量、成功数量和最终资源状态，而不能只检查 SQL 是否执行完成。

修复后的回放应该满足：Redis 锁让同一资源尽量串行进入临界区，条件更新让数据库重新判断当前值，受影响行数为 0 的请求进入失败或重试分支。锁和 SQL 不是重复保险，而是分别负责访问顺序与最终裁决。

### 并发、幂等、事务和队列不是同一个词

在阅读悦动代码时，我会先问四个问题：

| 先问什么 | 它在防什么 | 例子 | 更合适的手段 |
|---|---|---|---|
| 谁在同时改同一资源？ | 资源竞争 | 两个请求抢 session 7 | Redis 锁、数据库条件更新 |
| 同一件事会不会再来一次？ | 重复处理 | 同一支付回调再次到达 | 状态短路、稳定业务 ID |
| 哪些本地写入必须一起成功？ | 部分提交 | 订单写了但报名没写 | Prisma transaction |
| 谁来处理延迟或失败？ | 跨系统不确定性 | 支付已成功但后续业务失败 | BullMQ、Cron、补偿逻辑 |

所以，Redis 锁不是事务，事务也不是幂等；队列可以重试，也不能自动让业务代码变得幂等。它们解决的是不同时间窗口中的不同问题。

### Day06 的设计原则如何换成悦动语言

Day06 讨论点赞系统时，强调功能要通用、独立，还要考虑热点并发和重复点赞。在悦动中，可以这样迁移这种分析方式：

| Day06 的观察角度 | 悦动里的对应物 | 代码上的落点 |
|---|---|---|
| 通用 | 不同入口都能调用同一套订单、库存和退款能力 | OrderService、BookingInventoryService |
| 独立 | 渠道支付事实与业务订单事实分开 | payment_order、payment_allocation、refund_order |
| 并发 | 场次和活动名额不能被超卖 | Redis 锁、条件 UPDATE |
| 安全 | 回调必须验签，业务动作必须校验状态和身份 | wxpay/notify、订单状态机、Guard |
| 可追溯 | 不能只留下一个变化后的数字 | 订单、报名、使用记录、资金流水、原始通知 |

点赞系统可以记录一条点赞事实，再异步通知业务方；悦动也需要先记录“支付成功”或“退款渠道成功”这类外部事实，再让本地业务补齐报名、库存和资金流。共享的是设计方法，不是业务表结构。

## 2. Redis 锁、条件更新与事务各守哪一层

![悦动体育 05：预约并发保护](/projects/yuedong-sports/yuedong-05-booking-concurrency.png)

### Redis 锁的最小正确形态

悦动把 Redis 锁封装在 RedisLockService 中。加锁使用 Redis 的 SET 命令，并同时传入 NX 和 EX：

~~~typescript
async tryLock(key: string, value: string, ttlSeconds: number): Promise<boolean> {
    const result = await this.redisService
        .getClient()
        .set(key, value, 'EX', ttlSeconds, 'NX');

    return result === 'OK';
}
~~~

三个关键参数可以翻译成普通话：

| 参数 | 含义 | 没有它会怎样 |
|---|---|---|
| NX | 只有 key 不存在时才写入 | 多个请求都可能认为自己拿到了锁 |
| EX | 给锁设置过期秒数 | 进程崩溃后锁可能一直不释放 |
| value | 本次持有者的随机身份 | 释放时无法判断是不是自己的锁 |

释放锁不能直接 DEL。A 拿到锁后执行很慢，锁过期；B 随后拿到同一个 key。此时 A 的 finally 如果无条件删除，删除的就是 B 的锁。项目使用 Lua 脚本把“比较 value”和“删除 key”放在同一个 Redis 原子动作中：

~~~typescript
async unlock(key: string, value: string): Promise<boolean> {
    const script = [
        'if redis.call("get", KEYS[1]) == ARGV[1] then',
        '    return redis.call("del", KEYS[1])',
        'end',
        'return 0'
    ].join('\n');

    const result = await this.redisService
        .getClient()
        .eval(script, 1, key, value);

    return result === 1;
}
~~~

这个锁解决的是“同一时刻哪些应用请求可以进入临界区”，它不等于数据库已经成功写入，也不等于外部支付已经成功。

### 多场次预约先去重，再按固定顺序加锁

一次预约可能包含多个 session。如果请求 A 按 [7, 9] 加锁，请求 B 按 [9, 7] 加锁，两个请求都可能先拿到第一把锁，然后互相等待第二把锁。withSessionLocks 先去重和排序，再生成稳定的 key：

~~~typescript
async withSessionLocks<T>(
    sessionIds: number[],
    callback: () => Promise<T>
): Promise<T> {
    const locked = await this.lockMany(
        Array.from(new Set(sessionIds))
            .sort((a, b) => a - b)
            .map((id) => 'booking:session:' + id)
    );

    try {
        return await callback();
    } finally {
        await this.releaseMany(locked);
    }
}
~~~

这里每一步都有实际作用：

- Set 避免同一个订单重复申请同一把锁。
- 数字排序让涉及多个资源的请求采用同一锁顺序。
- booking:session:<id> 让不同业务入口指向同一个资源锁。
- finally 保证成功和异常路径都会尝试释放已经拿到的锁。

如果中途拿不到锁，lockMany 会释放前面已经拿到的锁，再返回冲突：

~~~typescript
private async lockMany(keys: string[]): Promise<LockedResource[]> {
    const locked: LockedResource[] = [];

    for (const key of keys) {
        const value = uuidv4();
        const ok = await this.redisLockService.tryLock(
            key,
            value,
            this.lockTtlSeconds
        );

        if (!ok) {
            await this.releaseMany(locked);
            throw new HttpException('资源繁忙，请稍后重试', HttpStatus.CONFLICT);
        }

        locked.push({ key, value });
    }

    return locked;
}
~~~

排序不是为了让数据库更快，而是为了减少“多把锁申请顺序不一致”带来的互相等待。

### 容量场次让数据库直接做加法和判断

活动容量的实现把判断和累加放进同一条 SQL。为了突出并发原理，下面把 Prisma 的 tagged SQL 写成参数化 SQL 伪代码：

~~~typescript
const updateResult = await tx.executeRaw({
    sql: [
        'UPDATE event',
        'SET capacity_used = capacity_used + ?',
        'WHERE event_id = ?',
        'AND status = open',
        'AND is_hidden = false',
        'AND is_deleted = false',
        'AND capacity_used + ? <= capacity'
    ].join(' '),
    params: [quantity, eventId, quantity]
});

if (updateResult === 0) {
    throw new HttpException('活动名额不足或不可报名', HttpStatus.BAD_REQUEST);
}
~~~

真实项目使用的是 Prisma 的原始 SQL tagged API；关键不是 API 形式，而是 WHERE 中包含了业务条件。数据库执行这条更新时，会基于当前行判断 capacity_used + quantity <= capacity 是否成立。受影响行数是 0，就不能继续当作报名成功。

场次容量使用同一思想：

~~~typescript
const updateResult = await tx.executeRaw({
    sql: [
        'UPDATE session',
        'SET capacity_used = capacity_used + 1',
        'WHERE session_id = ?',
        'AND status = available',
        'AND capacity_total IS NOT NULL',
        'AND capacity_used < capacity_total'
    ].join(' '),
    params: [sessionId]
});

if (updateResult === 0) {
    const latest = await tx.session.findUnique({
        where: { session_id: sessionId },
        select: {
            status: true,
            capacity_total: true,
            capacity_used: true
        }
    });

    if (latest?.status !== 'available') {
        throw new BadRequestException('场次已被其他用户预订，请刷新后重试');
    }

    throw new BadRequestException('场次容量已满，请刷新后重试');
}
~~~

这比“查出旧值，在应用层加一，再写回”更适合做并发裁决。应用层查询仍然有用，但它的职责变成解释失败原因和返回用户提示，而不是决定库存是否可以增加。

### 普通场次通过状态条件完成抢占

普通场次没有容量计数器，竞争的是 available → reserved 这次状态推进。项目使用带条件的 updateMany：

~~~typescript
const result = await tx.session.updateMany({
    where: {
        session_id: sessionId,
        status: 'available',
        capacity_total: null
    },
    data: {
        status: 'reserved'
    }
});

if (result.count === 0) {
    throw new BadRequestException('场次已被其他用户预订，请刷新后重试');
}
~~~

两个请求同时执行时，只有第一个仍然满足 status = available 的更新会影响 1 行；另一个更新得到 0 行。这里可以记住一个实用判断：

| 写法 | 查询与写入的关系 | 并发时的可信度 |
|---|---|---|
| findUnique 后 update | 两个独立动作 | 旧读可能覆盖新事实 |
| updateMany(where 条件) | 条件和写入在一次数据库操作中判断 | 用 count 判断谁成功 |
| 原子 UPDATE ... SET used = used + 1 | 数据库在当前值上直接计算 | 适合计数器与容量 |

### 事务把一次预约的本地事实绑在一起

库存保护还不完整。一次预约通常至少要形成这些事实：订单、场次报名记录、订单明细；会员卡预约还要有会员卡使用记录。它们不能出现“库存已占用，但找不到订单”的半成品。

可以把预约事务理解成一张本地事实清单：

~~~typescript
return this.prisma.$transaction(async (tx) => {
    const order = await tx.order.create({
        data: buildPendingOrder(input)
    });

    await tx.session_reg.createMany({
        data: sessionIds.map((sessionId) => ({
            session_id: sessionId,
            user_id: openid,
            order_id: order.order_id
        }))
    });

    await this.orderItemService.createVenueItems(tx, order.order_id, sessions);

    await this.reserveSessionInventory(tx, sessions);

    return order;
});
~~~

这里的 tx 是同一事务上下文。库存更新成功但后续明细写入失败时，前面的本地写入会回滚；后续退款也能根据 order_id 找到完整的关联关系。

事务解决的是 MySQL 内部多表提交，不会把 Redis 或微信支付变成同一个事务。比如不能因为微信调用失败，就指望 MySQL 自动撤销一个已经发出的网络请求；外部系统要通过状态、查询和补偿来处理。

### 这一层的复盘：锁是协调，数据库是裁判

悦动目前的思路已经形成了正确的分层：Redis 锁减少同一资源的同时进入，数据库条件更新守住最后一道库存底线，Prisma transaction 绑定多个本地事实。但阅读到支付成功和退款容量处理时，还能看到“先查询当前值，再在 TypeScript 中计算，再 update”的路径：

~~~typescript
const current = await prisma.session.findUnique({
    where: { session_id: sessionId },
    select: { capacity_used: true }
});

const next = (current?.capacity_used || 0) + 1;

await prisma.session.update({
    where: { session_id: sessionId },
    data: { capacity_used: next }
});
~~~

它在单次执行时容易理解，但如果同一订单的支付成功任务被两个 worker 同时处理，就会重新暴露读写窗口。更稳妥的改造方向是：对同一 session 复用资源锁，并把增量或减量改为带条件的 SQL；用受影响行数判断本次补偿是否真正发生；再用订单状态或处理记录避免同一订单重复进入补偿。

## 3. 支付回调怎样做到“收到多次也只确认一次”

### 先从 C 端 UniApp 的支付流程开始

如果只从后端的 notify 接口开始读，容易把支付理解成“微信通知后端，后端改订单”。但在悦动里，用户首先经历的是一条跨 C 端、NestJS 和微信客户端的链路：

![悦动体育 05：小程序支付流程](/projects/yuedong-sports/yuedong-05-miniprogram-payment-flow.png)

| 步骤 | 发生在哪里 | 悦动里的动作 | 结果 |
|---|---|---|---|
| 1. 预约 | C 端 + NestJS | ConfirmVenue 根据场次类型调用普通或容量预约接口 | 创建/占用一个待支付订单，拿到业务 orderId |
| 2. 创建支付单 | C 端 → NestJS | createWxPayOrder 调用 /payment/wxpay/create | 后端生成微信订单号，建立 payment_order 和 allocation |
| 3. 统一下单 | NestJS → 微信支付 | 后端调用小程序/JSAPI 下单接口 | 获得 prepay_id，再生成小程序调起参数 |
| 4. 调起收银台 | C 端 UniApp | uni.requestPayment 传入 timeStamp、nonceStr、package、signType、paySign | 用户在微信收银台支付或取消 |
| 5. 返回页面 | C 端 + NestJS | PaymentResult 查询支付状态；后端同时接收微信异步通知 | 页面展示结果，后端确认并补齐业务事实 |

微信官方对小程序支付的描述也是这个顺序：商户后端先调用小程序下单接口获得 prepay_id，小程序再通过 requestPayment 调起收银台；用户完成或取消支付后回到小程序，商户前端收到 requestPayment 回调，同时后端还会收到微信支付成功通知。可以参考[微信支付小程序支付开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791911)和[小程序下单接口说明](https://pay.wechatpay.cn/doc/v3/merchant/4012525182)。

### C 端先预约，再请求后端准备支付参数

以场馆预约为例，ConfirmVenue 会先根据场次是否有容量选择预约接口：

~~~typescript
const attemptStandardReserve = async () => {
    return post(CONFIG.API.ENDPOINTS.SESSIONS_RESERVE, {
        sessionId: [sessionIdInt]
    }, {
        showLoading: false,
        showError: true,
        needAuth: true
    });
};

const attemptCapacityReserve = async () => {
    return post('/sessions/reserve-capacity/' + sessionIdInt, {}, {
        showLoading: false,
        showError: true,
        needAuth: true
    });
};
~~~

预约接口成功后，前端拿到业务 orderId 和后端计算出的 totalPrice。会员卡抵扣或免费活动可能在这里直接结束；需要微信支付的订单才继续调用 createWxPayOrder：

~~~typescript
const orderPayloadForPayment = {
    orderId,
    venueId: venueId.value,
    sessionIds: [sessionIdInt],
    totalAmount: Number(backendTotalPrice),
    venueName: venueData.value.name || '场馆预订',
    bookingDate: sessionDisplay.bookingDate,
    bookingTime: sessionDisplay.bookingTime,
    trade_type: 'JSAPI'
};

const payOrderResult = await createWxPayOrder(orderPayloadForPayment);
~~~

这里的 orderId 是悦动自己的业务订单 ID，不一定就是微信侧的 out_trade_no。后端会生成符合微信规则的 wxOrderId，并把它保存到订单 metadata、wx_order_id 以及结构化支付单中，后面支付回调和退款匹配都要靠这层映射。

### 后端统一下单，返回的是“调起支付所需参数”

paymentService.js 的 createWxPayOrder 向 /payment/wxpay/create 发送金额为元的 totalAmount，并要求后端处理单位转换。NestJS 的 createVenueOrder 会更新或创建 pending 订单，建立 payment_order 和 payment_allocation，然后调用微信支付统一下单：

~~~typescript
const params = {
    appid: this.appId,
    mchid: this.mchId,
    description: orderData.eventId
        ? '活动报名-' + orderData.eventId
        : (orderData.venueName || '场馆预订') + '-' +
          (orderData.bookingDate || ''),
    out_trade_no: wxOrderId,
    notify_url: this.notifyUrl,
    amount: {
        total: Math.floor(orderData.totalAmount * 100),
        currency: 'CNY'
    },
    payer: {
        openid
    },
    time_expire: this.getExpireTime(15)
};

const response = await this.httpService.post(
    'https://api.mch.weixin.qq.com/v3/pay/transactions/jsapi',
    params,
    { headers: this.buildWechatPayHeaders() }
);
~~~

微信返回 prepay_id 后，后端用商户私钥生成小程序调起支付签名，再返回以下五个字段：

~~~typescript
const prepayId = response.data.prepay_id;
const paySign = this.generatePaySign(prepayId, timestamp, nonceStr);

return {
    orderId: orderData.orderId,
    wxOrderId,
    timeStamp: timestamp,
    nonceStr,
    package: 'prepay_id=' + prepayId,
    signType: 'RSA',
    paySign
};
~~~

这五个字段不是让前端自己计算的订单数据，而是后端根据 prepay_id、商户配置和签名规则准备好的调起参数。前端不应该拿着 APIv3 密钥或商户私钥去签名。

### UniApp 调起微信收银台

前端把后端返回的字段原样交给 paymentService.js：

~~~typescript
const wxPayParams = {
    timeStamp: payOrderResult.timeStamp,
    nonceStr: payOrderResult.nonceStr,
    package: payOrderResult.package,
    signType: payOrderResult.signType,
    paySign: payOrderResult.paySign
};

await requestWxPayment(wxPayParams);
~~~

requestWxPayment 内部调用 UniApp 的小程序支付能力：

~~~typescript
export const requestWxPayment = async (payParams) => {
    return new Promise((resolve, reject) => {
        uni.requestPayment({
            provider: 'wxpay',
            timeStamp: payParams.timeStamp,
            nonceStr: payParams.nonceStr,
            package: payParams.package,
            signType: payParams.signType,
            paySign: payParams.paySign,
            success: resolve,
            fail: reject
        });
    });
};
~~~

用户取消支付时，Promise reject，ConfirmVenue 会延迟显示“取消订单/继续支付”；用户完成收银台操作后，前端保存一个 wxPaySuccess 标记，清空待支付页面状态，再跳到 PaymentResult。这个标记只能帮助页面处理“刚刚从微信返回”的体验，不能作为后端把订单改成 paid 的依据。

### 页面回调、后端查单和微信异步通知是三件事

这里最容易出现一个误解：requestPayment 的 success 回调不等于悦动后端已经完成支付业务。官方文档要求商户在用户回到小程序后调用查询订单接口确认状态；如果支付成功，微信支付系统还会向商户发送支付成功通知。小程序的调用结果、后端查单结果和微信异步通知可能存在时间差。

悦动的 PaymentResult 会根据 paymentOrderId 或 orderId 调用 queryWxPayOrder：

~~~typescript
const result = await queryWxPayOrder(orderId.value);

if (result && (
    result.status === 'paid' ||
    result.status === 'SUCCESS' ||
    result.status === 'success'
)) {
    paymentStatus.value = 'success';
} else {
    paymentStatus.value = 'fail';
}
~~~

实际阅读时要把三条状态线分开：

| 状态来源 | 能说明什么 | 不能单独说明什么 |
|---|---|---|
| requestPayment success | 收银台交互返回成功 | 后端订单、支付单和报名事实已完成 |
| /payment/wxpay/query 查单 | 后端查询到的当前订单状态 | 未来不会再收到重复通知 |
| 微信支付异步通知 | 渠道向商户确认的支付结果 | 本地异步业务补齐已经完成 |

官方还规定，prepay_id 是调起支付时使用的预支付交易会话标识，有效期为 2 小时；悦动下单参数里的 time_expire 则把业务订单的支付结束时间设为 15 分钟。两者不是同一个倒计时：prepay_id 失效后要重新下单获取新的 prepay_id，订单超过业务支付截止时间则应关单或重新创建订单。详细状态流转可参考[微信支付普通支付订单状态说明](https://pay.wechatpay.cn/doc/v3/merchant/4012791911)。

### 微信异步通知进入真正的幂等处理

用户回到小程序后，前端可以查单并展示“支付成功”或“支付查询中”；真正驱动服务端业务事实的入口仍然是 /api/payment/wxpay/notify。微信支付 V3 通知包含签名和加密 resource，服务端需要验证签名，再使用 APIv3 密钥、nonce、associated_data 和 ciphertext 解密业务内容。

官方通知文档还强调：通知可能重复，商户必须正确处理重复通知；成功接收后返回 HTTP 200 或 204，异常时返回错误状态码。悦动的 notify 服务当前会在验签解密后区分支付通知和退款通知，再进入 PaymentOrderService 或 RefundOrderService。接下来的“支付单、分摊单和业务订单各记录一层事实”就是从这条后端通知链继续往下读。

### 回调入口先验签、解密，再区分支付和退款

微信通知入口是：

~~~typescript
// yuedong_nestjs/src/payment/wxpay.controller.ts
@Post('notify')
async paymentNotify(@Body() notifyData: any): Promise<any> {
    return await this.wxpayService.handlePaymentNotify(notifyData);
}
~~~

handlePaymentNotify 进入业务处理前，先验证通知签名，再解密 resource.ciphertext。解密后的数据可能是支付成功，也可能是退款成功、退款关闭或退款异常，因此不能看到一个订单号就直接写 paid：

~~~typescript
if (!this.verifyNotifySign(notifyData)) {
    return { code: 'FAIL', message: '签名验证失败' };
}

const decryptedData = this.decryptNotifyResource(notifyData.resource);
const parsedData = JSON.parse(decryptedData);

const isRefundNotify =
    parsedData.event_type === 'REFUND.SUCCESS' ||
    parsedData.event_type === 'REFUND.ABNORMAL' ||
    parsedData.event_type === 'REFUND.CLOSED' ||
    parsedData.out_refund_no ||
    parsedData.refund_id;

if (isRefundNotify) {
    return this.handleRefundNotify(parsedData);
}

return this.handlePayNotify(parsedData);
~~~

这一步建立的是“外部事件可信且类型明确”的边界。支付成功和退款成功虽然都来自微信，但它们推动的是两条相反的状态流。

### 支付单、分摊单和业务订单各记录一层事实

悦动的结构化支付服务把一次渠道支付拆成三层：

| 对象 | 记录什么 | 为什么独立 |
|---|---|---|
| payment_order | 微信渠道看到的一次支付、out_trade_no、金额、付款人、支付状态 | 一次批量支付只有一个渠道支付号 |
| payment_allocation | 这笔支付分摊给哪些业务订单、各自金额和状态 | 一个支付可能对应多个订单 |
| order | 场馆预约、活动报名、会员购买等业务状态 | 业务订单有自己的生命周期 |

创建支付单时，服务会按 outTradeNo 查找已有记录；不存在才创建新的 payment_order，然后逐条维护 allocation：

~~~typescript
const existingPayment = await this.prisma.payment_order.findUnique({
    where: { out_trade_no: params.outTradeNo }
});

const payment = existingPayment
    ? await this.prisma.payment_order.update({
          where: { out_trade_no: params.outTradeNo },
          data: {
              total_amount: params.totalAmount,
              payer_id: params.payerId,
              status:
                  existingPayment.status === 'success'
                      ? existingPayment.status
                      : 'paying'
          }
      })
    : await this.prisma.payment_order.create({
          data: {
              payment_id: uuidv4(),
              channel: 'wxpay',
              out_trade_no: params.outTradeNo,
              status: 'paying',
              total_amount: params.totalAmount,
              payer_id: params.payerId
          }
      });
~~~

这一层拆分让系统能够表达“微信已经确认一笔合并支付，但内部还要推进多个订单”，也让资金流水能以支付单为入口建立，而不必猜测某个业务订单是否就是渠道订单。

### 支付成功的第一道幂等是状态短路

收到支付成功通知后，PaymentOrderService 通过 out_trade_no 找到结构化支付单。如果状态已经是 success，直接返回：

~~~typescript
const payment = await this.prisma.payment_order.findUnique({
    where: { out_trade_no: params.outTradeNo }
});

if (!payment) {
    this.logger.warn('未找到结构化支付单: ' + params.outTradeNo);
    return null;
}

if (payment.status === 'success') {
    this.logger.log(
        '支付单 ' + payment.payment_id + ' 已处理成功，跳过重复回调'
    );
    return payment;
}
~~~

首次成功则把支付单、分摊单和业务订单放进一次 Prisma transaction：

~~~typescript
await this.prisma.$transaction([
    this.prisma.payment_order.update({
        where: { payment_id: payment.payment_id },
        data: {
            status: 'success',
            channel_transaction_id: params.channelTransactionId ?? undefined,
            raw_notify: params.rawNotify ?? undefined,
            notify_at: new Date(),
            paid_at: paidAt
        }
    }),
    this.prisma.payment_allocation.updateMany({
        where: { payment_id: payment.payment_id },
        data: { status: 'paid' }
    }),
    this.prisma.order.updateMany({
        where: {
            order_id: { in: orderIds },
            status: { notIn: ['refund_pending', 'refunding', 'refunded'] }
        },
        data: {
            status: 'paid',
            paid_at: paidAt
        }
    })
]);
~~~

幂等的核心不是要求微信只通知一次，而是同一个业务事实通知多次时，后续结果仍然相同：支付单不会反复创建，allocation 不会重复生成，已经进入退款流程的订单也不会被迟到的支付通知覆盖回普通 paid。

### 资金流水和业务补齐是支付成功之后的两步

支付单确认后，服务会先生成支付资金流水，再投递支付成功任务：

~~~typescript
await this.fundFlowService.createPaymentFlows(payment.payment_id);

await this.orderQueueService.addPaymentSuccessJob(
    payment.payment_id,
    orderIds
);
~~~

支付成功任务的稳定 ID 是：

~~~typescript
await this.paymentQueue.add(
    'order.payment.success',
    { paymentId, orderIds },
    {
        jobId: 'payment:' + paymentId + ':success'
    }
);
~~~

worker 随后按订单 ID 调用 processSuccessfulPayment。活动订单会检查是否已经有 event_reg；场馆订单会读取 metadata 中的 processedSessions，只处理还没有处理过的场次。这样“支付事实已经成功”和“订单业务事实已经补齐”之间有了可重试的间隔。

### 合并支付不能用一个订单状态代替所有订单

合并支付时，微信回调只有一个 out_trade_no，本地却可能有多个业务订单。服务会通过 batchPaymentId 找到相关订单，并给它们补上 wxOrderId 映射：

~~~typescript
const relatedOrders = allOrders.filter((order) => {
    if (!order.metadata) return false;

    try {
        const metadata = JSON.parse(order.metadata);
        return metadata.batchPaymentId === wxOrderId;
    } catch {
        return false;
    }
});

for (const relatedOrder of relatedOrders) {
    const isAlreadyPaid = relatedOrder.status === 'paid';
    const hasRefundRequest =
        relatedOrder.status === 'refund_pending' ||
        relatedOrder.status === 'refunding';

    if (!isAlreadyPaid && !hasRefundRequest) {
        await this.prisma.order.update({
            where: { order_id: relatedOrder.order_id },
            data: { status: 'paid' }
        });
    }
}
~~~

批量支付的关键是把“一个外部事件”拆成“多个内部订单的状态推进”。每个订单都要能追溯到支付单，也要独立判断自己是否已经支付、是否已经进入退款。

### 重放一次支付通知，检查哪些事实不能重复

支付回调的验收也应该从“同一份通知到达两次”开始，而不是只看一次成功路径：

| 回放步骤 | 第一次通知 | 第二次相同通知 | 预期 |
|---|---|---|---|
| 支付单 | `paying → success` | 读取到 `success` | 第二次直接短路 |
| 分摊单 | 批量更新为 `paid` | 不新增、不重复生成 | 仍保持原有数量 |
| 业务订单 | 推进到 `paid` | 不覆盖 `refund_pending/refunding/refunded` | 状态不倒退 |
| 后续任务 | 投递固定 `jobId` | 复用同一 `jobId` | 不产生第二条业务事件 |

这里的“预期”是验收规则，不等同于已经运行过的线上结果。真正执行时还要把 `out_trade_no`、支付单状态、allocation 数量、订单状态和队列 jobId 一起记录，才能判断重复通知是否只改变了日志而没有重复改变业务事实。

## 4. 退款是一条补偿链，不是一个终态字段

### 用户申请退款只推进到待审核

退款申请阶段不应该直接把订单改成 refunded。C 端请求首先检查订单归属和当前状态，只允许已支付订单发起退款：

~~~typescript
const order = await this.prisma.order.findFirst({
    where: {
        order_id: orderId,
        user_id: openid
    }
});

if (!order) {
    throw new NotFoundException('订单不存在');
}

if (order.status !== 'paid') {
    throw new BadRequestException(
        '订单状态为 ' + order.status + '，无法发起退款'
    );
}
~~~

服务生成退款 ID，把理由、金额和申请时间放入订单 metadata，并将订单推进到 refund_pending：

~~~typescript
metadata.refundRequest = {
    refundId,
    refundAmount,
    reason: reason || null,
    requestTime: this.formatDateTime(new Date()),
    status: 'pending'
};

await this.prisma.order.update({
    where: { order_id: orderId },
    data: {
        status: 'refund_pending',
        metadata: JSON.stringify(metadata)
    }
});
~~~

此时只代表“用户提出退款申请”，还没有代表商家审核通过，更没有代表微信渠道已经退款成功。

### 退款单把审核状态和渠道状态拆开

结构化退款服务会创建 refund_order，里面保存退款 ID、原支付单、业务订单、商户退款单号、金额、申请状态和渠道状态：

~~~typescript
const existing = await this.prisma.refund_order.findUnique({
    where: { refund_id: params.refundId }
});

if (existing) {
    return existing;
}

return await this.prisma.refund_order.create({
    data: {
        refund_id: params.refundId,
        order_id: params.orderId,
        payment_id: params.paymentId ?? null,
        channel: 'wxpay',
        out_refund_no: params.outRefundNo,
        refund_amount: params.amount,
        reason: params.reason ?? null,
        apply_status: 'pending',
        channel_status: 'not_submitted'
    }
});
~~~

apply_status 和 channel_status 不是重复字段：

| 业务阶段 | apply_status | channel_status | 能否称为退款完成 |
|---|---|---|---|
| 用户申请 | pending | not_submitted | 不能 |
| 商家审核通过 | approved | processing | 不能 |
| 微信处理中 | approved | processing | 不能 |
| 微信成功 | approved | success | 渠道层完成，本地补偿仍要完成 |
| 商家拒绝 | rejected | 可能未提交/关闭 | 不是成功退款 |

一个 refunded 字段无法表达这些中间状态，后续也很难判断该由用户、审核员、渠道查询还是补偿任务接手。

### 退款成功通知先确认渠道事实

结构化退款服务通过 out_refund_no 找到退款单。如果渠道状态已经成功，就直接跳过；第一次成功则保存微信退款号、原始通知和成功时间：

~~~typescript
const refund = await this.prisma.refund_order.findUnique({
    where: { out_refund_no: params.outRefundNo }
});

if (!refund) {
    this.logger.warn('未找到结构化退款单: ' + params.outRefundNo);
    return null;
}

if (refund.channel_status === 'success') {
    this.logger.log(
        '退款单 ' + refund.refund_id + ' 已处理成功，跳过重复回调'
    );
    return refund;
}

await this.prisma.refund_order.update({
    where: { refund_id: refund.refund_id },
    data: {
        channel_status: 'success',
        channel_refund_id: params.channelRefundId ?? undefined,
        raw_notify: params.rawNotify ?? undefined,
        refunded_at: new Date()
    }
});
~~~

随后写退款资金流水，并投递 refund:<refundId>:success 任务：

~~~typescript
await this.fundFlowService.createRefundFlow({
    refundId: refund.refund_id,
    orderId: refund.order_id,
    paymentId: refund.payment_id,
    amount: Number(refund.refund_amount)
});

await this.orderQueueService.addRefundSuccessJob(
    refund.refund_id,
    refund.order_id
);
~~~

退款回调的成功只说明“钱从渠道侧退回去了”。场次、活动和会员卡是本地业务资源，要由后续补偿逻辑恢复。

### 退款补偿也要准备中途失败的回放

退款成功后可以把补偿拆成几个可观察的检查点：

1. 渠道退款单已经是 `success`；
2. 退款资金流水已经存在；
3. 场次、活动名额或会员卡次数按订单明细逐项恢复；
4. 本地订单和关联报名记录进入最终可解释状态。

如果第 3 步执行到一半就失败，下一次任务不能重新盲目执行全部补偿。它需要依据退款单状态、订单状态、资源锁和处理进度判断哪些动作已经完成。重复回放时，最少要验证三件事：容量不能恢复两次、活动名额不能减成负数、会员卡次数不能超过购买或发放上限。

### 一笔退款要归还三类业务资源

processRefund 在 Prisma transaction 中读取订单关联的 session_reg 和 event_reg，再按订单实际关联的领域事实做反向处理：

| 资源 | 支付/预约时发生什么 | 退款时做什么 | 历史怎样保留 |
|---|---|---|---|
| 普通场次 | available → reserved | 恢复为 available | session_reg.status = refunded |
| 容量场次 | capacity_used + 1 | 容量减一，必要时恢复状态 | 保留 session 与订单关系 |
| 活动名额 | 活动已用容量增加 | 活动容量减回 | event_reg.status = refunded |
| 会员卡次数 | 创建 usage，剩余次数减一 | 次数加一，必要时恢复 active | usage 状态/快照记录过程 |

场次退款的核心结构类似这样：

~~~typescript
return await this.prisma.$transaction(async (tx) => {
    const order = await tx.order.findUnique({
        where: { order_id: orderId },
        include: {
            session_reg: true,
            event_reg: true
        }
    });

    if (!order || order.status === 'refunded') {
        return;
    }

    const sessions = await tx.session.findMany({
        where: {
            session_id: {
                in: order.session_reg.map((reg) => reg.session_id)
            }
        }
    });

    await tx.session_reg.updateMany({
        where: { order_id: orderId },
        data: { status: 'refunded' }
    });

    await tx.event_reg.updateMany({
        where: { order_id: orderId },
        data: { status: 'refunded' }
    });

    await tx.order.update({
        where: { order_id: orderId },
        data: { status: 'refunded' }
    });
});
~~~

真实代码还会保存场次快照、恢复会员卡 usage、按容量场次和普通场次分类处理，并把使用记录标记或清理，让历史订单能够解释“当时预订了什么、后来怎样退款”。退款不是删除订单，而是写入一组反向业务事实。

会员卡尤其容易漏掉：退款时不仅要把 remaining_times 加回去，还要把已经 exhausted 的卡在恢复后重新置为 active；否则数字恢复了，卡的状态仍然会阻止用户继续使用。

![悦动体育 05：退款补偿链](/projects/yuedong-sports/yuedong-05-refund-lifecycle.png)

### 退款补偿的幂等边界

退款成功通知可能重复，退款成功队列也可能重试。因此本地补偿至少要有两道门：

~~~typescript
const order = await tx.order.findUnique({
    where: { order_id: orderId },
    include: {
        session_reg: true,
        event_reg: true
    }
});

if (!order) {
    return;
}

if (order.status === 'refund_rejected' || order.status === 'refunded') {
    return;
}

// 只有通过状态门后，才执行容量、报名、会员卡和资金的补偿。
~~~

这里的状态门能挡住已经完成的第二次调用，但还要继续关注一个并发细节：如果两个 worker 同时读到订单仍未 refunded，并且退款恢复代码包含“先查容量，再计算，再 update”，仍可能发生重复减量。更完整的方案是让退款补偿也按 session/event 加锁，并使用带条件的减量更新；补偿完成后再推进最终状态。

### 这一层的复盘：不要把渠道成功当成本地完成

支付和退款都跨越了外部渠道、本地数据库与业务资源。更容易维护的状态写法是把它拆成几条可观察的事实：

- 渠道事实：微信支付或退款是否成功，外部流水号是什么。
- 账务事实：支付/退款资金流水是否建立。
- 业务事实：订单状态、报名记录、场次容量和会员卡次数是否已经完成。
- 任务事实：后续补齐任务是否成功、失败次数是多少。

如果只更新 order.status，就很难回答“钱退了但名额是否释放”“微信通知成功但活动报名是否写入”这些运营问题。结构化表、原始通知、状态字段和可重试任务组合起来，才是一条可排查的交易链。

## 5. BullMQ 把“马上做”改成“可重试地做”

### 三条队列对应三类后续动作

悦动的 OrderQueueService 没有只建立一个“大杂烩订单队列”，而是按后续动作拆成三条：

| 队列 | job name | payload | processor 最终调用 |
|---|---|---|---|
| order-payment | order.payment.success | paymentId、orderIds | processSuccessfulPayment |
| order-expire | order.expire | orderId | cancelOrder |
| order-refund | order.refund.success | refundId、orderId | processRefund |

初始化代码很直白：

~~~typescript
this.paymentQueue = new Queue('order-payment', { connection });
this.expireQueue = new Queue('order-expire', { connection });
this.refundQueue = new Queue('order-refund', { connection });
~~~

队列名实际上是一张后台业务地图：支付成功负责补齐支付后的事实，订单过期负责释放未支付占用，退款成功负责归还已退款资源。

### 固定 jobId、指数退避和失败保留

所有任务经过公共 add 方法投递，默认配置包括 5 次尝试、指数退避、完成任务保留 1000 条、失败任务不自动删除：

~~~typescript
private async add(
    queue: Queue,
    name: string,
    data: any,
    opts: JobsOptions = {}
) {
    await queue.add(name, data, {
        attempts: 5,
        backoff: {
            type: 'exponential',
            delay: 1000
        },
        removeOnComplete: 1000,
        removeOnFail: false,
        ...opts
    });
}
~~~

任务 ID 使用业务事实的 ID，而不是每次随机生成：

~~~typescript
async addOrderExpireJob(orderId: string, expireAt: Date) {
    const delay = Math.max(0, expireAt.getTime() - Date.now());

    await this.add(
        this.expireQueue,
        'order.expire',
        { orderId },
        {
            delay,
            jobId: 'order:' + orderId + ':expire'
        }
    );
}
~~~

这些设置各自解决不同问题：

| 设置 | 解决的问题 | 不能替代的东西 |
|---|---|---|
| 固定 jobId | 同一业务事件重复投递 | processor 内部幂等 |
| attempts: 5 | 临时网络/数据库故障 | 永久失败后的人工处理 |
| 指数退避 | 避免失败后立即打满下游 | 业务状态设计 |
| removeOnFail: false | 保留失败任务供排查 | 监控和告警 |

如果支付业务已经成功，但 worker 在发消息时失败，重试会再次进入 processor；所以 processSuccessfulPayment 仍然必须检查报名记录和已处理场次，不能只依赖 jobId。

### processor 负责路由，OrderService 负责业务

支付 processor 的职责是建立 worker、校验任务名称、根据订单 ID 找数据，再把业务交给公共订单服务：

~~~typescript
onModuleInit() {
    this.worker = new Worker(
        'order-payment',
        async (job) => this.handle(job),
        { connection: this.connection() }
    );
}

private async handle(
    job: Job<{ paymentId: string; orderIds: string[] }>
) {
    if (job.name !== 'order.payment.success') {
        return;
    }

    const orderService = this.moduleRef.get(OrderService, {
        strict: false
    });

    for (const orderId of job.data.orderIds || []) {
        const order = await this.prisma.order.findUnique({
            where: { order_id: orderId }
        });

        if (order) {
            await orderService.processSuccessfulPayment(order);
        }
    }
}
~~~

订单过期和退款成功 processor 采用同样的结构，只是分别调用 cancelOrder 和 processRefund。这样 HTTP 入口、队列入口和 Cron 入口可以复用同一套订单状态判断，不需要把“释放库存”“恢复会员卡”复制三份。

### 支付回调为什么可以先返回

微信回调的同步响应和本地业务完成不是同一件事。项目在支付通知中先完成验签、解密和结构化支付处理，然后异步触发订单业务处理，返回成功：

~~~typescript
this.orderService
    .processSuccessfulPayment(orderForProcess)
    .then(() => {
        this.logger.log(
            '订单 ' + order.order_id + ' 支付成功处理完成'
        );
    })
    .catch((error) => {
        this.logger.error(
            '处理订单支付成功逻辑失败: ' + error.message,
            error.stack
        );
    });

return { code: 'SUCCESS', message: 'OK' };
~~~

这样做的动机是避免报名、容量、会员卡和消息等复杂逻辑阻塞微信回调，触发渠道重复通知。但它也提出一个明确的可靠性要求：如果异步 Promise 失败，不能只依赖日志；更稳妥的边界是先持久化一个可重试的本地任务或事件，再返回渠道成功。当前 BullMQ 已经提供了任务模型，因此支付成功的业务补齐应该尽量统一走 queue，而不是存在无法重试的 fire-and-forget 分支。

### 队列和 Cron 的分工

![悦动体育 05：队列与重试](/projects/yuedong-sports/yuedong-05-queue-retry.png)

队列处理“我刚刚收到的事件”，Cron 处理“定期找出仍停留在中间状态的对象”：

| 触发方式 | 适合的问题 | 悦动里的例子 |
|---|---|---|
| 延迟队列 | 已知未来某个时间点执行一次 | order:<id>:expire 到期取消 |
| 事件队列 | 某个外部/本地事实刚刚发生 | 支付成功、退款成功 |
| Cron 扫描 | 任务丢失、回调延迟或状态长期停留 | 扫描 pending、refunding、长时间 refund_pending |

订单服务中的定时检查包括：扫描 pending 订单并取消、查询 refunding 订单的退款状态、处理超过时间窗口的待审核退款，以及检查已支付订单的后续状态。Cron 不是队列的替代品，它更像最后一道“找漏网之鱼”的补偿扫描。

## 6. 日期、时间和时区是业务规则的一部分

### 先区分业务日期、墙上时间和瞬时

场次的几个字段看起来都像日期时间，但语义不同：

![悦动体育 05：时间边界](/projects/yuedong-sports/yuedong-05-time-boundaries.png)

| 语义 | 例子 | 悦动字段 | 是否需要时区转换 |
|---|---|---|---|
| 业务日期 | 2026-09-10 | session.date、usage_date | 通常作为日历字符串处理 |
| 当天时段 | 19:30:00 | start_time、end_time | 需要和业务日期组合时再处理 |
| 组合业务时间 | 2026-09-10 19:30:00 | 订单/场次输入输出 | 按统一约定解析 |
| 时间线上的瞬时 | 2026-09-10T11:30:00.000Z | paid_at、notify_at、refunded_at、过期时间 | 需要明确 UTC 与展示时区 |

2026-09-10 回答的是“哪一天”，不是全球时间线上的一个瞬间。把它无脑转换成当地午夜，再用 toISOString 返回，可能因为时区偏移显示成前一天。对于场次业务日期，保留 YYYY-MM-DD 往往比创建一个“午夜 Date”更符合语义。

### date-time-field.util.ts 负责归一化

项目的时间字段工具先用正则区分 DATE、TIME 和 DATETIME，再将输入归一化：

~~~typescript
const DATE_RE = /^\\d{4}-\\d{2}-\\d{2}$/;
const TIME_RE = /^([0-1]\\d|2[0-3]):([0-5]\\d)(?::([0-5]\\d))?$/;
const DATETIME_RE =
    /^(\\d{4}-\\d{2}-\\d{2})[ T]([0-1]\\d|2[0-3]):([0-5]\\d):([0-5]\\d)$/;

export function normalizeTimeString(input?: string | null): string | null {
    if (input == null) return null;

    const value = input.trim();
    if (!value) return null;

    const directMatch = value.match(TIME_RE);
    if (directMatch) {
        const [, hh, mm, ss] = directMatch;
        return hh + ':' + mm + ':' + (ss || '00');
    }

    const date = new Date(value);
    if (Number.isNaN(date.getTime())) return null;

    return pad2(date.getUTCHours()) + ':' +
        pad2(date.getUTCMinutes()) + ':' +
        pad2(date.getUTCSeconds());
}
~~~

19:30 会被统一成 19:30:00；normalizeDateTimeString 会把 T 形式和空格形式统一成 YYYY-MM-DD HH:mm:ss。解析成 Date 时，工具使用 Date.UTC：

~~~typescript
export function parseDateTimeToUtcDate(
    input?: string | null
): Date | null {
    const datetimeStr = normalizeDateTimeString(input);
    if (!datetimeStr) return null;

    const [datePart, timePart] = datetimeStr.split(' ');
    const [year, month, day] = datePart.split('-').map(Number);
    const [hour, minute, second] = timePart.split(':').map(Number);

    return new Date(
        Date.UTC(year, month - 1, day, hour, minute, second, 0)
    );
}
~~~

输出时又使用 getUTCFullYear、getUTCHours 等 UTC getter，避免同一 Date 在不同运行环境被格式化成不同结果。归一化工具的价值是让输入和输出有固定契约，但调用方仍要先明确输入代表日历字段还是已带时区的瞬时。

### timezone.ts 暗含的调用约定

项目还有一组 UTC 边界工具：

~~~typescript
export function dateStartUTC(date: Date | string): Date {
    const inputDate = typeof date === 'string' ? new Date(date) : date;

    return new Date(
        Date.UTC(
            inputDate.getFullYear(),
            inputDate.getMonth(),
            inputDate.getDate(),
            0,
            0,
            0,
            0
        )
    );
}

export function formatDateString(date: Date | string): string {
    const inputDate = typeof date === 'string' ? new Date(date) : date;
    return inputDate.toISOString().split('T')[0];
}
~~~

dateStartUTC 读取的是本地 getFullYear/getMonth/getDate，再用 Date.UTC 组装。这个函数表达的是“把某个本地日历日期的零点作为 UTC 边界”，而不是“把任意已有瞬时转换到 UTC”。如果传入的 Date 已经表示一个带 Z 的瞬时，再用本地 getter 拆开重组，语义就可能变化。

因此时间工具不能脱离字段语义单独背诵：

- 场次 date 适合保持为业务日期字符串。
- 场次 start_time/end_time 适合在边界统一成 HH:mm:ss。
- paid_at、notify_at、refunded_at 和过期时间应当作为时间线上的瞬时，保存和比较使用统一时区。
- 前端展示再根据用户或业务区域格式化，不把展示格式反向写成存储契约。

### 星期工具也是领域规则

场次生成不是简单的 UI 日期格式化。JavaScript 的 Date#getDay() 使用 0 表示周日，而项目对外使用 1～7，其中 7 表示周日：

~~~typescript
export function getWeekday(date: Date): number {
    const day = date.getDay();
    return day === 0 ? 7 : day;
}

export function isValidWeekday(weekday: number): boolean {
    return Number.isInteger(weekday) && weekday >= 1 && weekday <= 7;
}

export function getDatesByWeekday(
    startDate: Date,
    endDate: Date,
    weekday: number
): Date[] {
    const dates: Date[] = [];
    const current = new Date(startDate);

    while (current <= endDate) {
        if (getWeekday(current) === weekday) {
            dates.push(new Date(current));
        }
        current.setDate(current.getDate() + 1);
    }

    return dates;
}
~~~

这个约定会影响后台批量生成 session。如果一端认为周日是 0，另一端认为周日是 7，同一条“每周日营业”的配置就可能生成错误日期。星期编号应当像状态枚举一样，在系统边界固定下来。

### 用契约测试锁住时间规则

时间问题不适合靠“我在开发机上看起来正确”来判断。项目已有 time-field-contract.spec.ts 和 order-time-fields.spec.ts，它们把时间字段的读取、格式化和订单时间映射写成测试。最小测试集可以包含：

~~~typescript
describe('time field contract', () => {
    it('keeps a business date as a calendar date', () => {
        expect(normalizeDateString('2026-09-10')).toBe('2026-09-10');
    });

    it('fills missing seconds for a time field', () => {
        expect(normalizeTimeString('19:30')).toBe('19:30:00');

~~~

订单时间测试还应该固定当前时间，覆盖创建、支付、退款和过期判断；跨天场景要覆盖 23:xx → 00:xx，空值和非法格式也要覆盖。测试的目的不是证明某个时区“更正确”，而是把项目选择的时间语义固定下来，避免 Node.js、MySQL、B 端和 C 端各自采用一套解释。

### 把整条链路收束成七个问题

一笔 C 端预约可以按下面的顺序复盘：

1. 查询场次时，业务日期、时段和库存字段分别代表什么？
2. 进入预约临界区时，是否按资源 ID 加 Redis 锁，并在异常时释放？
3. 真正扣减库存时，数据库条件是否仍然检查了 available 和容量上限？
4. 订单、报名、明细和会员卡使用记录是否在同一个本地事务中？
5. 创建支付单时，是否使用稳定的 out_trade_no，并区分支付单与业务订单？
6. 渠道回调重复或延迟时，支付单、退款单和队列任务能否安全重试？
7. 订单过期和退款时，是否能按同一时间语义找到需要补偿的对象？

如果这七个问题都能被具体代码回答，系统就不只是“用了 Redis、微信支付和 MQ”，而是形成了一条能够解释成功、冲突、重复、延迟和补偿的业务链路。

### 本篇验证清单

在面试复盘前，把前面的设计转成可以执行的检查项：

| 场景 | 初始事实 | 重点观察 | 通过条件 |
|---|---|---|---|
| 最后一个容量被两个请求争抢 | `capacity_total = 1`、`capacity_used = 0` | 成功数、失败数、最终容量 | 只有一个请求获得资源 |
| 支付通知重复到达 | 同一 `out_trade_no` 两份相同通知 | payment_order、allocation、order、jobId | 第二次不重复推进 |
| 退款补偿中途失败 | 渠道退款成功、本地只完成部分资源恢复 | 重试后的处理进度 | 已完成动作不重复，剩余动作最终补齐 |
| 订单跨日过期 | 创建时间、过期时间跨越 23:xx → 00:xx | Date 解析和 Cron 查询边界 | 不提前过期，也不漏掉应处理订单 |
| 队列任务重复执行 | 相同业务 ID、两次 worker 触发 | processor 的状态短路和唯一标识 | 业务事实只改变一次 |

记录结果时要把“渠道事实、本地状态、业务资源和任务状态”放在同一张验收表中。只记录接口返回 200，无法证明支付、退款或补偿已经完整完成。

## 7. 面试复盘

### 你们为什么同时使用 Redis 锁和数据库条件更新？

Redis 锁负责应用层协调，让同一资源的请求尽量串行进入临界区；数据库条件更新是数据层最后裁决，即使锁过期、多实例或出现绕过锁的入口，也不会把已经满的容量继续增加。锁解决访问顺序，数据库解决事实是否合法。

### Redis 锁的 NX、EX 和随机 value 分别解决什么问题？

NX 表示只有 key 不存在时才成功，避免多个请求同时拿锁；EX 设置过期时间，避免进程崩溃后永久占锁；随机 value 标识当前持有者，释放时可以确认删除的是自己的锁。

### 为什么解锁不能直接 DEL key？

锁可能在持有者执行期间过期并被另一个请求重新获得。原持有者如果直接 DEL，会误删新持有者的锁。悦动用 Lua 在 Redis 内原子比较 value，再决定是否删除。

### 多场次预约时为什么要对 session id 去重并排序？

去重避免重复申请同一把锁；排序让所有请求按照相同顺序申请多把锁，减少锁顺序相反导致的互相等待。key 还要保持统一，确保不同入口锁住的是同一个资源。

### capacity_used < capacity_total 放在 SQL 的 WHERE 中有什么意义？

它让数据库在执行更新时基于当前行值判断容量，而不是使用应用层稍早查到的旧值。只有条件成立的更新才能影响这一行，受影响行数为 0 就代表本次没有成功占用容量。

### updateMany.count === 0 时你如何区分容量已满和状态已变化？

先把 0 行视为竞争失败，再查询最新的状态、总容量和已用容量，用于返回“已被预订”“容量已满”或通用重试提示。查询用于解释原因，不能替代前面的条件更新。

### Prisma transaction 能不能把微信支付调用也回滚？

不能。Prisma transaction 只能保证同一数据库中的本地写入一起提交或回滚。微信支付是外部网络调用，要通过支付单状态、渠道查询、回调幂等和补偿任务处理跨系统结果。

### 订单过期释放库存和用户主动取消释放库存应该复用什么？

应该复用同一个订单取消 service，例如 cancelOrder，让状态条件、场次释放、活动容量、会员卡次数恢复和历史记录处理保持一致。区别只在调用入口是用户请求还是过期 processor。

### 微信支付回调为什么会重复到达？

外部系统需要确认服务端已经收到通知；网络超时、响应过慢或服务端处理失败时，渠道可能再次通知。因此服务端必须把通知当成可重复事件，而不是假设每个通知只来一次。

### 支付单和业务订单为什么要拆成两层？

渠道支付有自己的 out_trade_no 和状态，一次合并支付还可能对应多个业务订单。拆开后可以独立记录渠道事实、支付分摊关系和场馆/活动/会员业务状态，也方便资金流水和退款匹配。

### payment_allocation 解决了什么问题？

它记录一笔支付分摊给哪些业务订单、每个订单对应的金额和支付状态。这样一个微信支付号可以对应多个内部订单，回调只处理一次支付事实，再逐个推进内部订单。

### 你如何保证支付成功不会重复创建报名记录？

支付单成功状态先短路；订单业务处理时再查询该订单是否已有 event_reg，已存在就跳过创建。数据库唯一约束和 createMany 的重复处理也应作为最后一道保护。

### processedSessions 这种 metadata 幂等标记有什么优点和缺点？

优点是改动小，能记录一个订单已经处理过哪些场次，队列重试时可以跳过已完成部分。缺点是 JSON metadata 不如独立处理表结构化，难做条件更新和并发控制；长期可以沉淀为带唯一键的业务处理记录。

### 为什么支付回调可以快速返回，业务逻辑放到队列？

回调需要尽快确认，避免渠道因等待复杂业务处理而重复通知；报名、容量、会员卡和消息等后续动作可以由 worker 重试。但回调返回成功前，应至少把支付事实和可重试任务可靠地落到本地，不能只启动一个无持久化的 Promise。

### 只用 order.status = paid 能不能说明支付流程全部完成？

不能。它最多表示订单支付状态已经推进，活动报名、场次容量、会员卡购买、资金流水和消息可能仍在异步处理。应分别观察支付单、allocation、订单、业务关联记录和任务状态。

### 退款申请、审核通过、渠道处理中、退款成功分别是什么状态？

用户申请后是 refund_pending；审核通过后进入 refunding 或结构化退款单的 approved/processing；微信通知成功后退款单 channel status 为 success，并触发本地资源补偿；所有本地补偿完成后订单才应保持 refunded。

### 退款成功后为什么还要恢复场次容量、活动名额和会员卡次数？

这些资源在预约或购买时已经被占用。退款只退钱而不释放资源，会让用户看不到可预约的场次、活动容量持续虚高，或者会员卡次数永久减少。退款是对正向业务事实的一组反向补偿。

### 退款回调重复到达时，如何避免资源被释放两次？

以稳定的 out_refund_no/refund_id 找到结构化退款单，渠道状态已经 success 时直接返回；本地订单已经 refunded 时跳过补偿。同时应让容量恢复使用资源锁和条件更新，避免两个 worker 同时通过状态检查后重复减量。

### BullMQ 的固定 jobId、attempts、backoff 分别解决什么问题？

固定 jobId 识别同一个业务事件的重复投递；attempts 允许临时失败重试；backoff 拉开重试间隔，避免瞬时故障时持续冲击下游。它们都不能替代 processor 内部的幂等逻辑。

### 队列 processor 为什么不直接复制订单业务代码？

processor 负责后台入口、任务名称和 payload 路由，OrderService 负责状态判断、事务和业务事实。复用 service 可以让 HTTP、队列和 Cron 入口共享规则，避免三套释放库存或退款代码逐渐产生差异。

### 队列和 Cron 扫描分别适合什么场景？

队列适合已知事件发生后的即时处理，例如支付成功或退款成功；延迟队列适合订单到期；Cron 适合周期性检查长时间停留在中间状态的订单，补偿丢失的回调或失败任务。

### 如果支付成功回调返回成功，但本地异步处理失败，怎样恢复？

支付单和原始通知已经落库后，应通过 BullMQ 任务重试；processor 要能安全重复执行；Cron 或后台管理任务还要能扫描“支付成功但业务事实未补齐”的订单。失败任务保留、日志和告警用于定位最终需要人工介入的情况。

### DATE、TIME、DATETIME 和带时区的 Date 如何区分？

DATE 表示业务日历日期，TIME 表示一天中的时段，DATETIME 表示日期和时段的组合，带时区的 Date 表示时间线上的瞬时。场次日期不应和支付时间使用同一种解析与展示规则。

### 为什么业务日期不建议直接转成午夜 Date？

业务日期只表示哪一天，强行转成午夜后再进行 ISO 或时区转换，可能在展示或查询时偏移到前一天。除非查询边界确实需要时间瞬时，否则保留 YYYY-MM-DD 更能保留原意。

### Date.UTC、getUTC* 和本地 get* 混用会带来什么风险？

本地 getter 读取的是运行环境的日历字段，UTC getter 读取的是全球时间线字段；把一个已经代表瞬时的 Date 拆成本地字段再用 Date.UTC 重组，可能改变实际时间。必须先约定输入是墙上时间还是瞬时。

### 悦动如何保证场次生成中的星期编号一致？

统一把 JavaScript 的周日 0 转成业务约定的周日 7，并用 isValidWeekday 校验 1～7。场次生成、B 端配置和 C 端展示都应使用同一个映射。

### 你会为时间字段补哪些测试？

测试日期不被偏移、时间缺秒时能补齐、日期时间格式固定、支付/退款/过期时间使用同一时钟语义，并覆盖跨天、空值、非法输入和不同运行时区。订单时间字段还要测试来源与状态转移的对应关系。

### 如果让你继续改造 05，你会先改哪一个一致性风险？

我会先统一支付成功和退款补偿中的库存增减路径：按资源加锁，改成条件增量/减量，以受影响行数判断结果，再将处理进度从 metadata 逐步沉淀为带唯一约束的处理记录。这样既能降低重复任务的风险，也让后续排查有更结构化的证据。

面试时不要只回答“用了 Redis 锁、事务和 MQ”。更完整的回答顺序是：先指出会重复或并发的业务事实，再说哪个组件负责协调、哪个组件负责裁决、哪些本地写入在事务里、失败后由哪个任务接手，最后补充状态和时间字段如何让这条链路可追溯。
