# 悦动体育 07：B 端管理台与运营工作流——从菜单权限到资源状态

06 沿着 C 端用户的点击走了一遍“选场次—创建订单—支付—凭证”。07 换成另一种角色：商家管理员或平台管理员登录后，怎样把场馆配置成可预约资源，怎样发布活动，怎样处理订单退款，以及怎样把这些操作交给子账号协作？

这次我参照 Day09 对管理端的拆法来读 `yuedong_front`：先看列表和筛选，再看表单与接口，然后追审核、发布和状态转换。这样 B 端就不再是一张很长的侧边栏，而是一条可以复盘的运营工作流。

![悦动体育 07：B 端管理台的认证、角色、菜单与 API 边界](/projects/yuedong-sports/yuedong-07-b-workbench.png)

> **本篇任务卡**
>
> 以“商家管理员登录 → 查看或创建场馆 → 平台审核 → 配置场地、价格计划和场次”为主线。主线走通后，再用活动、订单退款、会员和子账号验证这套阅读方法能不能迁移到其他运营模块。
>
> 完成标准不是记住组件文件名，而是能把一次操作还原成：谁在什么页面点击了什么、携带了哪个 ID、调用了什么接口、页面展示了哪个过渡状态、服务端最终应该保存什么事实。

## 1. 先把 B 端看成一张可进入的运营工作台

### 从运营任务而不是文件目录进入项目

B 端前端最容易读成“组件目录导览”：`VenuePanel.vue` 管场馆，`EventPanel.vue` 管活动，`OrderPanel.vue` 管订单。这样的阅读顺序能告诉我文件在哪里，却不能说明运营人员是怎样完成一项工作。

我先给自己一个具体任务：商家管理员登录管理台，查看自己的场馆；没有场馆就填写信息创建；创建申请交给平台审核；审核通过后继续配置场地、价格计划和场次。这个任务会穿过列表、表单、审核、资源配置和结果查询，正好把 B 端的主要阅读动作串起来。

Day09 讲优惠券管理时，先把管理端和用户端分开，再把管理端拆成基础增删改查、审核、发布方式、暂停/恢复和状态转换。悦动的场馆和活动虽然业务对象不同，但阅读方法相同：先找操作对象，再找状态，最后找每个状态由哪个接口推动。

| 运营动作 | 前端入口 | 需要继续追踪的对象 |
|---|---|---|
| 查看自己的场馆 | `VenueList.vue` | `merchantId`、`venueId` |
| 创建场馆申请 | `VenueCreateDialog.vue` | 表单字段、创建响应、审核记录 |
| 平台审核 | `VenueAuditList.vue` | `auditId`、`action`、`reason` |
| 配置可预约资源 | `CourtOperations.vue`、`SessionPanel.vue` | `courtId`、weekday、timeSlot、sessionId |
| 发布活动 | `EventList.vue` | `eventId`、审核状态、报名字段 |
| 处理退款 | `OrderPanel.vue`、`RefundAuditDialog.vue` | `orderId`、退款动作、服务端状态 |

这张表把文章的阅读方向固定下来：所有页面最后都要回到业务 ID、接口契约和服务端状态。

### HomeView 把菜单键映射成异步面板

`HomeView.vue` 是管理台的壳层。它通过 `defineAsyncComponent` 延迟加载业务面板，再用一个 `componentMap` 把菜单索引映射成组件：

```javascript
const DashboardPanel = defineAsyncComponent(() =>
  import('@/components/DashboardPanel.vue')
);
const VenuePanel = defineAsyncComponent(() =>
  import('@/components/venue/VenuePanel.vue')
);
const OrderPanel = defineAsyncComponent(() =>
  import('@/components/OrderPanel.vue')
);

const componentMap = {
  '0': DashboardPanel,
  '1': VenuePanel,
  '2': OrderPanel,
  '3': EventPanel,
  '4-1': MembershipPanel,
  '8': SettingPanel
};

function handleSelect(key) {
  currentPanelIndex.value = key;
}
```

点击侧边栏时，修改的是 `currentPanelIndex`，并不是直接跳转到另一条 URL。随后 `currentComponent` 根据这个索引取出异步组件，`<Suspense>` 在组件还没加载完成时显示 loading 状态。

这也解释了为什么 B 端的“页面”不能只按路由来理解。路由层只负责 `/home` 能不能进来，进入以后，`HomeView` 还要负责面板切换、移动端抽屉、未读消息刷新和部分角色菜单。

## 2. 登录身份与权限边界

### 路由守卫只回答是否登录

`router/index.js` 中有两类 meta：`requiresAuth` 和 `requiresGuest`。管理台 `/home`、移动扫码页和场馆详情页需要登录；登录页和注册页只允许访客访问。

浏览器刷新时，守卫会先尝试恢复认证状态：

```javascript
router.beforeEach(async (to, from, next) => {
  const authStore = useAuthStore();

  if (!authStore.isLoggedIn) {
    await authStore.initAuth();
  }

  if (to.meta.requiresAuth && !authStore.isLoggedIn) {
    next({ name: 'index' });
    return;
  }

  if (to.meta.requiresGuest && authStore.isLoggedIn) {
    next({ name: 'home' });
    return;
  }

  next();
});
```

`initAuth()` 从 `localStorage` 读取 `jwt_token` 和 `user_info`，再请求 `/business/admin/profile` 验证 token。如果 profile 请求失败，auth store 清理本地登录信息。

这里要先建立一个边界：路由守卫回答的是“当前请求是否有登录态”，它没有回答“当前用户能不能审核活动”“当前子账号能不能管理某个场馆”。后两个问题属于角色授权和数据范围。

### JWT 进入请求头，角色进入 UI 分支

`api/index.js` 集中封装了 fetch 请求。每次请求会读取 token，并把它写成 Bearer Token：

```javascript
getHeaders() {
  const headers = {
    'Content-Type': 'application/json'
  };

  const token = this.getToken();
  if (token) {
    headers.Authorization = `Bearer ${token}`;
  }

  return headers;
}
```

登录成功后，`auth` store 同时保存用户信息、token 和 `isAuthenticated`，并调用 `apiClient.setToken()`。退出登录时，除了清理 `user_info` 和 `jwt_token`，还会重置场馆、场地、场次等业务 store，避免下一个用户继续看到上一个用户的选中场馆。

角色再进入 UI 分支。`HomeView.vue` 用 `platform_admin` 判断平台管理员；`NavBar.vue` 把几个角色转换成展示文本：

```javascript
const roleMap = {
  platform_admin: '平台管理员',
  merchant_admin: '商家管理员',
  venue_manager: '场馆管理员',
  event_organizer: '活动组织方'
};

const userRole = computed(() => {
  return roleMap[userInfo.value?.role] || '用户';
});
```

平台管理员能看到平台场馆、商家管理和账号管理入口；普通商家账号则使用另一组面板索引显示商家工具和账号设置。角色范围可以先画成一张阅读矩阵：

![悦动体育 07：角色与业务范围矩阵](/projects/yuedong-sports/yuedong-07-role-scope.png)

| 角色 | 主要前端入口 | 从页面能观察到的范围 |
|---|---|---|
| `platform_admin` | 平台场馆、商家管理、账号管理、审核入口 | 平台级运营视角 |
| `merchant_admin` | 场地、订单、活动、会员、账号设置 | 商家运营视角 |
| `venue_manager` | 场馆资源和日常运营 | 场馆管理视角 |
| `event_organizer` | 活动创建和活动配置 | 活动组织视角 |

这里的“从页面能观察到”很重要。隐藏菜单只能减少误操作入口，不能代替 NestJS 服务端的 guard、DTO 校验和 merchantId/venueId 数据范围。把前端 `v-if` 说成完整权限系统，是面试中很容易被追问的地方。

## 3. 场馆管理的申请、审核与资源化

### 列表页是运营任务的入口

`VenuePanel.vue` 继续组合 `VenueList`、`CourtOperations` 和 `SessionPanel`。`VenueList.vue` 挂载时从认证用户中取 `merchantId`，调用 venue store 加载商家的场馆：

```javascript
onMounted(async () => {
  const userInfo = authStore.getUserInfo;
  if (userInfo?.merchantId) {
    await venueStore.getVenueList(userInfo.merchantId);
  }
});
```

列表中的场馆卡可以打开五类动作：创建、查看详情、编辑、图片管理和删除申请。点击“管理场地”时，组件会把 `venueId` 交给 venue store 的 `activeVenueId`，再通过 `switchPanel` 事件切换到场地管理面板：

```javascript
const handleManageVenue = async (venueId) => {
  venueStore.setActiveVenue(venueId);
  window.dispatchEvent(new CustomEvent('switchPanel', {
    detail: { index: '1' }
  }));
};
```

这一步把列表和后续资源配置接起来了。`venueId` 不是只用于卡片显示，它决定之后读哪家场馆的营业时间、场地、价格计划和 session。

### 创建与平台审核是两个不同角色的动作

`VenueCreateDialog.vue` 把新增场馆呈现成三个步骤：

1. 信息填写：名称、区域、品牌、描述、运动类别、电话、地址、经纬度。
2. 保证金提交：页面呈现保证金金额和微信支付入口。
3. 平台审核：提交后显示等待审核结果。

第一步的表单校验由 Element Plus `el-form` 完成。真正创建时，venue store 会把当前用户的 `merchantId` 写入 `newVenue`，再调用：

```javascript
const result = await venueStore.createVenue(userInfo.merchantId);

if (result.success) {
  currentStep.value = 1;
  emit('success', result.data);
}
```

API 模块的路径是：

```javascript
export const venueApi = {
  createVenue: (data) => {
    return apiClient.post('/business/venues', data);
  },
  getVenueList: (merchantId) => {
    return apiClient.get(`/business/venues/${merchantId}`);
  },
  getVenueDetail: (venueId) => {
    return apiClient.get(`/business/venues/detail/${venueId}`);
  }
};
```

store 按 `statusCode === 201` 处理创建成功，然后重新获取场馆列表。这里的“创建成功”表示申请已经提交，不代表平台审核已经通过。

平台审核在另一块组件中完成。`VenueAuditList.vue` 以 `auditType` 和 `action` 作为筛选条件，待审核记录的 `action` 为 `pending` 时才显示审核按钮。提交审核时携带申请记录的 `id`、当前审核人 ID、`approve/reject` 和审核意见：

```javascript
const res = await platformVenueApi.auditVenue({
  auditId: currentAudit.value.id,
  auditorId: authStore.user.id,
  action: auditForm.action,
  reason: auditForm.reason || undefined
});

if (res.statusCode === 200) {
  auditDialogVisible.value = false;
  fetchAuditList();
}
```

平台场馆接口集中在 `platform-venue.js`：

| 动作 | 方法与路径 | 关键输入 |
|---|---|---|
| 查询全量场馆 | `GET /business/venues` | page、pageSize、筛选条件 |
| 查场馆详情 | `GET /business/venues/detail/:venueId` | venueId |
| 查询审核列表 | `GET /business/venues/audit/list` | auditType、action、分页 |
| 提交审核 | `PUT /business/venues/audit/review` | auditId、auditorId、action、reason |
| 查已删除场馆 | `GET /business/venues/audit/deleted` | 分页条件 |

场馆生命周期可以还原成下面这条路径：

![悦动体育 07：场馆从创建申请到场次运营](/projects/yuedong-sports/yuedong-07-venue-flow.png)

| 状态或动作 | 谁发起 | 页面上的下一步 |
|---|---|---|
| 信息填写 | 商家管理员 | 校验表单并创建申请 |
| 已提交 | 商家管理员 | 等待平台审核 |
| `pending` | 平台审核列表 | 显示审核按钮 |
| `approve` | 平台管理员 | 进入场馆详情与资源配置 |
| `reject` | 平台管理员 | 保留审核意见，回到修改申请 |
| 删除申请 | 商家管理员 | 进入删除审核流程 |

这个状态机也带来一个验收重点：前端显示“已提交”不能直接推断 C 端已经可以预约。要判断场馆是否真正可用，还需要结合服务端审核状态、场地和 session 数据一起验证。

## 4. 场地、价格计划与场次配置

### CourtOperations 先选场馆、星期和运动类别

场馆审核通过后，真正可运营的资源还没有出现。`CourtOperations.vue` 维护四个关键上下文：

```javascript
const selectedVenue = ref(null);
const selectedWeekday = ref(1); // 1=周一 ... 7=周日
const selectedCategory = ref(null);
const venueBusinessHours = ref(null);
```

场馆切换时，组件读取营业时间，再按运动类别加载场地；星期变化时重新加载对应日期的价格。`CourtTable.vue` 负责把场地和时间段画成表格，价格编辑、时段新增、删除和工作日复制则由多个对话框完成。

这四个状态可以理解成一次配置操作的作用域：

| 状态 | 作用 |
|---|---|
| `selectedVenue` / `activeVenueId` | 决定正在管理哪家场馆 |
| `selectedWeekday` | 决定查看哪一天的价格规则 |
| `selectedCategory` | 决定加载哪类运动场地 |
| `venueBusinessHours` | 限制可配置的时间轴范围 |

如果只看“编辑价格”按钮，很容易漏掉这些隐含输入。一个 `courtId` 还不够，因为同一块场地在不同 weekday、不同 timeSlot 可能有不同价格。

### 价格计划不是展示价格，而是场次生成的输入

`price-plan.js` 里的接口说明了价格配置的完整动作：

```javascript
export const pricePlanApi = {
  updatePricePlanPrices: (courtId, data) =>
    apiClient.put(`/business/price-plans/court/${courtId}/prices`, data),

  createPricePlanDetail: (courtId, data) =>
    apiClient.post(`/business/price-plans/court/${courtId}/timeSlot`, data),

  batchUpdatePriceByWeekday: (courtId, data) =>
    apiClient.patch(`/business/price-plans/court/${courtId}/batch-price`, data),

  syncSessionsFromPricePlan: (courtId, data) =>
    apiClient.post(`/business/price-plans/court/${courtId}/sync-sessions`, data),

  cloneCourtPricePlan: (targetCourtId, fromCourtId) =>
    apiClient.post(`/business/price-plans/court/${targetCourtId}/clone`, {
      fromCourtId
    })
};
```

而 `session.js` 把已经生成的可运营时间资源暴露给管理台：

```javascript
export const sessionApi = {
  getSessionsMatrix: (venueId, date, category = null) => {
    return apiClient.get(`/business/sessions/matrix/${venueId}`, {
      date,
      ...(category ? { category } : {})
    });
  },

  updateSession: (sessionId, data) =>
    apiClient.patch(`/business/sessions/${sessionId}`, data),

  batchUpdateCourtSessions: (data) =>
    apiClient.patch('/business/sessions/batch-update', data),

  generateSessions: (venueId, courtId = null) =>
    apiClient.post('/business/sessions/generate', {
      venueId,
      ...(courtId ? { courtId } : {})
    }),

  assignToEvent: (data) =>
    apiClient.post('/business/sessions/assign-to-event', data)
};
```

这条配置链的关键不是把几个名词排成一行，而是明确每次操作的输入和边界：改价接口只说明价格计划变了，是否立即影响已有 session、已有订单和退款金额，要看后端规则，不能从 `sync-sessions` 这个名字直接推导出所有结果。

SessionPanel 还支持按 7 天窗口查看 session 数量、切换日期、按运动类别筛选和批量选择。运营人员在批量更新时，页面要把选择的 session ID 集合交给后端，不能只保存表格的行列索引。

## 5. 活动发布与动态报名表单

### 活动列表把角色、分页和状态动作聚在一起

Day09 对管理端的一个启发是：看到列表时，先把搜索条件、分页字段、状态标签、操作按钮和定时/发布动作列出来，再进入数据库或服务实现。`EventList.vue` 也可以这样读。

活动创建按钮不是所有角色都能使用：

```javascript
const canCreateEvent = computed(() => {
  const role = userInfo.value?.role;
  return role === 'event_organizer' || role === 'platform_admin';
});

const showAuditTab = computed(() => {
  return userInfo.value?.role === 'platform_admin';
});

const pendingPublishCount = computed(() => {
  return eventStore.events.filter(event => event.needsApproval).length;
});
```

event API 又把动作拆得很清楚：

```javascript
getEventList: (params = {}) =>
  apiClient.get('/business/events', normalizeDateTimeParams(params)),

createEvent: (data) =>
  apiClient.post('/business/events', data),

auditEvent: (data) =>
  apiClient.post('/business/events/audit', data),

publishEvent: (eventId) =>
  apiClient.post('/business/events/publish', { eventId }),

updateEventVisibility: (eventId, hidden) =>
  apiClient.put(`/business/events/${eventId}/visibility`, { hidden })
```

从这里可以区分至少四个状态：

| 状态或动作 | 作用 |
|---|---|
| 草稿/已创建 | 运营人员编辑活动基本信息 |
| 待审核 | 进入平台审核列表 |
| 发布 | 允许用户端按活动规则发现和报名 |
| 隐藏 | 运营人员控制可见性，不等于删除活动 |

活动在列表里出现，不代表用户端已经可以报名；`needsApproval`、publish 和 visibility 是不同的业务信息。

### RegistrationFormDesigner 把字段配置变成契约

活动基本信息之外，`RegistrationFormDesigner.vue` 负责配置动态报名字段。组件打开时请求：

```javascript
const loadFormData = async () => {
  loading.value = true;
  try {
    const res = await eventApi.getRegistrationForm(props.eventId);
    if (res.statusCode === 200) {
      formData.value = res.data;
    }
  } finally {
    loading.value = false;
  }
};

const sortedFields = computed(() => {
  return [...formData.value.fields].sort((a, b) => a.order - b.order);
});
```

`event.js` 对字段提供增删改接口：

```javascript
getRegistrationForm: (eventId) =>
  apiClient.get(`/business/events/${eventId}/registration-form`),

updateRegistrationForm: (eventId, formData) =>
  apiClient.put(`/business/events/${eventId}/registration-form`, formData),

addRegistrationField: (eventId, fieldData) =>
  apiClient.post(
    `/business/events/${eventId}/registration-form/fields`,
    fieldData
  ),

updateRegistrationField: (eventId, fieldData) =>
  apiClient.patch(
    `/business/events/${eventId}/registration-form/fields`,
    fieldData
  ),

deleteRegistrationField: (eventId, fieldId) =>
  apiClient.delete(
    `/business/events/${eventId}/registration-form/fields/${fieldId}`
  )
```

一个动态字段至少要有这些信息：

| 字段 | 作用 |
|---|---|
| `id` | C 端提交和回显时识别同一个字段 |
| `type` | 决定 text、number、select 等输入控件 |
| `order` | 决定表单展示和提交顺序 |
| `required` | 决定前端和后端是否必须填写 |
| `options` | 为 select 等枚举字段提供可选值 |

例如活动需要报名人姓名、年龄和运动水平，管理端会配置 `text`、`number`、`select` 三类字段。表单设计器的收益是不同活动可以复用同一套 C 端渲染逻辑；代价是字段配置已经成为前后端共同契约。

我会把“活动发布后冻结破坏性字段变更”作为工程规则：可以修改文案和展示顺序，但删除已经被报名数据使用的字段，需要版本化或迁移。当前组件提供了字段编辑接口，却没有一个统一的“发布后不可删除”前端守卫，因此真正的约束应该放在服务端或明确的状态策略中。

## 6. 订单、退款、会员与子账号的运营收口

### 订单面板把查询和审核分开

资源配置和活动发布最后都要落到真实交易。`OrderPanel.vue` 的查询条件比普通列表多一层业务范围：订单状态、订单类型、场馆、活动、商家、组织方、关键词、排序字段和时间范围都会影响请求参数。

```javascript
const buildQueryParams = () => ({
  page: query.page,
  pageSize: query.pageSize,
  status: query.status || undefined,
  type: query.type || undefined,
  venueId: query.venueId || undefined,
  eventId: query.eventId || undefined,
  merchantId: query.merchantId || undefined,
  organizerId: query.organizerId || undefined,
  keyword: query.keyword || undefined
});
```

查看详情时，组件再次请求 `/business/orders/:orderId`。退款审核则打开 `RefundAuditDialog.vue`，提交动作和原因：

```javascript
const res = await orderApi.auditRefund(
  props.orderDetail.orderId,
  form.value.action,
  form.value.reason
);

if (res.statusCode === 200) {
  emit('audited', res.data);
}
```

API 的具体路径是：

```javascript
list: (params = {}) =>
  apiClient.get('/business/orders', normalizeDateTimeParams(params)),

detail: (orderId) =>
  apiClient.get(`/business/orders/${orderId}`),

auditRefund: (orderId, action, reason) =>
  apiClient.post(`/business/orders/${orderId}/refund/audit`, {
    action,
    reason
  })
```

退款审核的状态边界可以这样理解：

| 页面动作 | 前端提交 | 页面可显示的过渡状态 | 最终事实 |
|---|---|---|---|
| 查看退款申请 | `orderId` | 打开审核弹窗 | 服务端退款申请记录 |
| 同意 | `action=approve`、reason | `refunding` 等待执行 | 支付/退款服务的结果 |
| 拒绝 | `action=reject`、reason | 订单恢复可见状态 | 服务端拒绝记录 |
| 刷新详情 | `orderId` | 重新加载 | 订单和退款记录的当前状态 |

order store 会在审核响应后局部更新列表里的 status，这能让表格马上反馈操作结果，但不能把本地 status 当成退款成功凭证。网络超时、重复点击和服务端异步执行都要求页面重新查询订单或退款详情。

### B 端验收清单

把正文的主线收束成一张手工验收表：

| 场景 | 进入状态 | 应检查的结果 |
|---|---|---|
| 未登录访问管理台 | 无 token | 跳转登录页，不能加载业务面板 |
| 普通商家登录 | role 非 `platform_admin` | 看不到平台场馆、商家管理和平台账号入口 |
| 创建场馆 | 表单字段不完整 | 阻止提交并显示字段错误 |
| 创建成功 | HTTP 201 | 进入下一步并刷新场馆列表 |
| 审核申请 | `action=pending` | 显示审核按钮，提交 approve/reject 后刷新列表 |
| 切换场馆和星期 | active venue、weekday 变化 | 场地、价格和营业时间重新加载 |
| 批量更新场次 | 选中多个 session | 请求携带业务 ID 集合，成功后刷新矩阵 |
| 活动审核发布 | `needsApproval` 或隐藏状态 | 只有符合角色和状态才显示操作按钮 |
| 动态报名表单 | fields 改变 | order、required、options 在预览和保存后保持一致 |
| 退款审核 | orderId、action、reason | 提交后以服务端详情确认最终状态 |
| 子账号停用 | active 子账号 | 状态更新后列表刷新，主账号不受影响 |

每一条验收最好同时记录四列：请求路径、输入参数、页面状态、服务端事实。这样遇到“按钮点了但状态没变”时，能判断问题是在组件事件、请求参数、后端状态转换，还是列表没有重新加载。

## 7. 面试复盘

面试时，我会用三句话先交代 B 端主线：管理台通过路由守卫恢复登录态，再按角色装配业务面板；商家管理员从场馆列表发起创建，平台管理员完成审核，场馆继续沉淀成场地、价格计划和 session；活动发布、订单退款、会员和子账号则分别把运营工作收口到状态和组织边界。

### 管理台壳层与权限

**Q：为什么 HomeView 使用动态组件？**

A：HomeView 是管理台壳层，菜单只修改 `currentPanelIndex`，再通过 `componentMap` 切换异步业务组件。这样大型面板可以按需加载，壳层也不用把所有业务组件同步打入首屏。

**Q：`requiresAuth` 能不能代替角色权限？**

A：不能。它只判断当前是否有登录态；平台管理员、商家管理员、场馆管理员和活动组织方的操作范围，还需要角色分支与服务端授权共同决定。

**Q：前端隐藏菜单有什么安全作用？**

A：它能减少无权限用户的误操作入口，改善界面体验，但不能阻止用户手动构造请求。真正的安全边界必须在 NestJS 的 guard、DTO 校验和数据范围查询。

**Q：刷新浏览器后，登录状态怎么恢复？**

A：auth store 从 localStorage 读取 JWT，再请求 `/business/admin/profile` 验证 token。验证成功后恢复用户信息，失败就清理本地 token 和业务 store。

### 场馆、场地与场次

**Q：为什么创建场馆后还要审核？**

A：创建接口表示申请已经提交，审核接口由平台角色处理 `pending` 记录，提交 `approve` 或 `reject`。申请提交和审核通过属于两个不同状态转换。

**Q：场馆创建表单为什么不是一次提交就结束？**

A：页面把它表达为信息填写、保证金提交和平台审核三个业务步骤。即使第一步得到 HTTP 201，也只能说明创建申请成功，不能直接推断平台审核完成。

**Q：价格计划和 session 有什么关系？**

A：价格计划描述场地在 weekday 和 timeSlot 上的运营规则；session 是按照这些配置生成或同步出来的可预约时间资源。前端通过 price-plan 和 session 两组 API 把它们连接起来。

**Q：为什么批量编辑时要保存 sessionId，不能只保存表格行列？**

A：行列索引只属于当前矩阵，换日期、类别或重新加载后可能变化；sessionId 是后端识别具体时间资源的业务 ID，行列只适合更新当前 UI。

### 活动和动态表单

**Q：活动的创建、审核、发布和隐藏有什么区别？**

A：创建形成活动记录，审核决定是否通过平台检查，发布决定是否进入用户可发现的运营状态，隐藏控制可见性。列表里出现活动不等于用户端可以报名。

**Q：为什么活动要允许动态报名字段？**

A：不同活动需要的字段不同，动态表单让 C 端按 `fields` 配置渲染，不需要每个活动复制一套页面。它的代价是字段 id、type、order、required 和 options 变成了前后端共同契约。

**Q：发布后还可以随便删除报名字段吗？**

A：不建议。已经产生报名记录的字段如果被删除，历史数据就失去解释方式。更稳妥的做法是发布后冻结破坏性变更，或使用版本化和数据迁移；这属于需要前后端共同落实的工程规则。

### 订单、退款与组织协作

**Q：退款审核成功后为什么不能只修改表格里的 status？**

A：表格更新只是局部 UI 反馈。退款可能还在异步执行，最终状态要通过订单和退款详情确认，服务端记录才是业务事实。

**Q：退款审核接口为什么要同时传 action 和 reason？**

A：action 表示通过或拒绝，reason 保存运营人员的审核依据。两个字段一起提交，服务端才能记录可追踪的审核动作，而不是只收到一个布尔值。

**Q：会员产品、会员卡和使用记录为什么分成不同模块？**

A：产品是商家配置的售卖规则，会员卡是用户购买后的实例，使用记录是消费流水，统计是聚合视图。它们的生命周期和查询方式不同，拆开更容易维护。

**Q：子账号管理和业务权限有什么关系？**

A：子账号决定谁参与商家运营。账号的角色、状态和所属商家/场馆会影响它能看到哪些资源、能否继续操作；前端可以提供启停和编辑入口，但数据范围必须由服务端落实。

### 测试与复盘

**Q：你会怎么验证这套 B 端主流程？**

A：先验证未登录和角色菜单，再验证创建/审核状态机；然后验证 venue、court、price plan、session 的依赖链；最后覆盖活动发布、动态表单、退款审核、子账号启停，以及空列表、接口失败、重复提交和刷新恢复。每个场景记录请求路径、输入参数、页面状态和服务端结果。

**Q：这部分项目最容易被追问的边界是什么？**

A：前端菜单隐藏不等于后端授权，创建成功不等于审核通过，支付弹窗或退款按钮返回成功不等于最终业务完成，store 的局部状态也不等于数据库事实。回答时把这些边界说清楚，比罗列更多组件名更有说服力。

**Q：如果继续完善 07，你会做什么？**

A：把前端的角色分支与 `yuedong_nestjs` 的 guard、DTO 和数据范围查询逐项对照；为创建/审核、价格同步、活动发布、退款审核和子账号越权补充自动化接口测试；为动态报名表单增加发布后版本策略；再把 B 端关键请求接入统一的操作日志。

至此，B 端不再只是“有很多管理页面”，而是一条可以复述的运营工作流：身份进入工作台，角色限制入口，资源经历申请与审核，价格计划生成可用场次，活动和退款通过状态转换收口，会员与子账号把业务交给组织协作。
