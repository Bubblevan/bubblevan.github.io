# 悦动体育 08：三端交付与联调验证——从本地构建到线上请求链

07 把 B 端的场馆、活动、订单和账号操作串成了运营工作流。08 再往前走一步：一个功能写完以后，怎样从三个项目的源码变成用户真正能访问的版本？

我把这件事想成一次很具体的发布任务：后端提供一个新的可预约版本，B 端管理台可以配置资源，C 端小程序可以查询和预约。这个任务不以“某个项目执行过 build 命令”结束，而要继续回答：构建出了什么、请求去了哪里、服务是否健康、错误怎样定位、旧版本怎样保留。

Day01 对我的启发正是这里：熟悉项目不只是看目录和业务演示，还要把环境搭建、部署、BUG 重现、请求链、远程调试、接口测试和部署联调放在一条学习路径上。下面我就沿着这条路径，把 `yuedong-v2-frontend`、`yuedong_front` 和 `yuedong_nestjs` 重新拼起来。

![悦动体育 08：三个项目从源码到生产运行时的交付链](/projects/yuedong-sports/yuedong-08-release-chain.png)

> **本篇任务卡**
>
> 以“准备一个可预约版本”为主线，依次完成四件事：
>
> 1. 识别 C 端包、B 端 `dist`、后端镜像/`dist` 和运行时依赖。
> 2. 沿着一次 `/api` 请求，对齐客户端 URL、Nginx、NestJS、认证和数据库。
> 3. 把静态文件、容器、密钥和数据库结构变更放到正确的责任边界。
> 4. 用 build、health、API、UI 和回滚证据组成发布验收。
>
> 读完后，我希望自己能把“我做过三端项目”说成一条可验证的交付链，而不是三个互相孤立的技术栈名词。

## 1. 先建立一次可交付版本的任务卡

### 把“发布版本”拆成四个结果

“构建”这个词在三个项目里不是同一个动作。B 端是浏览器加载的静态文件，小程序是要交给 UniApp/HBuilderX 和微信开发工具处理的客户端包，后端是 NestJS 编译结果加 Prisma Client 和运行时依赖。它们最后都服务于同一个用户动作，但产物形态不同。

| 项目 | 本地阅读入口 | 交付产物 | 运行时依赖 | 最小验收 |
|---|---|---|---|---|
| `yuedong-v2-frontend` | `npm install`、`npm run dev:mp-weixin` | 微信小程序构建包 | 小程序合法域名、HTTPS、OSS 图片域名、微信 AppID | 能打开首页，并完成一次登录或公开列表请求 |
| `yuedong_front` | `npm run dev`、`npm run build` | `dist/` 静态文件 | Nginx `/admin/` 静态目录、`/api` 代理或 API 基址 | `/admin/` 能加载，刷新子路由不 404，接口返回正常 |
| `yuedong_nestjs` | `npm run start`、`npm run build` | `dist/`、Prisma Client 或 Docker 镜像 | Node/Docker、MySQL、Redis、环境变量、8080 端口 | `/api/health` 返回健康结果，业务接口能进入数据库 |
| 生产运行时 | Nginx、Docker Compose 或 PM2 | 静态目录、容器、持久化 volume | HTTPS 证书、密钥、日志、备份 | 新版本可访问，旧版本可回退 |

这里的“四个结果”不是四份都要上传到同一个目录，而是四个需要分别验收的对象：客户端能运行、静态站点能加载、API 服务能处理请求、生产环境能保留恢复路径。

我会先把一件容易混淆的事记下来：仓库里的“脚本存在”不等于“这台 Windows 机器已经能完成生产发布”。比如 B 端 `package.json` 的 `deploy` 脚本指向 `./deploy.sh`，但本次读取的项目根目录里看到的是 `auto-deploy.sh`。这不是业务 bug，却会在交付时直接变成命令级故障。发布前检查“脚本引用的文件是否存在”，和检查接口路径一样重要。

### 用请求链作为验收主线

构建产物只是起点。我会挑一个最小请求，例如 C 端查询场馆，或者 B 端打开场馆列表，把它拆成几个观察点：

| 观察点 | 要看什么 | 常见证据 |
|---|---|---|
| 客户端 | 拼出来的完整 URL、请求方法、请求头 | 小程序调试面板、浏览器 Network |
| 网关 | HTTPS 是否终止、`/api` 是否转发、`/admin` 是否 fallback | Nginx 配置、访问日志、响应状态码 |
| NestJS | global prefix、CORS、Guard、中间件、Controller | `main.ts`、Guard 日志、应用日志 |
| 依赖 | MySQL、Redis、Prisma 连接是否可用 | 容器状态、healthcheck、应用启动日志 |
| 页面 | loading、空态、错误提示、成功数据是否正确展示 | 页面录屏或截图、业务结果 |

所以“联调成功”至少是五类证据的交集。只看到浏览器返回 200，并不能说明小程序白名单正确；只看到 `/api/health` 返回 200，也不能说明预约的业务事务没有问题。

![悦动体育 08：C 端和 B 端请求经过 Nginx 进入 NestJS 的排错链](/projects/yuedong-sports/yuedong-08-request-debug.png)

> **请求链最小验收清单**
>
> - [ ] 客户端看到的 URL 与环境预期一致。
> - [ ] B 端生产资源使用 `/admin/` 前缀，API 使用 `/api` 入口。
> - [ ] C 端请求域名在小程序合法域名配置内，并且图片域名也能访问。
> - [ ] 无 token 的公开请求、带 token 的用户请求、管理员请求分别得到预期结果。
> - [ ] `/api/health`、容器状态和应用日志互相吻合。
> - [ ] 页面成功、空数据、401、5xx 都有可理解的反馈。

## 2. 三端如何生成可运行的产物

### B 端 Vite 的 base 和分包决定部署形态

先看 `yuedong_front/package.json` 的脚本。B 端把开发、普通构建、生产构建、分析和预览分开：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "build:prod": "NODE_ENV=production vite build",
    "build:analyze": "node scripts/build-analyze.js",
    "preview": "vite preview",
    "deploy": "chmod +x ./deploy.sh && ./deploy.sh"
  }
}
```

在我当前的 Windows 工作区里，日常验证使用 `npm run build` 更直接；`build:prod` 明确写入了生产环境变量，但这种 `KEY=value command` 写法还受到执行 shell 的影响。这里应该把“脚本想做什么”和“当前操作系统能否直接执行”分开判断。

Vite 配置里有两个尤其关键的值：

```js
export default defineConfig(async ({ command }) => {
  return {
    base: process.env.NODE_ENV === 'production' ? '/admin/' : '/',
    build: {
      outDir: 'dist',
      assetsDir: 'assets',
      rollupOptions: {
        output: {
          entryFileNames: 'assets/[name].[hash].js',
          chunkFileNames: 'assets/[name].[hash].js',
          manualChunks: {
            'vue-vendor': ['vue', 'vue-router', 'pinia'],
            'element-plus': ['element-plus', '@element-plus/icons-vue'],
            'charts': ['vega-embed'],
            'utils': ['dayjs'],
            'qrcode': ['qrcode', 'html5-qrcode', 'vue-qrcode-reader']
          }
        }
      }
    }
  }
})
```

`base` 解决的是“静态资源从哪个 URL 前缀加载”。生产值为 `/admin/`，所以最终网站不是把 `index.html` 当作根路径应用，而是挂在管理台前缀下。`manualChunks` 解决的是“第三方依赖怎样拆包和缓存”，它不会改变 API 的地址。

这两个维度经常被混成一个问题：

| 配置 | 解决的问题 | 错了以后会怎样 |
|---|---|---|
| `base: '/admin/'` | JS、CSS、图片从哪里加载 | `/admin` 打开后出现资源 404 或白屏 |
| `VITE_API_BASE` | fetch 把请求发到哪里 | 页面能打开，但列表请求发错服务器 |
| `server.proxy['/api']` | 开发时谁代发 `/api` 请求 | 本地浏览器遇到 CORS 或连错端口 |
| `outDir: 'dist'` | 构建产物放在哪里 | 部署脚本找不到要上传的目录 |

B 端部署文档推荐只上传 `dist`，原因不只是体积。源码、`docs`、`scripts`、`.env` 和 `node_modules` 属于开发或构建环境，不应该成为网站可访问路径。最终服务器需要的是一个静态入口和它引用的哈希资源。

> **B 端构建后的第一轮检查**
>
> - [ ] `dist/index.html` 存在。
> - [ ] `dist/assets/` 有带 hash 的 JS/CSS 文件。
> - [ ] 生产 HTML 中资源路径包含 `/admin/`，不是误指向开发根路径。
> - [ ] 浏览器直接访问 `/admin/` 能加载页面。
> - [ ] 深层路由刷新时，Nginx 会回退到 `/admin/index.html`。
> - [ ] 页面打开后，Network 中 API URL 与 `VITE_API_BASE` 或相对 `/api` 策略一致。

### C 端环境配置同时受小程序白名单和 OSS 影响

`yuedong-v2-frontend` 的 README 没有提供一个与 B 端相同的 Vite build 脚本，而是把开发入口写成：

```bash
npm install
npm run dev:mp-weixin
```

这个差异本身就是项目事实：C 端是 UniApp 小程序工程，最终构建和上传要经过对应的小程序工具链；仓库里的 `scripts/package.json` 主要服务于静态资源上传、迁移和监听，不要把它误当成 C 端应用的完整构建脚本。

C 端配置把 API 和图片域名放在了一起：

```js
const ENV_CONFIG = {
  local: {
    API_BASE_URL: 'http://localhost:8081/api',
    WEB_BASE_URL: 'http://localhost:8081'
  },
  production: {
    API_BASE_URL: 'https://yuedongjump.com/api',
    WEB_BASE_URL: 'https://yuedongjump.com'
  }
};

const OSS_CONFIG = {
  BUCKET_NAME: 'yuedong-img',
  REGION: 'oss-cn-hangzhou',
  DOMAIN: 'https://yuedong-img.oss-cn-hangzhou.aliyuncs.com',
  STATIC_PATH: '/static/'
};
```

接着，`request.js` 负责把相对路径拼成完整 URL，并按需添加 JWT：

```js
const fullUrl = url.startsWith('http')
  ? url
  : CONFIG.API.BASE_URL + url;

const requestHeaders = {
  'Content-Type': 'application/json',
  ...header
};

if (needAuth) {
  const token = uni.getStorageSync('token');
  if (token) {
    requestHeaders.Authorization = `Bearer ${token}`;
  }
}
```

因此小程序能否访问 API，至少受四层条件约束：

| 层次 | 代码里的位置 | 要验证什么 |
|---|---|---|
| URL | `CONFIG.API.BASE_URL` | 是否为正确的 HTTPS API 地址 |
| 微信平台 | `manifest.json`、小程序后台 | request 域名是否在合法域名白名单 |
| 认证 | `utils/request.js` | 需要登录的接口是否带 `Bearer` token |
| 图片 | `OSS_CONFIG.DOMAIN`、`getImageUrl` | OSS 对象 URL 是否可访问、路径是否重复拼接 |

`manifest.json` 中配置了微信小程序 AppID，`pages.json` 中声明了定位权限和 `getLocation` 私有信息。它们不是普通的页面配置：AppID 决定构建目标，定位权限会影响平台审核和用户授权，API 与 OSS 域名则直接影响线上请求能否发出。

当前 `getCurrentEnv` 对 develop、trial 和 release 都返回 production，意味着开发版和体验版也会访问生产 API。这可以绕过部分域名白名单或环境切换问题，但它不是严格的多环境隔离。实际联调时要额外确认：测试账号、测试数据、支付开关和日志范围不会与生产混用。

### 后端 build 同时生成 Prisma Client 和 Nest dist

后端 `package.json` 的核心脚本是：

```json
{
  "scripts": {
    "build": "prisma generate && nest build",
    "start": "nest start",
    "start:prod": "node dist/main",
    "test": "jest",
    "test:cov": "jest --coverage",
    "test:e2e": "jest --config ./test/jest-e2e.json"
  }
}
```

这里的顺序有意义：

1. `prisma generate` 根据 schema 生成客户端代码。
2. `nest build` 把 TypeScript 编译到 `dist`。
3. 生产启动执行 `node dist/main`，但运行时仍需要生成后的 Prisma Client、依赖包和环境变量。

`PrismaService` 把数据库连接生命周期放到 Nest 模块生命周期里：

```ts
@Injectable()
export class PrismaService extends PrismaClient
  implements OnModuleInit, OnModuleDestroy {
  async onModuleInit() {
    await this.$connect();
  }

  async onModuleDestroy() {
    await this.$disconnect();
  }
}
```

这解释了为什么后端不能只上传 `dist/main.js`：编译文件只是应用逻辑，Prisma Client、生产依赖、数据库连接配置和 MySQL/Redis 仍然是运行时的一部分。

后端 Dockerfile 用多阶段构建表达了相同的边界：

```dockerfile
FROM node:22-bookworm-slim AS build
WORKDIR /app
ENV NODE_ENV=development

COPY package*.json ./
RUN npm install --no-audit --no-fund
COPY prisma ./prisma
COPY nest-cli.json tsconfig*.json ./
COPY src ./src
RUN npm run build \
    && npm prune --omit=dev

FROM node:22-bookworm-slim AS runtime
WORKDIR /app
ENV NODE_ENV=production PORT=8080 TZ=Asia/Shanghai
COPY --from=build /app/package*.json ./
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/prisma ./prisma
COPY --from=build /app/dist ./dist
```

build stage 负责安装开发依赖和编译，runtime stage 只保留运行所需文件，并且后面切换到非 root 用户。这个分层让我读 Dockerfile 时有了一个简单问题：某个文件是“编译时需要”，还是“运行时需要”？两者都需要的文件才应该复制进最终镜像。

## 3. 请求地址、前缀与认证怎样接上

### B 端开发代理与生产相对路径是两种策略

B 端 API 客户端先读取 Vite 环境变量，没设置时回退到相对路径：

```js
const BASE_URL = import.meta.env?.VITE_API_BASE
  ? import.meta.env.VITE_API_BASE
  : '/api';

async request(url, options = {}) {
  const fullUrl = url.startsWith('http')
    ? url
    : `${this.baseURL}${url}`;

  const response = await fetch(fullUrl, {
    headers: this.getHeaders(),
    ...options
  });

  const responseData = await response.json();
  if (!response.ok) {
    throw new Error(responseData.message || `HTTP Error: ${response.status}`);
  }
  return responseData;
}
```

本地开发时，Vite 再把 `/api` 代理给 NestJS：

```js
server: {
  host: '0.0.0.0',
  port: process.env.VITE_PORT || 3344,
  proxy: {
    '/api': {
      target: 'http://localhost:8080',
      changeOrigin: true,
      secure: false
    }
  }
}
```

于是同一个接口可以展开成两种 URL：

| 场景 | 客户端代码 | 实际请求 |
|---|---|---|
| B 本地开发 | `apiClient.get('/venues')` | `https://localhost:3344/api/venues`，再由 Vite 代理到 `http://localhost:8080/api/venues` |
| B 生产、相对 API | `apiClient.get('/venues')` | `https://yuedongjump.com/api/venues` |
| B 生产、显式 API | `VITE_API_BASE=https://api.example.com/api` | `https://api.example.com/api/venues` |
| C 小程序 | `get('/venues')` | `https://yuedongjump.com/api/venues` |

注意这里有两个前缀：`/admin/` 是 B 端静态页面的前缀，`/api/` 是后端接口的前缀。一个负责“页面文件从哪里加载”，一个负责“请求转发到哪个服务”，不能拿其中一个替代另一个。

我会在浏览器 Network 里同时看 Request URL 和页面资源 URL：如果 JS/CSS 404，先查 `base`；如果页面能打开但接口 404，查 `VITE_API_BASE`、Vite proxy 和 NestJS global prefix；如果接口 401，才进入 token 和 Guard 排查。

### C 端 request 封装把 401、500、502 变成用户可理解的结果

C 端请求工具比一行 `uni.request` 多出来的部分，主要是在做错误分类。它会把非 2xx 响应包装成带有 `statusCode` 和 `response` 的错误，并对特定状态码做处理：

```js
if (response.statusCode >= 200 && response.statusCode < 300) {
  return response.data;
}

const error = new Error(
  `HTTP ${response.statusCode}: ${response.data?.message || '网络请求失败'}`
);
error.statusCode = response.statusCode;
error.response = response;
throw error;
```

三个状态码的处理目的不同：

| 状态 | request.js 的动作 | 我应该观察什么 |
|---|---|---|
| 401 | 删除 token 和用户信息，触发 `tokenExpired`，提示重新登录 | token 是否过期、请求是否需要登录、后端 AuthGuard 是否识别 openid |
| 500 | 统一包装为服务器内部错误 | 后端异常日志、数据库查询、业务参数 |
| 502 | 最多按 `maxRetries` 重试，仍失败则提示服务维护 | Nginx 上游、8080 端口、容器状态和应用日志 |

源码中的 502 重试默认上限是 2 次，并按 1 秒、2 秒递增等待。它适合处理服务刚重启的短暂窗口，但不能掩盖后端进程崩溃、Nginx 端口错误或数据库不可用。客户端重试改变的是用户体验，不是服务器事实。

错误提示还专门识别了“域名白名单”“SSL 证书”“连接超时”等小程序平台错误。这个设计把面向开发者的错误信息转成用户能理解的 Toast 和详细 Modal；联调时我仍然要保留原始 `errMsg`、完整 URL 和当前环境，否则友好提示会把根因隐藏掉。

### NestJS bootstrap 决定所有请求的共同入口

后端启动代码是三端对齐的关键：

```ts
const app = await NestFactory.create(AppModule);

app.enableCors({
  origin: [
    'http://localhost:5173',
    'http://localhost:3344',
    'https://localhost:3344',
    'https://yuedongjump.com'
  ],
  credentials: true,
  methods: ['GET', 'POST', 'PUT', 'DELETE', 'PATCH', 'OPTIONS'],
  allowedHeaders: [
    'Content-Type', 'Authorization', 'Accept', 'Origin', 'X-Requested-With'
  ]
});

app.setGlobalPrefix('api');

const port = process.env.PORT ?? 8080;
await app.listen(port, '0.0.0.0');
```

这段代码同时回答四个问题：

- 浏览器跨域请求允许哪些来源；
- 是否允许携带凭证；
- 接受哪些 HTTP 方法和请求头；
- 所有 Controller 路径前面是否统一加 `/api`，应用监听哪个端口。

`HealthController` 的路径是 `@Controller('health')` 加 `@Get()`。因为 bootstrap 设置了 global prefix，所以外部入口就是：

```text
GET /api/health
```

应用模块还注册了全局 `AuthGuard`、Prisma、TypeORM、定时任务、订单、微信支付、OSS、C 端和 B 端模块，并把日志中间件和清理中间件应用到所有路由。请求进入业务 Controller 前，已经经过共同入口的规则。

认证也分成两个角色边界：

```ts
// 用户请求：从 Bearer JWT 解析 openid，并查询用户是否存在
const payload = this.jwtservice.verify(token);
const { openid } = payload;
const user = await this.userService.findUser(openid);
request.openid = openid;

// 管理员请求：从 JWT 解析 username，再读取管理员角色和数据范围
const payload = this.jwtService.verify(token);
const { username } = payload;
const admin = await this.prisma.admin.findUnique({ where: { username } });
request.admin = {
  id: admin.id,
  role: admin.role,
  merchantId: admin.merchant_id,
  venueId: admin.venue_id
};
```

`AuthGuard` 会放行登录、注册、公开查询、OSS 和 health 等路径；`AdminGuard` 则继续检查管理员状态和 `@Roles()` 需要的角色。前端隐藏一个菜单，只是减少误操作入口；真正决定接口能否执行的仍然是服务端 Guard 和业务查询条件。

## 4. 部署边界与运行时依赖

### B 端只发布 dist，源仓库不等于网站根目录

部署安全文档给出的推荐路径很明确：本地或 CI 构建 `dist`，然后只上传 `dist` 中的文件。它把构建环境和生产静态目录隔开：

![悦动体育 08：源码、构建环境和生产服务器之间的安全边界](/projects/yuedong-sports/yuedong-08-deploy-boundary.png)

```bash
# 构建环境
npm run build:prod

# 生产服务器只接收构建结果
scp -r ./dist/* user@server:/var/www/yuedong-admin/
```

为什么不把整个项目传上去？因为整个项目里可能有 `.env`、依赖版本、源代码、接口参数、注释、脚本和文档。即便这些文件暂时没有被页面引用，只要 Nginx 配置不严谨，就可能被当作静态资源访问。生产站点应该只暴露浏览器需要的文件。

文档里的 Nginx 示例体现了两个动作：敏感路径拒绝访问，`/admin` 深层路由回退到入口文件。

```nginx
location ~ /\. {
    deny all;
}

location ~ \.(json|md|txt|log)$ {
    deny all;
}

location ~ ^/(src/|scripts/|docs/) {
    deny all;
}

location /admin {
    alias /var/www/yuedong-admin/dist;
    try_files $uri $uri/ /admin/index.html;
}
```

这里的 `try_files ... /admin/index.html` 很容易被忽略。Vue Router 的前端路由是在浏览器里工作的，用户直接刷新 `/admin/venues` 时，第一次请求先到 Nginx。如果 Nginx 只按文件路径查找，服务器会认为 `venues` 不是一个真实文件并返回 404；fallback 才能把请求交回前端路由。

我会把静态发布目录分成三栏检查：

| 位置 | 应该包含 | 不应该包含 |
|---|---|---|
| 源仓库 | `src`、`docs`、`scripts`、配置和依赖声明 | 不直接作为网站根目录 |
| 构建目录 | `index.html`、`assets`、哈希资源 | `.env`、`node_modules`、源码目录 |
| 生产静态目录 | `dist` 内容、Nginx 需要的入口 | package、Markdown、证书私钥、构建缓存 |

### 后端 Docker 通过多阶段构建缩小运行时边界

前端可以只发布静态文件，后端不行。NestJS 需要 Node 运行时、编译后的 `dist`、生产依赖、Prisma Client 和数据库/Redis 的连接配置。后端 Dockerfile 用两个 stage 表达这个事实：

```dockerfile
# build stage：安装开发依赖、生成 Prisma Client、编译 NestJS
FROM node:22-bookworm-slim AS build
WORKDIR /app
COPY package*.json ./
RUN npm install --no-audit --no-fund
COPY prisma ./prisma
COPY nest-cli.json tsconfig*.json ./
COPY src ./src
RUN npm run build \
    && npm prune --omit=dev

# runtime stage：只复制运行所需的文件
FROM node:22-bookworm-slim AS runtime
WORKDIR /app
ENV NODE_ENV=production PORT=8080 TZ=Asia/Shanghai
COPY --from=build /app/package*.json ./
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/prisma ./prisma
COPY --from=build /app/dist ./dist

USER nestjs
EXPOSE 8080

HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
  CMD curl -fsS http://127.0.0.1:${PORT}/api/health || exit 1
```

这个 Dockerfile 有三个值得记住的细节：

1. `npm run build` 不只是 TypeScript 编译，还包含 `prisma generate`。
2. runtime stage 保留 `/app/prisma`，因为运行时的 Prisma Client 和 schema 相关文件不能凭空出现。
3. 进程使用非 root 用户，并且 healthcheck 访问真实的 `/api/health`，让容器编排系统能判断“进程存在”之外的应用状态。

`docker-compose.yml` 再把应用和依赖组织起来：

```yaml
services:
  app:
    image: yuedong-nestjs:latest
    environment:
      NODE_ENV: production
      PORT: 8080
      DATABASE_HOST: mysql
      DATABASE_PORT: 3306
      REDIS_HOST: redis
      REDIS_PORT: 6379
    ports:
      - "${APP_PORT:-8080}:8080"
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy

  mysql:
    image: mysql:8.0
    volumes:
      - mysql-data:/var/lib/mysql

  redis:
    image: redis:latest
    volumes:
      - redis-data:/data
```

| 组件 | 作用 | 验收证据 |
|---|---|---|
| `app` | 运行编译后的 NestJS | 容器为 healthy，8080 端口可访问 |
| `mysql` | 持久化业务数据 | `mysql-data` volume 和连接日志 |
| `redis` | 缓存、锁或队列相关运行依赖 | `redis-cli ping`、容器 healthy |
| `depends_on` | 让 app 等待依赖健康 | compose 状态，而不是只看容器是否 created |

`ports` 的 `8080:8080` 只表示宿主机端口映射；公网是否能访问，还要看 Nginx 是否把 `/api` 转发到这个端口。容器启动了、端口映射了、Nginx 配好了，是三件不同的事。

### 部署脚本、密钥和 schema 变更必须拆开

后端目录里同时存在两类部署材料。

| 路线 | 主要材料 | 服务器承担什么 |
|---|---|---|
| PM2/Nginx 旧路线 | `DEPLOYMENT.md`、`deploy.sh` | 安装依赖、生成 Prisma Client、用 PM2 管理 Node 进程、Nginx 反代 |
| Docker 新路线 | `DEPLOYMENT_DOCKER.md`、`Dockerfile`、`docker-compose.yml`、`deploy-docker.sh` | `docker load` 镜像，`docker compose up -d`，管理 MySQL/Redis volume |

Docker 文档描述的新路线是：GitHub Actions 构建 Linux/amd64 镜像并上传压缩包，服务器加载镜像后由 Compose 启动；服务器上的 `.env.docker` 不被 CI 覆盖，生产密钥只留在服务器。

`deploy-docker.sh` 的主流程很短：

```bash
COMPOSE=(docker compose --env-file "${ENV_FILE}" \
  -f "${PROJECT_DIR}/docker-compose.yml")

case "${1:-}" in
  deploy)
    require_env_file
    "${COMPOSE[@]}" up -d
    "${COMPOSE[@]}" ps
    ;;
  load)
    require_env_file
    gzip -dc "${PROJECT_DIR}/yuedong-nestjs.tar.gz" | docker load
    ;;
esac
```

这条路线把“构建”和“运行”拆开：构建机负责生成镜像，服务器负责装载和启动。另一个重要开关是 `RUN_PRISMA_DB_PUSH`。部署文档明确把它默认为 `0`，也就是更新应用时不自动执行 `prisma db push`，结构变更交给人工确认的 DDL、回填和备份流程。

我会把一次 schema 变更拆成四步：

1. 先判断新代码能否兼容旧表结构，避免镜像一更新旧版本就无法启动。
2. 备份数据库并准备可重复执行的 DDL 或回填脚本。
3. 单独执行结构变更，再发布依赖新字段的应用版本。
4. 验证健康接口、关键查询和写入，保留旧镜像和备份。

这就是“发布”和“数据变更”分离的价值：一个镜像启动失败可以回滚镜像；一旦自动改坏生产表结构，回滚代码并不一定能恢复数据。

## 5. 联调、排错与发布验收

### 测试分层，先验证启动再验证业务

后端 `package.json` 提供了 build、单元测试、覆盖率和 e2e 入口：

```bash
npm run build
npm test
npm run test:cov
npm run test:e2e
```

这些命令不是四个互相替代的按钮，而是四个不同层次的检查：

| 层次 | 目标 | 通过说明什么 | 还不能说明什么 |
|---|---|---|---|
| TypeScript build | 代码能编译、依赖能生成 | 语法和类型入口基本成立 | 数据库、权限、页面可用 |
| 单元测试 | 小范围逻辑结果 | 某个 service/utility 的行为稳定 | 模块之间和真实依赖联通 |
| e2e | Nest 应用入口的 HTTP 行为 | 某组端到端断言成立 | C 端白名单、B 端静态资源、完整业务回归 |
| health | 运行进程和依赖入口 | 容器/服务可被探活 | 预约、支付、退款业务正确 |
| API/UI 回归 | 用户任务真正完成 | 业务链路能从页面走通 | 所有边界情况已覆盖 |

当前 e2e 示例有一个很好的阅读细节：测试文件自己调用 `createNestApplication()`，断言的是 `GET /` 返回 `Hello World!`；它不会自动执行 `src/main.ts` 里的 `setGlobalPrefix('api')`。所以这个样例通过，只能说明测试里的根 Controller 可用，不能直接拿来证明线上 `/api/health` 或业务接口都已覆盖。

我会按下面顺序执行一轮发布前检查：

```text
build → 启动 → health → 公开 API → 带 token API → 管理员 API → 页面入口 → 关键业务操作 → 回滚入口
```

顺序从便宜、稳定、容易定位的检查开始。若 `health` 都失败，就没有必要先在页面里反复点击；若公开查询已经返回 200，才值得进一步检查 token、角色和业务数据。

![悦动体育 08：发布验收矩阵——Build、Health、API、UI 与 Rollback](/projects/yuedong-sports/yuedong-08-validation-matrix.png)

### 用请求矩阵定位“哪一跳坏了”

我会为“打开 B 端场馆列表”或“C 端查询场馆”建立一张最小矩阵。它不要求一次覆盖全部业务，而是让每个结果都有对应的下一步。

| 步骤 | 检查动作 | 看到的证据 | 失败时先查 |
|---|---|---|---|
| 1 | 访问 `/admin/` | HTML、JS、CSS 返回 200 | Nginx root、`base`、文件权限 |
| 2 | 刷新 `/admin/venues` | 仍返回前端入口 | `try_files` fallback |
| 3 | 查询 `/api/health` | JSON 中有 `status`、`timestamp`、`uptime` | 容器、8080、Nginx upstream |
| 4 | 发送公开 GET | 业务 JSON 和状态码 | API 前缀、Controller、数据库 |
| 5 | 带 Bearer token 请求 | 200 或明确 401/403 | token、AuthGuard、AdminGuard、角色 |
| 6 | 页面完成列表/提交 | loading、数据、错误提示正确 | API client、字段映射、store、组件 |
| 7 | 模拟旧版本入口 | 旧静态包/镜像仍可启动 | 发布目录、镜像标签、备份记录 |

从 502 开始查客户端，通常会浪费时间。502 说明客户端和网关之间至少有一次 HTTP 交互，但网关没有从上游拿到可用响应。更高效的顺序是：

1. `curl http://127.0.0.1:8080/api/health`，确认宿主机直连后端是否成功。
2. 查看 `docker compose ps` 或 PM2 状态，确认进程是不是反复重启。
3. 查看应用日志和 Nginx error log，确认 upstream 地址、端口和超时。
4. 再回到 C 端或 B 端，看客户端重试和错误提示是否符合预期。

401 则是另一条路径：先看请求头有没有 `Authorization: Bearer ...`，再看 token 解析出的身份是否存在，最后看角色或数据范围。不要把 401、403、404、500 和 502 都统称为“网络问题”。

### 把常见失败写成可复述的排错闭环

我把排错记录成“现象 → 证据 → 根因候选 → 最小修复 → 回归动作”五列：

| 现象 | 先收集的证据 | 根因候选 | 最小修复 | 回归动作 |
|---|---|---|---|---|
| `/admin/` 白屏，资源 404 | HTML 中 script URL、Network、`vite.config.js` | `base` 前缀不对、dist 部署路径错 | 统一 `/admin/` 前缀并重新构建 | 访问 `/admin/` 和刷新深层路由 |
| `/admin/venues` 刷新 404 | Nginx 响应和配置 | 没有 fallback 到 `index.html` | 加 `try_files` | 直接刷新多个前端路由 |
| B 端页面能开，接口 404 | Request URL、Vite proxy、Nest 路径 | `/api` 重复或缺失 | 对齐 `VITE_API_BASE`、proxy、global prefix | 同一接口本地和生产各请求一次 |
| C 端提示合法域名错误 | `errMsg`、manifest、小程序后台配置 | API/OSS 域名未加入白名单 | 配置合法 HTTPS 域名 | 真机重新请求图片和 API |
| C/B 返回 401 | Authorization、token 生命周期、Guard 日志 | token 缺失/过期、身份不存在 | 重新登录或修复认证链 | 公开、用户、管理员请求分别回归 |
| 返回 502 | Nginx error log、8080 health、容器状态 | 上游进程未启动、端口或反代错误 | 修复进程/端口/反代配置 | 直连 health，再走公网 API |
| health 失败 | compose ps、应用启动日志、MySQL/Redis 状态 | 依赖不 healthy、环境变量错误、应用启动异常 | 修复运行时依赖或配置 | health 连续检查并观察重启次数 |
| 新镜像启动后旧接口异常 | 镜像 tag、schema 版本、数据库备份 | 代码与旧结构不兼容 | 先回滚镜像，单独处理 schema | 旧 API、关键读写、数据一致性 |

这里最重要的不是记住某个命令，而是每次修复都要有回归动作。比如把 API 地址改正确后，只打开首页不算回归；至少要重新请求列表、登录态接口和一个写操作。把 Nginx fallback 改好后，也不能只访问 `/admin/`，还要直接刷新一个深层路由。

B 端还有一个很实际的脚本风险：`package.json` 写的是：

```json
{
  "deploy": "chmod +x ./deploy.sh && ./deploy.sh"
}
```

而目录中读取到的自动部署脚本名是 `auto-deploy.sh`。`auto-deploy.sh` 自己包含检查 npm/ssh/scp、本地构建、压缩、上传、远端解压、重载 Nginx 和 health check 的流程：

```bash
check_requirements
test_connection
build_project
archive_name=$(create_archive)
deploy_to_server ${archive_name}
cleanup ${archive_name}
health_check
```

这给我一个发布前的低成本动作：先执行 `npm run deploy --help` 或直接检查 script 引用的文件，再决定是补齐 `deploy.sh`、修改 package script，还是明确从 shell 执行 `auto-deploy.sh`。不能等到已经构建并准备上传时才发现入口文件不存在。

## 6. 面试复盘

下面统一放面试式问题。回答时我会先给结论，再沿着“客户端 → 网关 → NestJS → 依赖 → 页面”补证据；如果只报技术栈名字，面试官很容易继续追问到细节。

### 项目主线

1. **面试官：你说悦动有 C 端、B 端和后端，三端分别交付什么？**

   **我：** C 端是 UniApp 微信小程序构建包，B 端是 Vite 生成的 `dist` 静态文件，后端是 NestJS 编译后的 `dist` 加 Prisma Client 和生产依赖；线上还要有 Nginx、MySQL、Redis、环境变量和 HTTPS。三端不是共用一个目录，而是通过 `/api` 请求入口连接起来。

2. **面试官：你怎样证明一个版本可以交付？**

   **我：** 我把证据分成 Build、Health、API、UI 和 Rollback 五类。先证明构建产物存在，再直连 `/api/health`，然后分别验证公开接口、用户 token、管理员角色和页面任务，最后确认旧静态包或旧镜像仍然能恢复。只说“npm run build 通过”不够。

3. **面试官：为什么 08 不从某个业务模块继续讲，而是讲部署？**

   **我：** 前面的文章已经把业务状态拆开了，Day01 的学习路径还强调环境搭建、BUG 重现、请求链、测试和部署联调。08 把这些横向能力补上，让我能从用户点击反推到服务，再从服务反推到版本交付。

### 构建与产物

4. **面试官：B 端的 `base: '/admin/'` 解决什么问题？**

   **我：** 它解决静态资源前缀。生产管理台挂在 `/admin/` 时，JS/CSS 也必须从 `/admin/assets/...` 加载；否则页面 HTML 可能返回 200，但资源会 404。它和 API 的 `/api` 前缀是两件事。

5. **面试官：`manualChunks` 和 API 地址有关系吗？**

   **我：** 没有直接关系。`manualChunks` 是 Rollup 分包策略，目的是把 Vue、Element Plus、图表、二维码等依赖拆开并利用缓存；API 地址由 `VITE_API_BASE` 或默认相对路径决定。

6. **面试官：为什么生产不直接上传 B 端整个项目？**

   **我：** 生产静态站点只需要 `dist`。整个项目可能带 `.env`、源码、脚本、文档和依赖信息，上传它会扩大暴露面、增加体积和 I/O。构建环境和 Nginx 静态目录应该分离。

7. **面试官：C 端为什么不能简单照搬浏览器的 localhost 配置？**

   **我：** 小程序请求受合法域名、HTTPS 和平台审核配置约束，真机上的 `localhost` 不是开发电脑。悦动的 C 端还要同时处理 API 域名和 OSS 图片域名，所以能在浏览器打开不等于小程序能请求。

8. **面试官：后端 `npm run build` 为什么先执行 Prisma generate？**

   **我：** NestJS 的 `dist` 只包含编译后的应用代码，Prisma Client 是根据 schema 生成的数据库访问代码。先生成 Client，再编译并把它和运行依赖放进 runtime，生产进程才能真正执行查询。

### URL、认证与错误

9. **面试官：本地 B 端请求 `/venues` 最终去了哪里？**

   **我：** API client 默认 base 是 `/api`，所以相对路径展开为 `/api/venues`；开发服务器的 Vite proxy 再把它转给 `http://localhost:8080`。NestJS 的 global prefix 也是 `api`，因此后端 Controller 的外部路径仍然是 `/api/venues`。

10. **面试官：B 端页面能打开但接口 404，你先查什么？**

    **我：** 先看浏览器 Network 的完整 Request URL，再对照 `VITE_API_BASE`、Vite proxy 和 NestJS 的 global prefix，确认有没有重复 `/api` 或缺少 `/api`。页面静态资源正常，只能证明 `base` 这一层可能正常，不能证明 API base 正确。

11. **面试官：C 端 request 封装为什么要自己处理 401 和 502？**

    **我：** 401 需要清理过期 token 并通知页面重新登录，502 则可以在服务重启的短窗口内有限重试；500 要给出服务器错误提示，域名白名单和 SSL 错误则要把平台错误翻译成人能理解的提示。这是统一请求层在做错误分类，不是把所有错误都吞掉。

12. **面试官：前端隐藏菜单能不能算权限控制？**

    **我：** 不能。菜单显隐只是用户界面层的授权提示，真正的接口权限要由服务端 Guard、JWT 身份、角色和数据范围决定。悦动的 `AdminGuard` 会查管理员状态、角色、merchantId 和 venueId，并把管理员信息写入 request。

13. **面试官：401 和 403 怎么区分排查？**

    **我：** 401 先查有没有 token、token 是否有效、身份是否存在；403 通常已经识别了身份，但角色或状态不允许操作。排查时我会同时看 Authorization header、AuthGuard/AdminGuard 日志和接口要求的角色。

14. **面试官：为什么 `/api/health` 要免认证？**

    **我：** 容器、Nginx 或外部探针要在没有用户 token 的情况下判断服务是否可用。如果 health 被普通业务认证拦住，探活会把“服务正常但没有 token”误判为故障。免认证只适合健康检查，不代表业务接口免认证。

### Docker、测试与回滚

15. **面试官：Dockerfile 的 build stage 和 runtime stage 有什么区别？**

    **我：** build stage 安装开发依赖、生成 Prisma Client 并编译 TypeScript；runtime stage 只复制生产依赖、Prisma、`dist` 和运行配置，再以非 root 用户启动。这样减少运行时边界，也让构建职责更清楚。

16. **面试官：`docker-compose.yml` 中 `depends_on: healthy` 解决了什么？**

    **我：** 它让 app 等 MySQL 和 Redis 通过健康检查后再启动，减少依赖尚未可用导致的启动失败。但它不等于业务一定正确，仍然要请求 `/api/health` 和关键 API。

17. **面试官：为什么 MySQL 和 Redis 要用 volume？**

    **我：** 容器可以替换，业务数据不能随着容器销毁。volume 把数据生命周期从容器生命周期里分离出来；发布应用镜像时不应该把数据库数据一起丢掉。

18. **面试官：为什么不在每次部署时自动执行 `prisma db push`？**

    **我：** 应用发布和生产 schema 变更的风险不同。自动 push 可能让结构变更不可控，甚至破坏旧版本兼容性。更稳妥的方式是备份、人工确认 DDL/回填、再发布依赖新结构的代码，并保留回滚路径。

19. **面试官：现有 e2e 测试断言 `/` 返回 Hello World，能证明线上 API 正常吗？**

    **我：** 不能。这个测试自己创建 Nest app，没有走 `main.ts` 的 `/api` global prefix，而且只断言根 Controller。它能说明示例入口有一个 HTTP 断言，但还需要 health、认证、业务 API 和 UI 回归。

20. **面试官：遇到 502，你为什么先查容器和 Nginx？**

    **我：** 502 通常意味着网关没有从上游拿到有效响应。我会先直连宿主机 `127.0.0.1:8080/api/health`，再看 Compose/PM2 状态、应用日志和 Nginx error log，确认是进程、端口、upstream 还是超时问题，最后再回到客户端重试逻辑。

21. **面试官：如何处理 B 端刷新子路由 404？**

    **我：** 先确认 Vite production base 和实际静态目录，再在 Nginx 中把 `/admin` 的未知路径 fallback 到 `/admin/index.html`。修复后不能只打开首页，要直接刷新 `/admin/venues`、订单等深层路径。

22. **面试官：你如何设计一次回滚？**

    **我：** 前端保留上一份可用静态包，后端保留上一份镜像和数据库备份。新版本异常时先恢复入口和服务可用性，再分析新版本；如果已经执行过不可逆的数据变更，不能只回滚代码，还要按数据恢复方案处理。
